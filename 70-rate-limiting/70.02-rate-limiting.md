# 70.02 — Rate Limiting & Abuse Protection (Walkthrough)

## Why rate limiting belongs at the middleware layer

Rate limiting is an infrastructure concern, not a business logic concern. It does not care
about what the route does — it only cares about who is making requests and how often. Middleware
is the right place for it: it runs before the route handler and can short-circuit the request
with a 429 before any business logic executes.

---

## How the Redis store works

Without a Redis store, `express-rate-limit` stores counters in memory. This breaks in two ways:

1. **Multiple instances**: if you run two Express servers behind a load balancer, each server
   has its own in-memory counter. A user can make 100 requests to server A and 100 to server B
   for a total of 200 — the limit is effectively doubled.

2. **Restarts**: when the server restarts, counters reset to zero. A user can trigger a restart
   and immediately get a fresh slate.

The Redis store fixes both problems. All server instances share the same Redis counters. Counters
survive restarts.

The `@express-rate-limit/redis` package bridges `express-rate-limit` and `ioredis`:

```ts
new RedisStore({
  sendCommand: (...args: string[]) => redis.sendCommand(args),
})
```

`redis.sendCommand(args)` passes raw Redis commands through the existing `ioredis` client.
No second Redis connection needed.

---

## Global vs route-specific limiters

### Global limiter

Applied in `app.ts` before any route:

```ts
app.use(globalLimiter);   // first middleware, before all routes
```

Config: 100 requests per 60 seconds per IP (defaults; override via env vars).

Every request to any route counts against this limit. It is the catch-all protection against
scrapers and bots hitting random endpoints.

### Auth limiter

Applied only to sensitive auth endpoints:

```ts
router.post('/login', authLimiter, loginHandler);
router.post('/register', authLimiter, registerHandler);
```

Config: 10 requests per 15 minutes per IP.

A credential-stuffing attack tries thousands of username/password combinations. At 10 attempts
per 15 minutes, an attacker can try ~960 passwords per day — down from potentially millions
without rate limiting.

---

## The prefix matters

Both limiters use a Redis store. Without a prefix, they would share the same Redis keys and
interfere with each other:

```ts
// Global limiter: uses default prefix 'rl:'
// Auth limiter: uses prefix 'rl:auth:'
store: new RedisStore({
  sendCommand: (...args: string[]) => redis.sendCommand(args),
  prefix: 'rl:auth:',
})
```

With separate prefixes, the counters are independent. A user who hits the global limit on GET
requests does not also hit the auth limit.

## Building it step by step

### Step 1 — Install the packages

```bash
npm install express-rate-limit @express-rate-limit/redis
```

### Step 2 — Add config fields

Open `src/shared/config.ts` and add:

```ts
RATE_LIMIT_WINDOW_MS: parseInt(process.env.RATE_LIMIT_WINDOW_MS ?? '60000', 10),
RATE_LIMIT_MAX: parseInt(process.env.RATE_LIMIT_MAX ?? '100', 10),
```

### Step 3 — Create src/shared/rateLimiter.ts

Define `globalLimiter` and `authLimiter` as shown in the guidelines. Use the same `handler`
function format for both to keep the 429 response consistent with the error format from
Chapter 17.

### Step 4 — Apply in app.ts

```ts
import { globalLimiter, authLimiter } from './shared/rateLimiter';

// Must be before any route
app.use(globalLimiter);

// Auth limiter on specific routes
```

### Step 5 — Test

```bash
# Test the global limiter (lower the RATE_LIMIT_MAX to 5 for testing)
RATE_LIMIT_MAX=5 npm run dev

# Make 6 requests to the health check
for i in {1..6}; do
  curl -s -o /dev/null -w "Request $i: %{http_code}\n" http://localhost:3000/health
done
# Expected: requests 1-5 return 200, request 6 returns 429

# Test the auth limiter (11 requests)
for i in {1..11}; do
  curl -s -o /dev/null -w "Auth $i: %{http_code}\n" \
    -X POST http://localhost:3000/api/auth/login \
    -H 'Content-Type: application/json' \
    -d '{"email":"x@x.com","password":"wrong"}'
done
# Expected: requests 1-10 return 401 (wrong password), request 11 returns 429
```

## Viewing the rate limit counters in Redis

```bash
redis-cli KEYS "rl:*"
# Shows: rl:<ip>:<timestamp_bucket> and rl:auth:<ip>:<timestamp_bucket>

redis-cli GET "rl:auth:::1:1717776000"   # example key (format varies by version)
```

---

## No `process.env` in this module

`rateLimiter.ts` reads from `config` (which reads `process.env` in `config.ts`). No direct
`process.env` access in `rateLimiter.ts` or any module in `src/modules/` or `src/shared/`.
