# 60.02 — Moderating Jobs & Managing Users (Walkthrough)

## Why admins need cross-company write access

Company members can only touch their own company's data — that is the isolation guarantee from
Chapter 28. Admins are different. An admin acts on behalf of the platform, not any single
company. The SQL queries in this chapter intentionally omit company-scoping: they read and write
across every company in the database.

This is not a bug. It is a deliberate policy decision. The `requireRole('admin')` guard ensures
only platform admins can reach these routes.

## Building the job moderation endpoints

### GET /api/admin/jobs

The query joins `jobs` with `companies` to return company name alongside job data. Two optional
filters are applied dynamically using the same pattern as Chapter 59:

```sql
SELECT j.id, j.title, j.status, j.created_at, c.name AS company_name
FROM jobs j
JOIN companies c ON c.id = j.company_id
WHERE j.status = $1 AND j.company_id = $2   -- only if params provided
ORDER BY j.created_at DESC
```

Call it with `?status=open` to see only open jobs. Call it with `?companyId=<uuid>` to see all
jobs for a specific company regardless of status. Both filters can be combined.

### PATCH /api/admin/jobs/:id/close

This endpoint does not check company membership. Any job, in any company, can be closed by an
admin. The service checks:

1. Does the job exist? → 404 if not
2. Is it already closed? → 409 if so
3. Run the UPDATE and return the updated row

```sql
UPDATE jobs SET status = 'closed' WHERE id = $1
RETURNING id, title, status
```

## Building the user management endpoints

### GET /api/admin/users

Returns all users with optional `?role=` and `?status=` filters. The password hash is never
selected — only `id, email, role, status, created_at`.

### PATCH /api/admin/users/:id/suspend

Three things happen in this service function:

```
1. Check adminId !== userId        (self-suspension guard)
2. Check user exists               (404 guard)
3. Check user is not already suspended  (409 guard)
4. UPDATE users SET status = 'suspended'
5. DELETE FROM refresh_tokens WHERE user_id = $1
```

Steps 4 and 5 are not in a database transaction. If step 5 fails, the user is suspended in the
`users` table but still has valid refresh tokens. This is an acceptable degraded state — the
tokens will expire on their own, and the admin can retry. For a stricter guarantee, wrap both
in a transaction using `pool.connect()`.

### PATCH /api/admin/users/:id/activate

Reverses a suspension. Does not issue new tokens — the user must log in again to get fresh
tokens.

## Testing with curl

```bash
# Assume $TOKEN is an admin JWT (from Chapter 59 setup)

# List all users
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/users" | jq '.users | length'

# List only suspended users
curl -s -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/users?status=suspended" | jq '.users[].email'

# Suspend a user (replace <USER_ID>)
curl -s -X PATCH -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/users/<USER_ID>/suspend" | jq '.user.status'
# Expected: "suspended"

# Confirm their refresh tokens are gone
psql $DATABASE_URL -c \
  "SELECT count(*) FROM refresh_tokens WHERE user_id = '<USER_ID>';"
# Expected: 0

# Try to suspend yourself (as admin) — expect 403
curl -s -o /dev/null -w "%{http_code}" -X PATCH \
  -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/users/<YOUR_ADMIN_USER_ID>/suspend"
# Expected: 403

# Reactivate the suspended user
curl -s -X PATCH -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/users/<USER_ID>/activate" | jq '.user.status'
# Expected: "active"

# Force-close a job (replace <JOB_ID>)
curl -s -X PATCH -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/jobs/<JOB_ID>/close" | jq '.job.status'
# Expected: "closed"
```

## Error reference

| Scenario | HTTP | Code |
|----------|------|------|
| Job not found | 404 | `NOT_FOUND` |
| Job already closed | 409 | `CONFLICT` |
| User not found | 404 | `NOT_FOUND` |
| User already in target status | 409 | `CONFLICT` |
| Admin suspending themselves | 403 | `FORBIDDEN` |
| Not an admin | 403 | `FORBIDDEN` |
| No token | 401 | `UNAUTHORIZED` |

## Access token gap

Suspending a user deletes their refresh tokens but not their current access token. If the access
token has a 15-minute TTL, the suspended user can still make authenticated requests for up to
15 minutes after suspension. Acceptable for most platforms. The fix is a Redis blocklist:
on suspension, write `suspended:<userId>` to Redis with a TTL equal to the access token TTL;
in `authMiddleware`, check the blocklist after verifying the JWT signature.
