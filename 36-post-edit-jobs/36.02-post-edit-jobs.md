# Posting and Editing Jobs

## The job lifecycle

```
draft → open → closed
```

A new job always starts as `draft`. It is not visible to anyone outside the company workspace. When the recruiter is satisfied with the listing, they publish it (`POST /api/jobs/:id/publish`), which moves it to `open`. An open job is visible on the public job board and accepts applications. Closing a job (`POST /api/jobs/:id/close`) moves it to `closed` — no new applications are accepted.

This chapter builds the create, edit, publish, and close endpoints. The public job board (where applicants browse open jobs) is in a later chapter.

---

## Creating a job

```bash
POST /api/jobs
Authorization: Bearer <recruiter-token>
Content-Type: application/json

{
  "title": "Senior Backend Engineer",
  "description": "You will build distributed systems at scale.",
  "location": "Remote",
  "employment_type": "full_time",
  "salary_min": 120000,
  "salary_max": 160000,
  "attributes": {
    "visa_sponsorship": false,
    "remote_friendly": true
  },
  "screening_questions": [
    { "text": "How many years of PostgreSQL experience do you have?" }
  ]
}
```

Response (201):

```json
{ "jobId": "<uuid>" }
```

The new job has `status = 'draft'`.

## Editing a job

`PATCH /api/jobs/:id` accepts any subset of the job fields. Fields not included in the request body are left unchanged.

```bash
PATCH /api/jobs/<job-id>
Authorization: Bearer <recruiter-token>
Content-Type: application/json

{ "salary_max": 175000 }
```

Response (200):

```json
{ "message": "Job updated." }
```

The patch is partial — built with a dynamic SQL `SET` clause that only updates the fields present in the request. This avoids accidentally resetting other fields to null.

`assertJobOwnership(jobId, companyId)` runs before the update. If the job ID does not belong to the caller's company, the update does not happen and the caller receives `404`.

## Publishing a job

```bash
POST /api/jobs/<job-id>/publish
Authorization: Bearer <recruiter-token>
```

Response (200):

```json
{ "message": "Job published." }
```

Sets `status = 'open'`. The isolation check (`assertJobOwnership`) runs first.

## Closing a job

```bash
POST /api/jobs/<job-id>/close
Authorization: Bearer <recruiter-token>
```

Response (200):

```json

```

Sets `status = 'closed'`. The isolation check runs first.

## Who can post jobs

| Company role | Can post/edit/publish/close? |
|---|---|
| owner | Yes |
| hr_manager | Yes |
| recruiter | Yes |
| hiring_manager | **No** |

A hiring manager calling `POST /api/jobs` receives `403`. This is enforced by `assertCompanyRole(company.companyRole, ['owner', 'hr_manager', 'recruiter'])` in each service function.

---

## The `attributes` field

`attributes` is a free-form JSONB object. There is no fixed schema for its contents. It exists so recruiters can attach job-specific metadata that does not fit the standard columns. Examples:

```json
{ "visa_sponsorship": true, "remote_friendly": true, "equity_offered": false }
{ "clearance_required": "SECRET", "on_call_rotation": true }
```

Whatever you put in, you get back. It is stored as JSONB, so PostgreSQL can index and query it, though that capability is not used in this chapter.

---

## What `assertJobOwnership` does

`assertJobOwnership(jobId, companyId)` (from Chapter 29) queries:

```sql
SELECT id FROM jobs WHERE id = $1 AND company_id = $2
```

If no row is returned — either because the job ID does not exist, or because it belongs to a different company — it throws `NotFoundError('Job not found.')`. The caller receives `404`.

This is the same error whether the job is genuinely missing or belongs to another company. No information is leaked.

## Dynamic UPDATE pattern

The `updateJob` repo function builds its `SET` clause dynamically from the fields present in the input. Here is why:

A naive `UPDATE jobs SET title = $1, description = $2, ... WHERE id = $n` requires all fields to be present. Sending `{ "salary_max": 175000 }` would require the caller to also send all the other fields, or they would be set to `null`.

The dynamic approach only updates what the caller provided. It iterates over a whitelist of allowed column names, adds each present field to the `SET` clause, and assigns sequential parameter positions. Only whitelisted columns can appear in the SET clause — there is no risk of injecting arbitrary column names.
