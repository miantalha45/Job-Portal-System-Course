# Chapter 99 — Closing: Document & Prove It

## What was built

A multi-tenant job portal built from the ground up in TypeScript, Node.js, Express 4, and
PostgreSQL, with Redis for caching, BullMQ for async processing, S3 for file storage, and
Next.js for the frontend.

The system supports three user roles (admin, recruiter, applicant), enforces tenant isolation
at the query level, runs background jobs reliably with retry and backoff, and is hardened with
rate limiting, security headers, and structured logging.

## Key Takeaways

1. **Parameterized queries eliminate SQL injection.** Every `db.query` call in this system
   uses `$1, $2` placeholders. The database driver sends the SQL and the parameters separately.
   User input never becomes SQL syntax. This is non-negotiable — it is the foundational
   defence against the most common web attack.

2. **Transactions make multi-step writes atomic.** The `applyToJob` function writes to three
   tables. Without a transaction, a crash between writes leaves the database in an inconsistent
   state. `pool.connect()` → `client.query('BEGIN')` → writes → `client.query('COMMIT')` →
   `client.release()` ensures all writes succeed or all fail together.

3. **Query scoping enforces tenant isolation.** A recruiter can only read and write records
   that belong to their company because every query includes `WHERE company_id = $1` with
   their company ID from the JWT. Relying on application logic alone (e.g., checking after
   fetching) is insufficient — the check must happen in SQL.

4. **At-least-once delivery requires idempotent workers.** BullMQ retries failed jobs. A
   worker that runs twice must produce the same result as running once. Use `ON CONFLICT DO
   NOTHING` for inserts, set absolute values (not relative increments) for updates, and use
   `job.id` as a deterministic key when you need to track whether a job has already run.

5. **Indexes change the performance ceiling.** A `SELECT` on a table with 1,000,000 rows and
   no index performs a full sequential scan: O(n). The same query with a B-tree index on the
   WHERE column is O(log n). The difference between "fast enough" and "unusably slow" at scale
   is often a single `CREATE INDEX`.

6. **Cache invalidation is harder than caching.** Adding a Redis cache for the job board
   (Chapter 44) is two lines of code. Ensuring the cache is purged when a company is suspended
   (Chapter 59), when a job is force-closed (Chapter 60), and when a job is created (Chapter 36)
   requires every write path to be aware of the cache. Missing one write path means stale data.

7. **The HTTP response must return before slow operations.** Moving email delivery to BullMQ
   reduced the `POST /api/applications` response time from ~180ms to ~35ms. The applicant got
   a faster response; the email still arrived. This is the core value of an async job queue —
   decoupling the response from the side effect.

8. **Short-lived access tokens + refresh rotation limit the blast radius of token theft.** A
   stolen access token is valid for 15 minutes. A stolen refresh token is invalidated on first
   use (rotation). Suspending a user immediately deletes their refresh tokens — the maximum
   time they retain access is one access token TTL.

9. **Defence in depth means no single mechanism is the last line of defence.** Zod validation
   strips unknown fields. Parameterized queries prevent injection. Helmet sets security headers.
   Rate limiting throttles brute force. httpOnly cookies prevent XSS token theft. CORS limits
   cross-origin browser requests. Each layer assumes the others may fail.

10. **Graceful shutdown preserves in-flight work.** SIGTERM → `server.close()` → let current
    requests finish → `pool.end()` → `redis.quit()` → `process.exit(0)`. In a rolling deploy,
    the old container receives SIGTERM when the new container is healthy. Without graceful
    shutdown, in-flight requests are killed and users see 502 errors during every deploy.

### Setup

```bash
# 1. Start dependencies

# 2. Run migrations
psql $DATABASE_URL -f migrations/001_init.sql

# 3. Start the API

```

### API reference (grouped by module)

- **Auth**: `POST /api/auth/register`, `/login`, `/verify-email`, `/refresh`, `/logout`
- **Companies**: `POST /api/companies`, `GET /api/companies/jobs`, `PATCH /api/companies/jobs/:id`
- **Members**: `POST /api/companies/invitations`, `POST /api/companies/invitations/:token/accept`
- **Public**: `GET /api/jobs`, `GET /api/jobs/:id`
- **Applications**: `POST /api/applications`, `GET /api/applicants/applications`
- **Stages**: `PATCH /api/applications/:id/stage`
- **Interviews**: `POST /api/interviews`, `POST /api/interviews/:id/feedback`
- **Admin**: `GET /api/admin/companies`, `PATCH /api/admin/companies/:id/verify`, etc.
- **Health**: `GET /health`, `GET /ready`

### Architecture notes

- PostgreSQL is the source of truth for all entity data
- Redis is used for two independent purposes: cache (TTL-based, deletable) and BullMQ queue
  (durable job storage — do not flush)
- The worker is a separate process and must be deployed alongside the API
- S3 stores résumé files; the `resumes` table stores metadata and the S3 key

  using PostgreSQL window functions or a dedicated OLAP tool
- **Mobile**: the same REST API serves a React Native or Flutter app with no changes — the
  auth (JWT Bearer token), pagination (cursor-based), and error formats are all mobile-friendly
