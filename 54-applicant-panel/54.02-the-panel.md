# 54.02 — The Applicant Panel: Design Notes

## Server Components vs Client Components

Next.js App Router gives you two component types. Choosing the wrong one has performance and security consequences.

**Server Components** (default in App Router):
- Run only on the server
- Can `await` directly — no `useEffect`, no loading states
- Can read cookies, access environment variables
- Cannot use React state, event handlers, or browser APIs

**Client Components** (`'use client'` directive at the top):
- Run in the browser (and also during SSR)
- Can use state, effects, event handlers
- Cannot read httpOnly cookies or call `cookies()` from `next/headers`

The applicant panel mixes both:

| Page/Component             | Type   | Reason |
|----------------------------|--------|--------|
| `/jobs`                    | Server | Fetch and render list; no interactivity needed |
| `/jobs/[id]`               | Client | Apply/Shortlist buttons need event handlers |
| `/dashboard/applications`  | Server | Fetch and render list; no interactivity |
| `/dashboard/profile`       | Client | File upload interaction requires browser APIs |
| `DashboardLayout`          | Server | Auth guard reads cookie server-side |

## The presigned upload in the browser

The three-step upload flow deserves attention. The browser's `fetch` is used for all three steps, but with different targets:

```
Step 1: fetch('/api/applicants/profile/resume-upload', { method: 'POST' })
        → hits your Node.js API server
        → returns { uploadUrl, key }

Step 2: fetch(uploadUrl, { method: 'PUT', body: file, headers: { 'Content-Type': 'application/pdf' } })
        → hits MinIO (localhost:9000) or S3 directly
        → your API server does not see the bytes

Step 3: fetch('/api/applicants/profile/resume', { method: 'POST', body: { key, filename } })
        → hits your Node.js API server
        → records metadata in the resumes table
```

The middle step is a cross-origin request (from `localhost:3001` to `localhost:9000` in dev, or from your app's origin to `s3.amazonaws.com` in production). For this to work:

**CORS on MinIO/S3 must allow PUT from your frontend origin.** In dev, MinIO's default CORS is permissive. In production, configure S3 bucket CORS:

```json
[{
  "AllowedOrigins": ["https://yourapp.example.com"],
  "AllowedMethods": ["PUT"],
  "AllowedHeaders": ["Content-Type"],
  "MaxAgeSeconds": 300
}]
```

## Error states

Each step of the upload can fail independently:

| Step | Failure | Recovery |
|------|---------|----------|
| Get presigned URL | API server error | Retry from step 1 |
| PUT to S3 | Network error, expired URL | Retry from step 1 (get fresh URL) |
| Confirm upload | API server error | The file is in S3 but not recorded; retry step 3 with the same key |

Step 3 is idempotent — the same `key` can be confirmed multiple times (each confirmation inserts a row, but that creates multiple rows with the same `s3_key`). If you want to prevent duplicate rows, add a `UNIQUE(s3_key)` constraint to the `resumes` table. This is a reasonable addition.

## Stage badge colours

The applications list uses a colour-coded badge to indicate stage:

```
applied         → grey
screening       → blue
interview       → yellow
final_interview → orange
offer           → green (light)
hired           → green (dark)
rejected        → red
```

The colour mapping is defined in the component as a constant object (`STAGE_COLOURS`). It is not fetched from the API — stages are a known, fixed set defined by the database CHECK constraint. The frontend can safely hard-code this mapping.

## Shortlist page structure

The `/dashboard/shortlist` page calls `GET /api/applicants/shortlist` and renders a list of job cards. Each card has:
- Job title and company name
- A "Remove" button → `DELETE /api/applicants/shortlist/:jobId`
- An "Apply" button → navigates to `/jobs/:id` or calls the apply endpoint directly
- A "Closed" badge if `job_status != 'open'` (the apply button is hidden for closed jobs)

The Remove interaction requires a Client Component (event handler) or a Server Action. A Server Action is preferred — it keeps the mutation server-side and avoids exposing the API token to the browser:

```tsx
// Server Action (Next.js App Router)
async function removeFromShortlist(jobId: string) {
  'use server';
  await apiFetch(`/api/applicants/shortlist/${jobId}`, { method: 'DELETE' });
  revalidatePath('/dashboard/shortlist');
}
```
