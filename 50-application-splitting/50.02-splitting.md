# 50.02 — Splitting Applications: Design Notes

## One row per job, not one row per submission

It is tempting to model a "submission" as a single row that references multiple jobs. Something like:

```sql
-- Anti-pattern
submissions (
  id           uuid PK,
  applicant_id uuid,
  job_ids      uuid[],    -- array of job IDs
  answers      jsonb,
  created_at   timestamptz
)
```

This breaks querying. Recruiters need to see applications for their jobs, not submissions that may include other companies' jobs. Queries like "show me all applications in the screening stage for job X" require one application row per job. The recruiter pipeline (Chapter 55) moves individual applications through stages — you cannot advance one job from a multi-job submission without untangling the array.

The correct model is one `applications` row per job. A "submission" is a UX concept: the applicant does one action, the API creates N rows. The rows are independent from the moment they are created.

---

## Screening answers per job

Each job may have different screening questions (stored in `jobs.screening_questions` as JSONB). The applicant provides answers per job:

```json
{
  "jobIds": ["job-uuid-1", "job-uuid-2"],
  "answers": {
    "job-uuid-1": [{ "questionId": "q1", "answer": "3 years" }],
    "job-uuid-2": [{ "questionId": "q2", "answer": "Yes, I am available to start immediately." }]
  }
}
```

The answers for job 1 go into `applications.answers` for the row with `job_id = job-uuid-1`. The answers for job 2 go into the separate row. There is no shared answers object — each application is self-contained.

---

## The `ANY($1::uuid[])` pattern

```sql
SELECT id FROM jobs WHERE id = ANY($1::uuid[]) AND status = 'open'
```

`ANY($1::uuid[])` is PostgreSQL syntax for "the column value appears in this array". It is equivalent to `WHERE id IN (uuid1, uuid2, uuid3)` but works cleanly with a parameterised array, avoiding query string concatenation.

The `::uuid[]` cast is necessary because `pg` sends the array as a string literal; PostgreSQL needs to know the element type to parse it correctly.

## Checking the result count

After calling `getOpenJobs`, the service compares the returned list to the requested list:

```ts
const openJobIds = new Set(openJobs.map((j) => j.id));
const closedOrMissing = body.jobIds.filter((id) => !openJobIds.has(id));
```

If any job ID was not returned by `getOpenJobs` (either it does not exist or it is not `status = 'open'`), the service rejects the entire request with a 404. This is a "fail fast" check — it is better to reject the request upfront than to partially insert and then fail on a later job.

---

## The skip-or-fail decision

| Approach | When already-applied | Trade-off |
|----------|---------------------|-----------|
| Fail the request | Return 409 | Simple, but blocks applying to genuinely new jobs |
| Skip and report | Skip, return `skipped` list | Better UX; client knows what happened |

The current implementation skips already-applied jobs and reports them in `skipped`. This works because `ON CONFLICT DO NOTHING` guarantees no duplicate row is ever created, even if the application-layer check misses a race condition. The database is the final guard.

## Transaction note

The loop calls `insertApplication` once per job, each call using a pool connection. If the fifth insert fails (e.g., a constraint violation), the first four are already committed. Chapter 52 wraps this in a transaction so that either all inserts succeed or none do.
