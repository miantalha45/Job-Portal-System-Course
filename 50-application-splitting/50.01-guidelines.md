# Chapter 50 — Splitting a Submission into Per-Job Applications

## What you will build

A single submit endpoint that accepts 1–10 job IDs and creates one `applications` row per job. The grouping applicants see ("applied to 3 jobs at BrightBuild") is a view concern — the data model is one row per job.

## Learning goals

- Map a multi-job submission to individual application rows
- Understand that grouping by company is a query/display concern, not a storage concern
- Prevent duplicate applications with a pre-check
- Return a structured result that reports which jobs succeeded

## Prerequisites

- Chapter 46: applicant profile (`applicantId` from `userId`)
- Chapter 48: résumé upload in place (snapshot will be added in ch51)
- `applications` table exists with the correct schema (see below)

## Schema reminder

```sql
CREATE TABLE applications (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  job_id       uuid REFERENCES jobs(id) NOT NULL,
  applicant_id uuid REFERENCES applicants(id) NOT NULL,
  stage        text NOT NULL DEFAULT 'applied'
                 CHECK(stage IN ('applied','screening','interview','final_interview','offer','hired','rejected')),
  status       text NOT NULL DEFAULT 'active'
                 CHECK(status IN ('active','withdrawn')),
  answers      jsonb NOT NULL DEFAULT '{}',
  snapshot     jsonb NOT NULL DEFAULT '{}',
  created_at   timestamptz NOT NULL DEFAULT now(),
  UNIQUE(job_id, applicant_id)
);
```

## Validation

- `jobIds`: array of 1–10 UUIDs, required
- `answers`: object, optional (defaults to `{}` per job if not provided)
- Each job must exist and be `status = 'open'`

## Implementation

### applicants.repo.ts

```ts
export async function checkExistingApplications(
  applicantId: string,
  jobIds: string[]
): Promise<string[]> {
  const result = await db.query(
    `SELECT job_id FROM applications
     WHERE applicant_id = $1 AND job_id = ANY($2::uuid[])`,
    [applicantId, jobIds]
  );
  return result.rows.map((r) => r.job_id);
}

export async function insertApplication(
  applicantId: string,
  jobId: string,
  answers: unknown,
  snapshot: unknown
) {
  const result = await db.query(
    `INSERT INTO applications (job_id, applicant_id, answers, snapshot)
     VALUES ($1, $2, $3, $4)
     ON CONFLICT (job_id, applicant_id) DO NOTHING
     RETURNING id`,
    [jobId, applicantId, JSON.stringify(answers), JSON.stringify(snapshot)]
  );
  return result.rows[0] ?? null; // null means already existed (DO NOTHING)
}

export async function getOpenJobs(jobIds: string[]): Promise<{ id: string }[]> {
  const result = await db.query(
    `SELECT id FROM jobs WHERE id = ANY($1::uuid[]) AND status = 'open'`,
    [jobIds]
  );
  return result.rows;
}
```

### applicants.service.ts — applyToJobs

```ts
export async function applyToJobs(
  userId: string,
  body: { jobIds: string[]; answers: Record<string, unknown[]> }
) {
  if (body.jobIds.length === 0 || body.jobIds.length > 10) {
    throw new ValidationError('jobIds must contain 1–10 items');
  }

  const profile = await repo.findApplicantByUserId(userId);
  if (!profile) throw new NotFoundError('Profile not found');

  // Verify all jobs exist and are open
  const openJobs = await repo.getOpenJobs(body.jobIds);
  const openJobIds = new Set(openJobs.map((j) => j.id));
  const closedOrMissing = body.jobIds.filter((id) => !openJobIds.has(id));
  if (closedOrMissing.length > 0) {
    throw new NotFoundError(`Jobs not found or not open: ${closedOrMissing.join(', ')}`);
  }

  // Find already-applied jobs (to skip them, not fail)
  const alreadyApplied = await repo.checkExistingApplications(profile.id, body.jobIds);
  const alreadyAppliedSet = new Set(alreadyApplied);

  const created: string[] = [];
  const skipped: string[] = [];

  for (const jobId of body.jobIds) {
    if (alreadyAppliedSet.has(jobId)) {
      skipped.push(jobId);
      continue;
    }

    const answers = body.answers[jobId] ?? [];
    // snapshot will be added in ch51 — for now, empty object
    const snapshot = {};

    const application = await repo.insertApplication(profile.id, jobId, answers, snapshot);
    if (application) {
      created.push(application.id);
    } else {
      skipped.push(jobId); // DO NOTHING fired (race condition)
    }
  }

  return { created, skipped };
}
```

### applicants.routes.ts

```ts
router.post('/apply', async (req, res, next) => {
  try {
    const { jobIds, answers = {} } = req.body;
    const result = await service.applyToJobs(req.user!.userId, { jobIds, answers });
    res.status(201).json(result);
  } catch (err) {
    next(err);
  }
});
```

## Why "skip duplicates" instead of "reject the whole request"

If an applicant submits 3 jobs and they have already applied to 1 of them, rejecting the whole request is a poor user experience. The data model already handles it — `ON CONFLICT DO NOTHING` ensures no duplicate row is created. Returning a `skipped` list gives the client enough information to display feedback ("Already applied to 1 job; applied to 2 new jobs").

Chapter 52 will wrap these inserts in a transaction. Chapter 53 will tighten the idempotency guarantee. For now, the individual `ON CONFLICT DO NOTHING` on each INSERT provides basic safety.

## Grouping by company — display, not storage

Recruiters at BrightBuild see all applications to BrightBuild jobs. Recruiters at NovaCorp see only NovaCorp applications. This grouping comes from `WHERE jobs.company_id = $companyId` in the recruiter query (Chapter 58), not from any grouping in the data model. Each application row knows only which job it belongs to; the company relationship comes through `jobs.company_id`.
