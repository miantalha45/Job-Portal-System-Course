# Build: the repo and service layers

## auth.repo.ts

The repo layer owns every SQL statement for the auth module. Nothing above it (service, route) writes SQL.

```ts
// src/modules/auth/auth.repo.ts
import db from '../../shared/db';

export interface UserRow {
  id:            string;
  email:         string;
  password_hash: string;
  role:          'admin' | 'recruiter' | 'applicant';
  status:        'active' | 'inactive' | 'pending' | 'suspended';
}

export async function findUserByEmail(email: string): Promise<UserRow | null> {
  const { rows } = await db.query<UserRow>(
    'SELECT id, email, password_hash, role, status FROM users WHERE email = $1',
    [email],
  );
  return rows[0] ?? null;
}

export async function createUser(
  email:        string,
  passwordHash: string,
  role:         'recruiter' | 'applicant',
): Promise<{ id: string; email: string; role: string }> {
  const { rows } = await db.query<{ id: string; email: string; role: string }>(
    `INSERT INTO users (email, password_hash, role, status)
     VALUES ($1, $2, $3, 'active')
     RETURNING id, email, role`,
    [email, passwordHash, role],
  );
  return rows[0];
}
```

**`UserRow` interface.** The `pg` driver types `rows` as `any[]` by default. Passing a type argument to `query<UserRow>()` narrows the rows to the expected shape. The interface includes `password_hash` — the repo layer needs to return it so the service layer can pass it to `verifyPassword`. The service layer strips it from what it returns to the route.

**Column selection in `findUserByEmail`.** The query names columns explicitly rather than using `SELECT *`. When you add a column to `users` in a future migration, `SELECT *` silently starts returning it — including if that column contains sensitive data. Named columns make the projection stable and auditable.

**`status = 'active'` hardcoded in `createUser`.** Self-registered users are set to active immediately in this chapter, which means email addresses are not verified before accounts become usable. Chapter 23 adds email verification; when that lands, the INSERT changes to `status = 'pending'` and a separate activation endpoint sets it to `'active'`. Until Chapter 23 is complete, your system accepts unverified email addresses. This is intentional for development — do not deploy to production before completing Chapter 23.

**`RETURNING id, email, role`.** The INSERT returns only the three fields the service needs to return to the caller. `password_hash` is never returned from any query that flows outward.

## auth.service.ts

The service layer enforces business rules and throws named application errors. It knows nothing about HTTP, Express, or response shapes.

```ts
// src/modules/auth/auth.service.ts
import { hashPassword, verifyPassword } from '../../shared/password';
import { ConflictError, UnauthorizedError } from '../../shared/errors';
import { findUserByEmail, createUser } from './auth.repo';
import type { RegisterInput, LoginInput } from './auth.schema';

// A pre-computed bcrypt hash of a throwaway string.
// Used in the login path when no user is found, so the timing cost of
// bcrypt.compare is always paid regardless of whether the email exists.
// Generate with: node -e "require('bcryptjs').hash('__dummy__',12).then(console.log)"
const DUMMY_HASH =
  '$2b$12$EixZaYVK1fsbw1ZfbX3OXePaWxn96p36zLklGLsR9XFKQZ5kQlbri';

export async function register(
  input: RegisterInput,
): Promise<{ id: string; email: string; role: string }> {
  const existing = await findUserByEmail(input.email);
  if (existing) {
    throw new ConflictError('Email already taken');
  }

  const passwordHash = await hashPassword(input.password);
  return createUser(input.email, passwordHash, input.role);
}

export async function login(
  input: LoginInput,
): Promise<{ id: string; email: string; role: string }> {
  const user = await findUserByEmail(input.email);

  if (!user) {
    // Always call verifyPassword, even with a dummy hash.
    // Without this call, a timing oracle exists: no-user paths return in ~0ms,
    // found-but-wrong-password paths return in ~250ms. An attacker measuring
    // response times can determine which emails are registered despite receiving
    // the same error message in both cases.
    await verifyPassword(input.password, DUMMY_HASH);
    throw new UnauthorizedError('Invalid credentials');
  }

  if (user.status !== 'active') {
    throw new UnauthorizedError('Account suspended');
  }

  const valid = await verifyPassword(input.password, user.password_hash);
  if (!valid) {
    throw new UnauthorizedError('Invalid credentials');
  }

  // Chapter 21 adds token issuance here.
  // The return value expands to { id, email, role, accessToken }.
  return { id: user.id, email: user.email, role: user.role };
}
```

---

## The DUMMY_HASH pattern

The problem it solves: bcrypt takes roughly 250ms per comparison. If the login path returns immediately when no user is found (no bcrypt call), and waits 250ms when the user exists but the password is wrong (bcrypt call happens), an attacker measuring HTTP response times can distinguish between "email not registered" and "email registered, wrong password" — even though both paths return `401 Invalid credentials`.

The fix: always call `verifyPassword`, regardless of whether a user row was found. When no user is found, pass the supplied password against a pre-computed constant hash. The bcrypt comparison runs and takes its normal 250ms. The result is discarded. The `UnauthorizedError` is thrown. Both paths take approximately the same wall-clock time.

**The constant must be a valid bcrypt hash.** `bcrypt.compare` needs to parse the hash string to extract the salt and cost factor — it will fail or behave unexpectedly on a malformed input. Generate the constant once with `node -e "require('bcryptjs').hash('__dummy__',12).then(console.log)"` and hardcode the result. The specific value does not matter; any valid `$2b$12$` hash works.

**Why define it in the service, not the repo.** DUMMY_HASH is used in the login *logic* — the decision "no user found, run dummy verify anyway" is a business rule. The repo's job is data access. If DUMMY_HASH lived in the repo, the service would still need to know when to use it.

## Why the service throws named application errors, not HTTP codes

`register` throws `ConflictError`. `login` throws `UnauthorizedError`. Neither touches `res` or knows the HTTP status code.

The service's contract is: given valid input, return a result; if something is wrong with the domain state, throw a named error that describes what is wrong. The error handler in `src/shared/error-handler.ts` (Chapter 17) maps `ConflictError` to 409 and `UnauthorizedError` to 401. That mapping lives in one place.

If the service threw HTTP codes directly, it would know about HTTP — and could not be reused from a CLI tool, a test harness, or a queue worker without carrying Express as a dependency. Named application errors have no such coupling.

## What Chapter 21 adds

Chapter 21 modifies `auth.service.ts` in two ways:

1. `login` generates a signed JWT access token and includes it in the return value: `{ id, email, role, accessToken }`.
2. The route handler in `auth.routes.ts` includes `accessToken` in the 200 response body.

The route handler's response shape is the only thing that changes for the caller. The repo layer is untouched. The service's error logic is untouched. Only the success return path grows.

Chapter 22 adds `refreshToken` generation and the `POST /auth/refresh` endpoint.
