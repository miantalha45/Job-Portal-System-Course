# Build: auth schemas

## File location

`src/modules/auth/auth.schema.ts`

The auth module follows the same structure as every other module: schemas live in `*.schema.ts`, one schema per operation, with inferred TypeScript types exported alongside them.

## The schema file

```ts
import { z } from 'zod';

export const registerSchema = z.object({
  email:    z.string().email('Must be a valid email address').transform(v => v.toLowerCase()),
  password: z.string().min(8, 'Password must be at least 8 characters').max(72, 'Password must be 72 characters or fewer'),
  role:     z.enum(['recruiter', 'applicant'], { errorMap: () => ({ message: 'Invalid role' }) }),
});

export const loginSchema = z.object({
  email:    z.string().email('Must be a valid email address').transform(v => v.toLowerCase()),
  password: z.string().min(1, 'Password is required').max(1000, 'Password too long'),
});

export type RegisterInput = z.infer<typeof registerSchema>;
export type LoginInput    = z.infer<typeof loginSchema>;
```

That is the complete file. Each decision below.

---

## Why 'admin' is excluded from the role enum

The enum for `registerSchema` is `['recruiter', 'applicant']` — not `['recruiter', 'applicant', 'admin']`.

Admin accounts are seeded directly into the database (Chapter 13). They are never self-registered. The reason is a design constraint, not an afterthought: if self-registration could produce admin accounts, a single API request would be enough to escalate any user's privilege to full platform control. The fix is not validation alone — validation can be bypassed in various ways — but the schema makes the intent explicit at the API boundary.

If the platform later needs an "invite an admin" flow, that is a separate authenticated endpoint callable only by an existing admin. It is not the same endpoint as public registration.

The `role` enum uses a custom error map: `{ errorMap: () => ({ message: 'Invalid role' }) }`. Without this, Zod's default enum error message is `"Invalid enum value. Expected 'recruiter' | 'applicant', got 'admin'"` — which exposes the full list of valid roles to anyone probing the API. The custom message returns `"Invalid role"` regardless of what was sent.

The `role` field on `registerSchema` has no `.default()`. Users must specify their role. An applicant who omits it receives a validation error — a 422 with a clear path. A default of `'applicant'` would be reasonable and removes one field from the form; the course leaves it explicit so the field's presence in the body is always intentional.

## Why `z.string().email()` is sufficient

`z.string().email()` checks format: it confirms the input matches the rough shape of an email address — an `@` sign, a local part, a domain segment. It does not check whether the mailbox exists. It does not send a probe. It does not parse every RFC 5321 edge case.

That is the right scope for a synchronous validator.

**Deliverability confirmation happens at verification time.** After registration, the system sends a confirmation email to the supplied address (Chapter 23). If the mailbox does not exist, the send bounces. If the user does not click the link, their account stays in a `pending` state and cannot be used. Format validation at registration is a fast, cheap gate that catches obvious typos. Real deliverability confirmation is a separate async step that catches everything else.

A more permissive check (`z.string().includes('@')`) would be easier to pass with garbage input. A stricter check (`z.string().regex(/[RFC5321-compliant monster regex]/))`) would reject valid addresses that happen to use unusual-but-legal characters. Zod's built-in `.email()` sits in the practical middle: it rejects `notanemail`, accepts `user@example.com`, and handles the vast majority of real addresses correctly. It does accept some edge cases like `a@b` (no TLD) — those are caught at the deliverability step in Chapter 23 anyway.

Both schemas normalize email to lowercase with `.transform(v => v.toLowerCase())`. `USER@EXAMPLE.COM` and `user@example.com` are the same mailbox; storing both as separate accounts is a bug. The transform runs after validation, so the returned `RegisterInput` and `LoginInput` always carry lowercase email.

## Why `max(72)` on the password

Chapter 19 documents bcrypt's hard limit: input longer than 72 bytes is silently truncated before hashing. Two passwords that share the same first 72 bytes will produce the same hash. `z.string().max(72)` rejects passwords longer than 72 characters before they reach `hashPassword`, making the truncation impossible to hit.

One precision: `z.string().max(72)` counts Unicode code points, not bytes. A password of 72 emoji exceeds 72 UTF-8 bytes and would still be truncated by bcryptjs despite passing the Zod check. For a typical ASCII-heavy password policy, the character count and the byte count are the same. For a system serving audiences whose passwords routinely include multibyte characters, replace the Zod check with a custom `refine`:

```ts
.refine(
  (val) => Buffer.byteLength(val, 'utf8') <= 72,
  { message: 'Password must be 72 bytes or fewer' },
)
```

This course uses the simpler `max(72)`. The limitation is documented so you know where the gap is if it matters for your own system.

## Why `loginSchema` has no `max(72)` on password

`loginSchema` uses `z.string().min(1, 'Password is required')` — the only constraint is non-empty.

The reasoning: at login time, `verifyPassword` calls `bcrypt.compare(plaintext, storedHash)`. bcryptjs truncates the plaintext to 72 bytes internally — the same truncation that happens at hash time. A user who registered with a 75-character password (before the `max(72)` constraint existed, or through a system migration) would have their hash computed from the first 72 bytes. `bcrypt.compare` would also use only the first 72 bytes of their supplied plaintext during login. The comparison would succeed.

If `loginSchema` added `max(72)`, that user's login would fail at the validation layer, never reaching `bcrypt.compare`. Their password would appear wrong even though it is correct.

The `max(72)` constraint on register prevents new accounts from being created with passwords that trigger silent truncation. It is not the right constraint on login.

`loginSchema` does apply `max(1000)` on password. Without any upper bound, a client could POST a 100 MB password string. bcryptjs truncates input to 72 bytes internally before hashing, but the allocation and parsing of an enormous string still consumes memory and CPU before truncation occurs. A generous upper limit (1000 characters) blocks obvious resource exhaustion attempts without affecting any legitimate user.
