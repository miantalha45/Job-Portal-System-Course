# Chapter 26 — Prerequisites and framing

## What you need in place

**Chapter 17 — AppError hierarchy** exists in `src/shared/errors.ts`. `UnauthorizedError` (401), `ForbiddenError` (403), `NotFoundError` (404), and `ConflictError` (409) are all defined and exported.

**Chapter 21 — `authMiddleware`** exists at `src/shared/auth-middleware.ts`. It verifies the Bearer token and attaches `req.user = { userId, role }` to every passing request. `src/types/express.d.ts` declares the `user` property on `Express.Request`.

**Chapter 24 — `requireRole`** exists at `src/shared/require-role.ts`. It accepts one or more role strings and returns a middleware that throws `ForbiddenError` (403) if `req.user.role` is not in the permitted list.

**Chapter 23 — The full auth flow is complete.** Register, verify-email, login, refresh, and logout all work. Run `npx tsc --noEmit` and confirm zero errors before you begin.

## What this chapter builds

This chapter wires `authMiddleware` and `requireRole` at the **router level** for the three role-gated module groups:

- Company routes (`/api/companies`) — restricted to the `recruiter` role
- Applicant routes (`/api/applicants`) — restricted to the `applicant` role
- Admin routes (`/api/admin`) — restricted to the `admin` role

The key pattern is `router.use(authMiddleware, requireRole(...))` placed before any route definitions on that router. Every route registered after that `router.use` call automatically inherits both guards. You write the guards once, and the entire router is protected.

The route handlers for these routers are **placeholder stubs** — they return `501 Not Implemented`. Real business logic is added in later chapters. The purpose of this chapter is the auth wiring, not the business logic.

`src/app.ts` also receives the three new routers mounted at their base paths.

---

## Why `router.use` instead of per-route middleware

Applying `authMiddleware` and `requireRole` to each route individually works, but it introduces a class of mistake: a developer adds a new route to a protected router and forgets to add the middleware. The route is silently public.

`router.use(authMiddleware, requireRole(...))` eliminates this class of mistake. The guard runs on every request that reaches the router, regardless of path or method. New routes added to the router inherit the guard automatically. There is no way to add an unguarded route — it would have to be registered on a different router.

This is the recommended pattern for module-level role gates in Express.
