# Chapter 47 — Why Files Don't Belong in the Database

## The question

A résumé is just bytes. PostgreSQL can store bytes in a `bytea` column. Why not do that?

The short answer is cost — three kinds of it.

---

## Cost 1: Storage cost

Managed PostgreSQL on AWS RDS, Google Cloud SQL, or Supabase costs roughly **$0.10–0.25 per GB per month** for storage. Amazon S3 costs **$0.023 per GB per month**. That is approximately a 5–10× difference.

At small scale — a few hundred résumés — the difference is immaterial. At 100,000 résumés averaging 200 KB each, you are storing 20 GB of binary data. In S3 that is $0.46/month. In RDS it is $2–5/month, plus the fact that database storage typically scales in larger increments than object storage, so you often pay for more than you use.

The gap widens as you add more file types: profile photos, company logos, portfolio attachments. Files are the heaviest thing a typical web application stores, and they are the worst possible fit for a pricing model built around structured query capacity.

---

## Cost 2: Throughput cost

PostgreSQL serves data over a connection pool. Every connection is a finite resource — most production setups cap at 20–100 connections. A database query that returns a résumé file must hold a connection open for the entire duration of the transfer — potentially seconds for a large file on a slow network.

A connection serving a 500 KB PDF over a 5 Mbps connection holds that connection for about 0.8 seconds. During that time it cannot serve any other query. At 50 concurrent résumé downloads, you have consumed 50 connections doing nothing but pushing bytes — connections that could have served 500 lightweight record lookups per second instead.

Object storage (S3, MinIO, Google Cloud Storage) is built specifically for high-throughput binary transfer. Connections to S3 are not shared with your query workload. Serving a file from S3 has zero impact on your PostgreSQL connection pool.

---

## Cost 3: Operational cost

Binary data in the database makes everything heavier:

**Backups.** A `pg_dump` or continuous WAL archiving backup must include every blob. A 20 GB résumé store turns a lightweight schema backup into a multi-hour, multi-GB operation.

**Migrations.** `ALTER TABLE` operations that touch `bytea` columns scan the entire table. A schema migration that would take seconds on a 500 MB data table takes hours on a 20 GB blob-heavy table — during which the table is often locked.

**Replication.** WAL replication sends every change to replicas. Binary INSERT writes are replicated byte-for-byte, adding significant bandwidth pressure between primary and read replicas.

**Restore testing.** The only way to know your backups work is to restore them. With a bloated database, restore tests are slow and expensive — so teams stop doing them.

---

## The solution: object storage

Object storage decouples file bytes from structured data. The database stores only metadata:

```sql
resumes (
  id          uuid PK,
  applicant_id uuid FK→applicants,
  filename    text,       -- "talha-resume-2025.pdf"
  s3_key      text,       -- "resumes/abc123/uuid.pdf"
  uploaded_at timestamptz
)
```

The actual bytes live in S3 (or MinIO, Google Cloud Storage, Cloudflare R2 — all S3-compatible). Retrieval is a presigned URL, not a database query.

---

## Presigned URLs: the upload flow

A presigned URL is a time-limited, cryptographically signed URL that grants a single operation (GET or PUT) to a specific S3 object without requiring the caller to have AWS credentials.

The upload flow for résumés:

```
Client                  API Server              S3
  |                         |                    |
  |-- POST /resume-upload -->|                    |
  |                         |-- sign URL -------->|  (no file bytes)
  |                         |<-- presigned URL ---|
  |<-- { uploadUrl, key } --|                    |
  |                         |                    |
  |-- PUT bytes ------------|-------------------->|  (direct, no API server)
  |                                              |
  |-- POST /resume { key, filename } -->          |
  |<-- { resumeId } ----------------------------- |
```

The API server is involved in two lightweight steps: generating the presigned URL and recording the upload metadata. The file bytes never pass through the API server — they go directly from the client to S3.

This means:
- Your API server's CPU and network bandwidth are not spent on file transfer
- S3 handles the burst of concurrent uploads natively
- The database stores only a small metadata row (< 1 KB) per résumé

## Key Takeaways

- Storing file bytes in PostgreSQL costs 5–10× more per GB than object storage
- Binary blobs served through the DB connection pool block connections that should be serving queries
- Large binary stores inflate backup size, slow migrations, and increase replication pressure
- Object storage (S3/MinIO/GCS) is purpose-built for high-throughput binary transfer
- The database stores only metadata (`key`, `filename`, `size`); the bytes live in object storage
- Presigned URLs let clients upload directly to S3 — the API server signs the URL but never touches the file bytes
