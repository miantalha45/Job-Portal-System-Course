## 2. Record `moved_forward` feedback

```bash
RECRUITER_TOKEN="<recruiter access token>"

# Get the interview ID from the database
INTERVIEW_ID=$(psql $DATABASE_URL -t -c \
  "SELECT i.id FROM interviews i
   JOIN applications a ON a.id = i.application_id
   JOIN jobs j ON j.id = a.job_id
   WHERE j.company_id = '<your-company-id>'
     AND i.outcome = 'pending'
   LIMIT 1;" | tr -d ' ')

echo "Interview ID: $INTERVIEW_ID"

curl -s -X PATCH "http://localhost:3000/api/companies/interviews/$INTERVIEW_ID/feedback" \
  -H "Authorization: Bearer $RECRUITER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"feedback":"Excellent performance. Recommend advancing.","outcome":"moved_forward"}' \
  | jq .
```

Expected: HTTP 200, response contains `interview.outcome = "moved_forward"` and `application.stage` advanced to the next stage.

## Quiz

**Q1.** The `outcome → next stage` mapping uses `STAGE_ORDER[currentIdx + 1]`. If the application is at `offer` when feedback is recorded with `moved_forward`, `currentIdx + 1` gives `hired`. Is it correct to automatically move an application to `hired` based on interview feedback alone? Argue for a design where `hired` can only be set explicitly by a separate "mark as hired" action, not automatically from interview feedback.

**Q2.** The `withdrawn` check happens after the ownership check (`findInterviewForCompany`). Explain why this order matters for security. Write the sequence of events that would allow an IDOR attack if the `withdrawn` check ran before the ownership check.

**Q3.** The response includes both the updated `interview` and the updated `application`. An alternative design returns only the `interview` and makes the client re-fetch the application separately. Compare these two designs on: number of HTTP round-trips, over-fetching (returning data the client may not need), and the risk of a stale state if the client does not re-fetch.
