# 57.02 — Interview Feedback: Design Notes

## Why feedback is a one-time write

Once a recruiter records that an interview outcome is `moved_forward` or `rejected`, the application stage has changed accordingly. Allowing the recruiter to overwrite the outcome would require reversing the stage change — a backward stage transition, which Chapter 55 explicitly blocks.

The `outcome !== 'pending'` guard prevents:
1. Overwriting a `moved_forward` with a `rejected` (or vice versa) after the stage has already advanced
2. Retroactive re-evaluations that create inconsistent application history

If a recruiter genuinely needs to change a recorded outcome, the correct path is to create a new interview record for the same application and record feedback on that one. This is consistent with allowing multiple interviews per application (Chapter 56).

---

## The two-query update and atomicity

`recordInterviewFeedback` makes two sequential writes:

1. `updateInterviewFeedback` — sets `feedback` and `outcome` on the interview row
2. `updateApplicationStage` — advances or terminates the application

If the first succeeds and the second fails, the interview shows `outcome = 'moved_forward'` but the application stage has not advanced. The `outcome !== 'pending'` guard would then block any retry.

The fix is to wrap both in a transaction (Chapter 52 pattern). For this chapter, the sequential pattern is acceptable — the failure mode is rare and detectable by comparing `interview.outcome` with `application.stage`.

## What "next stage" means from different starting stages

| Application stage at feedback time | `moved_forward` → | `rejected` → |
|------------------------------------|-------------------|--------------|
| interview                          | final_interview   | rejected     |
| final_interview                    | offer             | rejected     |
| offer                              | hired             | rejected     |
| screening                          | interview         | rejected     |

The advancement is always exactly one step in `STAGE_ORDER`. This is the expected behaviour — `moved_forward` after a first-round interview should go to `final_interview`, not skip directly to `offer`.

---

## Scoping via the interview → application → job → company chain

The ownership check requires traversing three foreign keys:

```
interviews (application_id)
  → applications (job_id)
    → jobs (company_id) === companyId from token
```

The query does this in a single JOIN:

```sql
WHERE i.id = $1 AND j.company_id = $2
```

If the interview ID is valid but belongs to another company, the query returns no rows and the service throws `NotFoundError` — not `ForbiddenError`. Same IDOR pattern as Chapters 29 and 55: do not confirm that the resource exists to an unauthorised caller.

---

## The `withdrawn` check

A recruiter might attempt to record feedback after the applicant withdrew their application. This is a meaningless operation — the application is no longer active. The service rejects it with `ValidationError`.

This check runs after the ownership check. The order matters: confirm the record belongs to you before validating its state. If the order is reversed, a recruiter could learn that a withdrawn application exists at another company (by getting a "this application is withdrawn" error when probing IDs).

---

## Response shape

The response includes both the updated interview and the updated application. The recruiter's frontend needs both to update the UI — the interview's outcome badge and the application's stage badge both change. Returning both in one response avoids a second round-trip from the client.

```json
{
  "interview": { "id": "...", "outcome": "moved_forward", ... },
  "application": { "id": "...", "stage": "final_interview", ... }
}
```

If `outcome = 'moved_forward'` and the application was already at a stage where no further advancement is possible (e.g., `offer`), `application` in the response may be `null`. The client should handle this gracefully.
