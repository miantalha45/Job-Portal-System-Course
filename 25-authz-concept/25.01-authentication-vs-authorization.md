# Chapter 25 — Authentication vs Authorization

## Two questions, two answers

Every request to a protected route triggers two separate questions. They are often confused but they are not the same question, and the system answers them at different points in the middleware chain.

**Authentication** asks: *who are you?*

`authMiddleware` answers this. It reads the `Authorization` header, verifies the JWT signature, checks the expiry claim, and — if the token passes — attaches `req.user = { userId, role }` to the request. From this point forward the server knows exactly which user is behind the request. If the token is absent, expired, or tampered with, `authMiddleware` throws `UnauthorizedError` (401) and the request ends there.

**Authorization** asks: *are you allowed to do this?*

`requireRole` answers this. It reads `req.user.role` — the value `authMiddleware` attached — and checks it against the list of roles that are permitted on the route. If the role matches, the request continues to the handler. If it does not match, `requireRole` throws `ForbiddenError` (403).

These two questions are answered in strict sequence. Authorization cannot run without authentication having run first: you cannot ask "are you allowed here?" about someone whose identity you do not yet know.

---

## What 401 and 403 tell the client

The HTTP status codes carry meaning that the client must act on correctly.

**401 Unauthorized** means: the server does not know who is making this request. The token is missing, forged, or expired. The correct client response is to prompt the user to authenticate — redirect to login, prompt for credentials, or use the refresh token to obtain a new access token.

**403 Forbidden** means: the server knows exactly who is making this request, but that identity is not permitted to perform this action. Re-authenticating will not help. The user will get the same token with the same role and hit the same 403. The correct client response is to display a "you do not have permission" message — not to redirect to login.

Sending a 403 when you mean 401, or vice versa, misleads API consumers. A client that receives a 403 and redirects to login creates a confusing loop: the user logs in, gets the same token, calls the same route, gets the same 403. A client that receives a 401 and shows "you don't have permission" leaves the user stuck when they actually just need to log in again.

In this system:
- `authMiddleware` is the only place that throws `UnauthorizedError` (401).
- `requireRole` is the only place that throws `ForbiddenError` (403).

The separation keeps the status codes accurate.

## The 403 scenario: authenticated but not authorized

A user registers as an `applicant`, verifies their email, and logs in. The server issues a valid JWT with `role: 'applicant'`. The user calls `DELETE /users/:id` — an admin-only route wired as `authMiddleware, requireRole('admin')`.

`authMiddleware` runs. The token is valid. `req.user` is attached. Authentication passes.

`requireRole('admin')` runs. `req.user.role` is `'applicant'`. The role does not match. `ForbiddenError` is thrown. The response is 403.

The user is authenticated — the server knows who they are — but not authorized for this route. This is the fundamental scenario that the two-middleware design handles: not every authenticated user is authorized to do everything.

---

## Role-based access control (RBAC)

The authorization model in this system is Role-Based Access Control. RBAC assigns permissions to roles rather than to individual users. A user's role — `admin`, `recruiter`, or `applicant` — determines what they can do. Individual users are not granted permissions directly; they inherit whatever the role permits.

This simplifies access control significantly. To change what recruiters are allowed to do, you update the routes where `requireRole('recruiter')` appears. Every recruiter in the system is affected immediately without touching any user records.

The three roles in this system have a clear separation of responsibility:

- **`admin`** — platform-level control: managing users, moderating content, accessing system-wide data.
- **`recruiter`** — employer actions: creating and managing job postings, reviewing applications.
- **`applicant`** — job-seeker actions: browsing postings, submitting applications, managing their own profile.

`requireRole` enforces this at the route level. A route with `requireRole('recruiter', 'admin')` allows either role through. A route with `requireRole('admin')` allows only admins.

---

## What RBAC does not handle

RBAC answers "does this role have permission for this action?" It does not answer "does this user own this resource?"

Consider two recruiters, each with valid tokens. Recruiter A created job posting #42. Recruiter B also has the `recruiter` role. RBAC alone cannot prevent Recruiter B from editing or deleting posting #42 — both users pass `requireRole('recruiter')`.

Resource-level ownership is a different problem. It requires checking that the authenticated user is the owner of the specific record being accessed, not just that they hold the right role. This is the IDOR (Insecure Direct Object Reference) problem, covered in Chapter 29.

RBAC handles the role gate. Ownership checks handle the resource gate. Both layers are needed for a complete authorization model.

---

## How authentication and authorization compose

The middleware chain makes the relationship concrete:

```
request → authMiddleware → requireRole(...) → handler
              ↓                  ↓
           401 if            403 if role
         token bad          does not match
```

`authMiddleware` and `requireRole` know nothing about each other. `authMiddleware` does not know what role is required; it only establishes identity. `requireRole` does not know how identity was established; it only checks the role that is already on `req.user`. Each function has one job. They compose because they agree on one contract: `req.user = { userId, role }`.

Any route can mix and match:

- Public route: neither middleware.
- Authenticated but any role: `authMiddleware` only.
- Authenticated and specific role: `authMiddleware` then `requireRole(...)`.

Chapter 26 applies these combinations across all routes in the system.
