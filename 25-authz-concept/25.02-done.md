# Key Takeaways — Chapter 25

- **Authentication establishes identity; authorization checks permission.** `authMiddleware` answers "who are you?" by verifying the JWT. `requireRole` answers "are you allowed here?" by checking `req.user.role`. They are separate questions answered by separate functions.

- **The order is strict: authentication always runs before authorization.** You cannot check whether a user is permitted to do something until the server knows who the user is. `authMiddleware` must appear before `requireRole` in every route chain.

- **401 and 403 mean different things to the client.** 401 means identity is unknown — the client should prompt for re-authentication. 403 means identity is known but the action is not permitted — re-authenticating will not help and the client should not redirect to login.

- **A user can be authenticated but not authorized.** A valid token with `role: 'applicant'` passes `authMiddleware` (401 is not thrown) but fails `requireRole('admin')` (403 is thrown). Being authenticated does not imply being authorized for any particular route.

- **RBAC ties permissions to roles, not to individual users.** Access rules live on routes — in the arguments passed to `requireRole`. Changing what a role can do means updating routes, not user records. Every user with that role is affected immediately.

- **RBAC alone does not solve resource ownership.** Two users with the same role both pass the role gate. Preventing one recruiter from editing another recruiter's job posting requires an ownership check — that is a separate layer covered in Chapter 29.

- **The contract between the two middleware functions is `req.user = { userId, role }`.** `authMiddleware` writes it; `requireRole` reads it. Neither function depends on the internals of the other. They compose cleanly across any route combination.

## Log It

**A teammate argues that combining authentication and authorization into a single middleware — one function that both verifies the token and checks the role — would reduce boilerplate in route files. Every protected route would only need one middleware call instead of two. What does this gain? What does it cost in flexibility and clarity? Would you accept this design for this system?**

There is no single correct answer. Consider: what happens to routes that need authentication but no role restriction; how error codes (401 vs 403) would be handled inside a single function; and whether the coupling makes the function harder to test.

**An applicant's token is valid and not expired. They call a recruiter-only route and receive 403. They immediately log out and log back in. Their new token still carries `role: 'applicant'`. They call the same route and receive 403 again. From a UX perspective, what should the client display — and what should it not do?**

There is no single correct answer. Consider: what 403 communicates versus what 401 communicates; whether a login redirect is appropriate here; and how the application should handle a permission error gracefully without misleading the user.

## Quiz

**Q1.** A route is wired as `router.get('/dashboard', authMiddleware, handler)` — `requireRole` is intentionally omitted. An admin, a recruiter, and an applicant all call this route with valid tokens. Describe what each receives and why. Then explain the difference between this route and one wired with `requireRole('admin', 'recruiter', 'applicant')`. Is there a meaningful behavioral difference, or are they equivalent?

---

**Q2.** The system issues a JWT with `{ userId: 'abc', role: 'recruiter' }`. The recruiter's account is later suspended by an admin — the `users` table row is updated but the token is not revoked. The recruiter continues to call recruiter-only routes. `authMiddleware` passes (the token is structurally valid). `requireRole('recruiter')` passes (the role matches). The handler runs. What does this scenario reveal about the limits of JWT-based authentication and role-based authorization combined? What mechanisms could close this gap?

---

**Q3.** An applicant token passes `authMiddleware`. The applicant then calls `GET /jobs/:id/applications` — a route that should only return applications belonging to that applicant, but the route is wired with `requireRole('applicant')` and the handler returns all applications for that job posting without filtering by `userId`. Name the two distinct authorization problems present: the one that `requireRole` does handle and the one that `requireRole` cannot handle. What type of check is missing for the second problem?
