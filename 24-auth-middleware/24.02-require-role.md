# Build: requireRole

## `src/shared/require-role.ts`

```ts
import { Request, Response, NextFunction } from 'express';
import { ForbiddenError } from './errors';

export function requireRole(
  ...roles: ('admin' | 'recruiter' | 'applicant')[]
): (req: Request, res: Response, next: NextFunction) => void {
  return (req, res, next) => {
    if (!req.user || !roles.includes(req.user.role)) {
      return next(new ForbiddenError('Insufficient role'));
    }
    next();
  };
}
```

That is the entire file.

---

## Why 403, not 401

`UnauthorizedError` (401) means the server cannot identify who is making the request. The token is absent, expired, or forged. Identity is unknown.

`ForbiddenError` (403) means the server knows exactly who is making the request — the token was valid, `authMiddleware` ran, `req.user` is attached — but that identity is not permitted to perform this action.

When `requireRole` runs, the caller has already passed authentication. The `authMiddleware` has verified the token and attached `req.user`. Throwing 401 at this point would be misleading: it would tell the client "we don't know who you are" when in fact we know precisely who they are; they just don't have the right role. 403 communicates the correct situation.

This distinction matters for API consumers. A 401 should prompt the client to re-authenticate (redirect to login, prompt for credentials). A 403 should not — the user is already authenticated and re-authenticating would produce the same result. The client should instead display a "you don't have permission" message.

## The `!req.user` check

`requireRole` always runs after `authMiddleware`. If `authMiddleware` passes without throwing, `req.user` is guaranteed to be defined. So why check `!req.user` at all?

Two reasons.

First, TypeScript. The `user` property on `Express.Request` is declared as `user?` — optional — because not all routes use `authMiddleware`. TypeScript sees `req.user.role` as a potential access on `undefined` and flags it as an error. The `!req.user` guard satisfies the compiler without needing a non-null assertion (`req.user!.role`).

Second, safety net. If someone wires a route with `requireRole` but forgets `authMiddleware`, the request arrives at `requireRole` with `req.user` undefined. Without the guard, this throws a runtime `TypeError: Cannot read properties of undefined`. With the guard, it throws a `ForbiddenError` — a controlled, structured error response instead of an unhandled exception. The gate holds even when the chain is mis-wired.

## Chaining the middleware

`requireRole` is never used alone. The correct pattern is always `authMiddleware` first, then `requireRole`:

```ts
import { Router } from 'express';
import { authMiddleware } from '../../shared/auth-middleware';
import { requireRole } from '../../shared/require-role';

const router = Router();

// Admin-only route
router.delete('/users/:id', authMiddleware, requireRole('admin'), async (req, res, next) => {
  // req.user is defined and req.user.role === 'admin'
});

// Recruiter or admin can access
router.post('/jobs', authMiddleware, requireRole('recruiter', 'admin'), async (req, res, next) => {
  // req.user.role is either 'recruiter' or 'admin'
});
```

Express runs middleware in the order listed. `authMiddleware` runs first. If the token is missing or invalid, it calls `next(UnauthorizedError)` and Express skips the rest of the chain — `requireRole` never runs. If `authMiddleware` calls `next()` without an error, Express runs `requireRole`. If the role does not match, `requireRole` calls `next(ForbiddenError)` and the route handler never runs.

This separation keeps the two concerns distinct. `authMiddleware` answers "who are you?". `requireRole` answers "are you allowed here?". Neither function needs to know what the other does. They compose cleanly in any combination.
