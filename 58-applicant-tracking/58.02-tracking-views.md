# 58.02 — Tracking Views: Design Notes

## Why two different views of the same data

The `applications` table contains all the data both views need. But each consumer wants it shaped differently:

**Applicant view** — "What happened to my applications?"
- Ordered by recency (most recent first)
- Shows one application per row
- Shows upcoming interviews attached to each application
- Does not show other applicants' data

**Recruiter view** — "Where are all applicants in my pipeline?"
- Grouped by stage (the pipeline metaphor)
- Shows snapshot headline (not the live profile)
- Shows the last interview for each application
- Scoped to the recruiter's company only

Same source data, two projections. The database query handles the shape; the service does minimal transformation (grouping into the pipeline object).

---

## Correlated subquery vs LEFT JOIN + GROUP BY

Two common patterns for embedding child records (interviews) into parent rows (applications):

**Pattern A — Correlated subquery (used here):**

```sql
SELECT a.id, (
  SELECT row_to_json(sub)
  FROM (SELECT id, scheduled_at FROM interviews WHERE application_id = a.id LIMIT 1) sub
) AS interview
FROM applications a
WHERE ...
```

Runs one sub-select per application row. For 50 applications, PostgreSQL runs 50 sub-selects. This is O(N) sub-queries, but they are all within the same query plan — not separate round-trips. PostgreSQL typically executes them efficiently using index scans on `interviews.application_id`.

**Pattern B — LEFT JOIN + json_agg:**

```sql
SELECT a.id, json_agg(json_build_object('id', i.id, 'scheduled_at', i.scheduled_at))
  FILTER (WHERE i.id IS NOT NULL) AS interviews
FROM applications a
LEFT JOIN interviews i ON i.application_id = a.id
WHERE ...
GROUP BY a.id
```

Fetches all interviews for all applications in one join, then aggregates. More efficient for large numbers of interviews per application. Harder to express "most recent only" in the FILTER.

For this use case (one interview per application in the response), the correlated subquery is cleaner. For "all interviews per application" (e.g., a full interview history view), use the LEFT JOIN approach.

## The pipeline grouping in the service

The grouping happens in JavaScript, not SQL:

```ts
const pipeline: Record<string, Application[]> = Object.fromEntries(
  ALL_STAGES.map((stage) => [stage, []])
);
for (const app of applications) {
  pipeline[app.stage]?.push(app);
}
```

This works correctly because the SQL query returns rows with `stage` values that are all members of `ALL_STAGES` (enforced by the CHECK constraint). The `?.push` is defensive — if an unknown stage appears (should never happen with the CHECK constraint), it is silently skipped.

An alternative is to do the grouping in SQL with `GROUP BY stage` and `json_agg`, but JavaScript grouping is easier to read and has negligible performance impact for this data size.

## The snapshot headline

The recruiter view uses `a.snapshot->>'headline'` — the JSONB dereference operator (`->>`) extracts a value as text. This shows the headline the applicant had when they applied, not their current headline:

```sql
a.snapshot->>'headline' AS headline
```

If the snapshot was empty (e.g., from an early application before snapshots were implemented in Chapter 51), this returns `NULL`. The recruiter's pipeline card should display a fallback ("No headline provided").

---

## Scoping: the recruiter sees only their company

`findApplicationsForCompany` filters by `j.company_id = $1`. The company ID comes from `req.user!.companyId` (or the member lookup). A recruiter at BrightBuild sees only BrightBuild's applications; they cannot see NovaCorp's pipeline regardless of the endpoint URL.

This is multi-tenant isolation from Chapter 28, applied to the read path. It does not require the recruiter to specify which company they are looking at — the company is implicit from their authenticated session.

---

## N+1 prevention

Both queries retrieve interview data in the same database round-trip as the application data. Without the correlated subquery, the naive approach would be:

```ts
const applications = await getApplications();
for (const app of applications) {
  app.interview = await getLatestInterview(app.id); // N+1 queries!
}
```

50 applications = 51 queries. With the correlated subquery, it is always 1 query regardless of how many applications are returned. Chapter 40's N+1 lesson applied to the tracking view.
