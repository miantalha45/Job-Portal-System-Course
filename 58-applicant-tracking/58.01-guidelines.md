# Chapter 58 — Interview-Aware Tracking Views

## What you will build

Two read endpoints: one for applicants (their own applications + upcoming interviews) and one for recruiters (all applications for their company, grouped by stage).

## Learning goals

- Write JOIN-heavy read queries that aggregate child records (`interviews`) into parent objects (`applications`)
- Use `json_agg` / `json_build_object` for embedded aggregation without N+1 queries
- Return structured views suited to two different consumers of the same underlying data

## Prerequisites

- Chapter 50–53: `applications` table populated
- Chapter 56: `interviews` table populated
- Chapter 55: stage field in use

## Endpoint 1: Applicant's own applications

```
GET /api/applicants/applications
Authorization: Bearer <applicant token>
```

Returns the applicant's own applications with job title, company name, current stage, and upcoming interview details (if any).

```json
{
  "applications": [
    {
      "id": "uuid",
      "job_id": "uuid",
      "job_title": "Senior Backend Engineer",
      "company_name": "BrightBuild",
      "stage": "interview",
      "status": "active",
      "created_at": "...",
      "upcoming_interview": {
        "id": "uuid",
        "scheduled_at": "2026-08-01T10:00:00Z",
        "meeting_link": "https://meet.example.com/abc",
        "notes": "Bring portfolio"
      }
    }
  ]
}
```

`upcoming_interview` is the next scheduled interview with `outcome = 'pending'` and `scheduled_at > now()`. If there is none, the field is `null`.

## Endpoint 2: Recruiter's pipeline view

```
GET /api/companies/applications
Authorization: Bearer <recruiter token>
```

Returns all applications for the recruiter's company, grouped by stage.

```json
{
  "pipeline": {
    "applied":         [ { "id": "...", "headline": "...", "stage": "applied",   "interview": null } ],
    "screening":       [ { "id": "...", "headline": "...", "stage": "screening", "interview": null } ],
    "interview":       [ { "id": "...", "headline": "...", "stage": "interview", "interview": { "scheduled_at": "...", "meeting_link": "..." } } ],
    "final_interview": [],
    "offer":           [],
    "hired":           [],
    "rejected":        []
  }
}
```

Each application in the pipeline shows the snapshot headline (from `applications.snapshot->>'headline'`), the current stage, and the most recent interview (if any, regardless of outcome — to show the recruiter the last interaction).

## Implementation — Applicant view

### applicants.repo.ts

```ts
export async function findApplicationsForApplicant(applicantId: string) {
  const result = await db.query(
    `SELECT
       a.id,
       a.job_id,
       a.stage,
       a.status,
       a.created_at,
       j.title       AS job_title,
       c.name        AS company_name,
       -- Most recent upcoming interview with pending outcome
       (
         SELECT row_to_json(i_sub)
         FROM (
           SELECT id, scheduled_at, meeting_link, notes
           FROM interviews
           WHERE application_id = a.id
             AND outcome = 'pending'
             AND scheduled_at > now()
           ORDER BY scheduled_at ASC
           LIMIT 1
         ) i_sub
       ) AS upcoming_interview
     FROM applications a
     JOIN jobs      j ON j.id = a.job_id
     JOIN companies c ON c.id = j.company_id
     WHERE a.applicant_id = $1
     ORDER BY a.created_at DESC`,
    [applicantId]
  );
  return result.rows;
}
```

export async function getMyApplications(userId: string) {

## Implementation — Recruiter pipeline view

### companies/applications.repo.ts

```ts
export async function findApplicationsForCompany(companyId: string) {
  const result = await db.query(
    `SELECT
       a.id,
       a.stage,
       a.status,
       a.created_at,
       a.snapshot->>'headline' AS headline,
       a.applicant_id,
       j.title AS job_title,
       -- Most recent interview for this application
       (
         SELECT row_to_json(i_sub)
         FROM (
           SELECT id, scheduled_at, meeting_link, outcome
           FROM interviews
           WHERE application_id = a.id
           ORDER BY created_at DESC
           LIMIT 1
         ) i_sub
       ) AS latest_interview
     FROM applications a
     JOIN jobs j ON j.id = a.job_id
     WHERE j.company_id = $1
     ORDER BY a.stage, a.created_at DESC`,
    [companyId]
  );
  return result.rows;
}
```

### companies/applications.service.ts

```ts
const ALL_STAGES = [
  'applied', 'screening', 'interview', 'final_interview', 'offer', 'hired', 'rejected'
] as const;

export async function getCompanyPipeline(companyId: string) {
  const applications = await repo.findApplicationsForCompany(companyId);

  // Group into a pipeline object keyed by stage
  const pipeline: Record<string, typeof applications> = Object.fromEntries(
    ALL_STAGES.map((stage) => [stage, []])
  );

  for (const app of applications) {
    pipeline[app.stage]?.push(app);
  }

  return pipeline;
}
```

### companies/applications.routes.ts

```ts
// GET / — list all applications for this company, grouped by stage
router.get('/', async (req, res, next) => {
  try {
    const pipeline = await service.getCompanyPipeline(req.user!.companyId);
    res.json({ pipeline });
  } catch (err) {
    next(err);
  }
});
```

## The correlated subquery for interviews

Both queries use a correlated subquery to retrieve interview data without an outer GROUP BY or a separate query:

```sql
(
  SELECT row_to_json(i_sub)
  FROM (
    SELECT id, scheduled_at, meeting_link, notes
    FROM interviews
    WHERE application_id = a.id AND outcome = 'pending' AND scheduled_at > now()
    ORDER BY scheduled_at ASC
    LIMIT 1
  ) i_sub
) AS upcoming_interview
```

`row_to_json` converts the selected row into a JSON object. `LIMIT 1` ensures at most one interview is returned. If no matching interview exists, the subquery returns no rows and the outer `SELECT row_to_json(...)` returns `NULL` — which `pg` maps to `null` in JavaScript.

This avoids loading all interviews into Node.js and joining them in application code. The database handles the aggregation.

---

## No pagination for now

As stated in the chapter brief, these endpoints return all results without pagination. For most companies, the total number of active applications is manageable without pagination. When the recruiter pipeline grows to hundreds of applications per stage, add cursor pagination (Chapter 41 pattern) to the `/api/companies/applications` endpoint.
