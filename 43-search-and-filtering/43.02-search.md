# Full-Text Search & Filtering

## 1. The migration

Create `migrations/010_full_text_search.sql`:

```sql
-- migrations/010_full_text_search.sql

-- Step 1: Add the tsvector column
ALTER TABLE jobs ADD COLUMN search_vector tsvector;

-- Step 2: Populate existing rows
UPDATE jobs
SET search_vector = to_tsvector(
  'pg_catalog.english',
  coalesce(title, '') || ' ' || coalesce(description, '')
);

-- Step 3: GIN index for fast full-text lookup
CREATE INDEX idx_jobs_search ON jobs USING gin(search_vector);

-- Step 4: Trigger to keep search_vector current on every INSERT or UPDATE
CREATE TRIGGER jobs_search_vector_update
  BEFORE INSERT OR UPDATE ON jobs
  FOR EACH ROW
  EXECUTE FUNCTION tsvector_update_trigger(
    search_vector,
    'pg_catalog.english',
    title,
    description
  );
```

Apply it:

```bash
psql $DATABASE_URL -f migrations/010_full_text_search.sql
```

## 2. What `tsvector` stores

Running `to_tsvector('english', 'Build APIs in TypeScript and Node.js')` produces something like:

```
'api':2 'build':1 'node.js':6 'typescripton':4
```

This is a sorted list of lexemes — normalised, stemmed word forms. Notice:
- "APIs" → `'api'` (normalised, lowercased)
- "Build" → `'build'`
- "TypeScript" → `'typescripton'` (stemmed by the English dictionary)
- Stop words like "in", "and" are removed entirely — they appear in almost every document and carry no search signal

The positions (`:2`, `:4`) allow phrase search and relevance ranking, though we do not use ranking in this chapter.

## 3. How the trigger works

`tsvector_update_trigger` is a built-in PostgreSQL function. It takes three arguments in the `EXECUTE FUNCTION` clause:

1. The column to write to: `search_vector`
2. The text search configuration: `'pg_catalog.english'`
3. The source columns: `title, description`

When a job is inserted or updated, PostgreSQL calls the trigger before writing the row. The trigger sets `NEW.search_vector = to_tsvector('pg_catalog.english', NEW.title || ' ' || NEW.description)` automatically. Your application code does not need to compute or update the vector.

This means:
- Existing update endpoints (PATCH /api/jobs/:id) automatically keep the vector fresh.
- There is no risk of the search index drifting out of sync with the actual text.

## 4. Updating the public board service

In `src/modules/public/publicService.ts`, replace the ILIKE condition with a full-text search condition.

**Before (ILIKE):**

```typescript
if (q) {
  params.push(`%${q}%`);
  conditions.push(`(j.title ILIKE $${params.length} OR j.description ILIKE $${params.length})`);
}
```

**After (full-text search):**

```typescript
if (q) {
  params.push(q);
  conditions.push(`j.search_vector @@ plainto_tsquery('english', $${params.length})`);
}
```

The `@@` operator checks whether the query matches the vector. `plainto_tsquery` converts the user's search string to a tsquery — it handles punctuation, common words, and stemming automatically. It never throws on arbitrary input.

The full updated `getPublicJobs` function:

```typescript
export async function getPublicJobs(query: PublicJobsQuery) {
  const { q, location, employment_type, cursor, limit } = query;
  const params: unknown[] = [];
  const conditions: string[] = [
    `j.status = 'open'`,
    `c.status = 'verified'`,
  ];

  // Full-text search using tsvector + GIN index (replaces ILIKE from ch39)
  if (q) {
    params.push(q);
    conditions.push(
      `j.search_vector @@ plainto_tsquery('english', $${params.length})`
    );
  }

  if (location) {
    params.push(location);
    conditions.push(`j.location ILIKE $${params.length}`);
  }

  if (employment_type) {
    params.push(employment_type);
    conditions.push(`j.employment_type = $${params.length}`);
  }

  const decoded = cursor ? decodeCursor(cursor) : null;
  if (decoded) {
    params.push(decoded.createdAt, decoded.id);
    conditions.push(
      `(j.created_at, j.id) < ($${params.length - 1}::timestamptz, $${params.length})`
    );
  }

  const whereClause = conditions.join(' AND ');
  params.push(limit + 1);
  const limitParam = params.length;

  const sql = `
    SELECT
      j.id,
      j.title,
      j.location,
      j.employment_type,
      j.salary_min,
      j.salary_max,
      j.created_at,
      c.name AS company_name
    FROM jobs j
    JOIN companies c ON c.id = j.company_id
    WHERE ${whereClause}
    ORDER BY j.created_at DESC, j.id DESC
    LIMIT $${limitParam}
  `;

  const { rows } = await db.query(sql, params);

  const hasNextPage = rows.length > limit;
  const jobs = hasNextPage ? rows.slice(0, limit) : rows;
  const nextCursor =
    hasNextPage
      ? encodeCursor(jobs[jobs.length - 1].created_at, jobs[jobs.length - 1].id)
      : null;

  return {
    jobs: jobs.map((r) => ({
      id:             r.id,
      title:          r.title,
      companyName:    r.company_name,
      location:       r.location,
      employmentType: r.employment_type,
      salaryMin:      r.salary_min,
      salaryMax:      r.salary_max,
      createdAt:      r.created_at,
    })),
    nextCursor,
  };
}
```

Note: `location` still uses `ILIKE` because it is a short field with no stop words — full-text search would be overkill and ILIKE on a short, selective field is acceptable. The GIN index is only on `search_vector`.

## 5. Combining search with filters

The conditions array allows any combination of search, location, and employment_type. Examples:

```
GET /api/public/jobs?q=typescript
  → WHERE status='open' AND c.status='verified' AND search_vector @@ plainto_tsquery('english', 'typescript')

GET /api/public/jobs?q=backend&location=Remote&employment_type=full_time
  → WHERE status='open' AND c.status='verified'
       AND search_vector @@ plainto_tsquery('english', 'backend')
       AND location ILIKE 'Remote'
       AND employment_type = 'full_time'
```

All conditions are ANDed — a job must match every provided filter.

## 6. What `plainto_tsquery` does with edge cases

| Input | Result |
|---|---|
| `"typescript"` | `'typescript'` |
| `"TypeScript Engineer"` | `'typescript' & 'engin'` |
| `"node.js"` | `'node.j'` (varies by dictionary) |
| `""` (empty string) | empty tsquery — matches nothing |
| `"the and or"` (all stop words) | empty tsquery — matches nothing |
| `"'; DROP TABLE"` | harmless — it is parameterised; `plainto_tsquery` parses it as text |

The last point is important: because we use `$1` and pass `q` as a parameter, SQL injection is impossible. `plainto_tsquery` receives the string as data, not as SQL.

## 7. Verify the GIN index is used

```sql
EXPLAIN ANALYZE
SELECT j.id, j.title
FROM jobs j
JOIN companies c ON c.id = j.company_id
WHERE j.status = 'open'
  AND c.status = 'verified'
  AND j.search_vector @@ plainto_tsquery('english', 'engineer')
ORDER BY j.created_at DESC, j.id DESC
LIMIT 20;
```

Expected in the plan: `Bitmap Index Scan on idx_jobs_search` or `Index Scan using idx_jobs_search`. The GIN index serves the `@@` operator.

When a full-text `q` param is combined with the `status` filter, PostgreSQL uses both indexes (GIN for the text condition, B-tree for status) and combines the results via a Bitmap AND — or it may choose whichever is more selective. `EXPLAIN ANALYZE` will show the chosen plan.
