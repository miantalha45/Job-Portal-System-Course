# Chapter 68 — Scheduled Jobs (Cron-Style)

## What you will build

Two recurring background jobs: one that cleans up expired OTP rows from `email_verifications`
and one that cleans up expired refresh tokens from `refresh_tokens`. Both use BullMQ's
repeatable job feature with cron syntax.

## Learning goals

- Use BullMQ's repeatable jobs to run a job on a cron schedule
- Understand when to register repeatable jobs (worker startup, not application startup)
- Inspect registered repeatable jobs with `queue.getRepeatableJobs()`

## Prerequisites

- Chapter 23: `email_verifications` table with `expires_at`
- Chapter 22: `refresh_tokens` table with `expires_at`
- Chapter 63: queue and worker in place

## Implementation

### src/worker/handlers/cleanupExpiredOtps.ts

```ts
import db from '../../shared/db';

// Delete OTP rows that have passed their expiry time
export async function cleanupExpiredOtps(): Promise<void> {
  const result = await db.query(
    `DELETE FROM email_verifications WHERE expires_at < NOW()`
  );
  console.log(`[cleanup] Deleted ${result.rowCount} expired OTP rows`);
}
```

### src/worker/handlers/cleanupExpiredTokens.ts

```ts
import db from '../../shared/db';

// Delete refresh token rows that have passed their expiry time
export async function cleanupExpiredTokens(): Promise<void> {
  const result = await db.query(
    `DELETE FROM refresh_tokens WHERE expires_at < NOW()`
  );
  console.log(`[cleanup] Deleted ${result.rowCount} expired refresh token rows`);
}
```

### src/worker/worker.ts — register repeatable jobs on startup

```ts
import { Queue } from 'bullmq';
import config from '../shared/config';
import { cleanupExpiredOtps } from './handlers/cleanupExpiredOtps';
import { cleanupExpiredTokens } from './handlers/cleanupExpiredTokens';

// Use a Queue instance to register repeatable jobs
// (separate from the one used in the app, but same queue name)
const schedulerQueue = new Queue('jobs', {
  connection: { url: config.REDIS_URL },
});

async function registerRepeatableJobs() {
  // Daily at midnight UTC
  await schedulerQueue.add(
    'cleanup-expired-otps',
    {},   // no payload needed; the handler queries the DB at runtime
    { repeat: { pattern: '0 0 * * *' } }
  );

  // Daily at 01:00 UTC
  await schedulerQueue.add(
    'cleanup-expired-refresh-tokens',
    {},
    { repeat: { pattern: '0 1 * * *' } }
  );

  const jobs = await schedulerQueue.getRepeatableJobs();
  console.log('[worker] Repeatable jobs registered:', jobs.map(j => j.name));
  await schedulerQueue.close();
}

registerRepeatableJobs().catch(console.error);
```

Call `registerRepeatableJobs()` when the worker process starts, before the `Worker` instance
starts processing. BullMQ is idempotent about repeatable job registration — calling
`queue.add` with the same `{ repeat }` options does not create duplicates.

### src/worker/worker.ts — add the case handlers

```ts
import { cleanupExpiredOtps } from './handlers/cleanupExpiredOtps';
import { cleanupExpiredTokens } from './handlers/cleanupExpiredTokens';

case 'cleanup-expired-otps': {
  await cleanupExpiredOtps();
  break;
}

case 'cleanup-expired-refresh-tokens': {
  await cleanupExpiredTokens();
  break;
}
```

## Cron pattern reference

| Pattern | Meaning |
|---------|---------|
| `0 0 * * *` | Every day at midnight (00:00) UTC |
| `0 1 * * *` | Every day at 01:00 UTC |
| `0 8 * * 1` | Every Monday at 08:00 UTC |
| `*/15 * * * *` | Every 15 minutes |

BullMQ uses the `cron-parser` package to interpret patterns. Patterns are in standard 5-field
cron format: minute, hour, day-of-month, month, day-of-week.

---

## Why repeatable job registration at worker startup?

The worker process is the operational unit that owns background jobs. If you register repeatable
jobs in the Express app, they run even if the worker is not running — BullMQ queues the job, but
nothing processes it. Registering at worker startup keeps the scheduling responsibility with the
component that executes the work.

---

## No `process.env` in this module

Cron patterns are hardcoded in the worker. They are operational decisions, not deployment
secrets, so they do not belong in `config.ts` or `.env`.
