# Building the health check endpoint

## Where it lives — and why

The health check is **not a feature**. There's no `modules/health/` folder and there shouldn't be — it doesn't belong to companies, jobs, applications, or any other product concern. It's infrastructure: a signal from the process about the process itself.

Wire it directly in `src/app.ts`, **before** the feature route registrations. Keep your existing `buildApp()` setup — only add the health route:

```typescript
// src/app.ts  (add inside your existing buildApp function, before feature routes)

// ── Infrastructure ──────────────────────────────────────────────
app.get('/health', async (_request, reply) => {
  return reply.send({
    status: 'ok',
    uptime: Math.floor(process.uptime()),
    timestamp: new Date().toISOString(),
  });
});

// ── Feature routes (registered in later chapters) ───────────────
// app.register(authRoutes, { prefix: '/auth' });
// app.register(jobRoutes,  { prefix: '/jobs' });
```

Three fields in the response body:

- **`status: 'ok'`** — the machine-readable signal. Load balancers and monitors key off this value, not the HTTP status code alone.
- **`uptime`** — seconds since the process started. Useful for spotting an unexpected restart in a production incident.
- **`timestamp`** — confirms the response is live. A cached or replayed response is immediately visible.

The handler is `async` to match the rest of the codebase, even though it does no async work — consistency keeps the pattern clear for future contributors.

## What this handler deliberately does NOT do

It does not query the database. It does not ping Redis. A **liveness** probe must always answer fast and must answer even when dependencies are degraded — because the question it answers is "is the process alive?", not "is everything it depends on alive?".

If you query the database here and the database goes down:

1. The health check returns 500.
2. The orchestrator concludes the *process* is unhealthy.
3. It restarts a process that is, in fact, perfectly healthy.
4. The restart doesn't fix the database — and now you've also lost any in-flight requests.

Dependency probing belongs to the readiness endpoint, which you'll build in [Chapter 72](../72-readiness-and-shutdown/) once all the dependencies are established.
