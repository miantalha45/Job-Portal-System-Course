# What a health check is — and why you need one from day one

## The problem without one

A process either answers requests or it doesn't. Without a dedicated health endpoint, infrastructure that wants to know whether your service is alive has no reliable signal. It can try to guess:

- **TCP port open?** — passes even if your app is panicking after every request
- **Last request succeeded?** — only works if there was a recent request, and it reads the past, not the present

Neither is trustworthy. A **health check endpoint** is the authoritative answer from the process itself: *call this one route; `200` means healthy; anything else means stop sending me traffic.*

## Who calls it

| Consumer | What it does with the signal |
|---|---|
| Load balancer | Routes traffic only to instances returning 200; removes the rest |
| Container orchestrator (Kubernetes, ECS) | Restarts containers that fail to return 200 within a window |
| Uptime monitor | Pages on-call when 200 stops arriving |
| Deployment pipeline | Waits for the new version to return 200 before shifting traffic over |

You won't wire all of those during this chapter — the deployment plumbing arrives in [Chapter 74](../74-deploy/). But every tool above will expect this endpoint to exist, so building it now costs almost nothing and removes a future gap.

## Liveness vs readiness — two different questions

A health check can answer one of two questions:

| | Question | Checks |
|---|---|---|
| **Liveness** (`GET /health`) | Is the process alive and processing requests? | Nothing — if it answered, the event loop is running. If the event loop hangs, the request times out; orchestrators treat a timeout identically to a non-200 response. |
| **Readiness** (`GET /ready`) | Is the process ready to handle real requests right now? | Database reachable, Redis reachable, migrations run |

This chapter builds the **liveness** check: lightweight, always fast, never touches a dependency. [Chapter 72](../72-health-and-shutdown/) extends the picture with a readiness probe once all dependencies are wired.

Understanding the difference matters: a liveness probe failing should mean *restart the process*. A readiness probe failing should mean *stop routing traffic, but don't restart* — because the process is fine; its dependency is the problem.
