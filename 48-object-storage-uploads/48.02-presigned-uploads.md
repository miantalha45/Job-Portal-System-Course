# 48.02 — Presigned Uploads in Depth

## Why presigned URLs are safe

A presigned URL looks like a secret — it embeds an HMAC signature that grants write access to a specific S3 key. It is safe because:

1. **It is scoped to one object.** The signature is computed over the bucket, key, HTTP method, and expiry time. A presigned PUT URL for `resumes/abc/def.pdf` cannot be used to write to `resumes/abc/evil.pdf` or any other key.
2. **It expires.** The 300-second default means the URL is useless after five minutes. An intercepted URL cannot be replayed after it expires.
3. **The key prefix check in the API prevents spoofing.** Even if an applicant tried to get a presigned URL for another applicant's key path — they cannot, because the API server builds the key from the authenticated user's `applicantId`. The confirm endpoint validates the key prefix before writing the metadata row.

## forcePathStyle and MinIO

AWS S3 uses virtual-hosted style URLs by default:

```
https://job-portal.s3.us-east-1.amazonaws.com/resumes/abc/def.pdf
```

MinIO uses path style:

```
http://localhost:9000/job-portal/resumes/abc/def.pdf
```

Setting `forcePathStyle: true` in the S3 client constructor makes the SDK generate path-style URLs. This setting is transparent to the rest of the codebase — `storage.ts` always generates the same kind of presigned URL regardless of which backend is running.

In production you point `S3_ENDPOINT` at the real AWS endpoint (or remove it entirely — the SDK defaults to AWS if no endpoint is set). The `forcePathStyle` flag is harmless with real AWS.

## Key naming convention

```
resumes/{applicantId}/{uuid}.pdf
```

- `applicantId` — scopes the key to the applicant. Useful for listing all résumés for an applicant via S3 prefix listing (not used here, but possible).
- `uuid` — prevents collisions. An applicant who uploads the same filename twice gets two distinct objects.
- `.pdf` — sets the expected content type. The presigned URL specifies `ContentType: application/pdf`; if the client sends a different content type, S3 rejects the PUT.

## Expiry trade-offs

| Expiry | Risk | User impact |
|--------|------|-------------|
| 60 s   | Low — small window for URL leakage | Poor UX for slow connections or large files |
| 300 s  | Low — 5-minute window | Comfortable for most uploads |
| 3600 s | Higher — longer leakage window | Unnecessary for résumés |

300 seconds is a good default for résumé-sized files (< 5 MB). If you expect larger files, increase the expiry. Never cache the presigned URL across requests — each upload request generates a fresh URL.

## What happens if the client uploads but never confirms?

The file exists in S3 but no row exists in the `resumes` table. The file is an orphan. The API has no knowledge of it; no applicant's profile references it.

Two strategies for cleanup:
1. **S3 lifecycle rule** — configure the bucket so that objects with the `resumes/` prefix that have not been accessed in 24 hours are automatically deleted.
2. **Background sweep** — a scheduled job lists all S3 keys under `resumes/` and deletes any that have no matching `s3_key` in the `resumes` table.

Neither is required for this chapter. A TODO comment in `storage.ts` is sufficient.

## Listing résumés

The `GET /api/applicants/profile` route does not currently return résumés. You can add résumés to the profile response by joining:

```ts
// In applicants.repo.ts — extend findApplicantByUserId if desired:
const result = await db.query(
  `SELECT a.id, a.user_id, a.headline, a.bio, a.skills, a.created_at,
          json_agg(
            json_build_object('id', r.id, 'filename', r.filename, 's3_key', r.s3_key, 'uploaded_at', r.uploaded_at)
            ORDER BY r.uploaded_at DESC
          ) FILTER (WHERE r.id IS NOT NULL) AS resumes
   FROM applicants a
   LEFT JOIN resumes r ON r.applicant_id = a.id
   WHERE a.user_id = $1
   GROUP BY a.id`,
  [userId]
);
```

This is optional — the DoD does not require it. It is shown here so you understand how to extend the query when the frontend needs it.

- Delete test files
- Configure bucket policies

Log in with the `MINIO_ROOT_USER` / `MINIO_ROOT_PASSWORD` from docker-compose (both `minioadmin` in the dev setup).
