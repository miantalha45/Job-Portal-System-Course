# 67.02 — Interview Notification Jobs (Walkthrough)

## The async migration pattern

The same four steps apply every time you move an inline operation to a background job:

```
1. Find the inline call in the service function
2. Replace it with queue.add(jobName, payload)
3. Add a case to the worker switch statement
4. Test: confirm HTTP response is fast + background work completes
```

This chapter applies the pattern to interview notifications. Once you have done it twice
(Chapter 64 and Chapter 67), the pattern is mechanical.

---

## Why serialize Date to ISO string

A `Date` object in JavaScript is not directly serializable to JSON the way you might expect.
`JSON.stringify({ date: new Date() })` produces `{"date":"2026-06-07T10:30:00.000Z"}` — a
string, not a Date object. When the worker calls `JSON.parse`, it gets a string, not a Date.

If `sendInterviewNotification` expects a `Date` object, the worker must parse it:

```ts
const scheduledAt = new Date(job.data.scheduledAt);
await sendInterviewNotification(applicantEmail, scheduledAt, meetingLink);
```

If it expects a string (e.g., for formatting in the email), pass it directly. Be explicit about
the type your mailer function expects.

## Building it step by step

### Step 1 — Locate the inline call in interviews.service.ts

Find the call to `mailer.sendInterviewNotification` in `scheduleInterview`. It looks like:

```ts
await mailer.sendInterviewNotification(
  applicantEmail,
  interview.scheduled_at,
  interview.meeting_link
);
```

### Step 2 — Replace with queue.add

```ts
await queue.add('send-interview-notification', {
  applicantEmail,
  scheduledAt: interview.scheduled_at instanceof Date
    ? interview.scheduled_at.toISOString()
    : interview.scheduled_at,
  meetingLink: interview.meeting_link,
});
```

Remove the `mailer` import if it is no longer used in this file (TypeScript will warn about
unused imports).

### Step 3 — Add the worker case

```ts
import { sendInterviewNotification } from '../shared/mailer';

case 'send-interview-notification': {
  const { applicantEmail, scheduledAt, meetingLink } = job.data;
  await sendInterviewNotification(applicantEmail, scheduledAt, meetingLink);
  break;
}
```

### Step 4 — Test

Schedule an interview via the API:

```bash
curl -X POST http://localhost:3000/api/interviews \
  -H "Authorization: Bearer $RECRUITER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "applicationId": "<APPLICATION_ID>",
    "scheduledAt": "2026-07-01T10:00:00.000Z",
    "meetingLink": "https://meet.example.com/test"
  }'
```

Expected:
- HTTP response in < 50ms
- Worker log: `[worker] Processing job send-interview-notification`
- Email delivered to the applicant's inbox

---

## Before/after HTTP response time

With inline email (Chapter 56):
```
POST /api/interviews → 180ms (150ms SMTP + 30ms DB)
```

With async job (Chapter 67):
```
POST /api/interviews → 35ms (30ms DB + 5ms Redis enqueue)
```

The applicant still receives the notification email, but the recruiter who made the API call
gets a response 5x faster.

---

## Error handling

If `sendInterviewNotification` throws (SMTP down), BullMQ retries with exponential backoff
(configured in Chapter 65). The interview row is already in the database. On retry, the same
notification is sent — which is idempotent from the applicant's perspective (receiving the
same email twice is not a data consistency problem).
