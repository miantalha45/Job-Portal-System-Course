## Key Takeaways

- Offset pagination (`LIMIT n OFFSET k`) requires a sequential scan through the skipped rows. Cost is O(k) — it grows with the page number.
- Offset pagination is unstable: rows inserted or deleted between page requests cause duplicates or silent skips in the result set.
- Cursor pagination encodes the position of the last returned item (`created_at` + `id`). The next page queries `WHERE (created_at, id) < (cursor_ts, cursor_id)`, which is O(log n) with a composite index.
- Both columns of the cursor are necessary: timestamp ties are possible, and `id` (the primary key) resolves them uniquely.
- UUID v4 primary keys carry no insertion-order information. Using only `id` as the sort key would produce an arbitrary, non-meaningful order. Pair `id` with `created_at`.
- Cursor pagination cannot jump to an arbitrary page. You must walk forward from the beginning. For a sequential-browse use case (job board) this is fine.
- The +1 trick detects the next page without a `COUNT(*)` query: fetch `limit + 1` rows, check if `rows.length > limit`, return only `limit` rows to the caller.
- `COUNT(*)` on a large filtered table requires scanning all matching rows — it cannot use the cursor index for early termination.

## 2. Confirm cursor is not a page number

Decode the cursor to confirm it encodes a timestamp and UUID, not a page number or offset:

```bash
CURSOR=$(curl -s "http://localhost:3000/api/public/jobs?limit=1" | jq -r '.nextCursor')

# Decode the base64url cursor
echo $CURSOR | base64 -d 2>/dev/null || \
  node -e "console.log(Buffer.from('$CURSOR', 'base64url').toString('utf8'))"
```

Expected output format: `2026-06-07T10:00:00.000Z|<uuid>` — a timestamp and a UUID separated by a pipe character.

## 3. Demonstrate offset instability (optional but instructive)

This is a thought experiment — run it only if you want to observe the problem directly.

```bash
# Page 1 with limit=1 — note which job appears
curl -s "http://localhost:3000/api/public/jobs?limit=1" | jq '.jobs[0].title'

# While "reading page 1", insert a new job and publish it
# (use RECRUITER_TOKEN from earlier)
NEW_JOB=$(curl -s -X POST http://localhost:3000/api/jobs \
  -H "Authorization: Bearer $RECRUITER_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Brand New Job","employment_type":"full_time"}' \
  | jq -r '.jobId')

curl -s -X POST http://localhost:3000/api/jobs/$NEW_JOB/publish \
  -H "Authorization: Bearer $RECRUITER_TOKEN" | jq .

# Now request "page 2" using the cursor from page 1 — cursor pagination is stable
CURSOR=$(curl -s "http://localhost:3000/api/public/jobs?limit=1" | jq -r '.nextCursor')
curl -s "http://localhost:3000/api/public/jobs?limit=1&cursor=$CURSOR" | jq '.jobs[0].title'
```

The cursor-paginated page 2 returns the job that was at position 2 when page 1 was fetched — it does not skip or repeat. The new job appears on the refreshed page 1 but does not disturb later pages.
