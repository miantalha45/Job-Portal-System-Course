# Chapter 46 — The Applicant Profile & Onboarding

## What you will build

Three endpoints that let an applicant create and maintain their profile after email verification. A verified user with `role='applicant'` has a `users` row but no `applicants` row yet. These endpoints bridge that gap.

## Learning goals

- Understand the distinction between the `users` row (identity) and the `applicants` row (profile)
- Write a one-to-one extension table pattern (`applicants.user_id UNIQUE`)
- Store an unordered list (skills) as a JSONB array
- Use `requireRole('applicant')` already wired to the router from Chapter 26

## Prerequisites

- Chapter 26: `requireRole` middleware in place
- Chapter 20/23: applicant registers with `role='applicant'` and verifies email
- `applicants` table exists in your schema (see below)

## Schema reminder

```sql
CREATE TABLE applicants (
  id          uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     uuid REFERENCES users(id) UNIQUE NOT NULL,
  headline    text,
  bio         text,
  skills      jsonb NOT NULL DEFAULT '[]',
  created_at  timestamptz NOT NULL DEFAULT now()
);
```

## Endpoint summary

| Method | Path                      | Description            |
|--------|---------------------------|------------------------|
| POST   | /api/applicants/profile   | Create profile (once)  |
| GET    | /api/applicants/profile   | Get own profile        |
| PATCH  | /api/applicants/profile   | Update profile         |

All three require the `requireAuth` + `requireRole('applicant')` guards already wired to this router.

---

## Design decisions

**Why a separate `applicants` table?**
The `users` table is the identity layer — every user type lives there. Role-specific data (headline, bio, skills, résumés) belongs in a role-specific extension table. This keeps the schema clean and avoids nullable columns that only apply to one role.

**JSONB for skills**
Skills are an unordered list of strings. They are read and written together — you never query `WHERE skills @> '["python"]'` in the basic profile endpoints. JSONB is the right choice: it stores the array without a join and without a separate `applicant_skills` table.

**POST to create, PATCH to update**
`POST /api/applicants/profile` runs once: it creates the applicants row. If the row already exists, return `409 Conflict`. `PATCH` is strictly for updates — it never creates.

## Implementation

### applicants.repo.ts

```ts
import db from '../../shared/db';

export async function createApplicantProfile(
  userId: string,
  headline: string,
  bio: string,
  skills: string[]
) {
  const result = await db.query(
    `INSERT INTO applicants (user_id, headline, bio, skills)
     VALUES ($1, $2, $3, $4)
     RETURNING id, user_id, headline, bio, skills, created_at`,
    [userId, headline, bio, JSON.stringify(skills)]
  );
  return result.rows[0];
}

export async function findApplicantByUserId(userId: string) {
  const result = await db.query(
    `SELECT id, user_id, headline, bio, skills, created_at
     FROM applicants WHERE user_id = $1`,
    [userId]
  );
  return result.rows[0] ?? null;
}

export async function updateApplicantProfile(
  applicantId: string,
  fields: { headline?: string; bio?: string; skills?: string[] }
) {
  const sets: string[] = [];
  const values: unknown[] = [];
  let i = 1;

  if (fields.headline !== undefined) {
    sets.push(`headline = $${i++}`);
    values.push(fields.headline);
  }
  if (fields.bio !== undefined) {
    sets.push(`bio = $${i++}`);
    values.push(fields.bio);
  }
  if (fields.skills !== undefined) {
    sets.push(`skills = $${i++}`);
    values.push(JSON.stringify(fields.skills));
  }

  if (sets.length === 0) return null;

  values.push(applicantId);
  const result = await db.query(
    `UPDATE applicants SET ${sets.join(', ')}
     WHERE id = $${i}
     RETURNING id, user_id, headline, bio, skills, created_at`,
    values
  );
  return result.rows[0] ?? null;
}
```

### applicants.service.ts

```ts
import * as repo from './applicants.repo';
import { ConflictError, NotFoundError } from '../../shared/errors';

export async function createProfile(
  userId: string,
  body: { headline: string; bio: string; skills: string[] }
) {
  const existing = await repo.findApplicantByUserId(userId);
  if (existing) throw new ConflictError('Profile already exists');
  return repo.createApplicantProfile(userId, body.headline, body.bio, body.skills);
}

export async function getProfile(userId: string) {
  const profile = await repo.findApplicantByUserId(userId);
  if (!profile) throw new NotFoundError('Profile not found');
  return profile;
}

export async function updateProfile(
  userId: string,
  fields: { headline?: string; bio?: string; skills?: string[] }
) {
  const profile = await repo.findApplicantByUserId(userId);
  if (!profile) throw new NotFoundError('Profile not found');
  return repo.updateApplicantProfile(profile.id, fields);
}
```

### applicants.routes.ts

```ts
import { Router } from 'express';
import { requireAuth } from '../../shared/middleware/requireAuth';
import { requireRole } from '../../shared/middleware/requireRole';
import * as service from './applicants.service';

const router = Router();
router.use(requireAuth, requireRole('applicant'));

router.post('/profile', async (req, res, next) => {
  try {
    const { headline, bio, skills } = req.body;
    const profile = await service.createProfile(req.user!.userId, { headline, bio, skills });
    res.status(201).json(profile);
  } catch (err) {
    next(err);
  }
});

router.get('/profile', async (req, res, next) => {
  try {
    const profile = await service.getProfile(req.user!.userId);
    res.json(profile);
  } catch (err) {
    next(err);
  }
});

router.patch('/profile', async (req, res, next) => {
  try {
    const { headline, bio, skills } = req.body;
    const profile = await service.updateProfile(req.user!.userId, { headline, bio, skills });
    res.json(profile);
  } catch (err) {
    next(err);
  }
});

export default router;
```

## Validation notes

`POST /api/applicants/profile` should validate:
- `headline`: string, required, max 200 chars
- `bio`: string, required
- `skills`: array of strings, required (can be empty `[]`)

Use your existing validation middleware (Zod or similar) on the request body. Keep validation in the route layer; the service trusts that inputs are already clean.

## No `process.env` in service or repo

All environment-dependent values (DB URL, etc.) come from `config.ts` and are injected via the `db` client. No module in `src/modules/` reads `process.env` directly.
