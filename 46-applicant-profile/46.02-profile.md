# 46.02 — Applicant Profile Deep Dive

## The identity vs. profile split

After email verification an applicant has exactly one row in `users`. That row records email, hashed password, role, and status — nothing specific to being a job-seeker. The `applicants` table extends it with job-seeker fields.

```
users
  id uuid PK
  email text
  role text          ← 'applicant'
  status text        ← 'active' after email verification
  ...

applicants
  id uuid PK
  user_id uuid UNIQUE FK→users   ← the bridge
  headline text
  bio text
  skills jsonb
  created_at timestamptz
```

The `UNIQUE` constraint on `user_id` enforces the one-to-one relationship at the database level. There is no application-layer lock needed — a race condition where two requests simultaneously create the same applicants row will result in a `23505` unique violation from PostgreSQL. The service catches that and converts it to a `ConflictError`.

## Skills as JSONB

Skills are stored as a JSON array of strings:

```json
["TypeScript", "Node.js", "PostgreSQL"]
```

The JSONB type stores this efficiently and returns it as a proper JavaScript array when you query it. PostgreSQL deserialises `jsonb` columns automatically; `pg` (the Node.js driver) returns them as parsed JavaScript values — no `JSON.parse()` needed on the read path.

On the write path, pass `JSON.stringify(skills)` to the query parameter because `pg` sends parameters as strings and PostgreSQL needs to know it is receiving valid JSON.

### Why not a separate `skills` table?

A normalised `applicant_skills(applicant_id, skill)` table would be appropriate if you needed to:
- Query "all applicants who know Python"
- Enforce a controlled vocabulary (foreign key to a `skills` reference table)
- Track skill proficiency levels

For the basic profile — where skills are just a list of strings read and written together — JSONB is simpler and fast enough. Chapter 43's full-text search does not search skills individually; if you add skill-based search later, a GIN index on the `skills` column handles it.

## Partial update pattern

`PATCH /api/applicants/profile` accepts any combination of `headline`, `bio`, and `skills`. The repo builds the SET clause dynamically:

```ts
const sets: string[] = [];
const values: unknown[] = [];
let i = 1;

if (fields.headline !== undefined) { sets.push(`headline = $${i++}`); values.push(fields.headline); }
if (fields.bio !== undefined)      { sets.push(`bio = $${i++}`);      values.push(fields.bio); }
if (fields.skills !== undefined)   { sets.push(`skills = $${i++}`);   values.push(JSON.stringify(fields.skills)); }
```

The `$${i++}` pattern keeps parameter numbering correct regardless of which fields are present. If the client sends `{ "skills": ["Go"] }` and nothing else, the query is:

```sql
UPDATE applicants SET skills = $1 WHERE id = $2 RETURNING ...
```

If no fields are present (empty body), `sets.length === 0` and the function returns `null` immediately — no query is issued. The route can treat this as a no-op and return the existing profile.

## Error mapping

| Condition                        | Error class     | HTTP status |
|----------------------------------|-----------------|-------------|
| `POST` when profile already exists | `ConflictError` | 409         |
| `GET` / `PATCH` with no profile  | `NotFoundError` | 404         |

Both error classes come from `src/shared/errors.ts` established in Chapter 17. Your global error handler already maps them to the right status codes.

## Testing the flow manually

```bash
# 1. Register and verify an applicant account (ch20/ch23)
APPLICANT_TOKEN="<access token from login>"

# 2. Create the profile
curl -s -X POST http://localhost:3000/api/applicants/profile \
  -H "Authorization: Bearer $APPLICANT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"headline":"Full-stack engineer","bio":"Five years building web apps.","skills":["TypeScript","PostgreSQL"]}' \
  | jq .

# 3. Read it back
curl -s http://localhost:3000/api/applicants/profile \
  -H "Authorization: Bearer $APPLICANT_TOKEN" | jq .

# 4. Update skills only
curl -s -X PATCH http://localhost:3000/api/applicants/profile \
  -H "Authorization: Bearer $APPLICANT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"skills":["TypeScript","PostgreSQL","Redis"]}' \
  | jq .

# 5. Attempt to create the profile a second time — expect 409
curl -s -X POST http://localhost:3000/api/applicants/profile \
  -H "Authorization: Bearer $APPLICANT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"headline":"Duplicate","bio":"Should fail.","skills":[]}' \
  | jq .
```
