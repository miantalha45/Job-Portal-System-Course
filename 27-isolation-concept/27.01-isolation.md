# Chapter 27 — What multi-tenant isolation means

## The tenant

In this system, a **tenant** is a company. Acme Corp and Bright Labs are two tenants. They share the same database, the same application code, and the same server. Nothing physically separates their data — both companies' job postings, recruiter accounts, and application records live in the same tables.

Sharing infrastructure is the whole point of a multi-tenant system. It keeps operational costs low and simplifies deployment. But it creates a hard requirement: one company's data must be completely invisible to users of any other company. A recruiter at Acme Corp must not be able to see Bright Labs' unpublished job postings, application notes, or recruiter list — and vice versa.

This requirement is called **tenant isolation**, and it is the central data access rule for every company-scoped feature built from Chapter 28 onward.

---

## The isolation rule

Every database query that reads or writes company-scoped data must include a `WHERE company_id = $1` clause (or the JOIN-based equivalent), where the value bound to `$1` comes from the **authenticated recruiter's row in the database** — not from anything the user supplies in the request.

Written as a rule:

> **company_id for any query must come from the verified JWT userId, resolved through the recruiters table — never from a URL parameter or request body.**

The sequence is:

1. `authMiddleware` verifies the JWT and attaches `req.user = { userId, role }`.
2. The route handler calls `getRecruiterCompany(req.user.userId)` — a database lookup that returns `{ companyId, companyRole }` for this user.
3. Every subsequent query that touches company-scoped data uses `companyId` from step 2.

The URL parameter — `/api/companies/:companyId` or `/api/jobs/:id` — is never trusted as a scope boundary. It is used only to identify **which specific record** is being requested, not to determine **which company** the caller belongs to.

---

## Why URL parameters cannot be the scope boundary

Consider a recruiter from Acme Corp (company_id = `aaa`) who knows the UUID of a Bright Labs job posting (job_id = `bbb-job-1`). If the server uses the URL parameter to determine scope:

```
GET /api/jobs/bbb-job-1
```

The handler might query:

```sql
SELECT * FROM jobs WHERE id = $1
-- $1 = 'bbb-job-1'
```

This query has no company-scoping. It returns the Bright Labs job to the Acme Corp recruiter. The JWT was valid; the role was `recruiter`; `requireRole` passed. But the data belongs to a different company. The isolation rule was not enforced.

This is a specific vulnerability called **Insecure Direct Object Reference** (IDOR). The recruiter guessed or discovered a valid object ID and accessed it directly. Chapter 29 covers IDOR in detail and builds the ownership check that prevents it. This chapter establishes the underlying principle: role gates and URL parameters together are not sufficient for isolation.

---

## The correct scope: company_id from the recruiter row

The recruiter's JWT contains `userId`. The `recruiters` table has a row linking that `userId` to a `company_id`. That `company_id` is the ground truth for which company this recruiter belongs to.

The recruiter cannot forge this value. The JWT is signed by the server. The `recruiters` table is written by the server when the recruiter joins a company. The recruiter has no way to change which company_id the server resolves from their userId.

When the server runs:

```sql
SELECT company_id FROM recruiters WHERE user_id = $1
-- $1 comes from req.user.userId (the verified JWT)
```

The returned `company_id` is the only value that may be used to scope company data queries. It is derived entirely from server-controlled data, not from anything the recruiter provided in the request.

---

## The admin exception

Admins are the platform operators. They have a legitimate need to read across company boundaries — moderating content, resolving disputes, auditing data, managing accounts.

This access is **deliberate and explicit**, not accidental. Admin routes do not apply a `WHERE company_id = $1` scope. They are wired with `requireRole('admin')`, which ensures only users with the `admin` role reach them. The absence of a company-scope filter on admin routes is a documented design decision, not a gap.

The admin exception is sanctioned. Cross-company access through any other role is a bug.

---

## Applicant isolation

Applicants are not scoped to a company. An applicant's scope is their own records: their profile, their applications, their documents.

The isolation rule for applicants is: every query that touches applicant-scoped data must include `WHERE applicant_id = $1` where `$1` is resolved from `req.user.userId` through the `applicants` table — not from a URL parameter.

An applicant calling `GET /api/applicants/me/applications` should only ever receive their own applications. A query that returns all applications for a job (without filtering by applicant_id) would expose one applicant's data to another — the same IDOR vulnerability pattern, applied to a different resource type.

---

## What this means for every later chapter

From Chapter 28 onward, every company-scoped query follows the same two-step pattern:

1. Resolve `companyId` from `req.user.userId` via the recruiters table.
2. Include `company_id = companyId` in every query that touches company-scoped data.

This pattern is not optional and is not applied "where it seems relevant." It applies to every read and every write on company-scoped tables. Chapters that build real endpoints will follow this pattern without re-explaining it. This chapter is the explanation those chapters rely on.
