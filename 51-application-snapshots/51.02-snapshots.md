# 51.02 — Snapshots: Design Notes

## The mutability problem

Mutable references are dangerous in document workflows. The `applications` table has a foreign key `applicant_id → applicants`. Without a snapshot, the application effectively "points at" the current state of the applicant profile. When the applicant updates their profile, every application that references that applicant implicitly changes.

This is the same reason legal documents embed a copy of referenced terms rather than pointing to a URL. "See https://example.com/tos" is dangerous if the URL changes. Embedding the terms at signing time creates an immutable record.

---

## JSONB is the right column type for snapshots

Alternatives:

| Approach | Problem |
|----------|---------|
| Foreign key to `applicants` | Shows current profile, not snapshot |
| Separate `application_snapshots` table | Extra join for every read; more schema to maintain |
| Store snapshot as `text` (serialised JSON) | Cannot query into it with `->` operators; no type awareness |
| JSONB column on `applications` | Written once, never updated; queryable; no extra join |

JSONB wins for a snapshot: it is stored with the application row, requires no join to read, and PostgreSQL can index into it if needed. The trade-off is that schema changes to the snapshot shape (adding a new field) only affect future applications; old applications retain the shape they were written with. This is actually a feature — old applications are frozen.

---

## Building the snapshot once per submission

The snapshot is built once at the start of the multi-job submission, before the loop:

```ts
const snapshot = await repo.buildApplicantSnapshot(profile.id);
```

All applications in that submission share the same snapshot. This is correct because:

1. They are submitted at the same moment — the applicant's profile is the same for all of them
2. It avoids N+1 queries (one snapshot query per job instead of one total)
3. It is conceptually cleaner — a submission represents one point in time

---

## The résumé key in the snapshot

The snapshot includes `resumeKey` — the S3 key of the most recently uploaded résumé at submission time. A recruiter can generate a presigned download URL from this key to access the résumé as it was when the applicant applied.

If the applicant later uploads a new résumé, the old applications still reference the old key. The new résumé is only visible in applications submitted after the upload.

If the applicant has never uploaded a résumé, `resumeKey` is `null`. This is valid — not all jobs require a résumé, and some applicants apply without one.

---

## What the snapshot does NOT contain

- Email address — this is PII that does not belong in a snapshot; recruiters who need to contact the applicant use the application workflow
- User ID — the application already has `applicant_id`; the snapshot is about profile content, not identity
- Résumé bytes — the key is a pointer to S3; fetching the actual PDF requires a presigned download URL (generated at read time, not stored)

---

## Schema evolution and old snapshots

If you add a new field to the applicant profile (e.g., `location`) and start including it in future snapshots, old applications will have snapshots without `location`. Readers of the snapshot must handle missing fields gracefully:

```ts
const location = snapshot.location ?? null; // safe default for old snapshots
```

This is standard practice for JSONB-stored documents that evolve over time. Document the snapshot shape and its version history in a comment in the repo or service file.
