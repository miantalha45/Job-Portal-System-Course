# Chapter 51 — Résumé/Profile Snapshots

## What you will build

Capture the applicant's profile at the moment of application submission and store it immutably in `applications.snapshot`. Later profile edits have no effect on submitted applications.

## Learning goals

- Understand why snapshots are necessary for application integrity
- Capture a point-in-time view of mutable data at the moment of a write
- Compose a snapshot from multiple sources (profile + latest résumé)
- Confirm immutability by editing the profile and verifying old applications are unchanged

## Prerequisites

- Chapter 46: applicant profile (`applicants` table and service)
- Chapter 48: résumé metadata in `resumes` table
- Chapter 50: `insertApplication` in place, `snapshot` parameter already accepted

## What the snapshot contains

```ts
type ApplicationSnapshot = {
  headline: string | null;
  bio: string | null;
  skills: string[];
  resumeKey: string | null;   // s3_key of the most recently uploaded résumé at time of apply
};
```

The snapshot is stored in `applications.snapshot` (JSONB). It represents the applicant's profile as it looked when they submitted. A recruiter reading an old application always sees the profile that was presented at submission time.

## Implementation

### applicants.repo.ts — build the snapshot

```ts
export async function buildApplicantSnapshot(applicantId: string): Promise<ApplicationSnapshot> {
  const profileResult = await db.query(
    `SELECT headline, bio, skills FROM applicants WHERE id = $1`,
    [applicantId]
  );
  const profile = profileResult.rows[0];
  if (!profile) throw new NotFoundError('Applicant profile not found');

  const resumeResult = await db.query(
    `SELECT s3_key FROM resumes
     WHERE applicant_id = $1
     ORDER BY uploaded_at DESC
     LIMIT 1`,
    [applicantId]
  );
  const resumeKey = resumeResult.rows[0]?.s3_key ?? null;

  return {
    headline:  profile.headline ?? null,
    bio:       profile.bio ?? null,
    skills:    profile.skills ?? [],
    resumeKey,
  };
}
```

### applicants.service.ts — wire snapshot into applyToJobs

Update `applyToJobs` in `applicants.service.ts`. Replace the `const snapshot = {};` placeholder from Chapter 50 with:

```ts
// Build once for the whole submission — same profile at the same moment
const snapshot = await repo.buildApplicantSnapshot(profile.id);

for (const jobId of body.jobIds) {
  if (alreadyAppliedSet.has(jobId)) {
    skipped.push(jobId);
    continue;
  }
  const answers = body.answers[jobId] ?? [];
  const application = await repo.insertApplication(profile.id, jobId, answers, snapshot);
  if (application) {
    created.push(application.id);
  } else {
    skipped.push(jobId);
  }
}
```

Build the snapshot once before the loop — all applications in a single submission share the same point-in-time snapshot. There is no reason to re-query the profile for each job.

## Verifying immutability

The test sequence is:

1. Apply to a job → application is created with snapshot containing current headline
2. Update the applicant's profile with a new headline
3. Read the application — snapshot still shows the original headline

This is the correctness guarantee. The snapshot JSONB column is written once and never updated by profile edits. Profile updates touch only the `applicants` table, not `applications`.

---

## Why snapshots matter for recruiters

Without a snapshot, a recruiter reading an old application sees the applicant's *current* profile — which may have changed significantly. A recruiter who shortlisted an applicant three months ago based on a "Senior Go Engineer" headline might now see "Junior React Developer" because the applicant updated their profile. The snapshot preserves the context in which the recruiter evaluated the applicant.

This is not a theoretical concern. Job portals that show live profile data frequently confuse recruiters who added notes or moved an applicant through stages based on a profile that has since changed.

---

## Snapshot is not a changelog

The snapshot captures one point in time — the moment of application. It is not a full changelog of profile edits. If you need an audit trail of all profile changes, that requires an event log (a separate table with one row per change). For this application, a single snapshot at submission time is sufficient.
