# Chapter 28 — Prerequisites and framing

## What you need in place

**Chapter 27** — you understand the isolation rule: `company_id` for any company-scoped query must come from the authenticated recruiter's row in the database, never from a URL parameter or request body.

**Chapter 26** — `companiesRouter` is mounted at `/api/companies` with `router.use(authMiddleware, requireRole('recruiter'))`. Any request reaching this router is authenticated and carries `role: 'recruiter'`. `req.user.userId` is always defined inside these handlers.

**Database schema** — the `recruiters` table has the columns `user_id uuid` and `company_id uuid`. The `companies` table has `id uuid`, `name text`, and `status text`. Both tables are seeded with at least one recruiter row linking a user to a company.

Run `npx tsc --noEmit` and confirm zero errors before you begin.

---

## What this chapter builds

Two things:

**`getRecruiterCompany(userId)`** — a repo function in `src/modules/companies/companies.repo.ts`. It accepts a `userId` (from the verified JWT) and returns the recruiter's `company_id` and `company_role` from the database. This function is the bridge between the JWT and the company scope.

**`GET /api/companies/me`** — a real route (replacing the placeholder) that returns the authenticated recruiter's company details. This route demonstrates the full isolation pattern end-to-end: JWT → `getRecruiterCompany` → scoped query → response.

The route uses `companyId` from the recruiter row — not from the URL — to scope the companies query. This is the isolation rule made concrete in running code.
