# 69.02 — Recruiter Digests (Walkthrough)

## What makes this job interesting

The cleanup jobs from Chapter 68 were simple: DELETE rows, log the count, done. The recruiter
digest job has more moving parts:

- It queries data across four tables for every verified company
- It fans out email to potentially many recipients
- The query logic (aggregate counts) lives inside the worker, not inside an HTTP route

This is the pattern for any scheduled report: the worker owns the query logic because there is
no HTTP client to ask for the data.

---

## The aggregate query

The query selects one row per verified company. Each of the three counts is a correlated
subquery that fires once per company row:

```sql
(
  SELECT count(*)::int
  FROM jobs j
  WHERE j.company_id = c.id AND j.status = 'open'
) AS "openJobsCount"
```

The `::int` cast converts PostgreSQL's `bigint` (from `count(*)`) to a regular integer. Without
the cast, `pg` returns the count as a string in older driver versions.

The interviews-this-week count uses `date_trunc('week', NOW())` which returns the Monday of
the current week at 00:00 UTC. Adding 7 days gives the following Monday. This reliably captures
interviews scheduled Monday through Sunday of the current week, regardless of what day the job
runs.

## Building it step by step

### Step 1 — Create sendRecruiterDigest.ts

Separate the query logic into `fetchCompanyDigests()` and the fan-out into `sendRecruiterDigest()`.
This separation makes the handler testable: you can test `fetchCompanyDigests` independently
of the email sending.

### Step 2 — Add sendRecruiterDigestEmail to mailer.ts

Keep the email template minimal. The course is not about HTML emails — a plain-text summary
with clear labels is enough.

### Step 3 — Register the repeatable job

In `registerRepeatableJobs` in `worker.ts`:

```ts
await schedulerQueue.add(
  'send-recruiter-digest',
  {},
  { repeat: { pattern: '0 8 * * 1' } }
);
```

Cron breakdown: `0 8 * * 1` = minute 0, hour 8, any day of month, any month, day-of-week 1
(Monday). All times are UTC.

### Step 4 — Add the case to the worker switch

```ts
case 'send-recruiter-digest': {
  await sendRecruiterDigest();
  break;
}
```

### Step 5 — Manual test (no waiting for Monday)

```bash

(async () => {
  await queue.add('send-recruiter-digest', {});

```

## What happens if the SMTP call fails for one company?

The `for` loop calls `sendRecruiterDigestEmail` sequentially. If it throws for company 3
(out of 5), the loop stops at company 3 and the job fails. BullMQ retries the whole job.
On retry, companies 1 and 2 receive duplicate emails, companies 3, 4, 5 get their first email.

For a production system, consider:
- Per-company error handling: catch errors inside the loop, log them, continue to the next company
- Tracking which companies have already received the digest: store a `digest_sent_at` timestamp
  on the company row and skip companies where `digest_sent_at >= start_of_current_week`

The course implementation uses the simpler all-or-nothing approach.

## Sequential vs parallel fan-out

Current implementation (sequential):
```ts
for (const digest of digests) {
  await sendRecruiterDigestEmail(...);   // one at a time
}
```

Parallel alternative (faster, more SMTP load):
```ts
await Promise.all(digests.map(d => sendRecruiterDigestEmail(...)));
```

With 100 companies and 150ms per email: sequential takes 15 seconds, parallel takes ~150ms.
For a weekly batch job, 15 seconds is fine. Switch to parallel if the window is tight.
