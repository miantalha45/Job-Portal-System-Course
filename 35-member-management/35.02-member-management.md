# Member Management

## Three endpoints, three permission levels

| Endpoint | Who can call it |
|---|---|
| `GET /api/companies/members` | owner, hr_manager |
| `PATCH /api/companies/members/:recruiterId` | owner only |
| `DELETE /api/companies/members/:recruiterId` | owner, hr_manager |

All three are under the `companies.routes.ts` router, which already applies `authMiddleware` and `requireRole('recruiter')`.

---

## Listing members

```bash
GET /api/companies/members
Authorization: Bearer <owner-or-hr-manager-token>
```

Response:

```json
{
  "members": [
    {
      "recruiterId": "<uuid>",
      "userId": "<uuid>",
      "email": "owner@example.com",
      "companyRole": "owner",
      "joinedAt": "2026-06-01T10:00:00.000Z"
    },
    {
      "recruiterId": "<uuid>",
      "userId": "<uuid>",
      "email": "hr@example.com",
      "companyRole": "hr_manager",
      "joinedAt": "2026-06-02T09:00:00.000Z"
    }
  ]
}
```

Results are ordered by `created_at ASC` — oldest (first to join) at the top. This is a full list, not paginated. Member lists in a single company workspace are unlikely to grow large enough to require pagination.

A plain recruiter calling this endpoint receives `403`. A hiring manager receives `403`.

---

## Changing a member's role

Only the owner can change roles. An HR manager cannot.

```bash
PATCH /api/companies/members/<recruiter-id>
Authorization: Bearer <owner-token>
Content-Type: application/json

{ "role": "recruiter" }
```

Response (200):

```json
{ "message": "Role updated." }
```

**Cases that return errors:**

- Role changed to `'owner'` → `422` (Zod rejects the value — `'owner'` is not in the enum)
- Target is the caller themselves → `403` ("You cannot change your own role.")
- Target's current role is `'owner'` → `403` ("The owner role cannot be changed via this endpoint.")
- Recruiter ID not in this company → `404`

The restriction on changing the owner role protects against an accidental escalation path. There is exactly one owner per company and ownership transfer is not a feature in this build.

## Removing a member

```bash
DELETE /api/companies/members/<recruiter-id>
Authorization: Bearer <owner-or-hr-manager-token>
```

Response: `204 No Content`

**Cases that return errors:**

- Target is the caller themselves → `403` ("You cannot remove yourself from the company.")
- Recruiter ID not in this company → `404`
- Caller is a plain recruiter or hiring_manager → `403`

When a member is removed, their `recruiters` row is deleted. Their `users` row is untouched — they can still log in, but `getRecruiterCompany(userId)` returns `null` and they cannot access any company-scoped routes until they are invited again.

---

## Cross-company isolation

`getMemberById(recruiterId, companyId)` queries:

```sql
SELECT user_id, company_role
FROM recruiters
WHERE id = $1 AND company_id = $2
```

The `company_id` parameter comes from `getRecruiterCompany(userId)` — from the caller's own recruiter row, not from the URL. An owner who supplies a recruiter ID from a different company gets a `404` response, not a `403`. There is no confirmation that the recruiter ID exists at all.

---

## What happens to a removed member's data

The `recruiters` row is deleted. Any `jobs` or `applications` rows the member was associated with are not deleted or reassigned in this build. Jobs have `company_id`, not `recruiter_id`, so the company retains its jobs after a member is removed. Application records similarly belong to the job, not the individual who managed them.

If you need to track which recruiter posted a job, add a `posted_by` column to the `jobs` table. That is outside this chapter's scope.
