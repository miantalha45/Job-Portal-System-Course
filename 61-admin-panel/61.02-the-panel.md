# 61.02 — The Admin Panel (Walkthrough)

## Why a separate route group instead of a separate app?

The admin panel shares the same Next.js project as the applicant panel (Chapter 54) and the
company panel (Chapter 38). A route group `app/admin/` achieves logical separation without
running another process or maintaining another deployment. The layout guard (`role !== 'admin'
→ redirect`) means non-admin users never see admin UI even if they guess the URL.

## Data flow

```

   |                        |                         |                    |
   |-- GET /admin/companies--|                         |                    |
   |                        |-- fetch /api/admin/companies                 |
   |                        |  (Bearer token from cookie)                  |
   |                        |                  |-- SELECT companies JOIN users
   |                        |                  |<-- rows                   |
   |                        |<-- JSON ----------|                    |
   |                        | render <table>    |                    |

   |                        |                   |                    |
   |-- POST (form) -------->|                   |                    |
   |  (Server Action)       |-- fetch PATCH /api/admin/companies/:id/verify
   |                        |                  |-- UPDATE companies        |
   |                        |                  |<-- updated row            |
   |                        | revalidatePath    |                    |
   |<-- redirect / refresh--|                   |                    |
```

## Building the layout guard

The layout runs on every request to `/admin/*`. It does two things:

1. Checks for the session cookie — redirects to `/login` if absent
2. Calls `GET /api/auth/me` to verify the token and get the user's role — redirects to `/`
   if the role is not `admin`

```tsx
const res = await fetch(`${process.env.NEXT_PUBLIC_API_URL}/api/auth/me`, {
  headers: { Authorization: `Bearer ${token}` },
  cache: 'no-store',
});
if (!res.ok) redirect('/login');
const { user } = await res.json();
if (user.role !== 'admin') redirect('/');
```

`cache: 'no-store'` ensures every request checks the token freshly — it must not use a cached
response from a previous user's session.

## Server Actions vs fetch in a useEffect

In a Server Action, the code runs on the server. The mutation happens inside `actions.ts` and
the browser never sees the admin JWT — it only submits a form. This is safer than:

- Client-side fetch: the JWT would be in browser memory (accessible to XSS)
- API routes: an extra round-trip and extra file to maintain

The trade-off: Server Actions require a full page re-render after mutation. For a low-traffic
admin panel this is acceptable. For high-frequency dashboards, you would move to client-side
fetch with SWR or React Query.

## The disabled button pattern

Each action button is disabled when the action would have no effect:

```tsx
<button type="submit" disabled={c.status === 'verified'}>Verify</button>
```

This is a UI convenience only — it does not prevent a direct API call. The 409 conflict check
in the service layer is the real guard.

---

## Building the users page

Follow the companies pattern exactly. The only difference is the actions call `.../suspend`
and `.../activate` instead of `.../verify` and `.../suspend`. Use separate `<form>` elements
for each action, one per row.

```tsx
<form action={suspendUser}>
  <input type="hidden" name="id" value={u.id} />
  <button type="submit" disabled={u.status === 'suspended'}>Suspend</button>
</form>
<form action={activateUser}>
  <input type="hidden" name="id" value={u.id} />
  <button type="submit" disabled={u.status === 'active'}>Activate</button>
</form>
```

## Status filter links

Filter links are plain `<a>` tags that append `?status=` to the URL. Next.js re-renders the
Server Component with the new `searchParams`. No client-side state or JavaScript needed.

```tsx
<a href="/admin/companies?status=pending">Pending</a>
```

---

## Minimal HTML is intentional

The guidelines say: "No fancy UI required — semantic HTML table is enough." The purpose of this
chapter is to show how the admin data flows from API to UI, not to teach CSS. A `<table>` with
`<thead>` and `<tbody>` is readable and accessible without any framework.

---

## No `process.env` in Express modules

The Next.js pages read `NEXT_PUBLIC_API_URL` for the API base URL. This is a Next.js build-time
configuration value, not an application secret. It is appropriate to read it in Next.js files.
The Express API modules (`src/modules/`, `src/shared/`) never read any `process.env` key except
through `config.ts`.
