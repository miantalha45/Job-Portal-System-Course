# Build: Ownership checks and IDOR prevention

## What IDOR looks like without a check

A recruiter at Company A (token resolves to `company_id = 'cA'`) calls:

```
GET /api/jobs/job-xyz
Authorization: Bearer <company-A-recruiter-token>
```

If the handler queries:

```sql
SELECT id, title, company_id FROM jobs WHERE id = $1
-- $1 = 'job-xyz'
```

And `job-xyz` belongs to Company B (`company_id = 'cB'`), the query succeeds and returns Company B's job data to Company A's recruiter. The role gate passed. The resource was found. But the caller does not own it.

This is Insecure Direct Object Reference (IDOR). The attacker uses a direct object identifier (the job UUID) in the URL to access a resource they should not see.

## `src/modules/jobs/jobs.repo.ts`

```ts
import { db } from '../../shared/db';
import { NotFoundError } from '../../shared/errors';

/**
 * Asserts that the job identified by jobId belongs to companyId.
 *
 * Throws NotFoundError if:
 *   - No job row exists with that id.
 *   - The job's company_id does not match companyId.
 *
 * Both failure cases return 404, not 403. Returning 404 avoids
 * confirming to the caller that the resource exists — an attacker
 * probing UUIDs learns nothing from the response.
 *
 * companyId must come from getRecruiterCompany(req.user.userId),
 * never from the URL or request body.
 */
export async function assertJobOwnership(
  jobId: string,
  companyId: string,
): Promise<void> {
  const result = await db.query<{ id: string; company_id: string }>(
    `SELECT id, company_id FROM jobs WHERE id = $1`,
    [jobId],
  );

  if (result.rows.length === 0 || result.rows[0].company_id !== companyId) {
    throw new NotFoundError('Job not found');
  }
}
```

### Why 404, not 403

When an ownership check fails, the server has two honest options:

- **404 Not Found** — the server does not confirm whether the resource exists. An attacker probing UUIDs gets the same response whether the job does not exist at all or exists but belongs to another company. No information is leaked.
- **403 Forbidden** — the server confirms the resource exists but denies access. An attacker can enumerate valid UUIDs by looking for 403 responses, then try other techniques to access them.

For cross-company ownership checks, **404 is recommended**. The resource is genuinely "not found" from the perspective of the caller — it is not in their company's data. This is not a lie; it is accurate framing of the access boundary.

Use 403 for within-role permission checks where resource existence is not sensitive — for example, a recruiter trying to perform an admin action on their own company's data. In that case, confirming the resource exists and denying the action is appropriate.

## `src/modules/jobs/jobs.routes.ts`

```ts
import { Router } from 'express';
import { authMiddleware } from '../../shared/auth-middleware';
import { requireRole } from '../../shared/require-role';
import { getRecruiterCompany } from '../companies/companies.repo';
import { assertJobOwnership } from './jobs.repo';
import { NotFoundError } from '../../shared/errors';

const router = Router();

router.use(authMiddleware, requireRole('recruiter'));

/**
 * GET /api/jobs/:id
 *
 * Returns a job posting owned by the authenticated recruiter's company.
 * Steps:
 *  1. Resolve companyId from the verified JWT (via recruiters table).
 *  2. Assert the job belongs to that company.
 *  3. Return the job data.
 *
 * A recruiter from a different company receives 404 — not 403.
 * The response does not confirm the job exists at all.
 */
router.get('/:id', async (req, res, next) => {
  try {
    const recruiter = await getRecruiterCompany(req.user!.userId);

    if (!recruiter) {
      return next(new NotFoundError('No company associated with this account'));
    }

    await assertJobOwnership(req.params.id, recruiter.companyId);

    // assertJobOwnership throws if ownership fails.
    // Reaching this point means the job exists and belongs to this company.
    // A full implementation would fetch complete job details here.
    res.json({ jobId: req.params.id, companyId: recruiter.companyId });
  } catch (err) {
    next(err);
  }
});

export { router as jobsRouter };
```

Wire `jobsRouter` in `src/app.ts`:

```ts
import { jobsRouter } from './modules/jobs/jobs.routes';

// ... after the existing mounts ...
app.use('/api/jobs', jobsRouter);
```

## `src/modules/applicants/applicants.repo.ts`

The IDOR pattern applies to applicants too. An applicant should not access another applicant's profile or applications. The ownership check for applicants verifies `user_id` (from the JWT) against the applicant record.

```ts
import { db } from '../../shared/db';
import { NotFoundError } from '../../shared/errors';

/**
 * Asserts that the applicant record identified by applicantId belongs
 * to the user identified by userId (from req.user.userId).
 *
 * Throws NotFoundError if:
 *   - No applicant row exists with that id.
 *   - The applicant's user_id does not match userId.
 *
 * Returns 404 in both cases to avoid confirming the record's existence.
 */
export async function assertApplicantOwnership(
  applicantId: string,
  userId: string,
): Promise<void> {
  const result = await db.query<{ id: string; user_id: string }>(
    `SELECT id, user_id FROM applicants WHERE id = $1`,
    [applicantId],
  );

  if (result.rows.length === 0 || result.rows[0].user_id !== userId) {
    throw new NotFoundError('Applicant not found');
  }
}
```

The pattern is identical to `assertJobOwnership`:

- Fetch the row by primary key.
- Compare the ownership field (`user_id`) to the value from the verified JWT.
- Throw `NotFoundError` if either condition fails.
- The caller receives 404 regardless of whether the record exists.

---

## The ownership check pattern, generalized

Every resource that belongs to a specific owner follows this structure:

```
1. Fetch the resource by primary key (id from the URL).
2. Compare resource.owner_field to the value resolved from the JWT.
3. If mismatch: throw NotFoundError.
4. If match: proceed to the handler logic.
```

For company-scoped resources: `resource.company_id === recruiter.companyId`
For user-scoped resources: `resource.user_id === req.user.userId`

The key constraint: the right-hand side of the comparison **always** comes from the JWT (directly, or via a database lookup seeded by the JWT). Never from the URL or request body.
