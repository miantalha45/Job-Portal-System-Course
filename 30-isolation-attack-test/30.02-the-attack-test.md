# Build: The attack test and the admin exception

## The isolation rule (stated for the record)

The following rule governs every company-scoped query in this system. Place this comment in `src/modules/companies/companies.repo.ts` and `src/modules/jobs/jobs.repo.ts` as a permanent record:

```ts
// ISOLATION RULE: Every company-scoped query must include company_id from
// the authenticated recruiter row (resolved via getRecruiterCompany), never
// from a URL parameter or request body. The recruiter cannot control which
// company_id is used to scope their queries.
```

This comment is not documentation for its own sake. It is the stated constraint that reviewers and future developers can check new queries against.

---

## Setting up the attack test

You need two companies, each with a recruiter and at least one job. Confirm the setup with psql:

```bash
psql $DATABASE_URL -c "
  SELECT
    c.name AS company_name,
    u.email AS recruiter_email,
    j.id AS job_id,
    j.title
  FROM companies c
  JOIN recruiters r ON r.company_id = c.id
  JOIN users u ON u.id = r.user_id
  JOIN jobs j ON j.company_id = c.id
  ORDER BY c.name, j.title
  LIMIT 20;
"
```

From the output, identify:
- **Company A**: recruiter email, and one job UUID owned by Company A.
- **Company B**: one job UUID owned by Company B (you do not need to log in as Company B's recruiter).

Set shell variables for the test sequence:

```bash
COMPANY_A_RECRUITER_EMAIL="recruiter-a@example.com"
COMPANY_A_RECRUITER_PASSWORD="yourpassword"
COMPANY_A_JOB_ID="<uuid-of-a-job-owned-by-company-a>"
COMPANY_B_JOB_ID="<uuid-of-a-job-owned-by-company-b>"
ADMIN_EMAIL="admin@example.com"
ADMIN_PASSWORD="yourpassword"
```

```bash
RECRUITER_A_TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
```

```bash

  http://localhost:3000/api/jobs/$COMPANY_A_JOB_ID
```

Expected: `200` with a JSON body containing the job details.

```bash
curl -s -o /dev/null -w "%{http_code}" \
  -H "Authorization: Bearer $RECRUITER_A_TOKEN" \
  http://localhost:3000/api/jobs/$COMPANY_A_JOB_ID
```

Expected output: `200`

This is the baseline. Company A's recruiter can access their own data.

## Step 3 — The attack: Company A recruiter tries to access Company B's job

```bash
curl -s \
  -H "Authorization: Bearer $RECRUITER_A_TOKEN" \
  http://localhost:3000/api/jobs/$COMPANY_B_JOB_ID
```

Expected response body:

```json
{
  "error": "Job not found"
}
```

Expected status code:

```bash
curl -s -o /dev/null -w "%{http_code}" \
  -H "Authorization: Bearer $RECRUITER_A_TOKEN" \
  http://localhost:3000/api/jobs/$COMPANY_B_JOB_ID
```

Expected output: `404`

**If you see `200` here, isolation is broken.** The ownership check in `assertJobOwnership` is not running or is not comparing the correct values. Debug by adding a console.log inside `assertJobOwnership` to confirm what `company_id` is being compared.

**If you see `403` here, the role check is working but the ownership check returned the wrong status code.** Review `assertJobOwnership` — it should throw `NotFoundError`, not `ForbiddenError`.

**`404` is the correct response.** The isolation holds. Company A's recruiter cannot distinguish "this job does not exist" from "this job exists but belongs to another company."

---

## What the attack test proves

The attack test proves that the following defense chain is complete and in the correct order:

```
Request: GET /api/jobs/<company-B-job-id>
Token:   Company A recruiter JWT

1. authMiddleware         → PASSES (token is valid)
2. requireRole('recruiter') → PASSES (role matches)
3. getRecruiterCompany    → returns { companyId: 'company-A-id', ... }
4. assertJobOwnership     → job.company_id is 'company-B-id'
                           → 'company-B-id' !== 'company-A-id'
                           → throws NotFoundError
5. errorHandler           → 404 response

Handler never runs.
```

Steps 1 and 2 alone are not sufficient for isolation. A valid recruiter token passes both. Only step 4 — the ownership check against the company_id from the recruiter's database row — enforces the isolation boundary.

## Step 4 — The admin exception: admin accesses Company B's job

Log in as admin:

```bash
ADMIN_TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
  -H "Content-Type: application/json" \
  -d "{\"email\":\"$ADMIN_EMAIL\",\"password\":\"$ADMIN_PASSWORD\"}" \
  | jq -r '.accessToken')
```

Call the admin route for the same Company B job:

```bash
curl -s \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  http://localhost:3000/api/admin/jobs/$COMPANY_B_JOB_ID
```

Expected: `200` with Company B's job data.

```bash
curl -s -o /dev/null -w "%{http_code}" \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  http://localhost:3000/api/admin/jobs/$COMPANY_B_JOB_ID
```

Expected output: `200`

---

## What the admin test proves

The admin route query has no `WHERE company_id` clause. The admin receives Company B's job data. This is correct behavior — it is the sanctioned exception.

The isolation boundary is enforced by the route itself: `GET /api/admin/jobs/:id` is behind `router.use(authMiddleware, requireRole('admin'))`. A recruiter cannot call this route. The chain is:

```
Request: GET /api/admin/jobs/<company-B-job-id>
Token:   Admin JWT

1. authMiddleware         → PASSES (token is valid)
2. requireRole('admin')   → PASSES (role is 'admin')
3. Query: SELECT ... FROM jobs WHERE id = $1
          No company_id filter.
4. Returns Company B's job data.
```

A recruiter token hitting this same route fails at step 2 — `requireRole('admin')` rejects them with 403. The admin's cross-company access is gated by the role check; the absence of a company filter is deliberate on the admin routes only.

## Step 5 — Confirm the recruiter cannot reach the admin route

```bash
curl -s -o /dev/null -w "%{http_code}" \
  -H "Authorization: Bearer $RECRUITER_A_TOKEN" \
  http://localhost:3000/api/admin/jobs/$COMPANY_B_JOB_ID
```

Expected: `403` — the recruiter is rejected at the role gate before the unscoped query runs.

This confirms the two access paths are correctly isolated:

| Route | Token | Outcome |
|---|---|---|
| `GET /api/jobs/:id` | Company A recruiter | 200 for own job, 404 for other company |
| `GET /api/jobs/:id` | Admin | 403 (admin not a recruiter) |
| `GET /api/admin/jobs/:id` | Admin | 200 for any job |
| `GET /api/admin/jobs/:id` | Recruiter | 403 |

## Updated `src/modules/admin/admin.routes.ts`

```ts
import { Router } from 'express';
import { authMiddleware } from '../../shared/auth-middleware';
import { requireRole } from '../../shared/require-role';
import { NotFoundError } from '../../shared/errors';
import { db } from '../../shared/db';

const router = Router();

// Every route on this router requires a valid token with role 'admin'.
router.use(authMiddleware, requireRole('admin'));

// ADMIN EXCEPTION: Admin routes do not scope by company_id.
// Admins have sanctioned cross-company access. The isolation boundary
// here is enforced by requireRole('admin'), not by a company_id filter.
router.get('/jobs/:id', async (req, res, next) => {
  try {
    const result = await db.query<{
      id: string;
      title: string;
      company_id: string;
      status: string;
    }>(
      `SELECT id, title, company_id, status FROM jobs WHERE id = $1`,
      [req.params.id],
    );

    if (result.rows.length === 0) {
      return next(new NotFoundError('Job not found'));
    }

    res.json(result.rows[0]);
  } catch (err) {
    next(err);
  }
});

export { router as adminRouter };
```
