# Chapter 18.02 — The Threat Model

A threat model is a bounded answer to: what are we protecting, from whom, and with what controls? Defining scope matters because trying to defend against everything leads to a system that defends against nothing well. This chapter covers the threats in scope for the job portal's auth layer. It names what is out of scope, so the boundary is explicit.

---

## What the System Is Protecting

### Credentials at rest

The `users` table stores `password_hash`, not `password`. The hash is computed with bcrypt before the row is inserted — that implementation lands in Chapter 19. What matters now: if the database is dumped (by SQL injection, a misconfigured backup, or a compromised database credential), the attacker gets hashes, not passwords. The cost of reversing those hashes is what buys time and limits exposure.

### Sessions in transit and at rest

HTTPS is assumed throughout this system. In production, all traffic between client and server is encrypted in transit, so a network-level eavesdropper cannot read a token from a request header. This chapter takes HTTPS as a given and does not treat in-transit interception as a primary attack surface.

At rest, the session mechanism that matters is the refresh token. Refresh tokens are stored as SHA-256 hashes in the database — not as plaintext and not as the raw token. The implementation lands in Chapter 22. The reason: if the database is dumped, the attacker gets hashes. They cannot use a hash to call the refresh endpoint; they need the original token value, which only exists on the client. SHA-256 is used rather than bcrypt here because refresh tokens are high-entropy random values — an attacker cannot feasibly brute-force a 256-bit random string regardless of hash speed, so bcrypt's deliberate slowness (which exists to resist guessing of low-entropy passwords) buys nothing.

### Per-resource authorization

Authentication answers: is this a real, valid user? Authorization answers: is this user allowed to touch this specific resource?

A recruiter with a valid token should not be able to read another company's applications. An applicant with a valid token should not be able to read another applicant's CV. These controls live in route-level middleware and service-layer checks, covered in Chapters 26–30. This chapter establishes the distinction; it does not implement the checks.

---

## What Is Out of Scope for This Chapter

**SQL injection prevention.** Parameterized queries in the database layer handle this. It is a real threat, but it belongs to the data access layer, not the auth layer.

**DDoS.** Rate limiting at the infrastructure level (load balancer, reverse proxy) is the right tool. The application layer cannot absorb a volumetric attack.

**XSS and CSRF.** These are front-end security concerns that depend on how the React/Next.js client stores and transmits tokens. They are real, but they are not part of the server-side auth design this system builds first.

**Advanced persistent threats and nation-state attackers.** The job portal is not a hardened government system. Designing for that threat class would produce a system too complex to teach and too expensive to run.

## Three Attack Scenarios

### 1. Credential Stuffing

Credential stuffing is an automated attack that replays email/password pairs stolen from one service against a different service, exploiting the fact that many users reuse passwords.

**What the attack looks like.**
A threat actor downloads a breach database from an unrelated service — a password manager, an e-commerce site, a project tool. That database contains email/password pairs in plaintext (because the breached service stored passwords poorly). The attacker writes a script that sends login requests to the job portal using those pairs. For every user who reused their password, the script gets a valid session.

This is not a brute-force attack against unknown passwords. It is an authentication attack using correct credentials obtained elsewhere.

**What defense exists in this system.**
Short-lived access tokens bound the damage window automatically: a stolen session token is usable for at most 15 minutes without the refresh token. Once the compromise is detected, an admin suspends the account and revokes the refresh token (deletes the row); after the current access token expires, the attacker cannot obtain a new one. The access token itself is stateless — it cannot be revoked before expiry — so suspension takes effect only when the access token expires and the attacker tries to refresh.

Rate limiting on the login endpoint — one login attempt per IP per second, with exponential backoff — slows down the automated script. It does not stop a determined attacker with a large IP pool, but it raises the cost.

The root vulnerability (password reuse) cannot be eliminated by the server. It can be surfaced to users via guidance, but it cannot be enforced.

### 2. Token Theft

**What the attack looks like.**
A recruiter's laptop is compromised — malware, a rogue browser extension, or physical access. The attacker reads the access token from browser storage. The token is a signed JWT: it contains the user's `userId`, `role`, and `exp`. The attacker copies the token and makes API calls from a different machine, impersonating the recruiter until the token expires.

Note: the attacker does not need the password here. They have the token directly. The JWT payload contains `sub` (the user's UUID), `role`, and `exp` — enough to pass auth middleware on every protected route.

**What defense exists in this system.**
The access token is short-lived (15 minutes). After expiry, the attacker cannot generate a new access token without the refresh token, which is a separate, harder-to-extract secret. If the attacker does not have the refresh token, the window of impersonation is bounded by the 15-minute lifetime.

If the attacker does have the refresh token, they can generate new access tokens indefinitely — until the refresh token is revoked. Revocation requires deleting the refresh token row from the database. Forced logout from an admin panel or a user-initiated "sign out of all devices" action achieves this.

The access token itself cannot be revoked before expiry. That is a deliberate trade-off, not a bug. Stateless verification (no DB lookup) is what makes access token verification fast at scale.

### 3. IDOR — Insecure Direct Object Reference

**What the attack looks like.**
An applicant has a valid session token. They applied for a job at Company A. Their application has the ID `application_id = 1042`. They notice that the URL for their application detail page is `/applications/1042`. They change it to `/applications/1043`. If the server returns that application — which belongs to a different applicant — the attacker now has access to a stranger's CV, contact information, and application history.

The attacker is fully authenticated. The token is valid. The problem is that the server did not check whether the authenticated user owns the resource they are requesting.

**What defense exists in this system.**
Route handlers must verify ownership, not just authentication. For the application detail endpoint, the correct check is: `SELECT * FROM applications WHERE application_id = $1 AND applicant_id = $2` — where `$2` is the `sub` (UUID) extracted from the verified JWT. If the row does not exist, return a 404. Returning 403 would confirm the resource exists; returning 404 reveals nothing about whether the resource belongs to someone else. The tradeoff: 404 makes debugging harder for legitimate API consumers who typo a URL — they receive the same response as an authorization failure. Log the real reason server-side regardless. This pattern is implemented in Chapters 26–30.

IDOR is the most common authorization failure in web applications. A valid token is not a permission to access any resource — it is permission to access resources the token's owner is authorized to see.
