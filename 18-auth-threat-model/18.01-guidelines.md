# Chapter 18 — Auth & the Threat Model: Guidelines

## Prerequisites

Before starting this chapter you should have the following in place:

**From Chapter 8 — the users table schema.** The `users` table has columns `email`, `password_hash`, `role` (`'admin' | 'recruiter' | 'applicant'`), and `status` (`'active' | 'inactive' | 'suspended'`). There is no `password` column. The absence of a plaintext password column is not an accident — it is a constraint enforced at the schema level. Chapter 18 explains why that constraint matters.

**From Chapter 17 — the error class hierarchy.** You have `UnauthorizedError` (401), `ForbiddenError` (403), `NotFoundError` (404), and `ConflictError` (409). These are not just convenience wrappers. The distinction between 401 and 403 maps directly to the authentication / authorization distinction this chapter introduces. An unauthenticated request gets a 401. An authenticated request that lacks permission gets a 403. Understanding the threat model makes that distinction meaningful rather than arbitrary.

## Rethink Impact Prompt

Work through this scenario before reading the rest of the chapter.

A recruiter named Sarah uses the job portal to manage her company's open roles. She has posted 14 job listings, received 340 applications, and has access to the personal information of every applicant who applied — names, email addresses, uploaded CVs.

Sarah reused a password. The same email/password combination she uses on the job portal was also registered on a project-management tool that suffered a data breach six months ago. That breach database is now being sold on a darknet forum. An attacker purchases it, runs the email/password pairs against the job portal login endpoint, and gets in.

**Walk through what the attacker can do from the moment they have valid credentials.**

They have Sarah's role: `recruiter`. They have her company ID bound to her account. Through the normal recruiter UI — or directly via API calls — they can:

- Read the full application list for every job posted under Sarah's company, including applicant names, email addresses, phone numbers, and CV files stored in S3.
- Download all 340 CVs.
- Change the status of applications — rejecting applicants, or marking them as hired — without any further verification.
- Post new job listings under Sarah's company, potentially fraudulent ones.
- Modify or delete existing job listings.
- Read Sarah's account details, which may include her real name and contact information.

**What stops the damage from spreading?**

Role boundaries. The attacker has a `recruiter` token. They cannot access admin-only routes. They cannot read other companies' data — assuming per-resource authorization is implemented correctly (covered in chapters 26–30). They cannot access applicant accounts. The blast radius is scoped to Sarah's company and the data that flows through it.

Token expiry provides a secondary time boundary. If the system uses short-lived access tokens (15 minutes), a token stolen from client storage stops working when it expires. But this does not help here — the attacker has the password and can generate a fresh token at any time.

**What does NOT stop the damage?**

Password reuse is invisible to the job portal. The system has no way to know that Sarah's password exists in a breach database for an unrelated service. Even well-hashed passwords at rest offer no protection once the attacker has the original plaintext from another breach.

HTTPS does not help here. The attacker is not intercepting a session — they are logging in legitimately.

Rate limiting on the login endpoint slows down a credential-stuffing script against the full list of users — but it cannot prevent the individual successful attempt. It raises the cost and reduces the yield; it does not eliminate the attack.

No single technical control fully closes this gap. The chapter that follows explains which controls limit the damage and which category of problem (credential hygiene) falls outside what the system can enforce on behalf of its users.
