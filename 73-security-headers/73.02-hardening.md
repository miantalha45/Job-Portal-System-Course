# 73.02 — Security Headers & Hardening (Walkthrough)

## Why security headers matter

When a browser receives an HTTP response, it makes decisions based on the headers:
- Should I allow this page to be embedded in an iframe? (`X-Frame-Options`)
- Should I trust the content type declared by the server? (`X-Content-Type-Options`)
- Should I enforce HTTPS next time? (`Strict-Transport-Security`)

Without security headers, browsers use permissive defaults that attackers can exploit.
Helmet sets all the recommended headers in one call, based on OWASP recommendations.

## Building it step by step

### Step 1 — Install packages

```bash
npm install helmet cors
npm install -D @types/cors
```

### Step 2 — Add FRONTEND_URL to config.ts

```ts
FRONTEND_URL: process.env.FRONTEND_URL ?? 'http://localhost:3001',
```

### Step 3 — Apply in app.ts

Order is important. Security headers and CORS must come before routes:

```ts
app.disable('x-powered-by');

app.use(helmet());

app.use(cors({
  origin: config.FRONTEND_URL,
  credentials: true,
}));

app.use(requestIdMiddleware);
app.use(httpLogger);
app.use(globalLimiter);
app.use(healthRouter);
// ... routes
```

### Step 4 — Verify headers with curl

```bash
curl -I http://localhost:3000/health
```

Expected headers (partial):
```
X-Content-Type-Options: nosniff
X-Frame-Options: SAMEORIGIN
X-DNS-Prefetch-Control: off
Strict-Transport-Security: max-age=15552000; includeSubDomains
Referrer-Policy: no-referrer
```

Expected absent headers:
```
X-Powered-By: Express   ← should NOT be present
```

### Step 5 — Test CORS

```bash
# Allowed origin
curl -H "Origin: http://localhost:3001" \
  -H "Access-Control-Request-Method: GET" \
  -X OPTIONS http://localhost:3000/api/jobs -I
# Expected: Access-Control-Allow-Origin: http://localhost:3001

# Blocked origin
curl -H "Origin: http://evil.com" \
  -H "Access-Control-Request-Method: GET" \
  -X OPTIONS http://localhost:3000/api/jobs -I
# Expected: no Access-Control-Allow-Origin header (CORS blocked)
```

### Step 6 — SQL injection test

```bash
curl -s "http://localhost:3000/api/jobs?status=open' OR '1'='1" | jq '.jobs | length'
# Expected: 0 (the literal string matches no job status)

curl -s "http://localhost:3000/api/jobs?status=open" | jq '.jobs | length'
# Expected: N (the correct number of open jobs)
```

The difference in result count confirms parameterized queries work correctly.

## Content-Security-Policy and the frontend

Helmet's default CSP blocks inline scripts and styles. This can break the Next.js frontend
if it inlines scripts. For Next.js development, you may need to relax CSP:

```ts
app.use(helmet({
  contentSecurityPolicy: {
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'", "'unsafe-inline'"],   // Next.js needs this in dev
    },
  },
}));
```

For production, use nonces instead of `'unsafe-inline'`. This is beyond the course scope.

## The defence-in-depth picture

After this chapter, the system has multiple overlapping defences:

```
Attack: SQL injection
  Defence: parameterized queries (Chapter 28) → parameterized since the first query

Attack: XSS (stored cross-site scripting)
  Defence: Content-Security-Policy (Chapter 73) → restricts script sources
  Defence: X-Content-Type-Options (Chapter 73) → prevents MIME confusion

Attack: Clickjacking
  Defence: X-Frame-Options (Chapter 73) → prevents iframe embedding

Attack: CSRF (cross-site request forgery)
  Defence: CORS (Chapter 73) → restricts cross-origin requests from browsers
  Defence: httpOnly JWT cookie → not accessible to scripts (Chapter 38)

Attack: Mass assignment
  Defence: Zod schema allow-listing (Chapter 16) → only known fields pass through

Attack: Brute force
  Defence: Rate limiting (Chapter 70) → limits login attempts per IP

Attack: Token theft
  Defence: Short-lived access tokens + refresh rotation (Chapter 22)
```

No single mechanism is sufficient. Together, they make the attack surface small.
