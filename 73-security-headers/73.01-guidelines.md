## Implementation

### app.ts

```ts
import helmet from 'helmet';
import cors from 'cors';
import config from './shared/config';

// Remove X-Powered-By: Express header
app.disable('x-powered-by');

// Security headers (must be before routes)
app.use(helmet());

// CORS: allow only the known frontend origin, with credentials
app.use(cors({
  origin: config.FRONTEND_URL,
  credentials: true,
}));

// ... rest of middleware and routes
```

The order matters:
1. `app.disable('x-powered-by')` — Express-level, no middleware needed
2. `helmet()` — sets security headers on every response
3. `cors(...)` — sets CORS headers, must be before route handlers

### Headers added by helmet()

| Header | Value | Purpose |
|--------|-------|---------|
| `X-Content-Type-Options` | `nosniff` | Prevents MIME sniffing |
| `X-Frame-Options` | `SAMEORIGIN` | Prevents clickjacking |
| `Strict-Transport-Security` | `max-age=15552000` | Forces HTTPS on supported browsers |
| `X-DNS-Prefetch-Control` | `off` | Reduces info leakage via DNS |
| `Content-Security-Policy` | (default) | Restricts resource loading |
| `Referrer-Policy` | `no-referrer` | Prevents referrer leakage |

`X-Powered-By` is removed by `app.disable('x-powered-by')`. Helmet alone does not remove it.

## SQL injection: already prevented

All `db.query` calls use parameterized queries. The attack cannot succeed:

```bash
# Attempt SQL injection via query string
curl "http://localhost:3000/api/jobs?status=open' OR '1'='1"
```

PostgreSQL receives the literal string `open' OR '1'='1` as the value of the `$1` parameter —
not as SQL syntax. The query returns zero results (no job has that literal status). No injection.

```sql
-- What PostgreSQL actually sees:
SELECT ... FROM jobs WHERE status = 'open'' OR ''1''=''1'
-- (The input is escaped; the injected SQL is treated as a string value)
```

### Demonstrating parameterized safety

```ts
// This is what happens when you use db.query with params:
await db.query(
  `SELECT id, title FROM jobs WHERE status = $1`,
  ["open' OR '1'='1"]   // the attacker's input
);
// PostgreSQL binds this as a string, not as SQL
// Result: 0 rows (no job has that exact status string)
```

## Input validation: already in place

Zod schemas (from Chapter 16) reject unexpected fields. A request with an extra field like
`{ "email": "x@x.com", "password": "p", "role": "admin" }` on the register endpoint:

```ts
const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  // role is not in the schema
});
const parsed = schema.parse(req.body);
// parsed has only { email, password } — role is stripped
```

The extra `role` field is never passed to the database. Mass assignment is prevented by the
Zod schema acting as an allow-list.

## CORS: what it does and does not do

CORS headers tell browsers which origins can make cross-site requests. Setting
`origin: config.FRONTEND_URL` means:

- A browser on `http://localhost:3001` can call the API
- A browser on `http://evil.com` gets a CORS error and the request is blocked
- `curl` and Postman are not affected by CORS — they ignore CORS headers

CORS protects against cross-site request forgery from browsers. It does not protect against
direct API calls from scripts or other servers. The authentication layer (JWT, httpOnly cookie)
is the real protection for non-browser clients.
