# Cache Invalidation

## 1. The stale-read bug in detail

Before adding invalidation, this sequence causes a stale read:

```
T=0  Job "Data Engineer" is created as draft.
T=5  Recruiter publishes the job — status = 'open' written to PostgreSQL.
T=5  Cache key 'jobs:public:page1' still holds the pre-publication snapshot.
T=6  Applicant requests GET /api/public/jobs.
T=6  Redis hit — response served from cache.
T=6  "Data Engineer" is NOT in the response. Applicant sees nothing.
T=65 TTL expires. Cache key is evicted.
T=66 Next applicant requests GET /api/public/jobs.
T=66 Cache miss — query runs — "Data Engineer" now appears.
```

The bug: 60 seconds of invisibility for a published job. On a high-traffic board, thousands of applicants may see the stale result in that window.

---

## 2. The fix: invalidate after the DB write

In `src/modules/jobs/jobsService.ts`, add a `redis.del` call immediately after each DB write that changes job visibility on the public board.

Identify the three operations that change what the public board shows:

| Operation | Effect on public board |
|---|---|
| `publish` (`status → 'open'`) | Adds a job to the board |
| `close` (`status → 'closed'`) | Removes a job from the board |
| `createJob` when `status = 'open'` | Adds a job to the board (rare, but possible if status defaults to open) |

In this system, `createJob` always creates with `status = 'draft'`, so it does not affect the public board. Only `publish` and `close` need invalidation.

---

## 3. Adding invalidation to publishJob

In `src/modules/jobs/jobsService.ts`, find the `publishJob` function and add the invalidation:

```typescript
import redis from '../../shared/redis';

const PUBLIC_BOARD_CACHE_KEY = 'jobs:public:page1';

export async function publishJob(jobId: string, companyId: string): Promise<void> {
  await assertJobOwnership(jobId, companyId);

  await db.query(
    `UPDATE jobs SET status = 'open' WHERE id = $1`,
    [jobId]
  );

  // Invalidate the public board cache so the next request reflects this change.
  // This runs AFTER the DB write succeeds — if the update throws, we never reach here.
  // TODO: also invalidate when company status changes (ch59)
  await redis.del(PUBLIC_BOARD_CACHE_KEY);
}
```

The order is non-negotiable:
1. `assertJobOwnership` — verify the caller owns this job (throws on failure)
2. `db.query(UPDATE ...)` — write to the database (throws on failure)
3. `redis.del(...)` — invalidate the cache (runs only if steps 1 and 2 succeeded)

## 4. Adding invalidation to closeJob

```typescript
export async function closeJob(jobId: string, companyId: string): Promise<void> {
  await assertJobOwnership(jobId, companyId);

  await db.query(
    `UPDATE jobs SET status = 'closed' WHERE id = $1`,
    [jobId]
  );

  // Removing a job from open status also changes the public board.
  await redis.del(PUBLIC_BOARD_CACHE_KEY);
}
```

---

## 5. Why `redis.del` does not throw when the key does not exist

`redis.del` returns the number of keys deleted (0 or 1). If the key is already expired or was never set, it returns 0 and does not throw. This means the invalidation call is always safe to make — there is no need to check whether the key exists first.

```typescript
// Safe in all cases:
await redis.del('jobs:public:page1');  // returns 0 if missing, 1 if deleted
```

## 6. The wrong order and what goes wrong

**Wrong: invalidate before the DB write:**

```typescript
// WRONG
await redis.del(PUBLIC_BOARD_CACHE_KEY);   // cache cleared
await db.query(`UPDATE jobs SET status = 'open' WHERE id = $1`, [jobId]); // throws!
// → exception propagates, publish endpoint returns 500
// → but the cache is already cleared
// → next request is a cache miss, queries DB, reads status = 'draft', re-caches old state
// → the job never appears on the board until the next natural publish attempt
```

**Wrong: invalidate before ownership check:**

```typescript
// WRONG
await redis.del(PUBLIC_BOARD_CACHE_KEY);  // cache cleared unnecessarily
await assertJobOwnership(jobId, companyId); // throws 404 for a different company's job
// → cache was cleared for a job that was never actually published
// → next request hits DB, returns same stale list, re-caches it
// → no visible harm in this specific case, but the pattern is fragile
```

**Correct: invalidate after all writes succeed:**

```typescript
await assertJobOwnership(jobId, companyId);
await db.query(`UPDATE jobs SET status = 'open' WHERE id = $1`, [jobId]);
await redis.del(PUBLIC_BOARD_CACHE_KEY);  // only reached if both above succeed
```

## 7. What about Redis being down?

If the `redis.del` call throws (Redis is unreachable), the publish endpoint would return a 500 error even though the DB write succeeded. The job is published in PostgreSQL but the cache is not cleared.

Options:

**Option A: wrap in try/catch (tolerate Redis failure)**

```typescript
await db.query(`UPDATE jobs SET status = 'open' WHERE id = $1`, [jobId]);
try {
  await redis.del(PUBLIC_BOARD_CACHE_KEY);
} catch (err) {
  // Log the failure. The job is published. Cache will auto-expire in 60s.
  console.error('[cache] Failed to invalidate public board cache:', err);
}
```

The job is published successfully. Applicants may see stale data for up to 60 seconds (the TTL). This is usually the correct choice: Redis downtime should not block job publishing.

**Option B: fail the request (strict consistency)**

```typescript
await db.query(`UPDATE jobs SET status = 'open' WHERE id = $1`, [jobId]);
await redis.del(PUBLIC_BOARD_CACHE_KEY);  // throws on Redis failure → 500
```

The job is published in PostgreSQL but the API returns 500. The recruiter retries — the publish is idempotent (setting `status = 'open'` on an already-open job is harmless), but the recruiter does not know this. Confusing UX.

**This build uses Option A** — the try/catch pattern — because Redis is a cache, not the source of truth. The DB write is authoritative.
