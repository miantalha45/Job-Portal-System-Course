# 59.02 — Admin Moderation: Verify & Suspend (Walkthrough)

## Why admins need moderation controls

Any user can register a company in this system. Without moderation, a bad actor could post
fraudulent jobs immediately. The `status` column on `companies` gates what a company can do:

- `pending` — registered but not yet reviewed; jobs cannot go `open`
- `verified` — reviewed and approved; full access
- `suspended` — removed from the platform; all open jobs close automatically

The admin is the only role that can move a company between these states.

## Building it step by step

### Step 1 — Add the repo functions

Open `src/modules/admin/admin.repo.ts`. Add `listCompanies`, `findCompanyById`,
`setCompanyStatus`, and `closeOpenJobsForCompany` as shown in the guidelines.

Key SQL for listing with optional status filter:

```sql
SELECT c.id, c.name, c.status, c.created_at, u.email AS owner_email
FROM companies c
JOIN users u ON u.id = c.owner_id
WHERE c.status = $1        -- omitted when no filter
ORDER BY c.created_at DESC
```

### Step 2 — Add the service functions

Open `src/modules/admin/admin.service.ts`. The verify flow:

```ts
export async function verifyCompany(id: string) {
  const company = await repo.findCompanyById(id);
  if (!company) throw new NotFoundError('Company not found');
  if (company.status === 'verified') throw new ConflictError('Company is already verified');
  return repo.setCompanyStatus(id, 'verified');
}
```

The suspend flow adds two extra steps after updating the status:

```ts
await repo.closeOpenJobsForCompany(id);
await redis.del('jobs:public:page1');
```

These two operations are not wrapped in a database transaction because the cache deletion is not
transactional by nature. The order matters: close jobs first, then delete the cache. If the
cache deletion fails, the worst case is stale cached data that expires on its own TTL.

### Step 3 — Wire up the routes

Open `src/modules/admin/admin.routes.ts`. Add:

```ts
router.get('/companies', async (req, res, next) => { ... });
router.patch('/companies/:id/verify', async (req, res, next) => { ... });
router.patch('/companies/:id/suspend', async (req, res, next) => { ... });
```

The admin router is already mounted at `/api/admin` in `app.ts` with
`authMiddleware` → `requireRole('admin')` applied before mounting. Individual routes do not
need to repeat those middleware calls.

### Step 4 — Test with curl

Get a valid admin JWT first (register a user with role `admin` via direct DB insert, then log in):

```bash
# 1. Promote a user to admin in psql
UPDATE users SET role = 'admin' WHERE email = 'admin@example.com';

# 2. Log in and extract the token
TOKEN=$(curl -s -X POST http://localhost:3000/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"admin@example.com","password":"Secret123!"}' \
  | jq -r '.accessToken')

# 3. List pending companies
curl -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/companies?status=pending"

# 4. Verify a company
curl -X PATCH -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/companies/<company-id>/verify"

# 5. Suspend a company
curl -X PATCH -H "Authorization: Bearer $TOKEN" \
  "http://localhost:3000/api/admin/companies/<company-id>/suspend"
```

## What changes when a company is suspended

1. `companies.status` → `'suspended'`
2. All rows in `jobs` where `company_id = <id>` AND `status = 'open'` → `status = 'closed'`
3. Redis key `jobs:public:page1` is deleted

Recruiters at that company can still log in but their jobs will appear as `closed` to applicants.
A future improvement would be to revoke their session tokens; that is left as an exercise.
