# Chapter 62 — Why Async? Job Queues, Not Event-Driven

## Key Takeaways

1. **Slow operations should not block the HTTP response.** Email delivery, PDF processing, and
   external API calls can take hundreds of milliseconds or more. Making the user wait for them
   increases latency and hurts perceived performance. If the slow operation also fails, the user
   gets an error for something unrelated to what they actually submitted.

2. **A job queue is durable; an in-process event emitter is not.** Node.js `EventEmitter` fires
   and forgets inside the same process. If the process crashes between emitting the event and
   handling it, the event is lost with no record it ever happened. A job queue writes the job to
   Redis before the HTTP response returns. The job survives a worker crash or a server restart.

3. **BullMQ stores each job as a Redis key.** When you call `queue.add('job-name', payload)`,
   BullMQ serialises the payload to JSON and writes it into a Redis sorted set. Workers poll that
   sorted set and atomically move jobs to a "processing" state. If the worker crashes mid-job,
   the job moves back to waiting after a configurable lock expiry.

4. **At-least-once delivery means jobs can run more than once.** BullMQ guarantees that a job
   will eventually be processed at least once. It does not guarantee exactly once. If a worker
   completes the job but crashes before acknowledging it, the job may run again. Workers must be
   idempotent — running the job twice should produce the same outcome as running it once.

5. **Three things must happen before returning HTTP 200 (or 201).** Validate the input. Write
   to the database. Enqueue the background job. Everything else — sending the email, processing
   the file, calling the third-party API — happens after the response is returned. The user gets
   a fast, consistent response and the side effect happens within seconds.

6. **Queue vs event bus: the key question is "what happens if no consumer is running?"** A job
   queue holds the job in Redis until a worker picks it up. The job can wait hours or days. An
   event bus (Kafka, SNS, a simple in-memory emitter) fires the event immediately. If no consumer
   is listening, the event is gone. For this system — emails, file processing — a queue is the
   right choice because transient worker downtime must not cause silent data loss.

7. **Concurrency is explicit in BullMQ.** When you create a Worker, you set a concurrency
   number. `{ concurrency: 5 }` means the worker processes up to 5 jobs simultaneously. Default
   is 1 (sequential). This is different from the HTTP server, where every request is handled
   concurrently by Node.js's event loop.

## The mental model: the two-phase commit you already know

Chapters 50–52 introduced transactions to make the "apply to a job" operation atomic. The queue
introduces a different kind of two-phase thinking:

```
Phase 1 — synchronous (inside the HTTP request):
  validate input
  write to database (transaction if needed)
  enqueue job
  return HTTP 201

Phase 2 — asynchronous (in the background worker):
  dequeue job
  execute side effect (email, file processing)
  mark job complete (or retry on failure)
```

The user only waits for Phase 1. Phase 2 happens independently.

## Why not just use setTimeout?

`setTimeout(() => sendEmail(), 0)` schedules a callback after the current event loop tick. It
runs in the same process, in the same Node.js runtime. Problems:

- If the process crashes, the callback never runs
- There is no retry if `sendEmail` throws
- There is no visibility into what is pending, running, or failed
- It does not scale across multiple server instances

BullMQ solves all four of these problems.

## The vocabulary

| Term | Meaning |
|------|---------|
| Queue | A named list of jobs in Redis |
| Job | A unit of work with a name, payload, and metadata |
| Worker | A Node.js process that consumes jobs from a queue |
| Concurrency | Maximum parallel jobs a single Worker instance processes |
| Retry | Re-running a failed job after a delay |
| Backoff | Increasing the delay between retries (linear or exponential) |
| Dead letter | The "failed" set — jobs that exhausted all retries |
| Idempotent | A job that produces the same result regardless of how many times it runs |

## Quiz

1. A worker processes a job that inserts a row into the database and then sends an email. The
   database insert succeeds, but the worker crashes before the email is sent. BullMQ retries the
   job. The database now has two identical rows. What design change to the worker would prevent
   the duplicate row?

2. Explain the difference between `queue.add('my-job', payload)` and
   `queue.add('my-job', payload, { jobId: 'unique-key' })`. When would you use the second form?

3. A system uses an in-memory Node.js `EventEmitter` for email notifications and works fine in
   development. During a production deployment, the server process restarts to pick up the new
   code. What happens to in-flight events at the moment of restart, and why does a Redis-backed
   queue not have this problem?
