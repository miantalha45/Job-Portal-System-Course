# Writing the initial migrations

Generate each file with `npm run migrate:create -- <name>`, then fill in the `up` and `down` bodies. The tool creates the timestamp prefix automatically.

Run them all with one command at the end: `npm run migrate`.

## The dependency order

Tables must be created before any FK can reference them:

```
users → (recruiters, applicants, admins)
companies → (recruiters, jobs)
jobs → applications
applicants → applications
```

Create files in this order: `users`, `companies`, `recruiters`, `applicants`, `admins`, `jobs`, `applications`.

## A note on ON DELETE

The FK `ON DELETE` clauses in the migrations below reflect the decisions made in [Chapter 11](../11-foreign-keys-and-constraints/). The DDL sketches in chapters 8–10 left some FK clauses unspecified — this is where they become concrete. Verify your Chapter 11 learning log records the same decisions before running the migrations.

## Migration files

All seven files follow the same shape. Add the `import` statement shown in the first example to every file.

---

### `create_users`

`timestamptz` stores a timestamp with UTC offset, so reads are unambiguous regardless of the database server's time zone.

```ts
import { MigrationBuilder } from 'node-pg-migrate';

export async function up(pgm: MigrationBuilder): Promise<void> {
  pgm.sql(`
    CREATE TABLE users (
      id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
      email         text        NOT NULL UNIQUE,
      password_hash text        NOT NULL,
      role          text        NOT NULL CHECK (role IN ('admin', 'recruiter', 'applicant')),
      status        text        NOT NULL DEFAULT 'unverified'
                                  CHECK (status IN ('unverified', 'active', 'suspended')),
      created_at    timestamptz NOT NULL DEFAULT now(),
      updated_at    timestamptz NOT NULL DEFAULT now()
    );
  `);
}

export async function down(pgm: MigrationBuilder): Promise<void> {
  pgm.sql(`DROP TABLE users;`);
}
```

### `create_applications`

  pgm.sql(`
    CREATE TABLE applications (
      id                uuid        PRIMARY KEY DEFAULT gen_random_uuid(),

      applicant_id      uuid        NOT NULL REFERENCES applicants(id) ON DELETE RESTRICT,

      profile_snapshot  jsonb       NOT NULL DEFAULT '{}',
      created_at        timestamptz NOT NULL DEFAULT now(),
      updated_at        timestamptz NOT NULL DEFAULT now(),
      UNIQUE (job_id, applicant_id)
    );
  `);
}

export async function down(pgm: MigrationBuilder): Promise<void> {
  pgm.sql(`DROP TABLE applications;`);
}

## Run and verify

```bash
npm run migrate
```

The output lists each migration file applied in order. When all seven succeed, connect with `psql` and confirm the tables exist:

```bash
psql $DATABASE_URL -c "\dt"
```

You should see eight entries: the seven tables plus `pgmigrations` (the tracking table `node-pg-migrate` maintains). If any migration fails, fix the DDL in that file and rerun — the tool skips files it has already recorded in `pgmigrations`.

## Rolling back

`npm run migrate:down` always rolls back the most recently applied migration — it cannot jump over intermediate ones. This matters for `down` functions: `DROP TABLE companies` will fail with a FK violation if `recruiters` still references it. Because rollback runs in reverse application order (applications → jobs → applicants → admins → recruiters → companies → users), each `DOWN TABLE` reaches a state where no remaining table holds a FK into it.
