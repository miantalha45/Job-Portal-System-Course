# The Company Panel

## Architecture decisions

### Why httpOnly cookies?

Storing tokens in `localStorage` or `sessionStorage` makes them readable by any JavaScript on the page. An XSS vulnerability — a script injected via a compromised dependency, a user-generated content rendering bug, or a browser extension — can read `localStorage` and exfiltrate the token silently.

`httpOnly` cookies cannot be read by JavaScript. The browser attaches them automatically on every request to the same origin. An XSS script cannot steal a token it cannot read.

The trade-off: the frontend cannot access the token value itself. This is why the proxy API routes exist — the client component calls `/api/jobs` (a Next.js route handler on the same origin), which reads the cookie server-side, forwards the request to the backend with the token, and returns the result.

### Why proxy routes instead of calling the backend directly?

Three reasons:

1. **Token access**: Client components run in the browser and cannot read httpOnly cookies. The proxy route runs on the server and can.
2. **CORS**: The backend may not be configured to accept requests from the browser's origin. The proxy keeps the browser talking only to the Next.js server.
3. **Token refresh**: The proxy can intercept `401` responses and attempt a token refresh before returning the result to the client — transparent to the user.

### Why server components for data fetching?

Pages like `/dashboard/jobs` and `/dashboard/members` use **async server components** that call `apiFetch` directly. The data is fetched on the server, the HTML is rendered, and the browser receives a complete page.

Client components (`'use client'`) are used only where browser interactivity is required: form submission handlers, button click actions, and the router navigation after a mutation. Everything else is a server component.

## The token flow

```
Browser submits login form
  → POST /api/auth/login (Next.js route handler)
    → forwards to backend POST /api/auth/login
    → receives { accessToken, refreshToken }
    → sets httpOnly cookies: access_token, refresh_token
  → browser gets { ok: true } — never sees the tokens

Browser navigates to /dashboard/jobs
  → Next.js middleware reads access_token cookie
  → if absent, redirects to /login
  → if present, renders page

Page component calls apiFetch('/api/jobs')
  → apiFetch reads access_token from server-side cookie store
  → attaches Authorization: Bearer <token>
  → returns job list

Client component clicks "Publish"
  → POST /api/jobs/:id/publish (Next.js route handler)
    → reads cookie server-side
    → forwards to backend
  → router.refresh() re-renders the page with updated data
```

## What the pages look like

### `/dashboard/jobs`

A table of all company jobs. Each row shows the job title (linked to the detail page), status badge (color-coded: green for open, gray for draft, red for closed), and creation date. Status filter links at the top. "Next page" link when pagination is available.

### `/dashboard/jobs/new`

A simple form: title (required), description (textarea), location, and employment type (dropdown). Submits to the proxy route which POSTs to the backend. On success, redirects to the job detail page. On failure, shows the error message inline.

### `/dashboard/jobs/[id]`

Shows the job title, status, and description. Below the description: action buttons rendered by `JobActions.tsx`. A draft job shows a "Publish" button. An open job shows a "Close" button. A closed job shows neither. Clicking a button calls the proxy route, then `router.refresh()` re-fetches the page data.

### `/dashboard/members`

A table of all company members. Each row shows email, company role, and join date. For a full build, add a role-change dropdown (only rendered for the owner) and a "Remove" button.

## Limitations of this scaffold

This is a working scaffold, not a production frontend. Things intentionally not built:

- **No token refresh**: if the access token expires (15 minutes), the user gets a 401 response and must log in again. A production system would intercept 401s in the proxy route, call `POST /api/auth/refresh`, update the cookie, and retry the original request.
- **No optimistic updates**: the page re-fetches after every mutation. For a smooth UI, use React Query or SWR with optimistic updates.
- **No error boundaries**: if `apiFetch` throws a network error, the page crashes. Add `error.tsx` files alongside each `page.tsx` to handle this gracefully.
- **Middleware does not verify the JWT signature**: it only checks for the cookie's presence. A tampered token would pass the middleware check but fail at the backend.
- **Member actions (PATCH/DELETE) are not wired**: the proxy routes and client components for role-change and member removal are straightforward extensions of the patterns shown. Implement them following the same proxy + client-component pattern as the job publish/close buttons.

## Environment variables

| Variable | Where read | Value |
|---|---|---|
| `API_URL` | Server-side only (route handlers, middleware, server components via `apiFetch`) | `http://localhost:3000` |
| `NEXT_PUBLIC_API_URL` | Client-side (if ever needed for client-side fetching) | `http://localhost:3000` |

Both are in `frontend/.env.local`. Neither is committed to the repository (`.env.local` is in `.gitignore`). Neither is read from `process.env` anywhere in the backend — they belong to the frontend environment only.
