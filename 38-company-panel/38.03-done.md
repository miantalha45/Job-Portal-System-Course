## 3. Unauthenticated user is redirected

Open `http://localhost:3001/dashboard/jobs` in a browser without logging in.

Expected: browser redirects to `/login`.

Verify via curl (follow redirects):

```bash
curl -s -o /dev/null -w "%{http_code}" \
  -L http://localhost:3001/dashboard/jobs
```

Expected: ultimately lands on a page with a `200` status (the login page). The redirect itself is `307` or `302`.

## 4. Login sets httpOnly cookies

```bash
curl -s -c /tmp/cookies.txt -X POST http://localhost:3001/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"owner@example.com","password":"Password1!"}' \
  | jq .
```

Expected: `{ "ok": true }`

Inspect the cookies file:

```bash
cat /tmp/cookies.txt
```

Expected: two rows containing `access_token` and `refresh_token`. The `HttpOnly` flag should be present in the Set-Cookie headers (visible in browser dev tools).

## 6. Status filter works

Navigate to `http://localhost:3001/dashboard/jobs?status=open`.

Expected: only open jobs are shown. Verify the job count matches:

```bash
psql $DATABASE_URL -c \
  "SELECT COUNT(*) FROM jobs j
   JOIN recruiters r ON r.company_id = j.company_id
   JOIN users u ON u.id = r.user_id
   WHERE u.email = 'owner@example.com' AND j.status = 'open';"
```

The count in psql should match the number of rows in the browser table.

## 10. Token is never exposed to browser JavaScript

Open browser developer tools → Application → Cookies.

Expected: `access_token` and `refresh_token` cookies are listed but marked `HttpOnly`. The "Value" column is blank or shows `[HttpOnly]` — the JavaScript console cannot read them.

Confirm in the browser console:

```js
document.cookie
```

Expected: `access_token` and `refresh_token` do not appear in `document.cookie`.

## Quiz

**Q1.** The create-job form is a `'use client'` component that calls the Next.js proxy route at `/api/jobs`. An alternative design uses a React Server Action: an `async` function defined with `'use server'` that the form submits to directly. Compare these two approaches for the create-job use case. Which has better error handling ergonomics? Which is simpler to implement? Are there any security differences?

**Q2.** The job list page uses `router.refresh()` in the `JobActions` client component to re-fetch data after a publish or close action. `router.refresh()` causes the server component to re-run and re-fetch from the API. If the backend has a slight delay between writing the status change and it being visible in the next SELECT (e.g., due to read replicas), what would the user experience be — and how would you address this without removing the server-component architecture?

**Q3.** The Next.js proxy routes forward the `access_token` cookie to the backend as a `Bearer` token. If the token expires between the middleware check (which passes because the cookie exists) and the backend request (which returns 401), the proxy route returns the 401 to the client component. Describe the full token refresh flow you would implement in the proxy route to handle this case transparently — including what happens to the new tokens and how the original request is retried.
