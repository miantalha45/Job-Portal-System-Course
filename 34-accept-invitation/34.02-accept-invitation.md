# Accepting an Invitation

## Two cases for the same endpoint

`POST /auth/accept-invitation` handles two distinct situations with a single code path:

**Case A — New user.** The invitee has no account. They provide their email, the raw token from the email link, and a new password. The service creates a `users` row with `status='active'` — no email verification needed, because the invitation link proves they control the email address.

**Case B — Existing user.** The invitee already has an account (perhaps they registered earlier but haven't joined any company). They provide their email and the raw token. The password field is ignored. The service finds their existing user row and attaches a recruiter row to it.

In both cases, the invitation row is deleted and the invitee receives `{ accessToken, refreshToken }`. They are immediately logged in.

---

## Request and response

**New user (Case A):**

```bash
POST /auth/accept-invitation
Content-Type: application/json

{
  "token": "a3f9e2c1...64hexchars...",
  "email": "invitee@example.com",
  "password": "SecurePass1!"
}
```

**Existing user (Case B):**

```bash
POST /auth/accept-invitation
Content-Type: application/json

{
  "token": "a3f9e2c1...64hexchars...",
  "email": "invitee@example.com"
}
```

Successful response (200):

```json
{
  "accessToken": "<jwt>",
  "refreshToken": "<jwt>"
}
```

---

## What happens to the token

The raw token arrives in `input.token`. The service calls `findInvitationByToken(rawToken)`, which:

1. Computes `SHA-256(rawToken)`
2. Queries: `SELECT ... FROM invitations WHERE token_hash = $1 AND expires_at > NOW()`
3. Returns the invitation row, or `null` if not found / expired

If `null`, the service throws `BadRequestError('Invalid or expired invitation token.')`. The caller learns nothing about whether the token existed or was merely expired.

---

## Email matching

After finding the invitation, the service compares `invitation.email` to `input.email` (case-insensitive). If they differ, the same `BadRequestError` is thrown — identical message, no information about which check failed.

This step is important. Without it, an attacker who intercepts an invitation link could substitute their own email and join a company they were not invited to. The email in the request body must match the email in the invitation row.

---

## New user flow: no email verification

Normally, registering creates a user with `status='pending_verification'`. Email verification changes it to `'active'`.

The accept-invitation path bypasses this. The invitation itself — sent to a specific email, accepted with a token that proves receipt — is the verification. Creating the user with `status='active'` directly is correct and intentional.

The new user is a `recruiter` at the platform level (that is the only platform role that can belong to companies). The invitation `role` field controls their company role (`hr_manager`, `recruiter`, or `hiring_manager`) — stored in `recruiters.company_role`, not in `users.role`.

---

## After acceptance

The `invitations` row is deleted. The token cannot be reused. The `recruiters` row links the user to the company. `getRecruiterCompany(userId)` now returns `{ companyId, companyRole }` for this user.

Verify both in psql:

```sql
-- Invitation row should be gone
SELECT COUNT(*) FROM invitations WHERE email = 'invitee@example.com';
-- Expected: 0

-- Recruiter row should exist
SELECT r.company_role, c.name AS company_name
FROM recruiters r
JOIN companies c ON c.id = r.company_id
JOIN users u ON u.id = r.user_id
WHERE u.email = 'invitee@example.com';
-- Expected: one row with the invited company_role
```

## Error cases summary

| Situation | HTTP | Message |
|---|---|---|
| Token not found or expired | 400 | Invalid or expired invitation token. |
| Email mismatch | 400 | Invalid or expired invitation token. |
| Existing user not active | 403 | Your account is not active. |
| New user, no password provided | 400 | Password is required to create a new account. |
| Validation failure (bad email format) | 422 | Validation failed |
