# Guidelines — Chapter 34

## Before you start

- **Chapter 20** — `POST /api/auth/register` and the users table structure. `createUser` in the auth repo creates a user row.
- **Chapter 22** — `generateTokenPair(userId, role)` returns `{ accessToken, refreshToken }`. The accept-invitation handler returns the same pair so the invitee is immediately logged in.
- **Chapter 33** — the `invitations` table contains rows with `token_hash`, `expires_at`, `email`, `role`, and `company_id`. `createInvitation` stores only the SHA-256 hash; the raw token was sent by email.

The accept-invitation route lives in `auth.routes.ts`. It does not require `authMiddleware`. The raw token in the request body IS the credential — it proves the invitee received the email.

Run `npx tsc --noEmit` before you start.

## What to build

### 1. Schema — `src/modules/auth/auth.schema.ts`

```ts
export const acceptInvitationSchema = z.object({
  token: z.string().min(1),
  email: z.string().email(),
  password: z.string().min(8).optional(),
});

export type AcceptInvitationInput = z.infer<typeof acceptInvitationSchema>;
```

`password` is optional because the invitee may already have an account. If they do have an account, the password field is ignored.

### 2. Repository additions — `src/modules/auth/auth.repo.ts`

```ts
import crypto from 'crypto';
import db from '../../shared/db';

// Find a valid (non-expired) invitation by its raw token
export async function findInvitationByToken(rawToken: string): Promise<{
  id: string;
  companyId: string;
  email: string;
  role: string;
} | null> {
  const tokenHash = crypto.createHash('sha256').update(rawToken).digest('hex');
  const result = await db.query(
    `SELECT id, company_id AS "companyId", email, role
     FROM invitations
     WHERE token_hash = $1 AND expires_at > NOW()`,
    [tokenHash],
  );
  return result.rows[0] ?? null;
}

// Find a user by email; returns null if not found
export async function findUserByEmail(email: string): Promise<{
  id: string;
  status: string;
  role: string;
} | null> {
  const result = await db.query(
    `SELECT id, status, role FROM users WHERE email = $1`,
    [email],
  );
  return result.rows[0] ?? null;
}

// Create a pre-verified user (no email verification needed — invitation proves ownership)
export async function createVerifiedUser(
  email: string,
  passwordHash: string,
): Promise<string> {
  const userId = uuid();
  await db.query(
    `INSERT INTO users (id, email, password_hash, role, status)
     VALUES ($1, $2, $3, 'recruiter', 'active')`,
    [userId, email, passwordHash],
  );
  return userId;
}

// Attach a user to a company with the invited role
export async function createRecruiterRow(
  userId: string,
  companyId: string,
  role: string,
): Promise<void> {
  const recruiterId = uuid();
  await db.query(
    `INSERT INTO recruiters (id, user_id, company_id, company_role, created_at)
     VALUES ($1, $2, $3, $4, NOW())`,
    [recruiterId, userId, companyId, role],
  );
}

// Delete the invitation row after acceptance
export async function deleteInvitation(invitationId: string): Promise<void> {
  await db.query(`DELETE FROM invitations WHERE id = $1`, [invitationId]);
}
```

### 3. Service — `src/modules/auth/auth.service.ts`

```ts
import bcrypt from 'bcrypt';
import { BadRequestError, ForbiddenError } from '../../shared/errors';
import {
  findInvitationByToken,
  findUserByEmail,
  createVerifiedUser,
  createRecruiterRow,
  deleteInvitation,
} from './auth.repo';
import { generateTokenPair } from './auth.tokens';
import type { AcceptInvitationInput } from './auth.schema';

export async function acceptInvitation(input: AcceptInvitationInput) {
  // Step 1: Resolve the invitation
  const invitation = await findInvitationByToken(input.token);
  if (!invitation) {
    throw new BadRequestError('Invalid or expired invitation token.');
  }

  // Step 2: Email must match the invitation
  if (invitation.email.toLowerCase() !== input.email.toLowerCase()) {
    throw new BadRequestError('Invalid or expired invitation token.');
  }

  // Step 3: Resolve or create the user
  let userId: string;
  let userRole: string;

  const existingUser = await findUserByEmail(input.email);

  if (existingUser) {
    if (existingUser.status !== 'active') {
      throw new ForbiddenError('Your account is not active.');
    }
    userId = existingUser.id;
    userRole = existingUser.role;
  } else {
    // New user — password required
    if (!input.password) {
      throw new BadRequestError('Password is required to create a new account.');
    }
    const passwordHash = await bcrypt.hash(input.password, 12);
    userId = await createVerifiedUser(input.email, passwordHash);
    userRole = 'recruiter';
  }

  // Step 4: Attach the user to the company
  await createRecruiterRow(userId, invitation.companyId, invitation.role);

  // Step 5: Delete the invitation (one-time use)
  await deleteInvitation(invitation.id);

  // Step 6: Issue tokens so the invitee is immediately logged in
  return generateTokenPair(userId, userRole);
}
```

### 4. Route — `src/modules/auth/auth.routes.ts`

```ts
import { acceptInvitationSchema } from './auth.schema';
import { acceptInvitation } from './auth.service';

// No authMiddleware — the raw token is the credential
router.post('/accept-invitation', async (req, res, next) => {
  try {
    const input = validate(acceptInvitationSchema, req.body);
    const tokens = await acceptInvitation(input);
    res.status(200).json(tokens);
  } catch (err) {
    next(err);
  }
});
```

## Error message uniformity

The "invalid or expired invitation token" message is identical whether the token doesn't exist, has expired, or the email doesn't match. This is intentional. Returning different messages for "token not found" versus "email mismatch" would tell an attacker whether they have a valid token for a different email — leaking information about the invitation table.

---

## The one-time-use guarantee

The invitation row is deleted immediately after the recruiter row is created. If the request fails partway through — for example, after `createRecruiterRow` but before `deleteInvitation` — the invitation row remains and the link could be clicked again. A second click would attempt to create a duplicate `recruiters` row for the same `user_id` and `company_id`.

Add a unique constraint to prevent this:

```sql
ALTER TABLE recruiters ADD CONSTRAINT recruiters_user_company_unique
  UNIQUE (user_id, company_id);
```

With this constraint, a second click produces a database unique-violation error, which the error handler maps to a `409 Conflict`. The user is not harmed — they are already a member.

For complete atomicity, wrap steps 4 and 5 in a transaction. That is left as an exercise; the current build is correct under normal conditions.
