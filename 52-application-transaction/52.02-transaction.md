# 52.02 — Transactions: Design Notes

## What a transaction guarantees

PostgreSQL transactions provide ACID guarantees:

- **Atomic** — all statements in the transaction succeed, or none of them do
- **Consistent** — the database moves from one valid state to another; no partial state is observable by other connections
- **Isolated** — other connections cannot see the uncommitted changes (at the default READ COMMITTED isolation level, they see the state before BEGIN)
- **Durable** — once COMMIT succeeds, the changes survive crashes (they are written to the WAL)

For application submission, the relevant guarantee is atomicity. If an applicant submits to 5 jobs and the 4th insert fails, the transaction rolls back — zero applications are committed. Without the transaction, inserts 1–3 are committed and the applicant is in a partially applied state: applied to 3 jobs but not the other 2, with no error surfaced to them.

---

## Connection pool exhaustion — the real danger of not releasing

Every `pool.connect()` call checks out a connection. If `client.release()` is not called — because of an uncaught exception that bypasses it, or a missing `finally` block — that connection is gone until the pool times out (typically 10 seconds to never, depending on config).

Under load:

```
Request 1: pool.connect() → 1 connection held
Request 2: pool.connect() → 2 connections held
...
Request 20: pool.connect() → pool at capacity (20 connections max)
Request 21: pool.connect() → WAITING (no free connections)
```

All subsequent requests hang. The application becomes unresponsive. The fix is always `finally { client.release() }` — it executes whether the transaction succeeds or throws.

---

## Isolation level and the pre-flight checks

The pre-flight checks (is the job open? has the applicant already applied?) run outside the transaction, using `db.query`. They read committed data. Then the transaction begins.

Between the pre-flight check and the transaction INSERT, another request could:
1. Close the job — the INSERT into `applications` would succeed even for a now-closed job
2. Submit an overlapping application — the `ON CONFLICT DO NOTHING` handles this

For point 1, you can add a re-check inside the transaction:

```sql
SELECT id FROM jobs WHERE id = $1 AND status = 'open' FOR UPDATE
```

`FOR UPDATE` acquires a row-level lock, preventing concurrent UPDATEs to that job row until the transaction commits. This eliminates the race. Whether to add this depends on how critical it is to prevent applications to jobs closed in the millisecond between the pre-flight check and the INSERT.

For a job portal, a brief window where an application lands on a just-closed job is acceptable. The recruiter can reject it. Adding `FOR UPDATE` is correct but adds locking overhead.

---

## Rollback on any error

The `catch` block always rolls back:

```ts
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
}
```

`ROLLBACK` is safe to call even if the transaction was never properly started (e.g., if `BEGIN` itself failed). It is a no-op in that case. Always roll back in the catch block.

Re-throwing the error (`throw err`) after rollback is essential — without it, the service function returns `undefined` and the route sends a 200 response despite the failure.

## The `PoolClient` type

When you pass a transaction client to repo functions, the parameter type is `PoolClient` from the `pg` library:

```ts
import type { PoolClient } from 'pg';

export async function insertApplication(
  client: PoolClient,
  ...
) {
  const result = await client.query(...);
}
```

`PoolClient` has the same `query` method as the pool itself. The repo function does not know or care whether it is inside a transaction — it just calls `client.query`. This is the correct abstraction boundary: transactions are a service concern, not a repo concern.
