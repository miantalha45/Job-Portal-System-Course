```bash

JOB_A="<id of open job A — not yet applied to>"

  -H "Authorization: Bearer $APPLICANT_TOKEN" \
```

## 4. Demonstrate rollback on failure

To test rollback, temporarily break the second insert. One approach: apply to a job that has a valid ID but add a constraint violation on the second insert by manipulating the data in a test.

An easier observable test: apply to `[JOB_A, JOB_A]` — the second INSERT on the same job will trigger the `UNIQUE` constraint violation (if `ON CONFLICT DO NOTHING` is removed temporarily). With the transaction, the first insert should also roll back.

Check that without the transaction (before this chapter), partial inserts were possible by reading the Chapter 50 code and reasoning through the failure path. You do not need to reproduce a partial insert from Chapter 50 — reasoning through the code is sufficient.

## Quiz

**Q1.** The transaction wraps only the `insertApplication` calls, not the pre-flight checks (`getOpenJobs`, `checkExistingApplications`). A developer argues that the entire `applyToJobs` function should be in a transaction — from the `findApplicantByUserId` call through the final COMMIT. Evaluate this argument. What would be gained? What would be lost (consider connection hold time, lock contention, and the risk of long-lived transactions)?

**Q2.** `ROLLBACK` is called in the `catch` block. Describe what happens if the ROLLBACK itself fails (e.g., the database connection drops before ROLLBACK executes). What state is the database in? What does PostgreSQL do automatically with abandoned transactions, and how long does that take?

**Q3.** The service passes a `PoolClient` to the repo's `insertApplication` function. An alternative design puts the transaction entirely in the repo: a single repo function (`insertApplications`) acquires the client, runs BEGIN/COMMIT/ROLLBACK, and releases it. Compare the two designs on: separation of concerns (which layer owns the transaction boundary), testability, and flexibility when transaction scope needs to expand to include other operations (e.g., triggering a notification as part of the same transaction).
