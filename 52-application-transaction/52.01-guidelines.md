# Chapter 52 — The Application Transaction

## What you will build

Wrap the multi-job application submission in a single database transaction. All application inserts commit together or roll back together.

## Why `db.query` does not work for transactions

`db.query` is a convenience wrapper around `pool.query`. Each call to `pool.query` checks out a connection from the pool, runs the query, and immediately returns the connection. Two consecutive calls to `db.query` may run on two different connections.

PostgreSQL transactions are connection-scoped. `BEGIN` starts a transaction on one connection. `COMMIT` commits only the statements that ran on that same connection after `BEGIN`. If `INSERT 1` runs on connection A and `INSERT 2` runs on connection B, they are in different transactions — there is no atomic unit.

```
WRONG — not a transaction:
  await db.query('INSERT INTO applications ...');  // connection A
  await db.query('INSERT INTO applications ...');  // connection B (different!)
  // No shared transaction. If the second insert fails, the first is already committed.

CORRECT — one connection held for the duration:
  const client = await pool.connect();
  await client.query('BEGIN');
  await client.query('INSERT INTO applications ...');  // connection A
  await client.query('INSERT INTO applications ...');  // connection A
  await client.query('COMMIT');
  client.release();
```

## Export `pool` from `src/shared/db.ts`

```ts
// src/shared/db.ts
import { Pool } from 'pg';
import config from './config';

export const pool = new Pool({ connectionString: config.DATABASE_URL });

const db = { query: pool.query.bind(pool) };
export default db;
```

Exporting `pool` allows modules that need transactions to call `pool.connect()`. Modules that only run single queries continue using `db.query` — no change needed.

## The transaction pattern

```ts
import { pool } from '../../shared/db';

const client = await pool.connect();
try {
  await client.query('BEGIN');

  // All inserts use client.query, not db.query
  for (const jobId of jobsToInsert) {
    await client.query(
      `INSERT INTO applications (job_id, applicant_id, answers, snapshot)
       VALUES ($1, $2, $3, $4)
       ON CONFLICT (job_id, applicant_id) DO NOTHING
       RETURNING id`,
      [jobId, applicantId, JSON.stringify(answers[jobId] ?? []), JSON.stringify(snapshot)]
    );
  }

  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
} finally {
  client.release();
}
```

`finally { client.release() }` is non-negotiable. If `client.release()` is not called, the connection is never returned to the pool. Under load, the pool is exhausted and all new requests hang indefinitely waiting for a free connection.

## Updating `applyToJobs`

Refactor `applicants.service.ts` to use the transaction pattern. The repo functions (`insertApplication`, etc.) are now called with a `client` argument instead of using `db.query` directly. Two approaches:

**Option A — pass the client into repo functions:**

```ts
// applicants.repo.ts — modified insertApplication
import type { PoolClient } from 'pg';

export async function insertApplication(
  client: PoolClient,
  applicantId: string,
  jobId: string,
  answers: unknown,
  snapshot: unknown
) {
  const result = await client.query(
    `INSERT INTO applications (job_id, applicant_id, answers, snapshot)
     VALUES ($1, $2, $3, $4)
     ON CONFLICT (job_id, applicant_id) DO NOTHING
     RETURNING id`,
    [jobId, applicantId, JSON.stringify(answers), JSON.stringify(snapshot)]
  );
  return result.rows[0] ?? null;
}
```

The service acquires the client and passes it to the repo. The repo is unaware of whether it is inside a transaction — it just uses the connection it is given.

**Option B — inline the inserts in the service:**

Move the insert SQL directly into the service function, inside the transaction block. This is simpler but mixes SQL into the service layer, which reduces testability.

Option A is preferred. It keeps SQL in the repo and keeps the transaction lifecycle in the service.

## The full updated `applyToJobs` service function

```ts
export async function applyToJobs(
  userId: string,
  body: { jobIds: string[]; answers: Record<string, unknown[]> }
) {
  if (body.jobIds.length === 0 || body.jobIds.length > 10) {
    throw new ValidationError('jobIds must contain 1–10 items');
  }

  const profile = await repo.findApplicantByUserId(userId);
  if (!profile) throw new NotFoundError('Profile not found');

  const openJobs = await repo.getOpenJobs(body.jobIds);
  const openJobIds = new Set(openJobs.map((j) => j.id));
  const closedOrMissing = body.jobIds.filter((id) => !openJobIds.has(id));
  if (closedOrMissing.length > 0) {
    throw new NotFoundError(`Jobs not found or not open: ${closedOrMissing.join(', ')}`);
  }

  const alreadyApplied = await repo.checkExistingApplications(profile.id, body.jobIds);
  const alreadyAppliedSet = new Set(alreadyApplied);

  const snapshot = await repo.buildApplicantSnapshot(profile.id);

  const jobsToInsert = body.jobIds.filter((id) => !alreadyAppliedSet.has(id));
  const skipped = body.jobIds.filter((id) => alreadyAppliedSet.has(id));

  const created: string[] = [];

  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    for (const jobId of jobsToInsert) {
      const answers = body.answers[jobId] ?? [];
      const application = await repo.insertApplication(client, profile.id, jobId, answers, snapshot);
      if (application) created.push(application.id);
      else skipped.push(jobId);
    }

    await client.query('COMMIT');
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }

  return { created, skipped };
}
```
