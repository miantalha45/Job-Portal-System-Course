# 74.02 — Deploy: App + Worker, Secrets, HTTPS (Walkthrough)

## The multi-stage build pattern

A TypeScript application needs two categories of npm packages:

- **Build-time**: `typescript`, `@types/*`, `ts-node` — needed to compile, not to run
- **Runtime**: `express`, `bullmq`, `pg`, `pino` — needed to run, not to compile

Without multi-stage builds, the image would include all devDependencies (~200MB of TS tooling)
that serve no purpose at runtime. Multi-stage builds fix this:

```
Stage 1 (builder):  node_modules/ with devDeps + run tsc → dist/
Stage 2 (runner):   copy dist/ + npm ci --omit=dev
```

The final image contains only the compiled JavaScript and runtime dependencies. No TypeScript
source files, no devDeps. Smaller images pull faster and have a smaller attack surface.

## Building and running with Docker Compose

### Step 1 — Create .dockerignore

This prevents `node_modules` (large), `dist` (will be built inside Docker), `.env` files
(secrets), and logs from being sent to the Docker build context:

```
node_modules
dist
.env
.env.*
*.log
```

### Step 2 — Write the Dockerfiles

Two files:
- `Dockerfile` — CMD: `node dist/index.js` (API server)
- `Dockerfile.worker` — CMD: `node dist/worker/worker.js` (BullMQ worker)

Both use `node:20-alpine` (small base image). Alpine adds ~5MB vs ~130MB for the full node
image.

### Step 3 — Write docker-compose.prod.yml

Service dependency order:

```
postgres (health: pg_isready)
redis (health: redis-cli ping)
migrate (depends on postgres healthy, runs SQL files, exits 0)
api (depends on migrate completed, redis healthy)
worker (depends on migrate completed, redis healthy)
nginx (depends on api)
```

The `migrate` service using `condition: service_completed_successfully` ensures the API never
starts before all SQL migrations have run successfully.

### Step 4 — Create .env.production

```env
NODE_ENV=production
PORT=3000
DATABASE_URL=postgresql://postgres:secret@postgres:5432/jobportal
REDIS_URL=redis://redis:6379
JWT_SECRET=<long-random-string>
JWT_REFRESH_SECRET=<different-long-random-string>
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=noreply@example.com
SMTP_PASS=<smtp-password>
SMTP_FROM=noreply@example.com
S3_BUCKET=my-production-bucket
S3_REGION=us-east-1
AWS_ACCESS_KEY_ID=<key>
AWS_SECRET_ACCESS_KEY=<secret>
FRONTEND_URL=https://example.com
LOG_LEVEL=info
```

Do NOT commit this file. Add `.env.production` to `.gitignore`.

### Step 5 — Start the stack

```bash
docker compose -f docker-compose.prod.yml up --build -d
```

Watch logs:
```bash
docker compose -f docker-compose.prod.yml logs -f api
docker compose -f docker-compose.prod.yml logs -f worker
```

### Step 6 — Health checks

```bash
curl http://localhost:3000/health
# (via nginx on 443): curl -k https://localhost/health
```

## HTTPS with nginx

The nginx config terminates TLS and proxies plain HTTP to the API container. The API container
never sees HTTPS — this is the standard "TLS termination at the reverse proxy" pattern.

For a real certificate, use Let's Encrypt + Certbot or a managed certificate from your cloud
provider. For local testing, use a self-signed cert:

```bash
openssl req -x509 -newkey rsa:4096 -keyout nginx/certs/privkey.pem \
  -out nginx/certs/fullchain.pem -days 365 -nodes \
  -subj '/CN=localhost'
```

The `proxy_set_header X-Forwarded-Proto $scheme` header tells the Express app whether the
original request was HTTP or HTTPS. This matters for generating absolute URLs and for the
`Strict-Transport-Security` header to take effect.

## Secrets best practices

| Practice | Why |
|----------|-----|
| Never bake secrets into images | Images are stored in registries; anyone who can pull the image gets the secrets |
| Use `--env-file` at runtime | Secrets stay on the server, not in the image |
| Use a secrets manager in production | AWS Secrets Manager, HashiCorp Vault — secrets are not stored in plaintext on disk |
| Rotate secrets regularly | Limit the blast radius of a leak |
| Different secrets per environment | Dev secrets accidentally pushed cannot affect production |

## Migration strategy

Running migrations as a one-off `migrate` service (rather than inside the app on startup):

- Migrations run exactly once per deploy
- If migrations fail, the API never starts (Compose dependency chain)
- Multiple API instances do not race each other to run migrations (only one migrate service)
- Rollback is explicit: you must write a down-migration and run it manually

The `for f in /migrations/*.sql; do psql ...; done` loop runs migration files in alphabetical
order. File naming convention `001_`, `002_`, etc. ensures the correct order.

---

## No `process.env` in application modules

All secrets injected via `.env.production` are read only in `config.ts`. The Docker container
has these environment variables set at startup. No application code reads `process.env` directly.
