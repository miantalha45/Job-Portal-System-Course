# The `applications` table

```sql
CREATE TABLE applications (
  id                uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  job_id            uuid        NOT NULL REFERENCES jobs(id),
  applicant_id      uuid        NOT NULL REFERENCES applicants(id),
  stage             text        NOT NULL DEFAULT 'applied'
                                  CHECK (stage IN (
                                    'applied', 'screening', 'interview',
                                    'final_interview', 'offer',
                                    'hired', 'rejected'
                                  )),
  screening_answers jsonb       NOT NULL DEFAULT '{}',
  profile_snapshot  jsonb       NOT NULL DEFAULT '{}',
  created_at        timestamptz NOT NULL DEFAULT now(),
  updated_at        timestamptz NOT NULL DEFAULT now(),
  UNIQUE (job_id, applicant_id)
);
```

## Column by column

**`job_id`** — the specific job this application is for. `NOT NULL`. Multi-tenant isolation flows from here: a recruiter can only see applications where `job_id` belongs to one of their company's jobs.

**`applicant_id`** — the applicant who submitted. `NOT NULL`. References `applicants.id` (the profile table), not `users.id` — consistent with the data model where profile data lives in the role-specific table.

**`UNIQUE (job_id, applicant_id)`** — the schema-level guarantee that an applicant can only apply to a given job once. Without this, a network retry or a bug in the submission code could create duplicate applications. The idempotency layer in [Chapter 53](../53-idempotent-application/) adds a safe-to-retry submission on top of this constraint.

**`stage`** — where this application sits in the hiring pipeline. Defaults to `'applied'` at submission. The seven stages form the pipeline:

```
applied → screening → interview → final_interview → offer → hired
```

`rejected` is a terminal state reachable from **any** active stage — a recruiter can reject after screening, after an interview, or after an offer is extended. `hired` is only reachable from `offer`. The CHECK constraint enforces valid values; [Chapter 55](../55-application-stages/) enforces which transitions are legal and who may execute them.

`stage` is a real column — not JSONB — because recruiters filter and group by it ("show me all applicants in the interview stage") and stage transitions are gated by within-company roles (`recruiters.company_role` from [Chapter 8](../08-model-accounts/)). [Chapter 55](../55-application-stages/) covers who can advance which stages and when.

**`screening_answers`** — a JSONB object keyed by question UUID, value is the applicant's answer:

```json
{
  "a1b2c3d4-e5f6-7890-abcd-ef1234567890": "I've worked with distributed systems for three years, primarily Kafka and Kubernetes in a fintech context.",
  "b2c3d4e5-f6a7-8901-bcde-f12345678901": true,
  "c3d4e5f6-a7b8-9012-cdef-123456789012": "https://github.com/myusername/project-x"
}
```

The keys match the `id` fields from `jobs.screening_questions`. Values preserve their original type — a boolean question stores `true`, not `"true"`. To display answers alongside their questions, join on the UUID key:

```sql
-- application answers joined to job questions at read time
SELECT q.value->>'text'                       AS question,
       a.screening_answers->(q.value->>'id')  AS answer   -- returns jsonb, preserving original type
FROM jobs j,
     jsonb_array_elements(j.screening_questions) AS q,
     applications a
WHERE a.id = $1
  AND j.id = a.job_id;
```

`->` (not `->>`) is intentional: it returns the answer as `jsonb`, preserving its original type — `true` stays a boolean, not the string `"true"`. The display layer casts as needed (`answer::text`, `answer::boolean`, etc.).

**`profile_snapshot`** — a JSONB copy of the applicant's profile at the moment of submission. If the applicant later updates their résumé or headline, the snapshot does not change — it's what the recruiter evaluated. The full rationale and exactly what to freeze is [Chapter 51](../51-application-snapshots/)'s job. For now the column exists with an empty default.

**`updated_at`** — updated whenever stage advances or the record changes. The recruiter pipeline view uses this to show "last activity."
