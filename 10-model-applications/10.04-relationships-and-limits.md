# Relationships and what's deferred

## Updated entity map

```
users (1) ──── (0..1) recruiters(company_role) (N) ──── (1) companies (1) ──── (N) jobs
users (1) ──── (0..1) applicants               (1) ──── (N) applications (N) ──── (1) jobs
users (1) ──── (0..1) admins

jobs (1) ──── (N) interviews          ← Chapter 56
applications (1) ──── (N) interviews  ← Chapter 56
```

`applications` sits at the intersection of `jobs` and `applicants`. The many-to-many between jobs and applicants is resolved through this table — an applicant can apply to many jobs; a job can receive many applications.

Multi-tenant isolation passes through the `job_id` FK: a recruiter's company owns the job, which owns the application. An applicant never reads another applicant's application; a recruiter never reads another company's.

## Rules the schema enforces now

| Rule | How it's enforced |
|---|---|
| One application per applicant per job | `UNIQUE (job_id, applicant_id)` |
| Every application has a job | `NOT NULL` on `job_id` |
| Every application has an applicant | `NOT NULL` on `applicant_id` |
| Stage is one of seven values | `CHECK` constraint on `stage` |
| Answers and snapshot are valid JSON | `jsonb` column type |

## What's deliberately NOT in this chapter

**`ON DELETE` for `job_id` and `applicant_id`** — what happens to applications when a job is deleted, or when an applicant deletes their account? These are product decisions (restrict? archive? anonymise?), worked through in [Chapter 11](../11-foreign-keys-and-constraints/).

**Stage transition enforcement** — the CHECK constraint ensures `stage` holds a valid value; it does not prevent invalid transitions (e.g. jumping from `applied` straight to `hired`). Who can advance which stages, and what transitions are legal, is [Chapter 55](../55-application-stages/).

**Profile snapshot content** — `profile_snapshot` defaults to `'{}'` and is filled at submission time. Exactly what to freeze (and what not to), and when, is [Chapter 51](../51-application-snapshots/).

**Atomic submission** — submitting a shortlist creates multiple `applications` rows (one per job) in a single transaction. That transaction is [Chapter 52](../52-application-transaction/).

**Idempotent retry** — a network hiccup mid-submit must not create duplicate applications. The UNIQUE constraint catches the second insert at the DB level; [Chapter 53](../53-idempotent-application/) handles it gracefully in application code.

**The `interviews` table** — `applications` will be referenced by `interviews` once a recruiter schedules a call. That table arrives in [Chapter 56](../56-schedule-interview/).

**Indexes** — `applications.job_id`, `applications.applicant_id`, and `applications.stage` all need indexes. [Chapter 42](../42-indexing/).

**Migrations** — [Chapter 12](../12-migrations/).
