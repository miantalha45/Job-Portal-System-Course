# Three wrong approaches — and what breaks in each

## Wrong approach 1 — application per company

```sql
CREATE TABLE applications (
  id         uuid PRIMARY KEY,
  company_id uuid NOT NULL REFERENCES companies(id),
  applicant_id uuid NOT NULL REFERENCES applicants(id),
  ...
);
```

The rethink prompt already exposed this. Screening questions are defined per **job**, not per company. If a company has three open roles and an applicant applies to two of them, you have one application record for two sets of screening answers with no way to tell which answers belong to which job. The recruiter for the backend role can't see the backend answers; they can only see a blob of answers that might be for the data role.

Multi-tenant isolation also breaks: the same company-level record becomes visible anywhere the `company_id` is in scope, rather than being scoped to the specific job the recruiter is reviewing.

The fix: **one application per job** — the job is the unit that has the screening questions, the hiring manager, and the evaluation criteria.

## Wrong approach 2 — separate `screening_answers` table

```sql
CREATE TABLE screening_answers (
  id             uuid PRIMARY KEY,
  application_id uuid NOT NULL REFERENCES applications(id),
  question_id    text NOT NULL,  -- the UUID from jobs.screening_questions
  answer         text NOT NULL   -- everything forced to text
);
```

This normalises answers into rows. It looks tidy until you consider:

- **Answers are always read with the application** — every time you open an application, you load all its answers. That's always a join, never a lookup.
- **There's no `screening_questions` table to FK to** — the question IDs live in `jobs.screening_questions` JSONB, not in a relational table, so the `question_id` column is an unenforceable string.
- **`answer text` loses type fidelity** — a boolean answer (`true`) stored as the string `"true"` requires parsing back on every read. The JSONB approach preserves the original type.
- **You never query across answers** — you don't write "find all applications where the answer to question X was Y." Answers are displayed, not filtered.

A separate table earns its place only if answers need to be queried independently or reused across applications. Neither is true here.

## Wrong approach 3 — duplicate question text inside answers

```json
{
  "answers": [
    {
      "question": "Describe your distributed systems experience.",
      "answer": "I've worked with Kafka and Kubernetes for three years..."
    }
  ]
}
```

Storing the question text alongside the answer makes the application self-contained — but it's stale the moment a recruiter corrects a typo in the question. Now every previously submitted application shows the old question text while the job shows the corrected version. Matching a question to its answer across time requires comparing text, not a stable ID.

The fix: store only the **question UUID** as the key. The question text lives in `jobs.screening_questions` (the source of truth) and is fetched at display time. The UUID is stable even if the question text is later corrected for new applicants.
