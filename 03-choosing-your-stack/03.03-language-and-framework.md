# The language and the framework

Two decisions, both quick once you see the axis they turn on.

## Decision 1 — TypeScript, not plain JavaScript

You're on Node, so the fork is: plain JavaScript, or **TypeScript** (JavaScript with a type system layered on top, checked *before* your code runs).

Plain JS is faster to start — no build step, no annotations. For a weekend script, fine. For a job portal with companies, applications, and many moving parts, it disappoints fast: the bugs plain JS ships are exactly the costly ones — a `companyId` that's `undefined`, a screening-answer total that's the string `"3"` instead of the number `3`, a function called with the wrong shape. They surface at runtime, in front of an applicant, instead of at compile time, in front of you.

TypeScript catches that whole class before the code runs:

```ts
function scoreApplication(answerCount: number) { /* … */ }

scoreApplication("3");              // ❌ TS error: 'string' is not assignable to 'number'
scoreApplication(app.answerCount); // ❌ TS error if app.answerCount might be undefined
```

In plain JS both calls run happily, and you find out when the score comes back as `NaN`. TypeScript moves that discovery to your editor, and the types double as documentation — they tell the next developer (often future-you) what shape a function expects. That's why this course uses TypeScript, and why most serious Node teams do.

> **File this away now:** TypeScript's types exist only at *compile* time. They are **erased** before your code runs — at runtime there are no types at all. It sounds like a footnote; it's actually the reason Decision 4 (validation) exists. Hold the thought.

## Decision 2 — The web framework

Every Node web framework sits on one axis: **how much it does for you out of the box.**

- **Minimal** (e.g. **Express**) — routing and middleware, then it gets out of the way. Maximum freedom, maximum decisions, easy to make a mess if you're undisciplined.
- **Lean-modern** (e.g. **Fastify**) — Express's shape, but faster, with first-class TypeScript support and built-in schema-validation hooks. A strong middle ground.
- **Batteries-included** (e.g. **NestJS**) — a full structure: modules, dependency injection, conventions for everything. Less to decide, steeper learning curve, and the framework's opinions become your app's opinions.

You can *see* the axis in how you declare a route:

```ts
// Lean (Express / Fastify) — you wire each piece yourself, explicitly
app.get('/jobs', listJobs);

// Batteries-included (NestJS) — decorators and conventions do the wiring
@Controller('jobs')
class JobsController {
  @Get() list() { /* … */ }
}
```

Neither end is "better" — the top gives fewer surprises, the bottom gives more structure for free. The only real question is how much magic you want between your code and the request, because the more a framework does for you, the more you must understand when it breaks at 2 a.m.

**The mandate:** this course uses **Fastify** as its clean default — fast, typed, not too magical. **Express is perfectly fine** if it's what you already know. The point isn't the brand; it's that you can say *why* you landed where you did on that "how much does it do for me?" axis.
