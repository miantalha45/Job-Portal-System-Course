# Decision 4 — Validation, and the supporting cast

## Why a schema library, not just types

Remember the thought you filed away: **TypeScript's types vanish at runtime.** Here's why it matters now.

An applicant's browser (or a malicious script) sends your API a JSON body. TypeScript can *say* a request body is `{ jobId: string, answerCount: number }`, but that's a compile-time promise about *your* code — it does nothing to the bytes arriving over the network. At runtime that body could be anything: a missing `jobId`, an `answerCount` of `"three"`, a 10 MB string where you expected a short answer. Trust the type and skip a real check, and you've built validation on a guarantee that doesn't exist at the moment you need it.

So the production answer is a **runtime schema-validation library** — **zod** is the common TypeScript choice — that checks the *actual* incoming data at the boundary, and (bonus) infers the TypeScript type from the same schema, so compile-time and runtime truths can't drift apart:

```ts
// ❌ A TS type is ERASED before the request arrives — nothing checks the real bytes;
//    answerCount: "three" sails straight through.
type ApplyBody = { jobId: string; answerCount: number };

// ✅ A zod schema inspects the ACTUAL incoming data at the boundary…
const Apply = z.object({
  jobId: z.string().uuid(),
  answerCount: z.number().int().nonnegative(), // rejects "three", -1, 2.5
});
type Apply = z.infer<typeof Apply>;            // …and the type is INFERRED — one source of truth
```

You'll build this layer properly in the validation module ([Chapters 15–17](../15-validation-concept/)). For now the decision is simply: **validation is a real runtime step, done with a schema library — not the type system.**

## The supporting cast

A few more tools are already in your stack for reasons you'll meet later. Pick them now so the foundation is whole — one line each:

- **Redis** — an in-memory store that earns its place by **double duty**: it's your **cache** ([Module 9](../44-caching/), for hot reads) *and* the backbone of your **job queue** ([Week 4 Module 13](../62-why-async/)). One service, two jobs, fewer moving parts.
- **BullMQ** — a Redis-backed **job queue** that runs slow work (confirmation emails, résumé parsing, reports) in a separate worker instead of on the request. Note: it's a **job queue, not an event bus** — keep that distinction; event-driven architecture is out of scope.
- **S3-compatible object storage** — holds résumés, served by URL. **MinIO** runs an S3-compatible store locally; production uses real S3. Files don't belong in the database — you'll see exactly why in [Chapter 47](../47-files-concept/).
- **pino** — a structured (JSON) logger you'll wire up in Module 14.
- **Vitest** (or **Jest**) — your test runner.

You don't install these today; you've just chosen them and you know what each is *for*. Here's the whole stack at a glance — the shape of the dependencies you'll pull in over the course (illustration; exact names follow your framework/ORM picks):


Each one arrives in the chapter that needs it — this is just the map of where you're headed.
