# Decision 3 — How you talk to the database

This is the most consequential pick in the chapter, because the wrong instinct here causes pain for the whole project. There's a spectrum, from "you write every query" to "the tool writes them for you":

| Approach | What it is | The trade-off |
|---|---|---|
| **Raw SQL** | Every query is a hand-written SQL string | Total control, zero magic — but verbose, error-prone, and no type safety between your code and the result |
| **Query builder** (Drizzle, Knex) | You build SQL with typed function calls | Close to SQL, typed, predictable — you still think in queries |
| **ORM** (Prisma, TypeORM) | You work with objects; it generates the SQL | Fast to write, typed models — but it hides the SQL, which can hide performance problems |

The same query — *"jobs for this company"* — in each style (illustration; you'll write the real ones in Chapter 8):

```ts
// Raw SQL — you write the string and map the result yourself
const rows = await db.query('SELECT id, title FROM jobs WHERE company_id = $1', [companyId]);

// Query builder (Drizzle) — typed function calls, still clearly SQL-shaped
const rows = await db.select().from(jobs).where(eq(jobs.companyId, companyId));

// ORM (Prisma) — you ask for objects; it writes the SQL for you
const rows = await prisma.job.findMany({ where: { companyId } });
```

Read top to bottom and you watch the dial turn: most *control and visibility* at the top, most *convenience and abstraction* at the bottom. Neither end is wrong — but the extremes are where people get hurt. Two opposite temptations, and both disappoint:

- **Hand-roll everything in raw SQL** because "real engineers write SQL." Productive for a day, then you drown in string-concatenated queries with no type safety, and you reinvent migrations, connection pooling, and result mapping — badly.
- **Reach for a full ORM and let it do everything**, treating the database as invisible. Faster to write — until the ORM quietly issues *one query per item in a loop* (the **N+1 problem**, [Chapter 40](../40-n-plus-1/)) and your job board fires 200 queries while you wonder why it's slow. The ORM didn't create the problem; it made it *easy not to notice*.

**The mandate:** use a **typed ORM or query builder** for the productivity and type-safety — **Prisma** (excellent DX, typed client, first-class migrations) or **Drizzle** (lighter, SQL-first, typed) are both strong picks — **but keep your SQL literacy sharp** enough to know what it's doing underneath. The tool writes the boilerplate; *you* stay responsible for the queries it generates. Whichever you pick, the rule holds: never let the abstraction stop you from seeing and reasoning about the actual SQL.
