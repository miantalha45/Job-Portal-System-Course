# The auth anchor — the `users` table

The `users` table is not a profile table. It holds exactly what every account has in common, and nothing role-specific:

```sql
CREATE TABLE users (
  id            uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  email         text        NOT NULL UNIQUE,
  password_hash text        NOT NULL,   -- salted slow hash; hashing covered in ch19
  role          text        NOT NULL
                              CHECK (role IN ('recruiter', 'applicant', 'admin')),
  status        text        NOT NULL DEFAULT 'unverified'
                              CHECK (status IN ('active', 'unverified', 'suspended')),
  created_at    timestamptz NOT NULL DEFAULT now()
);
```

## Why a separate `users` table at all?

Auth is the same question regardless of role: *does this email + password combination match a stored account?* If you scatter `email` and `password_hash` across `recruiters`, `applicants`, and `admins` (wrong approach 2 from the previous sub-chapter), every login has to search three tables. With a single `users` table, login always queries one place.

## The `role` column

`role` is stored here, on the auth record, for the same reason: when a user logs in and receives a JWT, the token needs to carry the role so the auth middleware can enforce access control. That decision is made once, at login, from the one row that always exists regardless of profile completeness.

**One account, one role** is a deliberate product decision. An engineering recruiter who also wants to apply for jobs elsewhere needs two separate accounts. This trades flexibility for simplicity — role isolation means auth rules, route protection, and query scoping are all straightforward to reason about. If you ever needed to relax this, the migration path is clear: add a `roles text[]` column to `users` and update the auth middleware.

## The `status` column

Three states:

| Status | Meaning | Transition |
|---|---|---|
| `unverified` | Registered but email not yet confirmed | → `active` after email OTP verified (ch23); → `suspended` by admin before verification (ch52) |
| `active` | Normal operating state | → `suspended` by admin action (ch52) |
| `suspended` | Account blocked by admin | → `active` if reinstated (ch52) |

Status lives on `users` because it's an account-level decision. Suspending a recruiter suspends their login, not their company.

The column is `NOT NULL` from day one — every account must have a credential. What exactly goes in there (bcrypt hash, salt, work factor) is [Chapter 19](../19-password-hashing/)'s job.
