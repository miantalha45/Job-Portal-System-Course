# Three tempting approaches — and what breaks in each

Before designing the right schema, it's worth naming the designs that feel natural at first but fail under pressure.

## Wrong approach 1 — one fat `users` table

Put every account type in a single table, with nullable columns for role-specific data:

```sql
CREATE TABLE users (
  id           uuid PRIMARY KEY,
  email        text UNIQUE,
  role         text,           -- 'recruiter' | 'applicant' | 'admin'
  company_name text,           -- NULL for applicants and admins
  company_id   uuid,           -- NULL for applicants and admins
  full_name    text,           -- NULL for recruiters and admins
  headline     text,           -- NULL for recruiters and admins
  skills       text[],         -- NULL for recruiters and admins
  ...
);
```

This looks simple. It doesn't stay simple:

- Every recruiter row has `full_name = NULL`, `headline = NULL`, `skills = NULL`. The schema can't enforce that applicants always have `full_name` — the columns exist on every row whether they apply or not.
- Every applicant row has `company_name = NULL`, `company_id = NULL`. A recruiter with no company is representable; the schema can't stop it.
- The table grows a new column every time a role needs a new field, and that column is NULL for everyone else. This pattern is called a **sparse table** and it's a maintenance trap.

## Wrong approach 2 — separate tables per role with no shared auth table

Three independent tables, each with their own `email` and `password_hash`:

```sql
CREATE TABLE recruiters  (id uuid, email text UNIQUE, password_hash text, company_id uuid, ...);
CREATE TABLE applicants  (id uuid, email text UNIQUE, password_hash text, ...);
CREATE TABLE admins      (id uuid, email text UNIQUE, password_hash text, ...);
```

Email uniqueness is now per-table, not global. The same email address could register as both a recruiter and an applicant — two different accounts, two different passwords. When a login request arrives with an email and password, your auth code doesn't know which table to check first. You query all three and pick the match — a three-table scan on every login. When you add a fourth role, you update the auth code again.

## Wrong approach 3 — embed company data on the recruiter row

Keep a single `users` table and store company information directly on the recruiter's row:

```sql
CREATE TABLE users (
  id           uuid PRIMARY KEY,
  email        text UNIQUE,
  role         text,
  company_name text,   -- recruiter only
  company_slug text,   -- recruiter only
  ...
);
```

A company is now just a property of a user. When a second recruiter joins the same company, you copy `company_name` and `company_slug` onto their row. Now it's duplicated. When the company rebrands, you update every recruiter row. When an admin needs to suspend the company, there's no company row to flip a flag on — you suspend each recruiter individually and hope you got them all.

The company is a real entity in this system: it has its own name, its own jobs, its own moderation state. It deserves its own table.

---

The pattern that avoids all three problems: a shared **auth anchor** table every account type references, with separate **profile tables** for each role. That's what the next sub-chapter builds.
