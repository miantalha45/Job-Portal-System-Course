# The four profile tables

Each role has its own profile table that stores only what's relevant to that role, linked back to `users` via `user_id`. Auth always goes through `users`; profile data lives in the role-specific table.

## Companies

A company is a first-class entity — not a property of a recruiter:

```sql
CREATE TABLE companies (
  id         uuid    PRIMARY KEY DEFAULT gen_random_uuid(),
  name       text    NOT NULL,
  slug       text    NOT NULL UNIQUE,   -- URL-friendly: 'acme-corp', 'nova-labs'
  website    text,
  verified   boolean NOT NULL DEFAULT false,
  suspended  boolean NOT NULL DEFAULT false,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

`slug` is the URL-safe identifier used in public routes (`/companies/acme-corp/jobs`). It's separate from `name` because names can contain characters that don't belong in URLs, and names can change while the slug stays stable.

`verified` and `suspended` are admin moderation flags (built in [Chapter 59](../59-admin-moderation-companies/)). They belong on the company entity, not on each recruiter's `users` row — suspending a company affects all its jobs in one operation, because the company row is the single point of control. One thing to be aware of: the schema does not automatically propagate `companies.suspended` to block recruiter logins. When a company is suspended, the auth layer must check both `users.status` and the recruiter's `companies.suspended` — you'll wire that check in [Chapter 59](../59-admin-moderation-companies/).

## Recruiters

A recruiter is a user who belongs to a company:

```sql
CREATE TABLE recruiters (
  id           uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id      uuid NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  company_id   uuid NOT NULL REFERENCES companies(id),
  company_role text NOT NULL DEFAULT 'recruiter'
                 CHECK (company_role IN ('owner', 'hr_manager', 'recruiter', 'hiring_manager')),
  created_at   timestamptz NOT NULL DEFAULT now()
);
```

`company_id` is here, on the recruiter, because the relationship is *recruiter belongs to company* — many recruiters, one company. A recruiter without a company is not a valid state; `NOT NULL` enforces that.

`ON DELETE CASCADE` on `user_id`: if the `users` row is deleted (hard-delete path in ch52), the recruiter profile goes with it. The `companies` reference does **not** cascade — deleting a company should be an explicit, considered operation, not something that triggers silently from a recruiter deletion.

`company_role` is the within-company role — what this person is allowed to do inside the workspace. `owner` has full control (invite/remove members, all job operations). `hr_manager` can manage members and jobs. `recruiter` can post and edit jobs. `hiring_manager` can review applications and move applicants through stages but cannot post new jobs. The permission matrix is enforced in the service layer (ch32). The first recruiter to open a company workspace is automatically assigned `owner`.

## Applicants

An applicant is a user with a profile:

```sql
CREATE TABLE applicants (
  id         uuid  PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    uuid  NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  full_name  text  NOT NULL,
  headline   text,
  location   text,
  attributes jsonb NOT NULL DEFAULT '{}',
  created_at timestamptz NOT NULL DEFAULT now()
);
```

`full_name` is a real column — it's displayed everywhere (recruiter's inbox, application list) and sorted. `headline` and `location` are optional and never queried across the board, so `NULL` is fine there.

`attributes` JSONB holds per-person free-form data: skills list, portfolio links, years of experience. The same column-vs-JSONB split from [Chapter 2](../02-why-relational/) applies: things you filter on get real columns; things you only display live in JSONB. Résumé file references join the picture in [Chapter 48](../48-object-storage-uploads/).

## Admins

Admins are platform operators. Their profile is deliberately minimal — elevated privilege, not a rich profile:

```sql
CREATE TABLE admins (
  id         uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    uuid NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE,
  created_at timestamptz NOT NULL DEFAULT now()
);
```

If you need per-admin metadata later (name, last-active timestamp), you add columns here. For now, the `users` row carries everything the admin experience needs.
