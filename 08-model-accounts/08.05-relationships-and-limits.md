# Relationships, rules, and what's deliberately deferred

## The entity map

```
users (1) ──── (0..1) recruiters (N) ──── (1) companies
users (1) ──── (0..1) applicants
users (1) ──── (0..1) admins

companies (1) ──── (N) jobs          ← Chapter 9
jobs      (1) ──── (N) applications  ← Chapter 10
applicants (1) ──── (N) applications ← Chapter 10
```

Every `users` row has exactly one role. Because of that, each user row links to at most one of `recruiters`, `applicants`, or `admins` — whichever matches their role. This is enforced by application logic in the register flow, not by the schema alone. [Chapter 11](../11-foreign-keys-and-constraints/) discusses where constraint enforcement lives.

## Rules the schema enforces right now

| Rule | How it's enforced |
|---|---|
| Email is unique across all accounts | `UNIQUE` on `users.email` |
| One profile per user (no duplicate recruiters/applicants/admins) | `UNIQUE` on `user_id` in each profile table |
| Every recruiter belongs to a company | `NOT NULL` on `recruiters.company_id` |
| Every applicant has a name | `NOT NULL` on `applicants.full_name` |
| Role is one of three values | `CHECK` on `users.role` |
| Status is one of three values | `CHECK` on `users.status` |
| Company slug is unique | `UNIQUE` on `companies.slug` |

## What's deliberately NOT in this chapter

**Password hashing** — `password_hash` is `NOT NULL` in the DDL, but what goes in that column (bcrypt, argon2, work factor, salted rounds) is [Chapter 19](../19-password-hashing/)'s entire job. Don't try to fill it in yet.

**`ON DELETE` decisions for companies** — the `recruiters.company_id` FK deliberately has no `ON DELETE` clause here. What should happen when a company is deleted? That requires a design decision (restrict, cascade, set null), and [Chapter 11](../11-foreign-keys-and-constraints/) works through it properly.

**Indexes** — `users.email` is queried on every login and needs an index; `recruiters.company_id` is filtered on every recruiter-scoped query. The `UNIQUE` constraints imply indexes, but explicit index design is [Chapter 42](../42-indexing/).

**Migration files** — this chapter gives you the DDL to reason about. [Chapter 12](../12-migrations/) turns it into versioned, committed migration files you can run and roll back. Don't run raw `CREATE TABLE` commands yet.

**Jobs and applications** — `companies` has no `jobs` here because that table arrives in [Chapter 9](../09-model-job-postings/). Similarly, `applicants` references no `applications` yet — that's [Chapter 10](../10-model-applications/).
