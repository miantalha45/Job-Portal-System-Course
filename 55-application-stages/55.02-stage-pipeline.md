# 55.02 — Stage Pipeline: Design Notes

## Stages as a finite state machine

The application stage pipeline is a finite state machine (FSM). An FSM has:
- A finite set of states (the stages)
- A set of valid transitions between states
- An initial state (`applied`)
- Terminal states (`hired`, `rejected`)

Encoding the FSM as an ordered array (`STAGE_ORDER`) is the simplest correct approach for a linear pipeline. The ordering encodes the constraint: only forward transitions are valid. `STAGE_ORDER.indexOf(current) < STAGE_ORDER.indexOf(target)` is the entire validation logic for forward-only movement.

The exception — `rejected` is reachable from any non-terminal stage — breaks the pure linear ordering. Handling it with an explicit condition (`if (target === 'rejected') return`) is cleaner than trying to position `rejected` in the array such that all transitions are naturally forward.

---

## Why backward transitions are blocked

A recruiter moving an application from `offer` back to `interview` would create confusion:

- Interview notes were recorded for the interview stage — they are already done
- The applicant may have already received an offer letter — walking it back sends a contradictory signal
- Analytics and reporting assume stages are monotonically increasing — a backward move breaks pipelines that count "time in stage"

If a recruiter genuinely needs to reverse a decision, the correct action is to start a new application cycle or document the reason as a note on the interview/offer record. The stage pipeline moves in one direction.

---

## Terminal stages and the status field

`hired` and `rejected` are terminal — no further stage transitions are possible. However, the `status` field provides a separate dimension:

| stage    | status      | Meaning |
|----------|-------------|---------|
| applied  | active      | Live application in the pipeline |
| rejected | active      | Rejected by recruiter |
| applied  | withdrawn   | Applicant withdrew their application |

`status = 'withdrawn'` is set by the applicant (a future endpoint). The stage pipeline endpoint rejects requests to change the stage of a withdrawn application — there is no point advancing a withdrawn application.

---

## The `indexOf` lookup and performance

`STAGE_ORDER.indexOf(stage)` is a linear scan over a 7-element array. The performance impact is negligible — this is not a hot loop over large data. If the stage set ever grew to hundreds of entries (unlikely for a hiring pipeline), switch to a `Map<Stage, number>` for O(1) lookup.

---

## Ownership scoping — the JOIN-based check

```sql
SELECT a.id, a.job_id, a.applicant_id, a.stage, a.status
FROM applications a
JOIN jobs j ON j.id = a.job_id
WHERE a.id = $1 AND j.company_id = $2
```

This query returns a row only if the application exists AND the job belongs to the recruiter's company. If either condition fails, `rows[0]` is `undefined` and the service throws `NotFoundError`.

Returning `NotFoundError` (not `ForbiddenError`) when the application exists but belongs to another company is a deliberate security choice. It avoids leaking the existence of applications to recruiters at other companies. A recruiter who probes for application IDs gets 404s — indistinguishable from "this ID does not exist."

This is the same IDOR pattern from Chapter 29.

---

## Skipping stages

The transition validation allows skipping stages. A recruiter can move an application from `applied` directly to `offer` if they choose. The validation only enforces forward movement, not step-by-step progression.

Whether to enforce step-by-step movement is a product decision. Some hiring pipelines require every stage to be visited (e.g., every offer must go through an interview). Enforcing this in the service requires more complex transition rules — a graph or a transition table rather than an ordered array.

For this course, skipping is allowed. The ordered-array approach remains correct and minimal.
