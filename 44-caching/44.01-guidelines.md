# Chapter 44 — Caching Hot Reads with Redis

## What you will build

Cache the first page of `GET /api/public/jobs` (no filters) in Redis. Measure the speedup between a cache miss (first request) and a cache hit (subsequent requests).

## Learning goals

- Apply the cache-aside (read-through) pattern to an Express endpoint
- Use the existing `redis` client from `src/shared/redis.ts`
- Serialise and deserialise JSON for Redis storage
- Decide when to bypass the cache (filtered requests)
- Measure cache speedup with `curl` timing

## Prerequisites

- Chapter 39: public board built
- Redis running and `src/shared/redis.ts` exports a connected client
- `config.ts` has or will have a `CACHE_TTL_SECONDS` value

## Files you will modify

```
src/shared/config.ts                   ← add CACHE_TTL_SECONDS
src/modules/public/publicService.ts    ← cache-aside logic
```

No new files are created — the Redis client is already set up.

## The cache key

`'jobs:public:page1'`

Only the unfiltered first page is cached. Any request with `q`, `location`, `employment_type`, or `cursor` bypasses the cache and goes directly to PostgreSQL.

## Why only the first page

The first page of the public board is the page that every visitor sees. It is by far the most-requested page. Subsequent pages and filtered results are much less frequent and vary in shape — caching them provides diminishing returns and would require many more cache keys to manage.

## The TTL

`CACHE_TTL_SECONDS` defaults to 60 seconds. A new job that is published will appear on the board within at most 60 seconds without any manual cache invalidation. Chapter 45 shortens this latency to near-zero by invalidating the cache on write.

## The cache-aside pattern

```
Request arrives
→ Check Redis for cached result
→ Cache hit: return JSON from Redis (no DB query)
→ Cache miss: query PostgreSQL, store result in Redis with TTL, return result
```

The cache sits beside the database — it does not sit between the application and the database as a proxy. The application controls what goes in and what stays out.

## No `process.env` in the service

The service imports `config` from `../../shared/config` and reads `config.cacheTtlSeconds`. It does not read `process.env` directly.
