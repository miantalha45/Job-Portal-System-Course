## 2. Cache miss populates the key

Flush any existing key first:

```bash
redis-cli DEL jobs:public:page1
```

Make one request:

```bash
curl -s http://localhost:3000/api/public/jobs > /dev/null
```

Confirm the key now exists:

```bash
redis-cli EXISTS jobs:public:page1
```

Expected: `1`.

## 3. The key holds valid JSON

```bash
redis-cli GET jobs:public:page1 | jq '.jobs | length'
```

Expected: the number of open jobs (at least 1 if you have open jobs from a verified company).

## 4. The TTL is set

```bash
redis-cli TTL jobs:public:page1
```

Expected: a positive integer between 1 and 60. If the value is `-1` (no TTL) or `-2` (key missing), the `EX` option was not applied correctly.

## 5. Cache hit is faster than cache miss

```bash
# Flush the cache, time the miss
redis-cli DEL jobs:public:page1
curl -s -o /dev/null -w "Cache miss: %{time_total}s\n" http://localhost:3000/api/public/jobs

# Time the hit (no DEL)
curl -s -o /dev/null -w "Cache hit:  %{time_total}s\n" http://localhost:3000/api/public/jobs
```

Expected: cache hit time is meaningfully lower than cache miss time. On localhost the difference may be small (PostgreSQL is also local), but the hit should still be at least 2x faster.

## 6. Filtered requests bypass the cache

Make a filtered request, then check that the cache key still holds the unfiltered result:

```bash
# Flush cache
redis-cli DEL jobs:public:page1

# Filtered request — should NOT populate the cache
curl -s "http://localhost:3000/api/public/jobs?q=engineer" > /dev/null

redis-cli EXISTS jobs:public:page1
```

Expected: `0` — the filtered request did not write to the cache.

Now make an unfiltered request:

```bash
curl -s http://localhost:3000/api/public/jobs > /dev/null
redis-cli EXISTS jobs:public:page1
```

Expected: `1` — the unfiltered request populated the cache.

---

## 7. Cursor requests bypass the cache

```bash
redis-cli DEL jobs:public:page1

CURSOR=$(curl -s "http://localhost:3000/api/public/jobs?limit=1" | jq -r '.nextCursor')
curl -s "http://localhost:3000/api/public/jobs?limit=1&cursor=$CURSOR" > /dev/null

redis-cli EXISTS jobs:public:page1
```

Expected: `0` — paginated requests do not populate the cache.

```bash
grep -n 'cacheTtlSeconds\|CACHE_TTL' src/shared/config.ts
```

Expected: `cacheTtlSeconds: parseInt(process.env.CACHE_TTL_SECONDS ?? '60', 10)` appears in `config.ts`. The service reads `config.cacheTtlSeconds`, not `process.env` directly.

## 9. Cached response is identical to uncached

```bash
# Flush, get a fresh response directly from DB
redis-cli DEL jobs:public:page1
UNCACHED=$(curl -s http://localhost:3000/api/public/jobs)

# Next request is from cache
CACHED=$(curl -s http://localhost:3000/api/public/jobs)

# Compare
[ "$UNCACHED" = "$CACHED" ] && echo "MATCH" || echo "MISMATCH"
```

Expected: `MATCH` — the cached response is byte-for-byte identical to the DB response.

---

## 10. Cache expires and repopulates automatically

```bash
# Set a very short TTL for testing (override config temporarily)
# Instead, just wait for the natural expiry and re-verify

redis-cli TTL jobs:public:page1
# ... wait until the key expires ...
redis-cli EXISTS jobs:public:page1
```

Expected: `0` after TTL expires. On the next request, the cache is repopulated.

(In development, you can temporarily set `CACHE_TTL_SECONDS=5` in your `.env` to shorten the wait.)

## Quiz

**Q1.** The cache-aside pattern checks Redis first, then PostgreSQL on a miss. An alternative is the write-through pattern: when a job is published, the service immediately writes the new job board result to Redis rather than waiting for the next cache miss. Compare these two patterns on: implementation complexity, consistency guarantees, and behaviour during Redis downtime.

**Q2.** The current implementation uses `redis.get` and `redis.set` as two separate operations. If two requests arrive simultaneously during a cache miss (before either has written to Redis), both will query PostgreSQL and both will write the result to Redis. Explain why this is usually acceptable (as opposed to a bug), and describe a scenario where it could cause a problem. What Redis primitive would you use to prevent it?

**Q3.** `config.cacheTtlSeconds` defaults to 60 seconds. Without Chapter 45's active invalidation, a job published at second 0 could remain absent from the public board until second 60. Describe the impact of this latency on: the recruiter experience (they just published a job), the applicant experience (they are browsing the board), and search engine crawlers. Then explain how Chapter 45 eliminates this problem.
