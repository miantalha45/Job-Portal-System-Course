# What seed data is

## The problem with an empty database

Every feature you build in this project interacts with data: listing jobs, showing applications, filtering by stage, paginating results. Testing these features against an empty database tells you your endpoint runs — not that it works. A job listing with zero jobs, a recruiter inbox with no applications, an applicant view with no stage history — none of these surface the real behavior.

Seed data is a script that populates the database with a representative set of records you control. It is not fake data generated at random — it is a deliberate fixture: specific users with known credentials, specific companies with known states, specific jobs and applications at specific stages. Because you wrote it, you know exactly what the correct response should be for any query, which means a wrong response is immediately visible.

## Seed data vs production data

Seed data is a development tool. It:
- Uses well-known credentials (password `password123`) so every developer can log in without environment setup
- Is wiped and reloaded whenever you run the script — changes are intentional, not accidents
- Is committed to the repository so everyone on the team starts from the same state

Production data is the opposite: real credentials, never wiped, never committed, never shared.

## The correct scope

Seed data should be large enough to exercise every feature you plan to build — and no larger. For this portal that means:

- At least two companies (so multi-tenant isolation has something to test)
- At least two recruiters in different companies (so company-scoped queries are testable)
- At least one job in draft and at least one that is open (so status filtering works)
- At least three applicants (so the recruiter inbox has meaningful data)
- Applications at different stages (so stage pipeline logic has test cases)
- One admin (so the admin panel has someone to log in)
