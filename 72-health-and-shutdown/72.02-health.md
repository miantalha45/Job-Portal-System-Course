# 72.02 — Health, Readiness & Graceful Shutdown (Walkthrough)

## The two health endpoints and why they are different

### /health (liveness)

A liveness endpoint answers: "Is the process alive?" It should always return 200 as long as
the Node.js event loop is running. It should never check external dependencies.

If `/health` returned 503 because the database was down, Kubernetes would restart the container.
But restarting the container does not fix the database — you would be in a restart loop while
the database recovers. A bad liveness implementation makes an outage worse.

Correct behaviour: `/health` returns 200. The container stays running. The database recovers
on its own. Traffic resumes when `/ready` returns 200.

### /ready (readiness)

A readiness endpoint answers: "Is this instance ready to serve traffic?" It checks all external
dependencies the application needs to function.

For this system: PostgreSQL (`SELECT 1`) and Redis (`PING`). Both must respond for the
instance to be considered ready.

When a readiness check fails, the load balancer removes the instance from the pool. New
requests go to other healthy instances. The failing instance stays running, waiting for its
dependencies to recover.

## Building it step by step

### Step 1 — Create src/routes/health.ts

```ts
router.get('/health', (_req, res) => {
  res.json({ status: 'ok' });
});
```

No async, no DB calls, no Redis calls. Returns immediately.

```ts
router.get('/ready', async (_req, res) => {
  const checks = { db: 'ok', redis: 'ok' };
  let statusCode = 200;

  try {
    const client = await pool.connect();
    await client.query('SELECT 1');
    client.release();
  } catch {
    checks.db = 'error';
    statusCode = 503;
  }

  try {
    await redis.ping();
  } catch {
    checks.redis = 'error';
    statusCode = 503;
  }

  res.status(statusCode).json({ status: statusCode === 200 ? 'ok' : 'error', checks });
});
```

Two independent try/catch blocks. A Redis failure does not prevent the DB check from running —
you want to know which dependency failed, not just that something failed.

### Step 2 — Mount before auth middleware

```ts
app.use(healthRouter);   // no auth, no rate limiting
app.use(globalLimiter);
app.use('/api/auth', authRouter);
```

The health endpoints must be reachable by Kubernetes probes, which do not have auth tokens.
Mount them before `authMiddleware` and before the global limiter (health checks should not be
rate limited — they can fire frequently in production).

### Step 3 — Graceful shutdown in src/index.ts

The SIGTERM pattern:

```ts
const server = app.listen(config.PORT);

process.on('SIGTERM', () => {
  server.close(async () => {
    await pool.end();
    await redis.quit();
    process.exit(0);
  });

  setTimeout(() => process.exit(1), 5000);
});
```

`server.close()` stops accepting new connections but lets existing connections finish. The
callback fires when all connections are closed. The 5-second timeout forces exit if some
connection is hung (e.g., a long-polling client).

### Step 4 — Graceful shutdown in worker.ts

```ts
process.on('SIGTERM', async () => {
  await worker.close();
  process.exit(0);
});
```

`worker.close()` waits for the current job to finish (up to the `closingTimeout`). In-progress
jobs are not lost. Jobs that were waiting are not affected — they stay in Redis.

## Testing graceful shutdown

```bash
# Start the API
npm run dev &
API_PID=$!

# Send a long-running request (if you have one)
# Then send SIGTERM and confirm the response still arrives
kill -SIGTERM $API_PID

# Expected log output:
# SIGTERM received — starting graceful shutdown
# HTTP server closed — cleaning up
# DB pool closed
# Redis connection closed
# Graceful shutdown complete
```

## Docker Compose health check

In `docker-compose.yml` or `docker-compose.prod.yml`:

```yaml
api:
  healthcheck:
    test: ["CMD", "curl", "-f", "http://localhost:3000/health"]
    interval: 30s
    timeout: 5s
    retries: 3
    start_period: 10s
```

Docker waits `start_period` before starting health checks (allows the app to boot). After that,
checks run every 30 seconds. Three consecutive failures mark the container as unhealthy.
