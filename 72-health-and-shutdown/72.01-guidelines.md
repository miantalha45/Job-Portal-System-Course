# Chapter 72 — Health, Readiness & Graceful Shutdown

## What you will build

Two health check endpoints (`/health` and `/ready`) and graceful shutdown handlers for both
the API server and the BullMQ worker.

## Learning goals

- Distinguish liveness from readiness: what each endpoint means to an orchestrator
- Implement readiness checks against PostgreSQL and Redis
- Handle SIGTERM cleanly so in-flight requests complete before the process exits

## Prerequisites

- Chapter 63: worker process in place
- `pool` exported from `src/shared/db.ts` (for `SELECT 1` check and clean shutdown)
- `redis` exported from `src/shared/redis.ts`

## Implementation

### src/routes/health.ts

```ts
import { Router } from 'express';
import { pool } from '../shared/db';
import { redis } from '../shared/redis';

const router = Router();

// Liveness: always 200 if the process is running
router.get('/health', (_req, res) => {
  res.json({ status: 'ok' });
});

// Readiness: checks DB and Redis before serving traffic
router.get('/ready', async (_req, res) => {
  const checks: { db: string; redis: string } = { db: 'ok', redis: 'ok' };
  let statusCode = 200;

  try {
    const client = await pool.connect();
    await client.query('SELECT 1');
    client.release();
  } catch {
    checks.db = 'error';
    statusCode = 503;
  }

  try {
    await redis.ping();
  } catch {
    checks.redis = 'error';
    statusCode = 503;
  }

  res.status(statusCode).json({ status: statusCode === 200 ? 'ok' : 'error', checks });
});

export default router;
```

### src/index.ts — server startup and SIGTERM

```ts
import { pool } from './shared/db';
import { redis } from './shared/redis';
import logger from './shared/logger';

const server = app.listen(config.PORT, () => {
  logger.info({ port: config.PORT }, 'API server started');
});

process.on('SIGTERM', () => {
  logger.info('SIGTERM received — starting graceful shutdown');

  // Stop accepting new connections
  server.close(async () => {
    logger.info('HTTP server closed — cleaning up');

    try {
      await pool.end();
      logger.info('DB pool closed');
    } catch (err) {
      logger.error({ err }, 'Error closing DB pool');
    }

    try {
      await redis.quit();
      logger.info('Redis connection closed');
    } catch (err) {
      logger.error({ err }, 'Error closing Redis');
    }

    logger.info('Graceful shutdown complete');
    process.exit(0);
  });

  // Force exit after 5 seconds if requests are still in flight
  setTimeout(() => {
    logger.error('Graceful shutdown timeout — forcing exit');
    process.exit(1);
  }, 5000);
});
```

### src/worker/worker.ts — worker SIGTERM

```ts
process.on('SIGTERM', async () => {
  logger.info('Worker SIGTERM received — closing');
  await worker.close();
  logger.info('Worker closed');
  process.exit(0);
});
```

`worker.close()` waits for the currently processing job to complete before shutting down.
No in-progress job is lost.

## Liveness vs readiness

| Check | URL | Purpose | Fails if... |
|-------|-----|---------|-------------|
| Liveness | `/health` | Is the process alive? | Process is dead |
| Readiness | `/ready` | Can it serve traffic? | DB or Redis unreachable |

Kubernetes uses liveness to decide whether to restart a container. It uses readiness to decide
whether to send traffic to a container. A failing readiness check removes the container from
the load balancer pool without restarting it — useful when the DB is temporarily overloaded.
