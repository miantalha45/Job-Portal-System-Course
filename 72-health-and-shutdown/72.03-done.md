# Chapter 72 — Definition of Done

## Verifiable checklist

```bash
# 1. TypeScript compiles with zero errors
npx tsc --noEmit

# 2. /health returns 200 with { status: 'ok' }
curl -s http://localhost:3000/health | jq '.'
# Expected: { "status": "ok" }

curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/health
# Expected: 200

# 3. /ready returns 200 with checks when DB and Redis are up
curl -s http://localhost:3000/ready | jq '.'
# Expected:
# { "status": "ok", "checks": { "db": "ok", "redis": "ok" } }

# 4. /ready returns 503 when Redis is stopped
redis-cli SHUTDOWN NOSAVE 2>/dev/null || true   # stop Redis
sleep 1
curl -s http://localhost:3000/ready | jq '.'
# Expected:
# { "status": "error", "checks": { "db": "ok", "redis": "error" } }
# HTTP status: 503

curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/ready
# Expected: 503

# 5. Restart Redis and confirm /ready returns 200 again
redis-server --daemonize yes
sleep 2
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/ready
# Expected: 200

# 6. /health does NOT require authentication
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/health
# Expected: 200 (no token needed)

# 7. /ready does NOT require authentication
curl -s -o /dev/null -w "%{http_code}" http://localhost:3000/ready
# Expected: 200 or 503 (never 401)

# 8. SIGTERM causes graceful shutdown of the API
npm run dev &
API_PID=$!
sleep 3
kill -SIGTERM $API_PID
# Expected log output (in the terminal or log file):
# SIGTERM received — starting graceful shutdown
# HTTP server closed — cleaning up
# DB pool closed
# Redis connection closed
# Graceful shutdown complete
# (Process exits with code 0)
echo "Exit code: $?"

# 9. SIGTERM causes graceful worker shutdown
npm run worker &
WORKER_PID=$!
sleep 3
kill -SIGTERM $WORKER_PID
# Expected: Worker closed log line, process exits 0

# 10. Health check response has no X-Powered-By header
# (This is verified in Chapter 73 — note it here for cross-chapter awareness)
curl -sI http://localhost:3000/health | grep -i powered
# Expected: no output (after Chapter 73)
```

## Quiz

1. The readiness check uses `pool.connect()` → `client.query('SELECT 1')` → `client.release()`.
   What happens to the connection pool if `client.release()` is never called (e.g., because the
   `query` throws and the catch block does not release the client)? How would you fix this with
   a `try/finally` block?

2. Kubernetes sends SIGTERM and then waits `terminationGracePeriodSeconds` (default: 30 seconds)
   before sending SIGKILL. The server's `setTimeout(..., 5000)` forces exit after 5 seconds.
   What happens if a request is still in flight when the 5-second timeout fires? Is `process.exit(1)`
   the right exit code, and what does Kubernetes do differently with exit code 0 vs 1?

3. The worker's `worker.close()` waits for the current job to finish. What is the default
   `closingTimeout` in BullMQ? What happens to a job that is still running when the timeout
   expires — does BullMQ mark it as failed, or leave it in the active state so another worker
   picks it up?
