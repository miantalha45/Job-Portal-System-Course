# Chapter 63 — Setting Up the Queue & a Worker

## What you will build

A BullMQ `Queue` instance shared across the Express API (for enqueuing jobs) and a separate
`Worker` entry point (for processing jobs). The worker runs as its own Node.js process.

## Learning goals

- Understand why the queue and the worker need separate Redis connections
- Set up a worker entry point that is independent of the Express app
- Handle unknown job names gracefully so a bad job name does not crash the worker

## Prerequisites

- Chapter 6: `config.ts` with `REDIS_URL`
- `src/shared/redis.ts` exists and exports the Redis client
- `npm install bullmq` done

## Implementation

### src/shared/queue.ts

```ts
import { Queue } from 'bullmq';
import config from './config';

// All background jobs go into this single queue
export type JobName =
  | 'send-application-confirmation'
  | 'send-interview-notification'
  | 'process-resume'
  | 'cleanup-expired-otps'
  | 'cleanup-expired-refresh-tokens'
  | 'send-recruiter-digest';

// BullMQ Queue uses its own Redis connection (not the shared cache client)
const queue = new Queue('jobs', {
  connection: { url: config.REDIS_URL },
});

export default queue;
```

**Why a separate connection?** The shared Redis client from `src/shared/redis.ts` is used for
cache reads and writes (GET, SET, DEL). BullMQ internally uses blocking Redis commands
(`BLPOP`, Lua scripts) that are incompatible with a client also used for regular commands.
BullMQ requires its own dedicated connection per Queue and per Worker instance.

### src/worker/worker.ts

```ts
import { Worker, Job } from 'bullmq';
import config from '../shared/config';
import { JobName } from '../shared/queue';

// Worker connection must be separate from the Queue connection
const worker = new Worker(
  'jobs',
  async (job: Job) => {
    console.log(`[worker] Processing job ${job.name} (id: ${job.id})`);

    switch (job.name as JobName) {
      // Handlers will be added in chapters 64–69
      default:
        console.warn(`[worker] Unknown job name: ${job.name}. Skipping.`);
    }
  },
  {
    connection: { url: config.REDIS_URL },
    concurrency: 5,
  }
);

worker.on('completed', (job) => {
  console.log(`[worker] Job completed: ${job.name} (id: ${job.id})`);
});

worker.on('failed', (job, err) => {
  console.error(`[worker] Job failed: ${job?.name} (id: ${job?.id})`, err.message);
});

console.log('[worker] Worker started and listening for jobs...');
```

The `default` case in the switch logs a warning and does nothing (returns undefined). BullMQ
considers a job completed when the handler resolves. Returning undefined from `default` marks
the job as completed — which is correct for unknown jobs (they should not be retried).

### package.json

```json
{
  "scripts": {
    "dev": "ts-node src/index.ts",
    "worker": "ts-node src/worker/worker.ts",
    "build": "tsc",
    "start": "node dist/index.js",
    "start:worker": "node dist/worker/worker.js"
  }
}
```

## Smoke test

Open two terminals:

```bash
# Terminal 1 — start the Express API
npm run dev

# Terminal 2 — start the worker
npm run worker
# Expected output:
# [worker] Worker started and listening for jobs...
```

Add a test job from a REPL or a temporary route:

```ts
import queue from '../shared/queue';
await queue.add('send-application-confirmation', { test: true });
```

Worker output should show:
```
[worker] Processing job send-application-confirmation (id: 1)
[worker] Unknown job name: send-application-confirmation. Skipping.
[worker] Job completed: send-application-confirmation (id: 1)
```

(The "unknown" log is expected at this stage — the handler is added in Chapter 64.)

## BullMQ dashboard (optional)

Bull-Board provides a web UI to view queued, processing, completed, and failed jobs.

```bash
npm install @bull-board/express @bull-board/api
```

```ts
// In app.ts — admin-only, not for production without auth
import { createBullBoard } from '@bull-board/api';
import { BullMQAdapter } from '@bull-board/api/bullMQAdapter';
import { ExpressAdapter } from '@bull-board/express';

const serverAdapter = new ExpressAdapter();
createBullBoard({ queues: [new BullMQAdapter(queue)], serverAdapter });
app.use('/admin/queues', serverAdapter.getRouter());
```

## No `process.env` in this module

`config.REDIS_URL` is the only configuration value used. It is read from `config.ts`, which is
the only file that touches `process.env`. The worker and the queue module both import from
`config.ts`.
