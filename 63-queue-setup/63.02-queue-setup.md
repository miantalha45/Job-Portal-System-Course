# 63.02 — Queue Setup Walkthrough

## Why BullMQ instead of building a queue yourself?

A naive implementation of a background job system might use `setTimeout` or a PostgreSQL table
polled by a `setInterval`. BullMQ handles all the complexity that makes queues production-ready:

- **Atomic job pickup**: multiple workers cannot claim the same job simultaneously. BullMQ uses
  a Lua script on Redis that atomically moves a job from "waiting" to "active". No two workers
  ever process the same job at the same time (within the same BullMQ instance).
- **Job persistence**: jobs survive server restarts. A `setTimeout` disappears when the process
  exits. A BullMQ job stays in Redis until a worker processes it.
- **Retry with backoff**: built-in exponential backoff — no cron to manage.
- **Observability**: `queue.getWaiting()`, `queue.getActive()`, `queue.getFailed()` give you
  programmatic access to job state.

## The connection architecture

```
Express API process              Worker process
┌────────────────────┐          ┌────────────────────────┐
│  queue.ts          │          │  worker.ts              │
│  Queue('jobs', {   │          │  Worker('jobs', fn, {   │
│    connection: {   │─────┐    │    connection: {        │
│      url: REDIS_URL│     │    │      url: REDIS_URL     │
│    }               │     │    │    }                    │
│  })                │     │    │  })                     │
└────────────────────┘     │    └────────────────────────┘
                           │              │
                           └──────────────┘
                                  │
                          ┌───────▼───────┐
                          │  Redis        │
                          │  bull:jobs:*  │
                          └───────────────┘
```

The Express API creates one `Queue` instance per process. It only enqueues jobs — it never
processes them. The worker creates one `Worker` instance. It only processes jobs — it never
handles HTTP requests. Both share the same Redis instance but use separate TCP connections.

## Step-by-step build

### Step 1 — Install BullMQ

```bash
npm install bullmq
```

Check that `bullmq` appears in `package.json` dependencies (not devDependencies).

### Step 2 — Create src/shared/queue.ts

Key decisions in this file:

- The `JobName` type is a union of string literals. This lets TypeScript catch typos when
  enqueueing jobs. If you call `queue.add('sned-email', payload)`, TypeScript flags the
  misspelled name.
- The queue is named `'jobs'`. BullMQ stores all queue data under Redis keys prefixed with
  `bull:jobs:`. You can choose any name — just be consistent between the Queue and Worker.
- The connection object uses `{ url: config.REDIS_URL }`. BullMQ parses the URL into host,
  port, password, and TLS settings automatically.

### Step 3 — Create src/worker/worker.ts

The worker's job handler is an async function that receives a `Job` object. The `Job` object
has:
- `job.name` — the job name (e.g., `'send-application-confirmation'`)
- `job.data` — the payload you passed to `queue.add`
- `job.id` — a unique string ID set by BullMQ at enqueue time
- `job.attemptsMade` — how many times this job has been attempted (starts at 0)

The `switch (job.name)` dispatches to the correct handler. Adding a new job type means adding
a new `case` — the rest of the dispatch infrastructure is already in place.

### Step 4 — Add the worker script to package.json

```json
"worker": "ts-node src/worker/worker.ts"
```

In production (after `npm run build`):
```json
"start:worker": "node dist/worker/worker.js"
```

### Step 5 — Verify the worker starts

```bash
npm run worker
```

Expected output:
```
[worker] Worker started and listening for jobs...
```

No errors. The worker is now polling the `bull:jobs:waiting` sorted set in Redis.

## Verifying BullMQ's Redis keys

After starting the worker, check what BullMQ has created in Redis:

```bash
redis-cli KEYS "bull:*"
```

You should see keys like:
```
bull:jobs:meta
bull:jobs:id
bull:jobs:events
bull:jobs:stalled-check
```

These are BullMQ's internal bookkeeping keys. Do not delete them.

## What happens when the worker crashes

1. Worker picks up a job — job moves from `waiting` to `active` in Redis
2. Worker crashes (process killed, OOM, etc.)
3. BullMQ has a "stall check" that runs periodically (default: every 30 seconds)
4. If a job in `active` state has not had its lock renewed, BullMQ considers it stalled
5. The stalled job moves back to `waiting` and is retried

The lock renewal happens automatically every 15 seconds while the job is in progress. A very
long-running job (> 15 seconds) must either complete before the lock expires or extend the lock
using `job.extendLock(ttl)`.
