# Guidelines — Chapter 31

## Before you start

Three things must be in place:

- **Chapter 20** — `POST /api/auth/register` creates a `users` row. A recruiter who registers ends up in the `users` table with `role='recruiter'` and `status='pending_verification'`. After email verification (Chapter 23), their status becomes `'active'`. No `recruiters` row exists yet.
- **Chapter 24** — `authMiddleware` extracts the verified JWT and attaches `req.user = { userId, role }` to every protected request.
- **Chapter 26** — `requireRole('recruiter')` is already applied to all routes under `companies.routes.ts` via `router.use(authMiddleware, requireRole('recruiter'))`.

Run `npx tsc --noEmit` before you start. Zero errors.

---

## The gap this chapter closes

After a recruiter verifies their email they can log in and receive a JWT, but they have no company. Every subsequent API call that tries to resolve `getRecruiterCompany(userId)` will find nothing and fail.

This chapter adds `POST /api/companies` so a recruiter can open a company workspace. The endpoint creates a `companies` row and a `recruiters` row in a single transaction, linking the user to the company as its owner.

The company starts with `status='pending'`. An admin will verify it in a later chapter. Pending companies can still post jobs — the status is informational until the admin layer enforces it.

## What to build

### 1. Schema — `src/modules/companies/companies.schema.ts`

Add a Zod schema for the request body:

```ts
import { z } from 'zod';

export const createCompanySchema = z.object({
  name: z.string().min(2).max(100),
  website: z.string().url().optional(),
  description: z.string().max(2000).optional(),
});

export type CreateCompanyInput = z.infer<typeof createCompanySchema>;
```

### 2. Repository — `src/modules/companies/companies.repo.ts`

Add `createCompany`:

```ts
import { v4 as uuid } from 'uuid';
import db from '../../shared/db';
import type { CreateCompanyInput } from './companies.schema';

export async function createCompany(
  userId: string,
  input: CreateCompanyInput,
): Promise<{ companyId: string; name: string }> {
  const companyId = uuid();
  const recruiterId = uuid();

  await db.query('BEGIN');
  try {
    await db.query(
      `INSERT INTO companies (id, name, website, description, status)
       VALUES ($1, $2, $3, $4, 'pending')`,
      [companyId, input.name, input.website ?? null, input.description ?? null],
    );
    await db.query(
      `INSERT INTO recruiters (id, user_id, company_id, company_role, created_at)
       VALUES ($1, $2, $3, 'owner', NOW())`,
      [recruiterId, userId, companyId],
    );
    await db.query('COMMIT');
  } catch (err) {
    await db.query('ROLLBACK');
    throw err;
  }

  return { companyId, name: input.name };
}
```

> `db.query` is the default export from `../../shared/db`. Never use `pool.query` directly.

### 3. Service — `src/modules/companies/companies.service.ts`

Add `openWorkspace`:

```ts
import { ConflictError } from '../../shared/errors';
import { getRecruiterCompany } from './companies.repo';
import { createCompany } from './companies.repo';
import type { CreateCompanyInput } from './companies.schema';

export async function openWorkspace(userId: string, input: CreateCompanyInput) {
  // Guard: a user can own at most one company
  const existing = await getRecruiterCompany(userId);
  if (existing) {
    throw new ConflictError('You already have a company workspace.');
  }

  return createCompany(userId, input);
}
```

### 4. Route — `src/modules/companies/companies.routes.ts`

Add the `POST /` handler. The router already applies `authMiddleware` and `requireRole('recruiter')` for all routes:

```ts
import { validate } from '../../shared/validate';
import { createCompanySchema } from './companies.schema';
import { openWorkspace } from './companies.service';

router.post('/', async (req, res, next) => {
  try {
    const input = validate(createCompanySchema, req.body);
    const result = await openWorkspace(req.user!.userId, input);
    res.status(201).json({
      companyId: result.companyId,
      name: result.name,
      status: 'pending',
    });
  } catch (err) {
    next(err);
  }
});
```

## Transaction rationale

The two inserts — `companies` and `recruiters` — must succeed or fail together. If the `companies` insert succeeds but the `recruiters` insert fails, the company record has no owner; `getRecruiterCompany` will not find it, and the recruiter will be permanently locked out of their workspace. Wrap both in a `BEGIN / COMMIT / ROLLBACK` block.

---

## Status: pending

The `companies.status` column has a check constraint: `CHECK (status IN ('pending','verified','suspended'))`. All new companies start as `'pending'`. This is the right default — a platform admin must verify the company before it is publicly listed. The recruiter, however, is not blocked by this status. They can use all recruiter-facing routes once their own `recruiters` row exists.
