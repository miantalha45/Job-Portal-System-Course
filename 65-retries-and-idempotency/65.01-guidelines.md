## Implementation

### src/shared/queue.ts — default job options

```ts
import { Queue, DefaultJobOptions } from 'bullmq';
import config from './config';

const defaultJobOptions: DefaultJobOptions = {
  attempts: 3,
  backoff: {
    type: 'exponential',
    delay: 1000,   // 1s, then 2s, then 4s
  },
  removeOnComplete: { count: 100 },   // keep last 100 completed jobs for inspection
  removeOnFail: { count: 50 },        // keep last 50 failed jobs
};

const queue = new Queue('jobs', {
  connection: { url: config.REDIS_URL },
  defaultJobOptions,
});

export default queue;
```

These options apply to every job added via `queue.add(...)` unless overridden per-call. The
`removeOnComplete` and `removeOnFail` settings prevent Redis from accumulating unbounded job
history.

## Inspecting failed jobs

After all retries are exhausted, a job moves to the `failed` set. Query it:

```ts
const failed = await queue.getFailed(0, 10);   // first 10 failed jobs
for (const job of failed) {
  console.log(job.name, job.failedReason, job.attemptsMade);
}
```

Or from the CLI:

```bash
redis-cli ZRANGE "bull:jobs:failed" 0 -1 WITHSCORES
```

## Idempotency for jobs with database side effects

Email jobs are naturally idempotent — sending the same email twice is redundant but not
harmful. Jobs that write to the database are not idempotent by default.

Example: a `'create-invoice'` job that inserts a row into `invoices`:

```ts
// NOT idempotent — inserts a duplicate row on retry
await db.query(`INSERT INTO invoices (id, amount) VALUES ($1, $2)`, [newId, amount]);

// Idempotent — uses the job's stable ID as the invoice ID
await db.query(
  `INSERT INTO invoices (id, amount) VALUES ($1, $2) ON CONFLICT (id) DO NOTHING`,
  [job.id, amount]   // job.id is stable across retries
);
```

BullMQ preserves `job.id` across retries. Using it as the primary key of any insert makes the
insert idempotent without extra bookkeeping.

## Retry with exponential backoff: timing

| Attempt | Delay before retry |
|---------|-------------------|
| 1 (first attempt) | — (no delay) |
| 2 | 1 second |
| 3 | 2 seconds |

After attempt 3 fails, the job moves to `failed`. Total time from first attempt to final
failure: ~3 seconds (1 + 2).
