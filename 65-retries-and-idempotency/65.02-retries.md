# 65.02 — Retries, Backoff, Failures & Idempotency (Walkthrough)

## Why retries matter

External services fail. SMTP servers go down. S3 returns 503. A network packet is lost. Without
retries, every transient failure becomes a permanent data loss — an email never sent, a file
never processed. With retries and backoff, transient failures are transparent to the user.

The backoff delay is critical. Without it, every worker immediately retries the failed job,
flooding an already-struggling external service and making the outage worse.

---

## How BullMQ retries work

```
Job added to queue
        │
        ▼
[attempt 1] handler runs
        │
        ├── success → job moves to 'completed'
        │
        └── throws → attempt count incremented
                    │
                    ▼
              [wait backoff delay: 1s]
                    │
                    ▼
              [attempt 2] handler runs
                    │
                    ├── success → job moves to 'completed'
                    │
                    └── throws
                              │
                        [wait 2s]
                              │
                        [attempt 3] handler runs
                              │
                              ├── success → job moves to 'completed'
                              │
                              └── throws → job moves to 'failed'
                                          failedReason = last error message
```

`job.attemptsMade` starts at 0 and increments on each failure. When `attemptsMade === attempts`,
BullMQ stops retrying and moves the job to `failed`.

## Step-by-step: observing a retry

### Step 1 — Add the default job options to queue.ts

```ts
const defaultJobOptions: DefaultJobOptions = {
  attempts: 3,
  backoff: { type: 'exponential', delay: 1000 },
  removeOnComplete: { count: 100 },
  removeOnFail: { count: 50 },
};
```

### Step 2 — Add the deliberate failure to mailer.ts

Add a module-level flag and a conditional throw before `transporter.sendMail`:

```ts
let failOnce = true;

export async function sendApplicationConfirmationEmail(...) {
  if (failOnce) {
    failOnce = false;
    throw new Error('SMTP timeout (simulated)');
  }
  await transporter.sendMail({ ... });
}
```

### Step 3 — Submit an application and watch the worker

Start the worker and watch the terminal:

```
[worker] Processing job send-application-confirmation (id: 1)
[worker] Job failed: send-application-confirmation (id: 1) SMTP timeout (simulated)
// (1 second passes)
[worker] Processing job send-application-confirmation (id: 1)
[worker] Job completed: send-application-confirmation (id: 1)
```

The job ID is the same across attempts. On attempt 2, `failOnce` is already `false`, so the
email sends successfully.

### Step 4 — Force a full failure (all retries exhausted)

Change `failOnce` to a counter:

```ts
let failCount = 5;   // always fail

export async function sendApplicationConfirmationEmail(...) {
  if (failCount-- > 0) throw new Error('SMTP unavailable (simulated)');
  ...
}
```

Watch the worker exhaust all 3 attempts. Then:

```ts
const failed = await queue.getFailed(0, 10);
console.log(failed.map(j => ({ name: j.name, reason: j.failedReason, attempts: j.attemptsMade })));
```

### Step 5 — Remove the deliberate failure

After the demonstration, remove the `failOnce` / `failCount` code from `mailer.ts`. Production
code should not simulate failures.

## Idempotency: the key question

Ask for every worker function: "If this handler runs twice with the same payload, is the
second run harmless?"

| Job type | Idempotent? | Why |
|----------|-------------|-----|
| Send email | Yes (mostly) | Duplicate email is annoying, not data-corrupting |
| Insert a row | No | Creates a duplicate row |
| Update a row | Yes (if setting absolute value) | Setting status='verified' twice is fine |
| Increment a counter | No | `count + 1` run twice gives wrong result |
| `INSERT ... ON CONFLICT DO NOTHING` | Yes | Second run does nothing |

---

## The job.id trick for idempotent inserts

BullMQ assigns a stable `job.id` at the time of enqueue. This ID is preserved across retries.
Use it as a deterministic key for database inserts:

```ts
await db.query(
  `INSERT INTO notifications (id, user_id, message, created_at)
   VALUES ($1, $2, $3, NOW())
   ON CONFLICT (id) DO NOTHING`,
  [job.id, userId, message]   // job.id is stable
);
```

The first run inserts the row. The second run finds the conflict and does nothing. The result
is the same both times.

## Removing failed jobs from Redis

Failed jobs stay in Redis (up to `removeOnFail.count`). To manually retry or discard a failed
job:

```ts
// Retry a specific failed job
await failedJob.retry();

// Discard it
await failedJob.remove();
```

In production, failed jobs warrant an alert (PagerDuty, Slack) and a manual review before
retrying. Automatic infinite retries are dangerous — they can flood an external service.
