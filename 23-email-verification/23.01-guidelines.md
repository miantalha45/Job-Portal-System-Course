# Chapter 23 — Prerequisites and framing

## What you need in place

**Chapter 22 — Refresh tokens work.** `POST /auth/login` returns `{ id, email, role, accessToken, refreshToken }`. Token rotation is implemented in `POST /auth/refresh`. `POST /auth/logout` deletes the refresh token row and returns 204. Every piece of this must be in place before you touch Chapter 23.

**Chapter 20 — `register` and `login` are in `src/modules/auth/auth.service.ts`.** `createUser` in `src/modules/auth/auth.repo.ts` inserts into the `users` table with `status = 'active'`. Chapter 23 changes that to `'pending'`. You must understand what you are changing before you change it.

**Chapter 17 — `UnauthorizedError` exists in `src/shared/errors.ts`.** The login gate in this chapter throws it with distinct messages depending on `status`. The error class is unchanged; only the message strings differ.

**Chapter 6 — `src/shared/config.ts` is the only module that reads `process.env`.** You will add six new fields: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS`, `SMTP_FROM`, and `OTP_EXPIRES_IN_MINUTES`. They go into `EnvSchema`. No other file reads `process.env`.

**Chapter 12 — You can write and run a migration.** This chapter adds an `email_verifications` table via a new migration file. The migration pattern was established in Chapter 12.

**Local SMTP catcher — Mailpit — is running.** This chapter sends actual emails via SMTP. For local development you do not want to deliver email to real inboxes. Mailpit is a lightweight local SMTP server and web UI that catches outgoing email. Install and start it before running the verification flow.

Install Mailpit (macOS via Homebrew, or download a binary from the Mailpit GitHub releases page):

```bash
brew install mailpit
```

Start it:

```bash
mailpit
```

Mailpit listens on port 1025 for SMTP and exposes a web UI at `http://localhost:4025`. Open that URL in your browser — every email your application sends will appear there. No email reaches any real inbox.

## What this chapter builds

1. A new migration that creates the `email_verifications` table.
2. Two new files in `src/shared/`: `mailer.ts` (nodemailer transport, `sendVerificationEmail`) and `otp.ts` (OTP generation and hashing).
3. Six new config fields in `src/shared/config.ts`: five SMTP fields plus `OTP_EXPIRES_IN_MINUTES`.
4. Four new functions in `src/modules/auth/auth.repo.ts`: `createEmailVerification`, `findEmailVerification`, `deleteEmailVerificationsForUser`, and `activateUser`.
5. Two new exported functions in `src/modules/auth/auth.service.ts`: `verifyEmail` and `resendVerification`.
6. A change to `register` in `auth.service.ts`: it now sets `status = 'pending'`, sends the verification email, and returns without an access token.
7. A change to `createUser` in `auth.repo.ts`: the INSERT uses `status = 'pending'` instead of `status = 'active'`.
8. A change to `login` in `auth.service.ts`: the status check now distinguishes `'pending'` from `'suspended'` with different messages.
9. Two new routes in `src/modules/auth/auth.routes.ts`: `POST /auth/verify-email` and `POST /auth/resend-verification`.

The token issuance mechanism from Chapters 21 and 22 is unchanged. Every previously guarded route continues to work. The only new constraint is that a freshly registered user cannot log in until they verify their email address.

## Rethink impact: what changes and what stays the same

### The register endpoint returns less

Before this chapter, `POST /auth/register` returned `{ id, email, role }`. You may have noticed Chapter 20's service returned that shape so the route could respond with it directly. After this chapter, `register` still returns `{ id, email, role }` — the shape is unchanged. What changes is what happens before the return: the user is created with `status = 'pending'` and an OTP email is sent.

The response code also stays 201. The client receives a 201 and knows to prompt the user to check their email. No access token is issued at registration time; that comes only after verification.

### Seed data is not affected

Chapters 13 set up seed users — alice@brightbuild.dev, jamie@example.dev, and others — with `status = 'active'`. Those rows are inserted directly by the seed script with a hardcoded status value. The seed script does not call `POST /auth/register`; it writes to the database directly. Changing `createUser` to `status = 'pending'` has no effect on the seed data.

This is intentional. During development you need to log in as seeded users without running through the email verification flow every time you reset the database. The seed script inserts `status = 'active'` to bypass verification. This is documented in the seed file as a development shortcut. It must not be applied to production data.

**alice@brightbuild.dev and every other seeded user can still log in after this chapter. Nothing in the seed flow changes.**

### The login check becomes more precise

Before this chapter, `login` checked `user.status !== 'active'` and threw a single `UnauthorizedError('Account suspended')` message for any non-active status. After this chapter, the check distinguishes between pending and suspended:

```
'pending'   → 'Email not verified'
'suspended' → 'Account suspended'
```

Both still throw `UnauthorizedError` (HTTP 401). The message is more precise, giving clients enough information to direct the user correctly — either to the verification flow or to a support contact — without revealing anything about other users' account states.

### An OTP, not a magic link

This chapter uses a 6-digit numeric OTP submitted via a `POST /auth/verify-email` endpoint, not a click-through magic link. The reasoning:

- A magic link embeds the token in a URL sent to the client via a `GET` request. Every `GET` of that URL is logged — by the email client, by link-tracking proxies, by browser history. The token appears in server access logs. If the link is forwarded or the email is scanned by a security tool, the token is exposed without any user action.
- A 6-digit OTP is presented by the user via a `POST` body. It travels over HTTPS, does not appear in URLs, and is not logged by intermediaries. It is the user who types it, not a browser following a link.
- The OTP is hashed before storage (SHA-256), expiring in 15 minutes, with a delete-before-reinsert pattern for resend — the same principles applied to refresh tokens in Chapter 22.

The trade-off is user experience: a magic link requires one click, an OTP requires typing. For a programming course the OTP flow is also easier to test with `curl` — you can see the OTP in the Mailpit UI and post it directly.
