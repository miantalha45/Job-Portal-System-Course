# Build: the email_verifications table

## The migration file

Create a new file in your migrations directory. It follows the same sequential numbering used in prior chapters:

```
migrations/008_create_email_verifications.sql
```

```sql
-- migrations/008_create_email_verifications.sql

CREATE TABLE email_verifications (
  id         UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id    UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  otp_hash   TEXT        NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_email_verifications_user_id ON email_verifications (user_id);
```

Run it:

```bash
psql $DATABASE_URL -f migrations/008_create_email_verifications.sql
```

Verify it was applied:

```bash
psql $DATABASE_URL -c "\d email_verifications"
```

## Column decisions

### `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`

Each row is a pending verification for one user. The primary key is a UUID consistent with every other table in this project. The `id` is not used in any lookup path — lookups go through `user_id`. It is present because a primary key is the right structural choice: it uniquely identifies the row and gives any future tooling (audit logs, admin UIs) a stable handle.

### `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`

Every OTP belongs to exactly one user. `NOT NULL` because an OTP without a user is meaningless and should never exist.

`ON DELETE CASCADE` means that when a user row is deleted, their pending verification row is automatically removed. The alternative — `ON DELETE RESTRICT` — would prevent deleting a user who has an active verification record, which would require the application to first delete the OTP row before deleting the account. The cascade is simpler and less error-prone.

There is intentionally no `UNIQUE` constraint on `user_id`. The application layer handles uniqueness by deleting any existing row for a user before inserting a new one (the resend flow, and the initial register flow if the user registers twice before verifying). A database constraint would enforce at most one row per user, but it would also produce a constraint violation error at the database level when a second OTP is requested — error handling that is less clear than the explicit delete-before-insert the application already does.

### `otp_hash TEXT NOT NULL`

This column stores the SHA-256 hex digest of the 6-digit OTP the user receives by email. The raw OTP is never stored — the same principle applied to refresh tokens in Chapter 22.

There is no `UNIQUE` constraint on `otp_hash`. OTPs are always looked up with `user_id` as the first filter (`WHERE user_id = $1 AND expires_at > NOW()`), so a hash that happens to match another user's OTP is irrelevant — it will not be found for the wrong user. A global uniqueness constraint would also reject two different users who happen to receive the same 6-digit OTP, which is a legitimate coincidence: there are only 900,000 possible values and many users in a real system.

`TEXT` stores the 64-character hex digest of SHA-256 without padding.

### `expires_at TIMESTAMPTZ NOT NULL`

The expiry is stored in the database and enforced in SQL: the `findEmailVerification` query includes `AND expires_at > NOW()` in its `WHERE` clause. An expired OTP is indistinguishable from a missing OTP from the application's point of view. The application never receives a row and then decides it is too old; that decision is made inside the database.

OTPs expire in 15 minutes. This window is short enough to limit the usefulness of a stolen OTP, and long enough that a user on a slow connection or mobile device can retrieve the email, open the app, and type the code without racing the clock.

`TIMESTAMPTZ` stores the absolute point in time in UTC, consistent with `refresh_tokens.expires_at` and every other timestamp in this project.

### `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`

Audit trail. You can query this column to investigate issues: "this user says they never received a verification email — when was the OTP created?" The `DEFAULT NOW()` means the application does not supply this value; the database fills it in at insert time.

## The index

### `idx_email_verifications_user_id`

The two most frequent operations on this table both filter by `user_id`:

1. **Before inserting a new OTP**: delete any existing row for that user — `DELETE FROM email_verifications WHERE user_id = $1`.
2. **When verifying**: look up the active OTP for that user — `SELECT ... WHERE user_id = $1 AND expires_at > NOW()`.

Without this index, both operations are full table scans. With it, they are O(log n) lookups. The table could grow large in a system with many registrations — a full scan every time someone registers or verifies is not acceptable.

The index is on `user_id` alone. It is not a composite index on `(user_id, expires_at)`, though that would also work for the `SELECT`. A single-column index on `user_id` is sufficient: the `user_id` filter is highly selective (one row per user in the normal case), so the database reaches the correct row quickly and checks `expires_at` in the row data without needing it in the index.

---

## What the table does NOT contain

There is no `is_used` boolean, no `verified_at` timestamp, and no soft-delete pattern. After a successful verification, the OTP row is not marked used — it is deleted. The application immediately sets `users.status = 'active'` and then has no further use for the OTP record. Keeping the row after verification would require a `used` flag in every lookup to exclude it, adding complexity for no benefit.

The trade-off: there is no durable record that a specific OTP was presented at a specific time. If you needed to audit the verification event — "prove this user verified their email on this date" — you would add a `verified_at` column to the `users` table or an audit log table. This project does not require that level of audit; the `users.status` column transitioning to `'active'` is the authoritative record of successful verification.
