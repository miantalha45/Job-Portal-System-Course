# Build: the new routes

## Schema additions in `auth.schema.ts`

Add two new schemas to `src/modules/auth/auth.schema.ts`. The existing `registerSchema` and `loginSchema` are unchanged.

```ts
// src/modules/auth/auth.schema.ts — additions

export const verifyEmailSchema = z.object({
  email: z.string().email(),
  otp:   z.string().length(6).regex(/^\d{6}$/),
});

export const resendVerificationSchema = z.object({
  email: z.string().email(),
});
```

### The `otp` field validation

`z.string().length(6).regex(/^\d{6}$/)` validates that the submitted value is exactly 6 characters and consists only of digits. Two constraints, one intention: enforce 6-digit numeric format.

`z.string().length(6)` rejects values that are too short or too long before the regex runs — a minor efficiency, but also a clearer error message if a client sends `"12345"` (5 digits) versus `"12345a"` (non-numeric).

`/^\d{6}$/` ensures no letters, spaces, or special characters. Without this, `"123 45"` would pass the length check.

This validation is a format check, not a security check. The service still hashes the submitted value and compares it to the stored hash. An OTP that passes the format check but does not match the stored hash is rejected by the service. The schema rejects obviously malformed input before it reaches the service — not because the service cannot handle it, but because there is no reason to pay for a hash computation and a database lookup for a value that cannot possibly be a valid OTP.

## Updated `auth.routes.ts`

Open `src/modules/auth/auth.routes.ts`. The existing routes for `/register`, `/login`, `/refresh`, and `/logout` remain unchanged. Add the new imports and two new routes.

```ts
// src/modules/auth/auth.routes.ts
import { Router } from 'express';
import { validateBody } from '../../shared/validate';
import {
  registerSchema,
  loginSchema,
  refreshSchema,
  logoutSchema,
  verifyEmailSchema,
  resendVerificationSchema,
} from './auth.schema';
import {
  register,
  login,
  refresh,
  logout,
  verifyEmail,
  resendVerification,
} from './auth.service';

const router = Router();

router.post('/register', async (req, res, next) => {
  try {
    const body = validateBody(registerSchema, req.body);
    const result = await register(body);
    res.status(201).json(result);
  } catch (err) {
    next(err);
  }
});

router.post('/login', async (req, res, next) => {
  try {
    const body = validateBody(loginSchema, req.body);
    const result = await login(body);
    res.status(200).json(result);
  } catch (err) {
    next(err);
  }
});

router.post('/refresh', async (req, res, next) => {
  try {
    const { refreshToken } = validateBody(refreshSchema, req.body);
    const tokens = await refresh(refreshToken);
    res.status(200).json(tokens);
  } catch (err) {
    next(err);
  }
});

router.post('/logout', async (req, res, next) => {
  try {
    const { refreshToken } = validateBody(logoutSchema, req.body);
    await logout(refreshToken);
    res.status(204).send();
  } catch (err) {
    next(err);
  }
});

router.post('/verify-email', async (req, res, next) => {
  try {
    const { email, otp } = validateBody(verifyEmailSchema, req.body);
    await verifyEmail(email, otp);
    res.status(200).json({ message: 'Email verified successfully' });
  } catch (err) {
    next(err);
  }
});

router.post('/resend-verification', async (req, res, next) => {
  try {
    const { email } = validateBody(resendVerificationSchema, req.body);
    await resendVerification(email);
    res.status(200).json({ message: 'If that email is pending verification, a new code has been sent' });
  } catch (err) {
    next(err);
  }
});

export { router as authRouter };
```

## Route design decisions

### `POST /auth/verify-email` returns 200 with a message body

`verifyEmail` in the service is a void function — it signals success by not throwing. The route responds 200 with `{ message: 'Email verified successfully' }`. A 204 would also be semantically correct (successful operation, nothing to return), but a 200 with a message makes the response easier to display to end users. The frontend can read `response.message` and show it directly.

The response does not include an access token. After verifying, the user must call `POST /auth/login` to obtain tokens. This is intentional: the login step confirms the password again, which is the right control point for issuing credentials.

### `POST /auth/resend-verification` always returns 200

The service function returns normally whether the email is registered, already verified, or unknown. The route reflects this: it responds 200 with a message that does not reveal whether an action was taken.

```json
{ "message": "If that email is pending verification, a new code has been sent" }
```

This phrasing is deliberate. "If that email is pending verification" communicates to a legitimate user what to expect (check their inbox if they registered and haven't verified yet) without telling an attacker whether the email is in the system.

### Neither route requires `authMiddleware`

`authMiddleware` validates the `Authorization: Bearer <token>` header. These routes exist precisely for users who do not yet have a valid access token — they have just registered or their OTP has expired. Requiring a token to verify would create a circular dependency: you need to verify to log in, but you need to log in to get a token to verify.

Both routes are intentionally unauthenticated. Rate limiting (not implemented in this chapter) is the production defence against abuse of unauthenticated endpoints.

### `POST /auth/verify-email` is idempotent from the client's perspective

If the user submits the same OTP twice (network retry, double-submit), the second call may succeed (if `user.status` is already `'active'`, `verifyEmail` returns early with a 200) or fail with 401 (if the OTP row was already deleted and the user is still pending). The first case is friendly; the second case is tolerable — the user is asked to re-enter or resend. In neither case does the endpoint corrupt state.

## Manual smoke test

Start your server and Mailpit. Work through these steps in order.

**Step 1 — Register a new user. The response should not include an access token.**

```bash
curl -s -X POST http://localhost:3000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"newuser@example.dev","password":"password123","role":"applicant"}' \
  | jq .
```

Expected: HTTP 201, body `{ "id": "...", "email": "newuser@example.dev", "role": "applicant" }`. No `accessToken` or `refreshToken` fields.

**Step 2 — Confirm the user's status is 'pending' in the database.**

```bash
psql $DATABASE_URL -c "SELECT email, status FROM users WHERE email = 'newuser@example.dev';"
```

Expected: one row, `status = 'pending'`.

**Step 3 — Confirm the OTP row exists.**

```bash
psql $DATABASE_URL -c "SELECT user_id, expires_at, created_at FROM email_verifications;"
```

Expected: one row. `expires_at` is approximately 15 minutes from `created_at`.

**Step 4 — Try to log in before verifying. Should fail.**

```bash
curl -s -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"newuser@example.dev","password":"password123"}' \
  | jq .
```

Expected: HTTP 401.

```json
{
  "error": {
    "code": "UNAUTHORIZED",
    "message": "Email not verified"
  }
}
```

**Step 5 — Open Mailpit and retrieve the OTP.**

Open `http://localhost:4025` in your browser. Click the email sent to `newuser@example.dev`. Find the 6-digit code in the body. Set it as a shell variable:

```bash
OTP=123456   # replace with the actual code from Mailpit
```

**Step 6 — Verify the email.**

```bash
curl -s -X POST http://localhost:3000/auth/verify-email \
  -H 'Content-Type: application/json' \
  -d "{\"email\":\"newuser@example.dev\",\"otp\":\"$OTP\"}" \
  | jq .
```

Expected: HTTP 200.

```json
{ "message": "Email verified successfully" }
```

**Step 7 — Confirm the user's status is now 'active'.**

```bash
psql $DATABASE_URL -c "SELECT email, status FROM users WHERE email = 'newuser@example.dev';"
```

Expected: `status = 'active'`.

**Step 8 — Confirm the OTP row has been deleted.**

```bash
psql $DATABASE_URL -c "SELECT COUNT(*) FROM email_verifications;"
```

Expected: `0`.

**Step 9 — Log in successfully.**

```bash
curl -s -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"newuser@example.dev","password":"password123"}' \
  | jq '{email: .email, role: .role, hasAccessToken: (.accessToken != null), hasRefreshToken: (.refreshToken != null)}'
```

Expected: HTTP 200, `hasAccessToken: true`, `hasRefreshToken: true`.

**Step 10 — Confirm seeded users are unaffected.**

```bash
curl -s -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@brightbuild.dev","password":"password123"}' \
  | jq '{email: .email, hasAccessToken: (.accessToken != null)}'
```

Expected: HTTP 200, `hasAccessToken: true`. Alice's status is `'active'` in the seed data and is not affected by the `createUser` change.

**Step 11 — Test resend.**

Register another user, then request a resend before verifying:

```bash
curl -s -X POST http://localhost:3000/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"resend@example.dev","password":"password123","role":"applicant"}' \
  | jq .
```

```bash
curl -s -X POST http://localhost:3000/auth/resend-verification \
  -H 'Content-Type: application/json' \
  -d '{"email":"resend@example.dev"}' \
  | jq .
```

Expected: HTTP 200, `{ "message": "If that email is pending verification, a new code has been sent" }`. Check Mailpit — a second email arrives for `resend@example.dev`. The OTP in the first email is now invalid; only the second one works.

**Step 12 — Test resend with an unknown email address.**

```bash
curl -s -X POST http://localhost:3000/auth/resend-verification \
  -H 'Content-Type: application/json' \
  -d '{"email":"nobody@unknown.dev"}' \
  | jq .
```

Expected: HTTP 200, same message. No error, no indication that the email is not registered.

**Step 13 — Test a wrong OTP.**

```bash
curl -s -X POST http://localhost:3000/auth/verify-email \
  -H 'Content-Type: application/json' \
  -d '{"email":"resend@example.dev","otp":"000000"}' \
  | jq .
```

Expected: HTTP 401, `"code": "UNAUTHORIZED"`, `"message": "Invalid verification code"`.
