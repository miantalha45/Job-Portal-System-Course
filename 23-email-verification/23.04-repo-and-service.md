### 2. Add three email verification functions to `auth.repo.ts`

Append these functions below the existing refresh token functions. The `db` import is already at the top of the file — do not add a second import.

```ts
// src/modules/auth/auth.repo.ts
// (additions — append below the existing refresh token functions)
// db is already imported at the top: import db from '../../shared/db';

// --- Email verification functions ---

// Delete any existing OTP rows for this user, then insert a new one.
// Two operations keep the logic explicit; a UNIQUE constraint would error
// on the second request instead of silently replacing the old OTP.
export async function createEmailVerification(
  userId: string,
  otpHash: string,
  expiresAt: Date,
): Promise<void> {
  await db.query(
    `DELETE FROM email_verifications WHERE user_id = $1`,
    [userId],
  );
  await db.query(
    `INSERT INTO email_verifications (user_id, otp_hash, expires_at)
     VALUES ($1, $2, $3)`,
    [userId, otpHash, expiresAt],
  );
}

export interface EmailVerificationRow {
  id:         string;
  user_id:    string;
  otp_hash:   string;
  expires_at: Date;
  created_at: Date;
}

// Returns null if no row exists OR if the row has expired — caller cannot distinguish.
export async function findEmailVerification(
  userId: string,
): Promise<EmailVerificationRow | null> {
  const result = await db.query<EmailVerificationRow>(
    `SELECT id, user_id, otp_hash, expires_at, created_at
     FROM email_verifications
     WHERE user_id = $1
       AND expires_at > NOW()`,
    [userId],
  );
  return result.rows[0] ?? null;
}

// Delete all OTP rows for a user — called after verification and before resend.
export async function deleteEmailVerificationsForUser(userId: string): Promise<void> {
  await db.query(
    `DELETE FROM email_verifications WHERE user_id = $1`,
    [userId],
  );
}

// Activate a user account after successful email verification.
export async function activateUser(userId: string): Promise<void> {
  await db.query(
    `UPDATE users SET status = 'active' WHERE id = $1`,
    [userId],
  );
}
```

Note that `createEmailVerification` already calls the delete internally. `deleteEmailVerificationsForUser` is a separate function for the post-verification cleanup step in the service, where only a delete (no subsequent insert) is needed. The two functions cover different call sites without duplicating the DELETE query logic in the service.

### 1. Update `register`

`register` now sends an OTP email after creating the user. The return type stays `{ id: string; email: string; role: string }` — no access token is issued at registration time.

```ts
export async function register(
  input: RegisterInput,
): Promise<{ id: string; email: string; role: string }> {
  const existing = await findUserByEmail(input.email);
  if (existing) {
    throw new ConflictError('Email already taken');
  }

  const passwordHash = await hashPassword(input.password);
  const user = await createUser(input.email, passwordHash, input.role);
  // user.id is the newly created user's UUID.
  // status is 'pending' — set by the INSERT in auth.repo.ts.

  // Generate a 6-digit OTP and store its hash.
  const otp = generateOtp();
  const otpHash = hashOtp(otp);
  const expiresAt = new Date(Date.now() + config.OTP_EXPIRES_IN_MINUTES * 60 * 1000);

  await createEmailVerification(user.id, otpHash, expiresAt);

  // Send the raw OTP to the user's email address.
  // The raw OTP is never stored — only the hash is in the database.
  await sendVerificationEmail(input.email, otp);

  return user;
}
```

**Why no access token at registration?** The user's account is `status = 'pending'`. The `login` function rejects pending accounts. Issuing a token here would let the client make authenticated API requests before the email address is verified — bypassing the point of this chapter. The client receives the user object and knows to prompt for the OTP.

**Why `sendVerificationEmail` is called after `createEmailVerification`, not before?** `createEmailVerification` involves two database operations (delete then insert). If the insert fails, the email has not been sent yet — no stale OTP circulates. If `sendVerificationEmail` fails after a successful insert, the OTP exists in the database but the user has no email. In that case, `POST /auth/resend-verification` recovers the situation. The database write is the durable side effect; the email send is the ephemeral one. Durable writes come first.

### 2. Update `login` — distinguish `'pending'` from `'suspended'`

Find the existing status check in the `login` function and replace it:

```ts
// Before (Chapter 22):
if (user.status !== 'active') {
  throw new UnauthorizedError('Account suspended');
}

// After (Chapter 23):
if (user.status === 'pending') {
  throw new UnauthorizedError('Email not verified');
}
if (user.status === 'suspended') {
  throw new UnauthorizedError('Account suspended');
}
// Any other non-active status (e.g. 'inactive') falls through to the
// password check and fails with 'Invalid credentials' — an intentional
// choice to not reveal which statuses exist.
```

Everything else in `login` is unchanged: the dummy hash call, the password verification, the `issueTokenPair` call, and the return shape.

**Why two separate `if` statements instead of a switch?** Readability. Each status maps to a specific message. Adding a new status in a future chapter means adding one `if` block — no risk of accidentally falling through a `switch` case.

**Why does `'inactive'` not get its own message?** `'inactive'` is a status defined in the schema but not currently assigned by any application path. If an admin sets a user to `'inactive'` via the database directly, that user will receive `'Invalid credentials'` — not a status-specific message. This is intentional: the login endpoint should not be a discovery mechanism for which statuses exist. A user receiving `'Invalid credentials'` for an inactive account should contact support to investigate.

### 3. Add `verifyEmail`

`activateUser` is already in the repo (added in the section above). The imports at the top of this section already include it.

```ts
export async function verifyEmail(
  email: string,
  otp: string,
): Promise<void> {
  // Use a generic error for all failure paths to avoid revealing whether
  // an email is registered, whether an OTP exists, or whether it expired.
  const user = await findUserByEmail(email);
  if (!user) {
    throw new UnauthorizedError('Invalid verification code');
  }

  // Already active: idempotent early return. Handles double-submit and
  // retries after a network failure on the success response.
  if (user.status === 'active') {
    return;
  }

  // Returns null if no row exists OR if the row has expired.
  const verification = await findEmailVerification(user.id);
  if (!verification) {
    throw new UnauthorizedError('Invalid verification code');
  }

  const submittedHash = hashOtp(otp);
  if (submittedHash !== verification.otp_hash) {
    throw new UnauthorizedError('Invalid verification code');
  }

  await activateUser(user.id);
  await deleteEmailVerificationsForUser(user.id);
}
```

**Why the same error message for all failure cases?** `'Invalid verification code'` is used whether the email is not found, the OTP does not exist, the OTP has expired, or the OTP is wrong. Distinct messages would tell an attacker whether an email address is registered (user-not-found vs. wrong-code), whether a valid OTP exists (expired vs. wrong-code), and so on. A single message reveals nothing.

**Why check `status === 'active'` and return early?** A client that successfully verifies may retry the request (network failure, double-submit). The early return makes `verifyEmail` idempotent: a second call with the same (now deleted) OTP would fail the `findEmailVerification` check and return 401. Treating already-active as a no-op is the more user-friendly behaviour — the user is verified; the operation succeeded. The OTP is already gone, so there is no security concern in returning 200 a second time.

### 4. Add `resendVerification`

```ts
export async function resendVerification(email: string): Promise<void> {
  const user = await findUserByEmail(email);

  // If the email is not registered, return normally — do not reveal
  // whether the address is in the system. The caller sees a 200 either way.
  if (!user) {
    return;
  }

  // If the account is already active, there is nothing to resend.
  // Return normally — do not error.
  if (user.status === 'active') {
    return;
  }

  // Only resend for pending accounts.
  // A suspended account should not receive a verification email.
  if (user.status !== 'pending') {
    return;
  }

  const otp = generateOtp();
  const otpHash = hashOtp(otp);
  const expiresAt = new Date(Date.now() + config.OTP_EXPIRES_IN_MINUTES * 60 * 1000);

  // createEmailVerification deletes any existing row before inserting the new one.
  // The old OTP is invalidated; user cannot use it after requesting a resend.
  await createEmailVerification(user.id, otpHash, expiresAt);
  await sendVerificationEmail(email, otp);
}
```

**Why does `resendVerification` return normally when the email is not found?** The resend endpoint accepts an email address and sends an OTP if appropriate. If an attacker calls it with random email addresses, a 404 response would confirm whether an address is registered. A 200 response regardless of outcome gives the attacker no information. This is the same design pattern used by password reset flows across the industry.

**Why does `resendVerification` return normally for already-active accounts?** An active user may click "resend" in a stale UI state (opened a tab before verifying, verified in another tab). Returning an error would confuse them. Returning 200 silently is correct: the user is verified, nothing needs to happen.

## Why the service is structured this way

### The repo owns all SQL, including `activateUser`

The service never writes SQL directly. Moving `UPDATE users SET status = 'active'` into the repo keeps the service layer free of database concerns. If the database schema changes — say, `status` is renamed, or a trigger is added — the change is localized to `auth.repo.ts`. The service calls `activateUser(user.id)` and does not know or care how it is implemented.

### `verifyEmail` and `resendVerification` are void functions

Neither function needs to return data. `verifyEmail` signals success by returning without throwing; the route responds 200. `resendVerification` is always a 200. The caller (the route handler) does not need a return value — the absence of an error is the success signal.

### OTP expiry is 15 minutes, enforced in SQL

The expiry check is inside `findEmailVerification` via `AND expires_at > NOW()`. The service does not check `verification.expires_at > new Date()`. This is the same pattern as `findRefreshTokenByHash` in Chapter 22: the database enforces expiry, the application trusts the query result. If the row is returned, it is valid. If it is not returned, it is either missing or expired — and the distinction does not matter to the caller.
