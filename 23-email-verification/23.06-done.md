## Log It

**`resendVerification` returns normally — HTTP 200 — when called with an email address that is not registered in the system. This means an attacker cannot use the resend endpoint to discover whether a given email address has an account. However, the registration endpoint itself responds 409 when an email is already taken, which does reveal that the address is registered. If the goal is to prevent email enumeration, the resend endpoint's design and the register endpoint's design are in tension. What would you need to change about `POST /auth/register` to make it consistent with `POST /auth/resend-verification` — and what would you lose by making that change?**

There is no single correct answer. Consider: what does a 409 tell an attacker that a 200 does not? What does a client UI lose if it cannot distinguish "email already registered" from "registration succeeded"? Is the risk of email enumeration via the register endpoint higher or lower than via the resend endpoint, given the different contexts in which each is typically called?

**The `verifyEmail` service function performs two database writes in sequence: `activateUser(user.id)` sets `status = 'active'`, and then `deleteEmailVerificationsForUser(user.id)` removes the OTP row. If the process crashes or loses its database connection between the first write and the second, the user's account is active but the OTP row remains in the database. Is this a problem — and would reversing the order (delete first, then activate) create a different problem?**

There is no single correct answer. Consider: what can an attacker do with a stale OTP row for an already-active user? What would happen to the user if the `activateUser` write succeeds but a crash prevents the OTP from being deleted, and the user logs in and uses the app normally — does the stale row cause any observable problem? Now consider the reversed order: if `deleteEmailVerificationsForUser` succeeds but `activateUser` fails, the user's account remains pending and the OTP is gone. What does the user experience, and how do they recover?

## Quiz

**Q1.** The `hashOtp` function uses SHA-256. The `hashPassword` function (from Chapter 19) uses bcrypt. Both are used in the authentication module. OTPs are 6 digits — there are only 900,000 possible values. Bcrypt is specifically designed to resist brute-force attacks. Why is SHA-256 used for OTP hashing instead of bcrypt, given that the OTP space is so much smaller than a password space?

Think about: what a brute-force attack on a stored hash requires; what the attacker must do to attempt each guess; how many guesses they would need to exhaust 900,000 values; and what controls exist outside of the hash function itself that limit the attack surface.

**Q2.** The `findEmailVerification` repo function queries `WHERE user_id = $1 AND expires_at > NOW()`. There is an index on `user_id` but no index on `expires_at`. A developer argues that adding an index on `expires_at` would make this query faster. Is the developer correct — and is the index worth adding?

Think about: how PostgreSQL uses an index; which condition in this query is more selective; what the cardinality of `user_id` results is in the normal case (one row per user, or many?); and how the database decides which index to use when multiple are available.

**Q3.** The verification flow in this chapter requires two HTTP requests after registration: one to `POST /auth/verify-email` (with the OTP), and then a separate `POST /auth/login` (with email and password) to obtain tokens. A developer proposes combining them: `POST /auth/verify-email` should verify the OTP and, if successful, immediately return an access token and refresh token — saving the user one round trip.

Evaluate this proposal. What does it simplify? What does it change about the login code path and the trust model for issued tokens?

Think about: what `POST /auth/login` does that `POST /auth/verify-email` does not currently do; whether a verified OTP is a sufficient credential for issuing tokens without re-confirming the password; and whether there are cases where the combined endpoint would issue tokens to someone who should not have them.
