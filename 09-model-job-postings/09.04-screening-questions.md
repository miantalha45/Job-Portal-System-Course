# Screening questions — design and shape

## What they are

Screening questions are per-job questions that applicants answer as part of their application. A recruiter posting an engineering role might ask "Describe your experience with distributed systems." A recruiter posting a sales role might ask "Are you comfortable with a commission-heavy compensation structure?" Each job defines its own questions; there is no shared question library.

## Why they live in a JSONB column

The alternative is a separate `job_screening_questions` table:

```sql
CREATE TABLE job_screening_questions (
  id      uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  job_id  uuid NOT NULL REFERENCES jobs(id),
  text    text NOT NULL,
  type    text NOT NULL,
  required boolean NOT NULL DEFAULT true,
  position integer NOT NULL  -- display order
);
```

A separate table is the right call if you need to:
- **Query across questions** — "find all jobs that ask about salary expectations"
- **Reuse questions** — a shared question library across postings
- **Attach complex structure** — multiple-choice questions with answer options, branching logic

None of those are requirements here. Screening questions are always loaded *with* the job — a job detail page fetches both in one go. They're always read as a unit, never queried across jobs, and their structure is simple enough to be predictable. JSONB is the right fit.

## The question shape

Each entry in `screening_questions` is an object with four fields:

```json
[
  {
    "id": "a1b2c3d4-e5f6-7890-abcd-ef1234567890",
    "text": "Describe your most recent experience working in a distributed system.",
    "type": "text",
    "required": true
  },
  {
    "id": "b2c3d4e5-f6a7-8901-bcde-f12345678901",
    "text": "Are you open to occasional travel (up to 20% of the time)?",
    "type": "boolean",
    "required": true
  },
  {
    "id": "c3d4e5f6-a7b8-9012-cdef-123456789012",
    "text": "Link to a relevant project or portfolio piece (optional).",
    "type": "url",
    "required": false
  }
]
```

| Field | Purpose |
|---|---|
| `id` | A stable identifier for the question. When an applicant submits their answers in ch10, each answer is keyed to this `id` — so you can correlate question to answer even if the question text later changes. |
| `text` | The question displayed to the applicant. |
| `type` | How the UI renders the input — `"text"` for a textarea, `"boolean"` for yes/no, `"url"` for a URL input. The validation layer (ch16) enforces type-appropriate answers. |
| `required` | Whether the applicant must answer this question to submit. |

Use UUIDs for question `id` values. Short sequential slugs (`"q1"`, `"q2"`) seem convenient but are dangerous: if a recruiter deletes a question and the remaining questions shift position, `"q2"` now refers to a different question — and every submitted application's answer for the old `"q2"` becomes misattributed. UUIDs are stable regardless of what else changes in the array.

Questions are displayed in array order — PostgreSQL preserves JSON array element order in JSONB columns, so the recruiter's intended sequence is maintained without a separate `position` field.

## What the validation layer enforces

The DDL constrains `screening_questions` to be a valid JSON array, nothing more. The shape of each question object — the required fields, the allowed `type` values — is enforced by the zod schema in the request validation layer (ch16). The database is not the right place for that level of structural validation.
