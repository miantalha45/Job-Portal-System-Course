# The `jobs` table

```sql
CREATE TABLE jobs (
  id                  uuid        PRIMARY KEY DEFAULT gen_random_uuid(),
  company_id          uuid        NOT NULL REFERENCES companies(id),
  title               text        NOT NULL,
  description         text        NOT NULL,
  status              text        NOT NULL DEFAULT 'draft'
                                    CHECK (status IN ('draft', 'open', 'closed')),
  deadline            date,
  attributes          jsonb       NOT NULL DEFAULT '{}',
  screening_questions jsonb       NOT NULL DEFAULT '[]',
  created_at          timestamptz NOT NULL DEFAULT now(),
  updated_at          timestamptz NOT NULL DEFAULT now()
);
```

## Column by column

**`company_id`** — every job belongs to exactly one company. `NOT NULL` because a job with no owner is meaningless. The `ON DELETE` behaviour on this FK (what happens if a company is deleted) is [Chapter 11](../11-foreign-keys-and-constraints/)'s job.

**`title`** — `NOT NULL`. A job posting without a title can't be displayed anywhere.

**`description`** — `NOT NULL`. The full posting text. Stored as plain text here; the API layer can accept markdown and render it in the UI. PostgreSQL `text` has no length ceiling — the validation schema in [Chapter 16](../16-request-validation/) must enforce a maximum byte length (e.g. 100 KB) to prevent abuse.

**`status`** — defaults to `'draft'`. A recruiter creates a job; it's invisible to applicants until they explicitly publish it (`'open'`). When the role is filled or the position is taken down, it becomes `'closed'`. The CHECK constraint validates the stored value — not the direction of the transition. Whether a `closed` job can be re-opened (`closed → open`) is an application-layer rule, not a schema rule.

```
draft  →  open  →  closed
           ↑
     (recruiter publishes)
```

The `deadline` field does not auto-close a job. A job stays `'open'` until application code explicitly sets `status = 'closed'`. The public board query (`WHERE deadline IS NULL OR deadline > CURRENT_DATE`) handles the display of expired jobs without touching `status`.

**`deadline`** — nullable. Not every job posting has a hard cutoff date. When it's set, the public board can filter out jobs whose deadline has passed: `WHERE deadline IS NULL OR deadline > CURRENT_DATE`. The type is `date` rather than `timestamptz` because job deadlines are calendar dates ("apply by 30 June"), not precise moments — `CURRENT_DATE` comparison is the right operator for this type.

**`attributes`** — JSONB, defaults to an empty object. What goes here is role-type-specific: an engineering job might store `{ "tech_stack": ["Go", "PostgreSQL"], "seniority": "mid", "remote_policy": "hybrid" }`, a sales job might store `{ "commission_plan": "10% of ARR", "territory": "EMEA" }`. The schema enforces nothing about the contents — the validation layer (ch16) does.

**`screening_questions`** — JSONB, defaults to an empty array. Structured differently from `attributes` — it's always an array of question objects, not a free-form bag. Covered in the next sub-chapter.

**`updated_at`** — needed for cache invalidation. When a recruiter edits a job, `updated_at` changes; the caching layer ([Chapter 44](../44-caching/)) uses this to decide whether a cached listing is stale.

> 💡 **Hint — keeping `updated_at` current.** You'll need to update this column on every edit. One clean approach: a PostgreSQL trigger that sets `updated_at = now()` on any `UPDATE`. Another: always include `updated_at = now()` in your `UPDATE` statements at the service layer. Either works — pick one and stay consistent.
