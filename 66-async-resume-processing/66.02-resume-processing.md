# 66.02 — Async Résumé Processing (Walkthrough)

## Why process résumés asynchronously?

A PDF résumé can be 1–5 MB. Parsing it — extracting text, counting words, extracting skills —
takes 200–2000ms depending on the file size and the parsing library. Making the upload endpoint
wait for parsing would make every résumé upload feel slow. Worse, if the parsing library
throws, the upload endpoint returns an error even though the file was already written to S3.

Async processing decouples the upload (fast, reliable) from the analysis (slow, fallible).

## The full flow

```
Applicant                Express API              S3               Worker          PostgreSQL
    |                         |                   |                  |                 |
    |-- POST /resume -------->|                   |                  |                 |
    |                         |-- PutObject ----->|                  |                 |
    |                         |<-- OK ------------|                  |                 |
    |                         |-- INSERT resumes (s3_key, id) -------|-- row --------->|
    |                         |-- queue.add('process-resume') ------>|                 |
    |<-- 201 { resumeId } ----|                   |                  |                 |
    |                         |                   |                  |                 |
    |                         |                   |<- GetObject -----|                 |
    |                         |                   |-- file bytes ---->|                 |
    |                         |                   |                  |-- UPDATE word_count
    |                         |                   |                  |---------------->|
```

## Building it step by step

### Step 1 — Run the migration

```bash
psql $DATABASE_URL -f migrations/012_resumes_word_count.sql
```

Verify:

```bash
psql $DATABASE_URL -c "\d resumes"
# Expected: word_count column with type integer (nullable)
```

### Step 2 — Create the handler

Create `src/worker/handlers/processResume.ts`. Separating handlers into individual files keeps
`worker.ts` from becoming a monolith. Each handler is a single exported async function.

The S3 download uses `GetObjectCommand`. The response body is a `Readable` stream. Stream to
a buffer by collecting chunks:

```ts
const stream = response.Body as Readable;
const chunks: Buffer[] = [];
for await (const chunk of stream) {
  chunks.push(typeof chunk === 'string' ? Buffer.from(chunk) : chunk);
}
const buffer = Buffer.concat(chunks);
```

The `for await ... of` loop on a `Readable` is clean and handles backpressure automatically.

### Step 3 — Word count from raw bytes

```ts
const text = buffer.toString('utf-8', 0, Math.min(buffer.length, 100_000));
const wordCount = text.split(/\s+/).filter(Boolean).length;
```

For a plain text résumé: accurate.
For a PDF binary: undercount (most bytes are binary, not text). For the course, this is
sufficient — the word_count column will have a non-null value, which proves the pipeline works.

### Step 4 — Update the database

```ts
await db.query(
  `UPDATE resumes SET word_count = $1 WHERE id = $2`,
  [wordCount, resumeId]
);
```

This is idempotent — running it twice with the same result just updates the same row to the
same value.

### Step 5 — Enqueue from the upload service

In `applicants.service.ts`, after the résumé row is inserted:

```ts
await queue.add('process-resume', {
  resumeId: resume.id,
  s3Key: resume.s3_key,
});
```

### Step 6 — Add the case to worker.ts

```ts
import { processResume } from './handlers/processResume';

case 'process-resume': {
  const { resumeId, s3Key } = job.data;
  await processResume(resumeId, s3Key);
  break;
}
```

## Error handling in the handler

If S3 returns an error (key not found, permissions, etc.), `processResume` throws. BullMQ will
retry up to the configured attempt limit. The `resumes` row will have `word_count = NULL` until
a successful attempt. This is fine — `word_count` is nullable.

If the UPDATE fails (row was deleted between enqueue and processing), the handler throws. BullMQ
retries. On retry, the row is still missing. After all retries, the job moves to `failed`.
This is the correct behaviour — the processing result can only be stored if the source row exists.
