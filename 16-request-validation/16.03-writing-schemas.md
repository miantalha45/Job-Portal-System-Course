# Writing schemas

## Where schemas live

Each feature module owns its schemas. The jobs module's schema file is `src/modules/jobs/jobs.schema.ts`. It exports one schema per operation (create, update, list query) and the derived TypeScript types.

## The jobs schema

```ts
import { z } from 'zod';

const screeningQuestionInputSchema = z.object({
  text:     z.string().min(1, 'Question text is required').max(500),
  type:     z.enum(['text', 'boolean', 'url']),
  required: z.boolean().default(true),
});

const jobFieldsSchema = z.object({
  title:               z.string().min(1, 'Title is required').max(200),
  description:         z.string().min(1, 'Description is required').max(100_000),
  status:              z.enum(['draft', 'open']),
  deadline:            z.string().date('Deadline must be a date in YYYY-MM-DD format').optional(),
  attributes:          z.object({}).catchall(z.unknown()),
  screening_questions: z.array(screeningQuestionInputSchema),
});

export const createJobSchema = jobFieldsSchema.extend({
  status:              z.enum(['draft', 'open']).default('draft'),
  attributes:          z.object({}).catchall(z.unknown()).default({}),
  screening_questions: z.array(screeningQuestionInputSchema).default([]),
});

export const updateJobSchema = jobFieldsSchema.partial();

export const listJobsQuerySchema = z.object({
  status: z.enum(['draft', 'open', 'closed']).optional(),
  page:   z.coerce.number().int().min(1).default(1),
  limit:  z.coerce.number().int().min(1).max(100).default(20),
});

export type CreateJobInput   = z.infer<typeof createJobSchema>;
export type UpdateJobInput   = z.infer<typeof updateJobSchema>;
export type ListJobsQuery    = z.infer<typeof listJobsQuerySchema>;
```

**Things to note:**

`screeningQuestionInputSchema` omits `id`. The service layer generates a UUID for each question before storing — the recruiter specifies the question content, not the identifier. This matches the ch9 design: questions are keyed by UUID in storage, but clients do not supply those keys.

`type: z.enum(['text', 'boolean', 'url'])` matches the three types defined in ch9: `"text"` for a textarea, `"boolean"` for a yes/no toggle, `"url"` for a URL input.

`z.string().date()` validates the YYYY-MM-DD format without converting to a `Date` object. The `pg` driver accepts YYYY-MM-DD strings directly for `date` columns.

**`jobFieldsSchema` / `createJobSchema` / `updateJobSchema`**: the schema is split into a base and two operation-specific schemas. `createJobSchema` extends the base with `default()` values — a POST body that omits `status` receives `'draft'`; a POST body that omits `screening_questions` receives `[]`. `updateJobSchema` is `jobFieldsSchema.partial()`: every field is optional, and *no defaults are applied*.

This matters for PATCH: if the request body omits `status`, `updateJobSchema` produces `{}` — the service sees `undefined` for that field and knows not to overwrite the stored value. If `createJobSchema.partial()` were used instead, `{}` would parse as `{ status: 'draft', attributes: {}, screening_questions: [] }`, silently overwriting existing data with defaults on every PATCH that omits those fields.

`z.object({}).catchall(z.unknown())`: `attributes` is arbitrary metadata — any key, any value. `catchall(z.unknown())` allows any string-keyed property. The resulting TypeScript type is `Record<string, unknown>` — an object whose keys are strings and whose values can be anything. `z.object({}).catchall()` is used rather than `z.record()` because `z.record()` silently accepts arrays (arrays are objects in JavaScript with numeric string keys); `z.object({})` rejects non-object inputs.

`z.coerce.number()` on query parameters: URL query strings are always strings (`?page=2` arrives as `"2"`). `z.coerce` converts the string to a number before validation. Without `coerce`, `z.number().min(1)` would fail on the string `"2"`.

`z.infer<typeof schema>` derives the TypeScript type from the schema. The type and the validator are always in sync — you cannot change one without updating the other.

## Error messages

Zod generates default error messages. Custom messages go in the validator call: `z.string().min(1, 'Title is required')`. The error contains the path to the failing field and the message, so multi-field failures are reported together:

```json
{
  "errors": [
    { "path": ["title"], "message": "Title is required" },
    { "path": ["screening_questions", 0, "text"], "message": "Question text is required" }
  ]
}
```

Chapter 17 formats the raw `ZodError` into this shape. Chapter 16's job is only to throw the error; the formatting happens in the error handler.
