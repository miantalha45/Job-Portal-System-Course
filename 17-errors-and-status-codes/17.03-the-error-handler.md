# Build: the error handler

## How Express recognises an error handler

Express distinguishes error-handling middleware from regular middleware by the number of parameters in the function signature. A regular middleware takes `(req, res, next)` — three parameters. An error handler takes `(err, req, res, next)` — four parameters. Express checks the function's `.length` property at registration time. If it is 4, Express treats it as an error handler and only invokes it when an error has been passed to `next(err)`, or when a synchronous route handler throws.

Two consequences follow from this:

1. The four-parameter signature is required even if you never call `next` inside the handler. Remove the fourth parameter and Express stops treating the function as an error handler — errors will pass through silently.
2. The error handler must be registered **after all routes**. Express processes middleware in registration order. If the error handler is mounted before a route, errors thrown by that route cannot reach it.

## Why not handle errors in each route

Without a centralised handler, every route that can fail must handle its own errors:

```ts
// Without a centralised handler — repeated in every route
router.get('/jobs/:id', async (req, res) => {
  try {
    const job = await jobsService.getJob(req.params.id);
    if (!job) {
      res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Job not found' } });
      return;
    }
    res.json(job);
  } catch (err) {
    console.error(err);
    res.status(500).json({ error: { code: 'INTERNAL_ERROR', message: 'Something went wrong' } });
  }
});
```

This pattern duplicates the try/catch, the status codes, and the response shape in every route file. A centralised error handler moves all of that to one place.

## The response shape

Every error response, regardless of type, uses this shape:

```json
{ "error": { "code": "ERROR_CODE", "message": "Human-readable message" } }
```

Validation errors add a `details` array:

```json
{
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Validation failed",
    "details": [
      { "path": "title", "message": "Required" },
      { "path": "salary", "message": "Expected number, received string" }
    ]
  }
}
```

The `path` field is the dot-notation field path from Zod — the keys traversed to reach the failing value, joined with dots. For a top-level field like `title`, it is just `"title"`. For a nested field it would be `"address.city"`. The `message` is Zod's validation message for that field.

422 Unprocessable Entity is used for validation failures — the request was syntactically well-formed (valid JSON) but semantically invalid (failed schema constraints). 400 Bad Request is also widely used for this; either is acceptable as long as it is applied consistently. This course uses 422.

## `src/shared/error-handler.ts`

```ts
import { Request, Response, NextFunction } from 'express';
import { config } from './config';
import { AppError } from './errors';
import { ValidationError } from './validate';

export function errorHandler(
  err: unknown,
  req: Request,
  res: Response,
  _next: NextFunction, // four-parameter signature required for Express to recognise this as an error handler
): void {
  if (err instanceof ValidationError) {
    const details = err.zodError.errors.map((issue) => ({
      path: issue.path.join('.'),
      message: issue.message,
    }));

    res.status(422).json({
      error: {
        code: 'VALIDATION_ERROR',
        message: 'Validation failed',
        details,
      },
    });
    return;
  }

  if (err instanceof AppError) {
    res.status(err.statusCode).json({
      error: {
        code: err.code,
        message: err.message,
      },
    });
    return;
  }

  // express.json() sends a SyntaxError with a status property when the request body is malformed JSON
  if (err instanceof SyntaxError && 'status' in err && (err as SyntaxError & { status: number }).status === 400) {
    res.status(400).json({
      error: {
        code: 'BAD_REQUEST',
        message: 'Malformed JSON in request body',
      },
    });
    return;
  }

  console.error('[unhandled error]', err);

  const message =
    config.NODE_ENV === 'development' && err instanceof Error
      ? err.message
      : 'An unexpected error occurred';

  res.status(500).json({
    error: {
      code: 'INTERNAL_ERROR',
      message,
    },
  });
}
```

### The 500 leak risk

When an unexpected error reaches the handler — a database connection failure, a null dereference, any unplanned throw — there are two audiences with conflicting needs:

- **The server operator** needs the full error: message, stack, context. They need to fix it.
- **The client** must not receive it. Raw error messages from a database or third-party library often contain table names, column names, connection strings, or internal identifiers. Returning them is an information disclosure vulnerability and confuses users.

The handler resolves this by logging the full error with `console.error` and returning a generic message to the client. In development, `err.message` is surfaced to the client to speed up local debugging — this is controlled by `config.NODE_ENV`, not by reading `process.env` directly.

### Why `err instanceof Error` check before accessing `.message`

TypeScript types the `err` parameter as `unknown` because anything can be thrown: `throw 'string'`, `throw 42`, `throw null` are all valid JavaScript. Accessing `.message` on an arbitrary `unknown` value is a type error. The `err instanceof Error` guard narrows the type before the property access.

### The `_next` parameter

ESLint flags unused function parameters. The `_next` parameter must be present for Express's signature detection but is never called in an error handler that always sends a response. Prefixing with an underscore (`_next`) is the idiomatic way to tell ESLint the parameter is intentionally unused — no disable comment needed.

### The `console.error` call

`console.error` is used here as a straightforward placeholder. In production you would replace this with a structured logger that attaches a request ID, timestamps, and severity level. Chapter 71 covers structured logging — for now, `console.error` logs to stderr and makes the output visible in your terminal.

## Wiring into `src/app.ts`

The error handler is added as the last line before `buildApp` returns:

```ts
// src/app.ts (relevant addition — your existing route mounts come before this)
import { errorHandler } from './shared/error-handler';

// ... all route registrations above ...

app.use(errorHandler);

return app;
```

The placement is the constraint: `app.use(errorHandler)` must come after every `app.use(router)` call. If any route is mounted after the error handler, errors from that route will not be caught.

## Testing it manually

Before ch19 adds real routes, add a temporary test route directly in `app.ts` to verify each branch of the error handler. Remove it when done.

```ts
import { NotFoundError } from './shared/errors';
import { ValidationError } from './shared/validate';
import { z } from 'zod';

// Temporary test routes — remove after verifying the error handler
app.get('/test/not-found', (_req, _res, next) => {
  next(new NotFoundError('Job not found'));
});

app.get('/test/validation', (_req, _res, next) => {
  const schema = z.object({ title: z.string().min(1) });
  const result = schema.safeParse({});
  if (!result.success) {
    next(new ValidationError(result.error));
  } else {
    next(new Error('Unexpected: schema should have failed'));
  }
});

app.get('/test/unhandled', (_req, _res, next) => {
  next(new Error('oops — raw error'));
});
```

Note the use of `next(err)` rather than `throw`. These test routes are synchronous, so either form would work — but the course uses Express 4, where `throw` inside an `async` route handler does **not** reach the error handler. Express 4 does not automatically catch rejected promises from async handlers; those become unhandled promise rejections. Using `next(err)` explicitly works in all cases and is the required pattern for async routes in Express 4.
