# Build: the error class hierarchy

## Why a class hierarchy instead of scattered `res.status().json()` calls

Without a shared error abstraction, throwing a 404 from a service function looks like this in every route handler that needs it:

```ts
// route handler A
const job = await jobsRepo.findById(id);
if (!job) {
  res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Job not found' } });
  return;
}

// route handler B — same pattern, probably slightly different shape
const company = await companiesRepo.findById(id);
if (!company) {
  res.status(404).json({ error: { code: 'NOT_FOUND', message: 'Company not found' } });
  return;
}
```

Two problems compound as the codebase grows:

**The service layer knows about HTTP.** A `jobsService.findById` that needs to signal "not found" has no clean way to do it without either returning `null` (pushing the 404 decision into every caller) or reaching into the HTTP layer directly (mixing concerns). The service layer should be able to say "this thing does not exist" and have the HTTP layer handle what that means.

**There is no single source of truth.** Status codes, response shapes, and error codes are duplicated wherever an error can occur. When the response shape needs to change — and it will — every callsite must be found and updated.

A class hierarchy solves both. The service throws `new NotFoundError('Job not found')`. It knows nothing about HTTP. The error handler — one place — maps that class to a 404 and formats the response.

## What stays in `validate.ts`

`ValidationError` is not an `AppError` subclass. It wraps a `ZodError`, which carries a structured list of field-level failures. Its data shape (`details` array) is different from a plain application error. It lives in `validate.ts` because it is tightly coupled to Zod — it exists to translate a Zod failure into something the error handler can recognise. That is a different job from "signal that a resource was not found."

The error handler handles both, but through separate branches.

## `src/shared/errors.ts`

```ts
export class AppError extends Error {
  constructor(
    public readonly statusCode: number,
    public readonly code: string,
    message: string,
  ) {
    super(message);
    this.name = this.constructor.name;
  }
}

export class NotFoundError extends AppError {
  constructor(message = 'Not found') {
    super(404, 'NOT_FOUND', message);
  }
}

export class UnauthorizedError extends AppError {
  constructor(message = 'Authentication required') {
    super(401, 'UNAUTHORIZED', message);
  }
}

export class ForbiddenError extends AppError {
  constructor(message = 'Access denied') {
    super(403, 'FORBIDDEN', message);
  }
}

export class ConflictError extends AppError {
  constructor(message = 'Conflict') {
    super(409, 'CONFLICT', message);
  }
}
```

### What each piece does

**`AppError` base class.** Holds `statusCode` and `code` as public readonly properties. The error handler reads them without needing to know the concrete subclass. `this.name = this.constructor.name` ensures `err.name` reflects the actual subclass (`"NotFoundError"`, etc.) rather than the generic `"Error"`.

An alternative design is a single `AppError` with no subclasses: `throw new AppError(404, 'NOT_FOUND', 'Job not found')`. That works, but loses the ability to use `instanceof NotFoundError` for type narrowing in tests or middleware that needs to inspect error types. Named subclasses cost very little and are more readable at the throw site.

**Named subclasses.** Each one fixes the status code and the machine-readable `code` string. The human-readable `message` has a sensible default but can be overridden at the throw site: `new NotFoundError('Job not found')`. The caller decides what message the client sees; the class decides the status code.

**Default messages.** Defaults exist so that `throw new UnauthorizedError()` is valid — no argument required when the generic message is sufficient.

### Usage in a service

```ts
// src/modules/jobs/jobs.service.ts
import { NotFoundError, ForbiddenError } from '../../shared/errors';

export async function getJob(jobId: string, requestingCompanyId: string) {
  const job = await jobsRepo.findById(jobId);
  if (!job) throw new NotFoundError('Job not found');
  if (job.companyId !== requestingCompanyId) throw new ForbiddenError('Access denied');
  return job;
}
```

The service throws typed errors. It imports from `shared/errors`. It does not touch `res`, does not know about HTTP status codes, and does not format JSON. The error handler — shown in the next section — handles all of that.
