## What this chapter builds

Two files and one wiring change:

1. `src/shared/errors.ts` — named error classes for application-level HTTP errors
2. `src/shared/error-handler.ts` — a single Express error-handling middleware
3. One line added to `src/app.ts` to mount it last

## Rethink impact — the inconsistent-error problem

Read this scenario, then answer the prompt below before writing any code.

---

A recruiter submits a job posting through your API. Their client app is written by a frontend developer consuming your endpoints. Three separate API endpoints have error handling written ad hoc — no shared conventions, no shared code:

- **Endpoint A** returns `{ "error": "invalid input" }` with HTTP 400 when a required field is missing.
- **Endpoint B** returns `{ "message": "Unprocessable Entity" }` with HTTP 422 for the same class of problem on a different route.
- **Endpoint C** — when it hits a unique-constraint violation in Postgres (a database error triggered when you try to insert a value that already exists in a column with a UNIQUE constraint) — returns a raw Postgres error string in a 500 response: `duplicate key value violates unique constraint "jobs_slug_key"`.

The frontend developer needs to display a validation error to the recruiter in a user-friendly way.

**Prompt:** What does the frontend developer have to build to handle errors across all three endpoints — and what happens when a fourth endpoint is added by a different backend developer next month?

Write your answer in your own words. Consider: how many code paths the frontend needs, what happens when the raw Postgres string is surfaced to a user, what the security implication of Endpoint C's response is, and what the maintenance cost looks like as the API grows.

---

The answer to that prompt is the reason this chapter exists. A single error handler, a shared set of named error classes, and one agreed response shape eliminate all of it.
