# 49.02 — The Shortlist: Design Notes

## Junction tables and composite UNIQUE constraints

`shortlist_items` is a junction table — it records a relationship between two entities (applicant and job) without adding data to either entity's own table. The `UNIQUE(applicant_id, job_id)` constraint is the key design decision: it enforces that any given pair appears at most once, at the database level.

This constraint is more reliable than an application-layer check because it survives concurrent requests. If two requests try to shortlist the same job simultaneously, the first INSERT succeeds and the second gets a `23505` unique violation. There is no window between "check if exists" and "insert" where a race condition can produce a duplicate row.

The application handles `23505` by catching it in the service layer and converting it to a `ConflictError` (HTTP 409). This keeps the error handling close to where the constraint is understood — the repo throws the raw pg error, the service converts it to an application-level error.

## The IDOR risk in DELETE

`DELETE /api/applicants/shortlist/:jobId` identifies the shortlist item by `jobId`, not by the shortlist item's `id`. The WHERE clause always includes `applicant_id = $applicantId`:

```sql
DELETE FROM shortlist_items
WHERE applicant_id = $1 AND job_id = $2
```

Even if an applicant provides a `jobId` that belongs to another applicant's shortlist, the DELETE finds no rows (because their `applicant_id` does not match) and returns `404`. No authorisation error is needed — the query itself is the guard.

This is query scoping from Chapter 28 applied to a DELETE. It works because the `applicantId` always comes from the authenticated session (`req.user.userId` → applicants lookup), never from the request body or URL parameters.

## The 100-item limit

The limit is enforced with a COUNT query before INSERT:

```sql
SELECT COUNT(*) FROM shortlist_items WHERE applicant_id = $1
```

This is not perfectly atomic — a concurrent request could pass the count check and both inserts succeed, briefly exceeding the limit. For a 100-item soft limit on a personal bookmark list, this is acceptable. If you need a hard limit, use a CHECK constraint or a trigger in PostgreSQL.

---

## The JOIN for list response

The list query joins across three tables to return useful data:

```sql
SELECT si.id, si.job_id, si.created_at,
       j.title, j.status AS job_status, j.created_at AS job_created_at,
       c.id AS company_id, c.name AS company_name
FROM shortlist_items si
JOIN jobs      j ON j.id = si.job_id
JOIN companies c ON c.id = j.company_id
WHERE si.applicant_id = $1
ORDER BY si.created_at DESC
LIMIT 100
```

Without the JOIN, the client would receive a list of UUIDs and need to make additional requests to get job titles and company names. That is the N+1 problem from Chapter 40. The JOIN eliminates it.

---

## Shortlisted jobs that become closed

An applicant may shortlist a job, and then the recruiter closes that job before the applicant applies. The shortlist item remains — the query returns the job with `job_status = 'closed'`. The frontend can display a "this job is no longer open" badge rather than showing the Apply button.

When the applicant attempts to apply from a shortlisted job (Chapter 50), the apply endpoint re-checks that the job is open. The shortlist is advisory; it does not guarantee the job is still available.
