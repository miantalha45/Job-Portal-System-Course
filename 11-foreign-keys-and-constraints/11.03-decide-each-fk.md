# Deciding every FK in the schema

Walk through each foreign key and choose its `ON DELETE` behaviour. The ones already in the DDL from chapters 8–10 are marked; the ones that were left open are decided here.

## `recruiters.user_id → users(id)` — CASCADE ✓ (already set)

If a user account is hard-deleted, their recruiter profile has no independent meaning. Cascade is correct: a recruiter without an auth record is an orphan. This was set in Chapter 8 and stands.

Note: the `recruiters` table has no inbound FK from `applications`. Applications are owned by applicants, not by recruiters. Deleting a recruiter row — regardless of how it happens — has no direct effect on any `applications` row.

## `recruiters.company_id → companies(id)` — RESTRICT

If you delete a company that still has recruiters, those recruiters would have a `company_id` pointing at nothing — but `company_id` is `NOT NULL`, so `SET NULL` isn't possible. `CASCADE` would silently delete all the recruiters' accounts. Neither is right.

**Decision: `RESTRICT`.** You cannot hard-delete a company while it has recruiters. The application layer must remove or transfer all recruiters first. In practice, companies are never hard-deleted — they're suspended via `companies.suspended = true` ([Chapter 59](../59-admin-moderation-companies/)). If a company truly needs removal, an admin manually removes members, then deletes the company.

## `applicants.user_id → users(id)` — CASCADE ✓ (already set)

Same reasoning as the recruiter: an applicant profile without its auth record is meaningless. Cascade is correct and was set in Chapter 8.

## `admins.user_id → users(id)` — CASCADE ✓ (already set)

Same. An admin record without a user row is an orphan. Cascade stands.

## `jobs.company_id → companies(id)` — RESTRICT

If a company is deleted, all its jobs — and by extension all applications received — would be affected. `CASCADE` here wipes the company's entire hiring history automatically.

**Decision: `RESTRICT`.** You cannot hard-delete a company with jobs. The same soft-delete approach applies: use `suspended` and `verified` flags to take a company off the board without destroying its data. If a company must be hard-deleted, the application layer processes the jobs (and their applications) first. This preserves the historical record for any legal or operational purpose.

## `applications.job_id → jobs(id)` — RESTRICT

An application is evidence that a specific person applied for a specific role. Deleting that job should not silently delete the application — the recruiter may need the application record for audit or reference purposes.

**Decision: `RESTRICT`.** You cannot hard-delete a job that has received applications. Closing a job is done by setting `jobs.status = 'closed'`, not by deleting the row. If a job truly needs to be removed (e.g. posted in error), the application layer archives or reassigns its applications first.

## `applications.applicant_id → applicants(id)` — RESTRICT

This is the most nuanced FK. Deleting an applicant's account should not automatically destroy every application they submitted — the recruiter's view of who applied is part of the hiring record.

**Decision: `RESTRICT`.** Account deletion triggers explicit application handling in the application layer:

- **Anonymise in place** (GDPR path): zero out personal data in the applicant row and the application's `profile_snapshot`, set a `deleted_at` flag, but keep the application row so the recruiter's count and stage history remain intact.
- **Hard-delete with prior cascade**: remove applications first (via explicit SQL), then delete the applicant row. This path loses history but is sometimes required.

The schema enforces nothing about which path you choose — `RESTRICT` simply means you must choose explicitly, not accidentally.

## Complete FK summary

```sql
-- Already set in chapters 8–10
recruiters.user_id    REFERENCES users(id)     ON DELETE CASCADE
applicants.user_id    REFERENCES users(id)     ON DELETE CASCADE
admins.user_id        REFERENCES users(id)     ON DELETE CASCADE

-- Decided in this chapter — add to your learning-log DDL
recruiters.company_id REFERENCES companies(id) ON DELETE RESTRICT
jobs.company_id       REFERENCES companies(id) ON DELETE RESTRICT
applications.job_id   REFERENCES jobs(id)      ON DELETE RESTRICT
applications.applicant_id REFERENCES applicants(id) ON DELETE RESTRICT
```
