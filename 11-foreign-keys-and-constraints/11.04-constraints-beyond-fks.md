# Constraints beyond foreign keys — and when not to use them

## What the schema already enforces

Looking across chapters 8–10, the DDL already contains three types of non-FK constraints:

**`NOT NULL`** — a column must always have a value. Used on anything that is structurally required and has no sensible default: `users.email`, `applicants.full_name`, `jobs.title`, `applications.job_id`. If the value is optional, the column is nullable — no constraint needed.

**`UNIQUE`** — a value must be distinct across all rows. Used on `users.email` (one account per email address), `companies.slug` (one URL identifier per company), `recruiters.user_id` / `applicants.user_id` / `admins.user_id` (one profile per user), and `UNIQUE (job_id, applicant_id)` on applications (one application per job per person).

**`CHECK`** — a value must satisfy a condition. Used for finite enumerations: `users.role`, `users.status`, `jobs.status`, `applications.stage`. The condition is evaluated on every insert and update.

These are **structural invariants** — rules about the shape of data that must hold regardless of which code path creates or changes the record. The database is the right enforcer because it applies universally.

## When the database is NOT the right place

Not every rule belongs in a constraint. The wrong place for a rule is worse than no rule — it bakes business logic into the schema, making it hard to change and impossible to give good error messages.

**Rules that belong in the validation layer ([Chapter 16](../16-request-validation/)):**

| Rule | Why not a DB constraint |
|---|---|
| Job title must be at least 5 characters | Business policy that may change; needs a useful error message to the API caller |
| Email must match a valid format | Complex regex in a CHECK constraint is brittle and gives a terrible error message |
| Deadline must be in the future | A `CHECK (deadline > CURRENT_DATE)` is only evaluated on INSERT/UPDATE — it never re-checks existing rows. The real problems: it blocks test fixtures with past deadlines, fails on historical data restores, and produces a raw database error instead of a user-friendly validation message. |
| Screening answer must match its question's type | Requires cross-row data (`jobs.screening_questions`) — PostgreSQL `CHECK` constraints cannot reference other tables |

**Rules that belong in the application layer:**

| Rule | Why not a DB constraint |
|---|---|
| An applicant can only apply to open jobs | Requires reading `jobs.status` — CHECK on `applications` can't access `jobs` |
| A recruiter can only post jobs in their own company | Requires reading the session's `company_id` — the database has no session concept |
| Stage transitions must follow the pipeline order | Involves comparing old and new values — possible via a trigger, but application logic is clearer |

## The boundary rule

Put it in the database if it is a **structural invariant** — it must be true of the data regardless of context, code path, or time. Put it in the validation or application layer if it is a **business rule** — it depends on context, involves relationships across tables, or needs to produce a user-facing error message.

A useful test: if a database administrator ran a direct `INSERT` bypassing your API, would violating this rule make the data structurally inconsistent in a way that is hard to detect or recover from? If yes, it belongs in the schema.

This heuristic has a subtlety: a duplicate application (same applicant, same job) is a "bad business outcome" — but the `UNIQUE (job_id, applicant_id)` constraint still belongs in the schema, not the application layer, because there is no reliable way for application code to prevent a race condition between two concurrent requests. Uniqueness constraints are structural invariants even when their violation seems like a business error rather than a data corruption. The boundary is about recoverability and enforcement guarantees, not just severity.
