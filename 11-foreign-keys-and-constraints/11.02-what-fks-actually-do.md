# What foreign keys actually do

## The problem they solve

A foreign key is a promise: *this column will always point at a row that exists*. Without it, nothing stops application code from inserting a `jobs` row with a `company_id` that doesn't exist in `companies`, or deleting a `companies` row while `jobs` still reference it. The data becomes internally inconsistent — and you only find out when a query that joins the two tables returns nothing, or crashes, or silently returns partial results.

**Referential integrity** is the guarantee that every FK value points at a row that actually exists. The database enforces it at the insert/update/delete level, regardless of which code path triggers the change — an API request, a background job, a migration script, or a direct SQL session. App code can be bypassed. The database cannot.

## The four ON DELETE behaviours

When you delete a row, any other rows that reference it via FK face one of four fates:

| Behaviour | What happens to referencing rows | Use when |
|---|---|---|
| `NO ACTION` | The delete is **blocked** with an error (checked at end of statement, or end of transaction if the FK is `DEFERRABLE`) | The default — you want to force explicit cleanup but may need deferred checking in complex transactions |
| `RESTRICT` | The delete is **blocked** with an error (checked immediately, cannot be deferred) | You want to force explicit cleanup and explicitly prevent deferral |
| `CASCADE` | Referencing rows are **deleted automatically** | The child is meaningless without the parent and there's no reason to keep it (e.g. a user's session tokens) |
| `SET NULL` | The FK column is set to `NULL` | The child can exist independently; the relationship becomes optional (column must be nullable) |
| `SET DEFAULT` | The FK column is set to its default value | Rare; only makes sense if there's a meaningful placeholder reference. The default value itself must be a valid FK — if the column has no real "fallback" row to point at, this will also fail with a FK violation. |

**`NO ACTION` vs `RESTRICT`:** For the plain (non-deferred) constraints in this schema, they behave identically — both block the delete immediately. The difference matters only if you declare a FK as `DEFERRABLE INITIALLY DEFERRED`, in which case `NO ACTION` lets PostgreSQL defer the check to transaction commit while `RESTRICT` still checks immediately. All FK decisions in chapters 11–13 use `RESTRICT` as an explicit signal that deferral is not wanted.

The default (if you write no `ON DELETE` clause) is `NO ACTION`. Being explicit is better regardless: it signals the choice was made deliberately, not by omission.

## The cascade temptation

`CASCADE` feels ergonomic — it keeps the database tidy automatically. But automatic deletion of referencing rows is a one-way door. There is no undo. In a hiring system, historical data (applications received, stages reached, interviews scheduled) has real value. Losing it because a company was hard-deleted — or an applicant account was blocked — is almost always the wrong trade-off.

The safer default for most FKs in a data-sensitive system: **`RESTRICT`**. It forces the application layer to make an explicit decision about each relationship before the parent row can be removed. The discipline is annoying during development and invaluable in production.
