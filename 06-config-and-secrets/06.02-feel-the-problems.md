# Feel the problems first

Your app boots (Chapter 4) and your services are up (Chapter 5), each reachable at a URL you named — `DATABASE_URL`, `REDIS_URL`. The job now is to get those settings *into* your app the production way. It sounds like plumbing, but configuration done sloppily is where two of the most common production disasters begin: a **secret leaked into Git**, and an app that **boots happily with broken settings** and fails unpredictably hours later.

We'll walk into both problems on purpose, see why the obvious fixes fall short, and let that make the final shape obvious instead of arbitrary.

## Where we're headed

By the end you'll have **one typed, validated configuration module** that is the single source of truth for every setting. It reads everything from the **environment** (never hardcoded), **validates it at startup**, and **refuses to boot** with a clear error if anything required is missing or malformed. Secrets will live in a git-ignored `.env`; a committed `.env.example` will document what's needed.

## Problem 1 — hardcoding

You need a database connection and a secret for signing tokens later. The fastest thing that works is to write the values right where you use them:

```ts
// the tempting first version — config baked into the code
const db = connect("postgresql://portal:localdevpw@localhost:5432/jobportal");
const jwtSecret = "super-secret-signing-key";
```

It works on your laptop. So what's wrong? Two things, both quiet until they're catastrophic:

- **You just wrote a secret into your source.** The moment you commit, that password and `jwtSecret` are in Git history *forever* — exactly the leak you've guarded against since Chapter 4. Deleting the line later doesn't help; history remembers.
- **These values can't change per environment.** Your laptop, a teammate's laptop, staging, and production each need *different* URLs and secrets. A hardcoded string can only be one of them. To deploy, you'd be editing source code — which is precisely how a staging password ends up pointed at the production database.

So hardcoding is out. The values have to come from *outside* the code, from a place with a standard name: the **environment**.

> The principle isn't ad-hoc — it's the **Twelve-Factor App** rule: *configuration lives in the environment, never in the code.* The same compiled app runs everywhere; only the environment around it changes.

## Problem 2 — ad-hoc `process.env`

Node exposes the environment as `process.env`, so the natural next move is to read values from there wherever you need them:

```ts
// better — but scattered, untyped, unvalidated
const port = process.env.PORT;            // the string "3000" — NOT the number 3000
const dbUrl = process.env.DATABASE_URL;   // might be undefined; you find out when it's used
const jwtSecret = process.env.JWT_SECRET; // …and this same pattern, repeated in twenty files
```

No more hardcoded secrets — real progress. But run this in anger and three new problems surface, every one of which bites in *production*, not on your laptop:

- **Everything is a string, or undefined.** `process.env.PORT` is the string `"3000"`, not the number `3000`. `process.env.DATABASE_URL` could be `undefined`. And TypeScript can't catch it — recall Chapter 3: types are erased at runtime, so TS *believes* these are strings even when they're missing.
- **Nothing warns you when a value is missing.** Forget to set `JWT_SECRET` and nothing complains at boot. The app starts *fine* — then crashes deep inside a request, or worse, runs **insecurely**. The failure happens far from its cause, at the worst possible time.
- **There's no single source of truth.** Twenty scattered reads mean twenty places to typo a key, twenty places with no default, and not one file that answers "what configuration does this app even need?"

The environment was the right *source*. Reading it ad-hoc all over the app is the wrong *method*. Next, we fix the method.
