# Build: one validated config module that fails fast

Here's the decision, stated plainly: **exactly one module** reads `process.env`. It validates the whole environment against a schema *at startup*, coerces strings into the right types, and exports a clean, typed `config` object. Everything else in the app imports that object and never touches `process.env` again.

Three properties make this work:

1. **Validate** — check every value up front, so a missing or malformed setting is caught immediately.
2. **Fail fast** — if validation fails, the app *refuses to boot*, loudly, pointing at the exact problem.
3. **Type & coerce** — turn `"3000"` into `3000` once, here, so the rest of the app gets real types.

You already have the validation tool: **zod** from Chapter 3. If it isn't installed yet, add it:

```bash
npm install zod
```

## Write the module

Create **`src/shared/config.ts`** — the only place in the app that reads `process.env`. Read it top to bottom; each part maps to one of the three properties above.

```ts
// src/shared/config.ts — the ONLY place in the app that reads process.env
import { z } from 'zod';

// (1) VALIDATE — declare every variable the app needs, and its rules.
const EnvSchema = z.object({
  NODE_ENV:     z.enum(['development', 'test', 'production']).default('development'),
  PORT:         z.coerce.number().int().positive().default(3000),  // (3) COERCE: "3000" → 3000
  DATABASE_URL: z.string().url(),                                  // required; secrets get no default
  REDIS_URL:    z.string().url(),
  JWT_SECRET:   z.string().min(32),                               // required AND long enough to be safe
});

// Validate the WHOLE environment once, here, at startup.
const parsed = EnvSchema.safeParse(process.env);

// (2) FAIL FAST — if anything is missing or malformed, crash NOW, on purpose.
if (!parsed.success) {
  // log the KEYS and the problem — NEVER the values — then exit
  console.error('✖ Invalid environment configuration', parsed.error.flatten().fieldErrors);
  process.exit(1);
}

// Typed, validated, guaranteed-present. The rest of the app imports THIS.
export const config = parsed.data;
```

Look at what each rule earns you: `z.coerce.number()` hands you a real number instead of a string; `.url()` rejects a malformed connection URL; `.min(32)` rejects a signing secret too short to be safe. And `safeParse` + `process.exit(1)` is the single most important habit in this chapter — **fail fast**. If the config is wrong, the app doesn't limp along; it stops at the door and names exactly what's wrong:

```
$ npm run dev
✖ Invalid environment configuration {
   JWT_SECRET: [ 'String must contain at least 32 character(s)' ],
   DATABASE_URL: [ 'Required' ]
 }
# app exits — fix your config and try again
```

A noisy crash at boot, in front of *you*, beats a quiet misconfiguration that surfaces as someone's weird bug three hours later. Every time.

> ✅ **Do** — fail fast: validate the whole environment at startup and `process.exit(1)` on any problem. Log the **key names** and the validation message so you know what to fix.
>
> ❌ **Don't** — let the app boot with bad or missing config "for now". And never log the *values* (`console.log(process.env)` or the parsed secret) — that drops your `JWT_SECRET` straight into your logs, which are themselves a place secrets leak from.

## Verify

You'll supply real values in the next step, but you can prove the guard works right now: temporarily blank out `JWT_SECRET` (or leave the environment empty) and start the app. It must **refuse to boot** and print a clear error naming `JWT_SECRET` (and any other missing key) — not a stack trace from deep in a request. If it boots anyway, the fail-fast wiring is wrong; fix it before moving on.
