# 56.02 — Scheduling Interviews: Design Notes

## Multiple interviews per application

The schema allows multiple `interviews` rows per application (there is no UNIQUE constraint on `application_id` in the `interviews` table). This is intentional:

- A first interview might lead to a `final_interview` stage, which has its own interview record
- An interview might be rescheduled — cancelling the old one and creating a new one
- Some companies conduct multiple rounds before a single stage advances

The current implementation creates a new interview row on every call. A recruiter calling the endpoint twice for the same application creates two interview rows. This may or may not be the desired behaviour — a future iteration might add a `status` field to interviews (`upcoming`, `cancelled`, `completed`) and enforce at most one `upcoming` interview per application.

For this chapter, creating a new row per call is correct and simple.

## The stage advancement is not transactional with the interview INSERT

The stage UPDATE (`updateApplicationStage`) and the interview INSERT (`createInterview`) are two separate queries using `db.query`. If the interview INSERT fails after the stage UPDATE succeeds, the application stage has advanced but no interview record exists.

This is a small inconsistency. The fix is to wrap both operations in a transaction (using the `pool.connect()` pattern from Chapter 52). For this chapter, the inline approach is acceptable — the failure mode is rare (interview INSERT failing after a stage UPDATE is unusual) and recoverable (a recruiter can manually advance the stage back and retry).

## Email delivery and SMTP failures

`sendInterviewNotification` is awaited inline. If the SMTP server returns an error, the `await` throws and the entire `scheduleInterview` function throws — meaning the HTTP request returns an error even though the interview row is already committed.

This creates a state where the database has the interview but the applicant received no email. Retrying the request would create a second interview row (a duplicate) while sending the email.

Strategies:

1. **Catch email errors, log, do not fail the request.** The interview is created; the email failure is logged for operational follow-up.

   ```ts
   try {
     await sendInterviewNotification(...);
   } catch (emailErr) {
     console.error('Failed to send interview notification:', emailErr);
     // Do not rethrow — the interview was committed successfully
   }
   ```

2. **Move email to a background job** (Chapter 67). The request creates the interview row and enqueues an email job. The job is processed asynchronously. The HTTP response does not wait for the email.

Option 1 is the simplest fix. Option 2 is the correct long-term pattern.

## What `scheduledAt` accepts

The endpoint accepts an ISO 8601 datetime string: `"2026-07-15T14:00:00Z"`. The service converts it with `new Date(body.scheduledAt)`. PostgreSQL stores it as `timestamptz` — always in UTC internally, displayed in the connection's timezone.

Validation should ensure `scheduledAt` is:
- A valid date string (parseable by `new Date`)
- In the future (at least a few minutes from now)

The second constraint prevents scheduling interviews in the past, which is almost always a mistake. Add to your validation layer:

```ts
const scheduled = new Date(body.scheduledAt);
if (isNaN(scheduled.getTime())) throw new ValidationError('scheduledAt is not a valid date');
if (scheduled <= new Date()) throw new ValidationError('scheduledAt must be in the future');
```

## The applicant email source

`findApplicationWithApplicant` retrieves the applicant's email by joining `applications → applicants → users`. This is the correct path — the email is on the `users` row; the `applicants` table does not duplicate it.

The join chain:

```
applications (applicant_id)
  → applicants (user_id)
    → users (email)
```

The email is returned in the same query as the application data — no extra round-trip.
