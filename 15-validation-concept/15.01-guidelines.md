# Guidelines — Chapter 15

By the end of this chapter you will be able to explain why HTTP request validation belongs at the route layer — not inside service functions or at the database — and what each layer is responsible for catching.

## Before you start

No specific prior chapter is a hard prerequisite, but the context you need is already in place:

- The project structure from [Chapter 4](../04-project-bootstrap/) defines `*.schema.ts` files per module — those files are where the validation schemas built in [Chapter 16](../16-request-validation/) will live.
- [Chapter 6](../06-config-and-secrets/) established the fail-fast principle for configuration: validate at startup and crash immediately with a clear error if something is wrong. Boundary validation applies the same principle to every incoming request.

No code is written in this chapter. The next chapter builds the implementation. This one establishes the reasoning so the implementation decisions in Chapter 16 are not arbitrary.

## Rethink impact

> A recruiter sends a `POST /jobs` request with no `title` field. Your route handler reads the body, constructs a SQL INSERT, and fires it at the database. The INSERT hits the `NOT NULL` constraint on `title` and PostgreSQL throws an error. Your catch-all error handler returns a `500 Internal Server Error`. The recruiter's client sees: `"error": "null value in column \"title\" of relation \"jobs\" violates not-null constraint"`.
>
> The recruiter does not know what a constraint is. They do not know what "relation" means. And the response just disclosed an internal table name to whoever sent the request.
>
> Two things failed here. First, the input was not rejected at the route layer before reaching the database. Second, the error handler forwarded a raw database error to the client instead of a safe, structured response. Where should the first failure have been caught, and what should that response have said?
