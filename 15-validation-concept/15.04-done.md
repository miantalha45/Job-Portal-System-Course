# Key takeaways — Chapter 15

- **The boundary is the entry point where untrusted external data enters the system.** Code inside the boundary can trust its inputs; code outside cannot. Validation is the mechanism that enforces the trust line.

- **Validate at the boundary, not scattered through the call stack.** A validation check deep inside a service function has no reliable contract: it may run before or after other logic, produce any error format, and leave the question "what has already been verified?" unanswered for every reader of that code.

- **Validation and database constraints are complementary, not alternatives.** Validation produces user-facing errors for bad client input. Constraints catch race conditions, direct database access, and application bugs. Removing one because the other exists removes either safety or clarity.

- **Fast rejection is cheaper than late rejection.** Catching an invalid field at the route handler avoids executing a database query, running service logic, and unwinding a partially-executed operation. The earlier a bad request fails, the less it costs.

- **The service layer's job is business logic, not input validation.** A service function that receives validated data can be read and tested without asking "but what if this value is null or the wrong type?" That mental overhead disappears when the contract is enforced at the boundary.

1. Your job-posting service function receives a `deadline` field. The validation layer has already verified it is a valid ISO date string. Describe what the service should do with it and explain what the boundary contract means for every layer below the route handler.

2. A colleague says: "We have NOT NULL and CHECK constraints on every important column, so we don't need a validation layer — the database will catch bad input." Explain what the database cannot catch that a validation layer can, and what the validation layer cannot catch without the database's help.
