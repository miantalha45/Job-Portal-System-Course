# Why validate at the boundary

## The wrong place: validating deep in the call stack

```ts
// ❌ Validation scattered through the service layer
// data: any — no static safety; properties accessed without guarantees
async function createJob(data: any) {
  if (!data.title) throw new Error('title required');
  // ... 30 lines later ...
  if (data.title.length > 200) throw new Error('title too long');
  // ... 20 lines later, in a helper ...
  if (!isValidStatus(data.status)) throw new Error('invalid status');
}
```

Every check is ad-hoc, inconsistently formatted, and interleaved with business logic. Some checks happen before DB calls; others happen after. The error format for each is different. Adding a new field means remembering to add its validation in the right place deep inside the function. There is no single answer to "what is the contract for input to this function?"

## What fails without boundary validation

**Leaking internals.** A raw database constraint violation (the rethink prompt scenario) tells the caller the table name, the column name, and the constraint type. That is implementation detail they should never see.

**Inconsistent errors.** Without a validation layer, one endpoint returns `{ "error": "title required" }`, another returns `{ "message": "Title is missing" }`, another throws a 500. Every client has to special-case each endpoint's error format.

**Wasted work.** A request missing a required field still enters the service, allocates objects, executes a database query, and only fails when it hits the constraint — after doing work that could have been skipped with a 400 at the door.

**Trust leakage.** If the service layer validates some things but not others, it is unclear what the service can trust. Developers reading the service code cannot tell whether an input has been validated already or needs defensive checks.

## What boundary validation gives you

**One clear contract.** The validation schema is the complete specification of what valid input looks like. If a value passes the schema, every layer below can trust it without re-checking.

**Consistent 400 errors.** The validation layer produces errors in a consistent format before any business logic runs. [Chapter 17](../17-errors-and-status-codes/) standardizes that format across the whole API.

**Fast rejection.** Bad input is rejected at the entry point, before any service functions are called, before any database queries are executed.

**Separation of concerns.** The service layer handles business logic. The validation layer handles input contracts. The repository layer handles data access. None of them need to reach into each other's responsibilities.

## What validation does NOT replace

Database constraints are not replaceable by validation. They serve different roles.

Validation catches bad input from clients — missing fields, wrong types, out-of-range values — and returns a user-facing error. It runs in the application process.

Database constraints catch the cases that validation cannot: race conditions (two concurrent requests that both pass validation but together violate a UNIQUE constraint), direct database access that bypasses the API entirely, bugs in the application code that accidentally produce invalid data.

The correct relationship: **validation is the intended mechanism; database constraints are the safety net.** Both must exist. Validation that says "remove the NOT NULL constraint because we validate in code" is removing the safety net. Constraints that say "remove validation because the database will catch it" are replacing user-friendly errors with raw database errors.

## The fail-fast principle

The pattern established in Chapter 6 for configuration — validate at startup, crash immediately with a clear message — applies here to every request. Validate at the entry point. Reject immediately. Return a clear error. Do not proceed until the contract is satisfied.
