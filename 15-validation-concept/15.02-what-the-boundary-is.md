# What the boundary is

## The trust line

Every system has a line between the outside world and its own internals. Code inside the line can make assumptions: function arguments have the expected types, IDs exist, required fields are present, values are within expected ranges. Code outside the line cannot be trusted — it comes from users, from other services, from mobile apps, from browsers running JavaScript that someone else wrote.

The **boundary** is the entry point where outside data crosses into the inside. In this project, that is the HTTP request layer: the route handler that receives the raw request body, query string, path parameters, and headers. Everything that arrives through those channels is untrusted until proven otherwise.

## What enters through the boundary

Not all untrusted input is the same. In this project:

- **Request body** — the JSON payload of POST/PUT/PATCH requests. A recruiter creating a job, an applicant submitting an application.
- **Path parameters** — `/jobs/:jobId`, `/companies/:companyId`. A valid UUID shape is expected; a string like `"not-a-uuid"` or a SQL fragment is not.
- **Query parameters** — `?page=2&status=open`. Numbers, enums, optional filters.
- **Request headers** — Authorization tokens, Content-Type. Format and presence are validated here; token authenticity is verified by the auth layer built in a later chapter.

File uploads are also boundary input and are handled separately when object storage is built in a later chapter.

## Where the boundary lives in the project

The `*.schema.ts` file in each feature module is where validation schemas are defined. The route handler is where those schemas are applied — before any service function is called. The service function receives data that has already passed validation and can treat it as trustworthy.

```
HTTP request
    ↓
route handler → validate() → reject with 400/422 if invalid
                           ↓ (if valid)
              service function (trusts its inputs)
                           ↓
              repository / database
```

400 Bad Request covers malformed or unparseable payloads. 422 Unprocessable Content is more precise for a well-formed body that fails schema validation (e.g., a valid JSON object where `deadline` is `"not-a-date"`). [Chapter 17](../17-errors-and-status-codes/) standardizes which status code the API returns for each failure category.

The service layer has no business checking whether `title` is a non-empty string. That check happened at the boundary. If a value reaches the service, the contract is: the boundary already verified it.
