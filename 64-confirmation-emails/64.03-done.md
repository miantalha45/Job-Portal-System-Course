# Chapter 64 — Definition of Done

## Verifiable checklist

```bash
# 1. TypeScript compiles with zero errors
npx tsc --noEmit

# 2. Start API and worker in separate terminals
# Terminal 1: npm run dev
# Terminal 2: npm run worker

# 3. Submit an application and confirm 201 returns quickly
time curl -s -o /dev/null -w "%{http_code}" \
  -X POST http://localhost:3000/api/applications \
  -H "Authorization: Bearer $APPLICANT_TOKEN" \
  -H "Content-Type: application/json" \
  -d "{\"jobId\": \"$JOB_ID\", \"answers\": {}}"
# Expected: "201" printed; total time < 200ms

# 4. Confirm the job appeared and was processed in the worker terminal
# Expected log lines (in the worker terminal):
# [worker] Processing job send-application-confirmation (id: <id>)
# [worker] Job completed: send-application-confirmation (id: <id>)

# 5. Confirm the job is in the completed set (not failed or waiting)
npx ts-node -e "
import queue from './src/shared/queue';
(async () => {
  const completed = await queue.getCompleted(0, 5);
  const found = completed.find(j => j.name === 'send-application-confirmation');
  console.log('Found:', found?.name, 'Status: completed');
  await queue.close();
})();
"
# Expected: "Found: send-application-confirmation Status: completed"

# 6. Confirm email was sent (check Mailtrap or local SMTP inbox)
# The email subject should be: "Application received: <job title> at <company name>"

# 7. Stop the worker, submit another application
# Worker is stopped → job is queued in Redis
redis-cli LLEN "bull:jobs:wait"
# Expected: 1 (job is waiting)

# Start the worker again
npm run worker
# Expected: job is processed immediately on worker startup

# 8. Confirm sendApplicationConfirmationEmail is exported from mailer.ts
npx ts-node -e "
import { sendApplicationConfirmationEmail } from './src/shared/mailer';
console.log('Function exists:', typeof sendApplicationConfirmationEmail);
"
# Expected: "Function exists: function"

# 9. Confirm no direct process.env usage in applications.service.ts
grep 'process\.env' src/modules/applications/applications.service.ts
# Expected: no output (empty)
```

## Quiz

1. An applicant submits a job application. The database transaction commits. Then `queue.add`
   is called, but Redis is temporarily down and throws a connection error. The catch block logs
   the error and the function returns the application anyway. The HTTP response is 201. Describe
   what the user experiences and what is missing from the system state. Is this acceptable?
   Justify your answer.

2. The worker receives the `send-application-confirmation` job and calls
   `sendApplicationConfirmationEmail`. The SMTP server responds with a timeout after 5 seconds.
   What does BullMQ do with the job, given the default configuration (no retry options set)?
   How would adding `{ attempts: 3, backoff: { type: 'exponential', delay: 1000 } }` change
   the outcome?

3. The `applyToJob` service function now calls `queue.add` after the database write. A new
   developer suggests moving `queue.add` to before the database write to "fail fast if Redis
   is down." What is wrong with this suggestion? Give a concrete example of what goes wrong
   if the database write subsequently fails.
