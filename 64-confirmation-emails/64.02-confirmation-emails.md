# 64.02 — Application Confirmation Emails (Walkthrough)

## Before: inline email sending

Before this chapter, `applyToJob` might have looked like this:

```ts
export async function applyToJob(...) {
  // 1. validate (Zod, done in route)
  // 2. write to DB (transaction)
  const application = await repo.createApplication(...);
  // 3. send email — BLOCKS the response
  await mailer.sendApplicationConfirmationEmail(email, jobTitle, companyName);
  return application;
}
```

The HTTP request waits for the SMTP server to accept the email. If the SMTP server is slow
(150ms) or unavailable, the apply endpoint becomes slow or broken — even though the application
was already saved to the database.

## After: async email via queue

```ts
export async function applyToJob(...) {
  // 1. validate (already done)
  // 2. write to DB (transaction)
  const application = await repo.createApplication(...);
  // 3. enqueue — returns immediately after writing the job to Redis
  await queue.add('send-application-confirmation', {
    applicantEmail: ..., jobTitle: ..., companyName: ...,
  });
  return application;   // HTTP 201 is returned now
}
```

`queue.add` writes a JSON blob to Redis and resolves in ~1ms. The SMTP call happens later, in
the worker process.

## Building it step by step

### Step 1 — Add sendApplicationConfirmationEmail to mailer.ts

Open `src/shared/mailer.ts`. The existing transporter is already configured. Add the new
function below the existing email functions:

```ts
export async function sendApplicationConfirmationEmail(
  to: string,
  jobTitle: string,
  companyName: string
): Promise<void> {
  await transporter.sendMail({
    from: config.SMTP_FROM,
    to,
    subject: `Application received: ${jobTitle} at ${companyName}`,
    text: [
      `Thank you for applying to ${jobTitle} at ${companyName}.`,
      `Your application has been received and is under review.`,
      `You will hear back from the hiring team if your profile is a match.`,
    ].join('\n\n'),
  });
}
```

Keep it simple. No HTML template — that is a UI concern, not a course concern.

### Step 2 — Modify applyToJob to enqueue instead of send

In `src/modules/applications/applications.service.ts`, import the queue:

```ts
import queue from '../../shared/queue';
```

Find the point in `applyToJob` after the application is created and add:

```ts
await queue.add('send-application-confirmation', {
  applicantEmail: applicantEmail,
  jobTitle: jobTitle,
  companyName: companyName,
});
```

Where do `applicantEmail`, `jobTitle`, and `companyName` come from? The application transaction
already fetches the job record (for the snapshot in Chapter 51). You can reuse that data. If
not, add a small query or pass the values as parameters to the service function.

### Step 3 — Add the handler to worker.ts

Open `src/worker/worker.ts`. Add the import at the top:

```ts
import { sendApplicationConfirmationEmail } from '../shared/mailer';
```

In the switch statement:

```ts
case 'send-application-confirmation': {
  const { applicantEmail, jobTitle, companyName } = job.data;
  await sendApplicationConfirmationEmail(applicantEmail, jobTitle, companyName);
  break;
}
```

### Step 4 — Verify the flow end-to-end

Start both processes:

```bash
# Terminal 1
npm run dev

# Terminal 2
npm run worker
```

Submit an application:

```bash
curl -X POST http://localhost:3000/api/applications \
  -H "Authorization: Bearer $APPLICANT_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"jobId": "<JOB_ID>", "answers": {}}'
```

Expected in Terminal 1: HTTP 201 returns quickly (< 50ms for the Redis enqueue)
Expected in Terminal 2: worker logs show the job being processed, then the email is sent

## Observing the job in Redis

While the worker is stopped, submit an application. The job sits in the queue:

```bash
redis-cli LLEN "bull:jobs:wait"
# Expected: 1 (or more if multiple applications were submitted)
```

Start the worker. The job is processed and the queue drains.

## What if queue.add fails?

If Redis is unavailable, `queue.add` throws. The application was already saved to the database.
The user gets a 500 error even though their application is persisted. Two options:

1. **Ignore the error** — catch the queue.add error, log it, and still return 201. The email
   is lost. Acceptable for non-critical notifications.
2. **Fail the request** — re-throw. The user must retry the apply action. The application row
   may already exist (idempotency check in Chapter 53 prevents a duplicate).

Option 1 is common for email notifications. Option 2 is required when the background job is
part of a critical business process.
