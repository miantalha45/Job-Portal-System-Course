# Build: the token utility

## Install the library

```bash
npm install jsonwebtoken
npm install --save-dev @types/jsonwebtoken
```

`jsonwebtoken` is the standard Node.js library for JWT issuance and verification. The `@types/jsonwebtoken` package provides the TypeScript type declarations; it goes in `devDependencies` because types are only needed during compilation.

## Update `src/shared/config.ts`

Add two fields to the `EnvSchema` object. The file already exists from Chapter 6; these are the only additions:

```ts
// src/shared/config.ts — additions to EnvSchema
JWT_SECRET:     z.string().min(32),
JWT_EXPIRES_IN: z.string().default('15m'),
```

The full updated schema (showing context, not the full file):

```ts
const EnvSchema = z.object({
  NODE_ENV:       z.enum(['development', 'test', 'production']).default('development'),
  PORT:           z.coerce.number().int().positive().default(3000),
  DATABASE_URL:   z.string().url(),
  REDIS_URL:      z.string().url(),
  JWT_SECRET:     z.string().min(32),
  JWT_EXPIRES_IN: z.string().default('15m'),
});
```

**Why `.min(32)` on `JWT_SECRET`?** HS256 uses the secret as the HMAC key. A secret shorter than 32 bytes provides weaker security against brute-force key searches. Enforcing the minimum at startup — before any token is ever signed — means the app refuses to boot with a weak key. You learn about the misconfiguration immediately, not when a security review catches it later.

**Why `JWT_EXPIRES_IN` in config with a default?** The token lifetime is a piece of runtime configuration. In production it is `'15m'`. In a test that needs to verify expiry behaviour, you can set `JWT_EXPIRES_IN=1s` in the test environment and have an expired token without sleeping for 15 minutes. If the value were hardcoded inside `token.ts`, tests would require either mocking or waiting. Config makes the lifetime overridable without touching application code.

Add the value to your `.env` file:

```
JWT_SECRET=replace-this-with-a-random-string-of-at-least-32-chars
JWT_EXPIRES_IN=15m
```

Generate a real secret: `node -e "console.log(require('crypto').randomBytes(48).toString('hex'))"`. Do not use the placeholder above in any environment.

## `src/shared/token.ts`

```ts
// src/shared/token.ts
import jwt, { JsonWebTokenError, TokenExpiredError } from 'jsonwebtoken';
import { config } from './config';
import { UnauthorizedError } from './errors';

// Input shape for signing — iat and exp are absent here because jwt.sign
// adds them automatically based on the expiresIn option.
interface SignInput {
  sub:  string;
  role: 'admin' | 'recruiter' | 'applicant';
}

// Shape of the decoded payload after a successful jwt.verify call.
// Includes iat and exp because jwt.sign embeds them at issuance time.
export interface TokenPayload {
  sub:  string;
  role: 'admin' | 'recruiter' | 'applicant';
  iat:  number;
  exp:  number;
}

export function signAccessToken(payload: SignInput): string {
  // config.JWT_EXPIRES_IN is typed as string. @types/jsonwebtoken types
  // expiresIn as StringValue (a branded type from the ms package), which is
  // narrower than string. The cast to any silences the type mismatch without
  // changing runtime behaviour — '15m' is a valid ms string regardless.
  return jwt.sign(payload, config.JWT_SECRET, {
    expiresIn: config.JWT_EXPIRES_IN as any,
  });
}

export function verifyAccessToken(token: string): TokenPayload {
  try {
    // jwt.verify returns JwtPayload | string. The cast to TokenPayload is a
    // type assertion, not a runtime check. We trust it here because this server
    // is the only issuer of tokens signed with JWT_SECRET, and signAccessToken
    // above controls the payload shape. If the signature verification passes,
    // the payload is what we put there.
    return jwt.verify(token, config.JWT_SECRET) as TokenPayload;
  } catch (err) {
    // TokenExpiredError must be caught before JsonWebTokenError because
    // TokenExpiredError extends JsonWebTokenError — catching JsonWebTokenError
    // first would match TokenExpiredError before reaching this branch.
    if (err instanceof TokenExpiredError) {
      throw new UnauthorizedError('Token expired');
    }
    if (err instanceof JsonWebTokenError) {
      throw new UnauthorizedError('Invalid token');
    }
    throw err;
  }
}
```

---

## Why each part is written this way

### Two types, not one

`SignInput` and `TokenPayload` describe different shapes at different points in the token lifecycle:

- `SignInput` is what you pass *into* `jwt.sign`. It has `sub` and `role`. No `iat`, no `exp` — those are added by the JWT library automatically based on the `expiresIn` option.
- `TokenPayload` is what comes *out of* `jwt.verify`. It has `sub`, `role`, `iat`, and `exp` — the full decoded payload, including the timestamps that `jwt.sign` embedded.

Using one interface for both would require marking `iat` and `exp` as optional in the sign input (where they are irrelevant) or as required in the verify output (where they are always present). Separate types make each use correct and self-documenting.

`TokenPayload` is exported; `SignInput` is not. Callers of `verifyAccessToken` receive a `TokenPayload` and can read `iat` and `exp`. Callers of `signAccessToken` pass `{ sub, role }` — there is nothing to export.

### `TokenPayload` lives in `token.ts`, not in routes

The payload type is the authoritative definition of what a verified token contains. Every consumer of `verifyAccessToken` — middleware, tests, future token utilities — gets the same type. If `TokenPayload` lived in a route file, it would be a module-local type that other files either duplicate or import from an unexpected place. The shared token utility is the right home: it owns the sign/verify contract and the type that contract produces.

### Catching specific error types

`jwt.verify` throws on two distinct failure conditions. You must handle them separately because they mean different things operationally:

- **`TokenExpiredError`** — the token is well-formed and the signature is valid, but `exp` is in the past. This is a legitimate token that ran out of time.
- **`JsonWebTokenError`** — the signature did not verify, the token is malformed, or the token is structurally invalid. This means the token was tampered with, truncated, or fabricated.

The catch order matters: `TokenExpiredError` extends `JsonWebTokenError`. If you catch `JsonWebTokenError` first, every `TokenExpiredError` would match that branch and the `TokenExpiredError` branch would be unreachable. Always catch the more specific subclass first.

Both conditions become `UnauthorizedError` for the client — there is no value in telling the client which one occurred, as the correct action in both cases is to re-authenticate. But the messages differ (`'Token expired'` vs `'Invalid token'`), which aids server-side debugging and logging. Chapter 22 will use this distinction in the refresh flow: a client receiving 401 after a request with an access token should attempt to refresh; if the refresh also fails with 401, the user must log in again.

The bare `throw err` at the end re-throws any error that is neither of the two JWT-specific types — a programming error in the token utility itself, for instance. The error handler in Chapter 17 will catch it and return a 500, which is correct.

### `jwt.decode()` vs `jwt.verify()` — what each one proves

`jwt.decode(token)` splits the token on dots, base64-decodes the payload, and returns the JSON object. It does not touch the signature. It does not contact any server. It does not know whether the token was issued by your server or fabricated in a text editor. It will happily decode a completely forged token.

`jwt.verify(token, secret)` does everything `decode` does, and then recomputes the HMAC signature using the same secret. It compares the computed signature to the one embedded in the token. If they match, the payload is trustworthy — it was produced by a holder of this secret. If they do not match, the payload cannot be trusted, regardless of what it claims.

Stated simply: decode tells you what the token claims. Verify tells you what the token proves.

Using `jwt.decode()` on the server to extract a user ID would be a security vulnerability — you would be trusting a payload without checking whether it was issued by your own server. Any client could craft a token with `{ "sub": "admin-uuid", "role": "admin" }` and your server would accept it. `verifyAccessToken` uses `jwt.verify` exclusively. There is no legitimate server-side use for `jwt.decode` on incoming tokens.
