# Build: the auth middleware

## Why `req.user` does not exist by default

Express ships a `Request` interface that includes `method`, `headers`, `body`, `params`, `query`, and similar HTTP properties. It does not include `user` because Express is not an authentication framework — it does not know what shape your user identity takes.

When the auth middleware verifies a token and extracts `{ userId, role }`, it needs to attach that identity somewhere accessible to downstream route handlers. The natural place is `req.user`. But assigning `req.user = { userId, role }` in TypeScript produces a compiler error: `Property 'user' does not exist on type 'Request'`.

The solution is TypeScript's declaration merging. You can add a `.d.ts` file that augments the `Express.Request` interface. TypeScript merges the augmentation with the original interface definition and the combined type is used everywhere.

---

## `src/types/express.d.ts`

Create this file. The directory `src/types/` may not exist yet; create it.

```ts
// src/types/express.d.ts
declare namespace Express {
  interface Request {
    user?: {
      userId: string;
      role:   'admin' | 'recruiter' | 'applicant';
    };
  }
}
```

Two things to get right here:

**The namespace is `Express`, not `express`.** TypeScript merges based on exact namespace and interface name. `Express.Request` is the augmentation point that Express types expose. Using `express.Request` (lowercase) references the type alias, not the mergeable interface, and the augmentation will not work.

**The `user` property is optional (`?`).** A request that has not passed through `authMiddleware` does not have `user` attached. Making it optional reflects reality: not all routes use the middleware. On protected routes — where `authMiddleware` runs before the handler — the middleware either attaches `user` or throws, so `req.user` is always defined by the time the handler runs. TypeScript cannot infer this from control flow across middleware boundaries, so the optional marker is a runtime guarantee the developer must reason about. If TypeScript's strictness matters to you, cast inside the handler: `const { userId } = req.user!`.

## `src/shared/auth-middleware.ts`

```ts
// src/shared/auth-middleware.ts
import { Request, Response, NextFunction } from 'express';
import { verifyAccessToken } from './token';
import { UnauthorizedError } from './errors';

export function authMiddleware(req: Request, res: Response, next: NextFunction): void {
  const authHeader = req.headers.authorization;

  if (!authHeader || !authHeader.startsWith('Bearer ')) {
    return next(new UnauthorizedError('Missing or malformed Authorization header'));
  }

  const token = authHeader.slice(7); // remove "Bearer " prefix (7 chars)

  if (!token) {
    // Header was exactly "Bearer " with nothing after — token is absent.
    return next(new UnauthorizedError('Missing or malformed Authorization header'));
  }

  try {
    const payload = verifyAccessToken(token);
    req.user = { userId: payload.sub, role: payload.role };
    next();
  } catch (err) {
    next(err);
  }
}
```

### What each part does

**`authHeader.startsWith('Bearer ')`** — the Authorization header value must begin with `Bearer ` (with a trailing space). RFC 6750 — the HTTP Bearer Token standard — specifies this format: a scheme name (`Bearer`) followed by a space and the token string. Rejecting anything that does not match this prefix avoids passing a malformed or empty string to `verifyAccessToken`.

**`authHeader.slice(7)` and the empty check** — removes the seven-character prefix `'Bearer '`. The empty-string check immediately after handles the edge case where the header is exactly `"Bearer "` with no token following — `startsWith` passes, but there is nothing left to verify.

**`verifyAccessToken(token)`** — calls `jwt.verify` inside a try/catch (defined in `token.ts`). If the token is invalid or expired, `verifyAccessToken` throws an `UnauthorizedError`. The `catch` block here passes that error to `next`, which routes it to the error handler from Chapter 17.

**`req.user = { userId: payload.sub, role: payload.role }`** — attaches the verified identity to the request. The property name `userId` is intentional: it is the application-level identifier for the user, not the raw `sub` claim name from the JWT spec. Route handlers read `req.user.userId`, not `req.user.sub`. This insulates route handlers from the JWT payload structure.

**`return next(...)`** on the early exit — the `return` prevents execution from continuing into the `try` block. Without `return`, Node.js would execute the `next(error)` call and then continue to the `try` block, calling `verifyAccessToken` on a malformed or absent token string.

## Using the middleware on a protected route

```ts
// Example: a protected route
import { Router } from 'express';
import { authMiddleware } from '../../shared/auth-middleware';

const router = Router();

router.get('/profile', authMiddleware, async (req, res, next) => {
  try {
    // req.user is guaranteed to be defined here:
    // authMiddleware either attaches it or calls next(UnauthorizedError)
    const { userId, role } = req.user!;

    // Use userId to fetch the user's profile from the database
    // ...

    res.json({ userId, role });
  } catch (err) {
    next(err);
  }
});
```

The middleware is listed before the route handler in the argument list. Express calls middleware and route handlers in the order they are listed. If `authMiddleware` calls `next(error)`, Express skips the async handler and routes the error to the error handler. The handler only runs if `authMiddleware` calls `next()` with no arguments.

## Session-based auth vs JWT auth

The auth middleware in this chapter performs no database queries. It extracts the token from the header, calls `jwt.verify`, and attaches identity to the request. That is all.

In a session-based system, the equivalent middleware would:

1. Read a session cookie from the request.
2. Look up the session ID in Redis or the database.
3. Fetch the associated user record.
4. Attach the user to the request.

That is one Redis or database query per authenticated request, before any business logic runs. At low traffic this is acceptable. At high traffic it becomes a bottleneck: a route that receives 1,000 concurrent requests generates 1,000 session lookups before doing any real work.

JWT auth trades that per-request lookup for a CPU cost: an HMAC-SHA256 computation (microseconds). The identity is in the token; the server trusts the signature. No network round-trip, no storage lookup.

The cost is irrevocability. A session row can be deleted — the user is logged out immediately. A JWT cannot be deleted from anywhere, because it does not live anywhere. It expires on its own timeline. A user whose account is suspended after an admin action will still have a valid access token for up to 15 minutes. A session-based system can terminate that session instantly.

This is why the two-token pattern in Chapter 18 exists: stateless access tokens (fast, irrevocable) plus revocable refresh tokens (stored in the database, can be deleted). The access token provides speed; the refresh token provides control. You build the refresh side in Chapter 22.
