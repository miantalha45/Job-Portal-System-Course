## Log It

**Why does `verifyAccessToken` throw `UnauthorizedError` for both expired and tampered tokens, when the causes are different?**

From the client's perspective, both conditions mean the same thing: re-authenticate. Whether the token is expired or forged, the correct client response is to either refresh (Chapter 22) or redirect to login. Sending different error codes for expired vs tampered would tell a potential attacker information about the server's token state that provides no benefit to a legitimate client. The distinction matters for server-side logging — log it there — but not for the response body.

**Why is `req.user` typed as optional even on protected routes?**

TypeScript resolves types statically. It cannot follow the runtime guarantee that `authMiddleware` either attaches `req.user` or throws before the handler runs. From TypeScript's static view, a `Request` arrives at the handler and `user` may or may not be set, because the type definition allows both. The non-null assertion `req.user!` is the correct mechanism: you are telling the compiler that you, the developer, know this property is present at this point because of a runtime invariant that the type system cannot see. This is an acceptable use of `!`; it is not suppressing a genuine uncertainty.

## Quiz

**Q1.** The JWT payload contains `role: 'recruiter'`. A recruiter is promoted to company owner. You update the role in the database. How long until their JWT reflects the new role — and what does this tell you about where role changes take effect in a JWT-based system?

Up to 15 minutes — the remaining lifetime of the access token they currently hold. The database update is immediate, but the access token was signed with the old role and remains valid until its `exp`. Any route handler reading `req.user.role` will see `'recruiter'` until the token expires and the user logs in again (or refreshes, in Chapter 22's flow).

This tells you something fundamental about JWT-based auth: the token is a snapshot of identity at the moment of issuance. Role changes, account suspensions, and permission updates do not propagate to existing access tokens — they take effect only when the next token is issued. If your system requires immediate propagation of role changes, you need either very short token lifetimes or a revocation mechanism (a DB lookup per request, which reintroduces the cost JWT was meant to avoid). The 15-minute access token is the trade-off: long enough for usability, short enough to bound the staleness window.

**Q2.** Your `verifyAccessToken` catches `TokenExpiredError` and throws `UnauthorizedError`. A client receives a 401 with `code: UNAUTHORIZED`. How does the client know whether the token was expired vs. tampered vs. completely absent — and should it know?

With the current design, the client cannot distinguish them from the response body alone. All three conditions produce `401 { "error": { "code": "UNAUTHORIZED" } }`. The message text differs (`"Token expired"`, `"Invalid token"`, `"Missing or malformed Authorization header"`), so a client parsing the message string could distinguish them — but message strings are for humans, not machines, and parsing them creates a fragile dependency on exact phrasing.

Whether the client should know depends on what it would do differently. For "expired": attempt a refresh. For "tampered": there is nothing the client can do — it received a token that was modified in transit or storage, which should not happen in a correctly implemented client. For "absent": the client forgot to attach the header.

A client that needs to implement automatic refresh (which Chapter 22 enables) benefits from knowing a token was expired vs invalid. One approach is a finer-grained error code: `"code": "TOKEN_EXPIRED"` vs `"code": "UNAUTHORIZED"`. Another is a dedicated `WWW-Authenticate` response header. The current design keeps the error surface small and consistent. Whether to add finer granularity is a product decision — make it deliberately, not accidentally.

**Q3.** A developer suggests decoding the JWT on the client to read the user's role and show/hide UI elements. The server still verifies the JWT on every request. Is this safe — and what is the client trusting when it reads the JWT payload directly?

It is safe in the sense that no security boundary is violated. The client is not granting access based on the decoded role; the server still verifies the token on every request and enforces authorization server-side. A forged token that a malicious client decodes to show a fake "admin" UI does not grant that client admin access to the API — the server will reject the token.

What the client is trusting when it reads the JWT payload without verifying the signature is the signature of the token itself — indirectly. The client received the token from the server over HTTPS. If HTTPS was not compromised, the token is what the server issued. The client does not have the server's signing secret, so it cannot verify the signature directly. But it does not need to: the server will verify it on the next request.

The subtlety: `jwt.decode()` on the client is not the same as `jwt.verify()` on the server. The client is not making a security decision — it is reading metadata to drive UI state. The security decision (is this user actually allowed to do X?) happens on the server. This division of responsibility is correct, provided the client is not the last line of defence.

The risk to name clearly: if the client shows UI elements based on `role: 'admin'` decoded from the token, and the server correctly rejects actions taken through those UI elements by non-admins, then a user who manually decodes a token and modifies their local UI state sees an admin interface but cannot actually do admin things. That is an acceptable outcome. If the client hides UI elements and the server's authorization check is missing or incomplete, the security depends entirely on UI visibility — which is no security at all.
