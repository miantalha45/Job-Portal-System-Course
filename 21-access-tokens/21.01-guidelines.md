## Rethink impact: identity without a database

Consider this scenario. A recruiter at BrightBuild calls `GET /jobs/mine` — a protected route that returns only jobs belonging to their company. The route handler needs to know which recruiter is calling it.

Without a token, the server has two choices. It either requires a session ID in a cookie and looks that session up in Redis or the database on every request — one DB query before any business logic runs — or it requires the client to send credentials (email and password) with every request, which is worse.

With a JWT, the route handler reads `req.user.userId` and `req.user.role`. No database query. The identity arrived in the token, was verified cryptographically, and was attached to the request by middleware. The handler can proceed directly to its own query.

That is the gain. But there is a cost worth naming clearly.

The JWT is signed, not encrypted. Anyone who holds the token can decode its payload with `jwt.decode()` — or simply paste it into jwt.io. The `sub`, `role`, `iat`, and `exp` fields are visible. This is by design: the server does not need to hide the payload from the bearer. The bearer is the user. What the signature guarantees is that the payload has not been tampered with since the server issued the token.

The deeper cost is irrevocability. Once the server signs a token, that token is valid until `exp`. There is no list of valid tokens for the server to check against. If a recruiter's access token is stolen — from browser storage, from a proxy log, from a compromised machine — the attacker can use it for up to 15 minutes. The server cannot stop them before expiry without introducing the very DB lookup the JWT was supposed to eliminate.

This is not a flaw in the design. It is the trade-off the threat model accepted in Chapter 18. A 15-minute window is short enough that the damage is bounded. Chapter 22 contains the refresh token, which has a longer lifetime but can be revoked (it is stored in the database). The two-token pattern manages the trade-off: stateless verification for access tokens, revocable storage for refresh tokens.

Keep that trade-off in mind throughout this chapter. When you see `verifyAccessToken` succeed without a DB call, that is the feature. When you wonder what happens if a token is stolen, the answer is: it expires in 15 minutes, and the threat model decided that is acceptable.
