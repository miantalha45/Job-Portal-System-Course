# Chapter 53 — Idempotent, Safe-to-Retry Application

## What you will build

Make the application submission endpoint safe to retry. A client that submits, loses the response, and retries will receive the same result — no duplicate applications are created.

## Learning goals

- Understand the idempotency problem in HTTP POST endpoints
- Use `ON CONFLICT DO NOTHING` (already in place) as the database-level idempotency guarantee
- Return consistent results on retry: same application IDs, same `created`/`skipped` split
- Understand why the UNIQUE constraint is the authoritative guarantee, not the application-layer check

## Prerequisites

- Chapter 50: `ON CONFLICT (job_id, applicant_id) DO NOTHING` already in `insertApplication`
- Chapter 52: transaction in place

## The problem

```
1. Client sends POST /api/applicants/apply → { jobIds: ["job-A"] }
2. Server processes, inserts application row, commits transaction
3. Response is lost (network timeout, client crash)
4. Client retries: POST /api/applicants/apply → { jobIds: ["job-A"] }
5. Without idempotency: a second application row is created → duplicate
6. With idempotency: the retry returns the existing application → no duplicate
```

This is not a theoretical concern. Mobile clients on flaky connections retry frequently. Frontend frameworks with loading states sometimes submit twice on double-tap. The server must be safe under any number of identical retries.

---

## The UNIQUE constraint is the guarantee

The `applications` table has:

```sql
UNIQUE(job_id, applicant_id)
```

This means the database physically cannot contain two rows with the same `(job_id, applicant_id)` pair. `ON CONFLICT DO NOTHING` makes the retry a silent no-op — the INSERT is accepted by the endpoint, produces no error, and results in exactly one row.

Application-layer checks (pre-flight `checkExistingApplications`) are an optimisation for user experience — they let us populate the `skipped` list and report which jobs were already applied to. But they are not the idempotency guarantee. The UNIQUE constraint is.

## Returning the existing application on retry

The current `insertApplication` returns `null` when `DO NOTHING` fires (already applied). For full idempotency, return the existing application:

```ts
// applicants.repo.ts — update insertApplication
export async function insertApplication(
  client: PoolClient,
  applicantId: string,
  jobId: string,
  answers: unknown,
  snapshot: unknown
) {
  const result = await client.query(
    `INSERT INTO applications (job_id, applicant_id, answers, snapshot)
     VALUES ($1, $2, $3, $4)
     ON CONFLICT (job_id, applicant_id) DO NOTHING
     RETURNING id`,
    [jobId, applicantId, JSON.stringify(answers), JSON.stringify(snapshot)]
  );

  if (result.rows[0]) {
    return { id: result.rows[0].id, created: true };
  }

  // Row already existed — fetch it
  const existing = await client.query(
    `SELECT id FROM applications WHERE job_id = $1 AND applicant_id = $2`,
    [jobId, applicantId]
  );
  return { id: existing.rows[0].id, created: false };
}
```

The service updates accordingly:

```ts
const application = await repo.insertApplication(client, profile.id, jobId, answers, snapshot);
if (application.created) {
  created.push(application.id);
} else {
  skipped.push(jobId);
}
```

On a retry, all jobs will come back with `created: false` and land in `skipped`. The response is:

```json
{ "created": [], "skipped": ["job-A"] }
```

The client receives an HTTP 201 response both times. The response body differs (`created` vs `skipped`), but both responses are valid — no error is thrown, no duplicate is created.

## Idempotency key (advanced, optional)

Some APIs use an explicit `Idempotency-Key` header. The client generates a UUID, sends it with the first request, and the server stores the response keyed to that UUID. On retry, the server detects the duplicate key and returns the cached response — byte-for-byte identical.

This pattern is required when:
- The operation is not naturally idempotent at the data layer (e.g., charging a credit card)
- The client needs byte-identical responses (including exact timestamps)

For application submission, the UNIQUE constraint makes the operation naturally idempotent. An explicit idempotency key is not required, though it could be added for higher-confidence replay detection.
