# 53.02 — Idempotency: Design Notes

## What idempotent means

An operation is idempotent if applying it multiple times produces the same result as applying it once. HTTP `GET`, `PUT`, and `DELETE` are defined as idempotent by the HTTP spec. `POST` is not — it is defined as non-idempotent by default. That is why submitting a form twice can create two orders, charge a card twice, or submit two job applications.

Making a `POST` endpoint idempotent requires deliberate design. The UNIQUE constraint approach is the most reliable because it operates at the database layer, beneath the application code.

---

## ON CONFLICT DO NOTHING vs ON CONFLICT DO UPDATE

Two PostgreSQL upsert variants:

```sql
-- Variant A: DO NOTHING — silently skip the conflicting insert
INSERT INTO applications (job_id, applicant_id, answers, snapshot)
VALUES ($1, $2, $3, $4)
ON CONFLICT (job_id, applicant_id) DO NOTHING
RETURNING id;
-- Returns 0 rows if the conflict fires.

-- Variant B: DO UPDATE with a no-op — always return the row
INSERT INTO applications (job_id, applicant_id, answers, snapshot)
VALUES ($1, $2, $3, $4)
ON CONFLICT (job_id, applicant_id) DO UPDATE
  SET created_at = EXCLUDED.created_at  -- no-op: sets to same value
RETURNING id;
-- Returns the row (original or new) in all cases.
```

`DO NOTHING` with a follow-up SELECT (as implemented in Chapter 53) and `DO UPDATE` no-op both achieve the same end result. `DO UPDATE` is more concise but semantically misleading — it implies an update when there is none. `DO NOTHING` + SELECT is clearer about intent.

---

## The pre-check is not the guarantee

The pre-flight `checkExistingApplications` runs before the transaction. It reads committed data. Between that read and the transaction INSERT, another request could insert the same application (if the applicant's browser double-submits). Without the UNIQUE constraint, both inserts would succeed and produce two rows.

With the UNIQUE constraint:
1. Pre-check: no existing application found
2. Request A begins transaction, inserts application
3. Request B begins transaction, attempts to insert the same application
4. Request B hits the UNIQUE constraint → `DO NOTHING` fires → returns existing row
5. Both requests commit successfully with one row in the database

The UNIQUE constraint resolves the race. The pre-check is an optimisation (avoids the INSERT + SELECT round-trip when the duplicate is already known before the transaction), not a safety net.

## HTTP status on retry

Returning 201 on a retry is debatable. Options:

| Status | Rationale | Drawback |
|--------|-----------|----------|
| 201 Created | Idiomatic for "submission accepted" regardless of whether a new row was created | Technically, nothing was created on retry |
| 200 OK | "Here is the existing resource" | Breaks clients that check for 201 to detect new creations |
| 409 Conflict | "This already exists" | Treats retry as an error, causing clients to log false failures |

201 is the most practical choice for application submission. The response body (`created` vs `skipped`) gives the client all the information it needs to distinguish a first submission from a retry. The HTTP status code does not need to encode this distinction.

---

## Idempotency and the snapshot

On retry, `DO NOTHING` fires — the existing row keeps its original snapshot. The snapshot from the retry is discarded. This is correct: the snapshot should represent the profile at first submission, not at retry time.

If the applicant edited their profile between the first submission and the retry, the retry does not update the snapshot. This is the expected behaviour — the snapshot is immutable.
