# The choice — and the concepts that justify it

For this project you'll use a **relational database**, and specifically **PostgreSQL** (Postgres). Let's make sure you can defend *why*, not just repeat it — because the reasons are the actual learning here.

The case, in one breath: a job portal's hardest requirements are all-or-nothing submission, honest ownership, reading across relationships, and never losing or duplicating an application. Every one of those is a guarantee a relational database gives you at the lowest level. The named bundle of those guarantees is **ACID** — so let's take it apart properly.

## ACID and transactions — the guarantee under your hiring data

Relational databases promise **ACID**, four guarantees that travel together. Read each through the lens of an application submission:

- **Atomicity** — a transaction is all-or-nothing. Either *every* part of an application submission lands (the application, the snapshot, the answers, the counter bump) or *none* of it does. This is exactly the all-or-nothing requirement from earlier.
- **Consistency** — every committed transaction leaves the database obeying all its rules (foreign keys, uniqueness, constraints). You can never commit a half-valid state — e.g. an application pointing at a job that doesn't exist, or a second application for a job this applicant already applied to.
- **Isolation** — concurrent transactions don't trip over each other; each runs as if it were alone. Two requests trying to create the same applicant's application for the same job *at the same instant* won't both succeed — isolation plus a uniqueness rule is how "one application per applicant per job" holds even under a double-click or a retry.
- **Durability** — once a transaction commits, it survives a crash. An applicant who got a confirmation will still be in the recruiter's list after the server restarts.

Two new words to keep straight: a transaction that **commits** has landed for good; one that **rolls back** is thrown away entirely, leaving the data exactly as it was before it started.

Here's what a transaction *looks like* — the **shape**, not your submission code (you'll write that in [Chapter 52](../52-application-transaction/)):

```sql
BEGIN;                                                       -- start: nothing is real yet
  INSERT INTO applications (applicant_id, job_id, status)    -- one application for this job
         VALUES ($1, $2, 'submitted');
  INSERT INTO screening_answers (application_id, ...) ...;   -- this job's screening answers
  INSERT INTO resume_snapshots (application_id, ...) ...;    -- freeze the résumé/profile as sent
  UPDATE jobs SET applicant_count = applicant_count + 1      -- keep the recruiter's count accurate
         WHERE id = $2;
COMMIT;                                                      -- all of it lands together…
-- ROLLBACK;                                                 -- …or if anything failed, NONE of it happened
```

Either every line commits, or the database throws *all* of it away and the data is exactly as it was before. That all-or-nothing boundary is **atomicity**, and it's why a half-finished submission can never leave you with screening answers recorded against an application that doesn't exist, or a counter bumped for an applicant who isn't really there.

For a job portal, **atomicity** and **isolation** are not nice-to-haves — they're the reason an application is never lost, never half-recorded, and never silently doubled. You'll lean on them directly in [the application transaction (Chapter 52)](../52-application-transaction/) and the [idempotent, safe-to-retry submission (Chapter 53)](../53-idempotent-application/).

## Why this beats the document-store version

Recall the nested-blob temptation from earlier — the whole submission in one document. Even there, the two *other* documents the submission must touch (each job's applicant count, the applicant's record) live outside the blob, and making all of them all-or-nothing is exactly what ACID gives you for free across tables and what a document store historically made you engineer by hand. The relational model doesn't make the hard guarantee *possible* — it makes it the **default**.

> 💡 **Hint — a way to test any "which database?" decision.** List the three or four things your system absolutely must never get wrong. For a job portal that's *a lost application, a duplicated application, and broken ownership between companies and their jobs*. Then ask which model enforces those for you versus which leaves them to application code you must write perfectly every time. The answer usually picks itself.
