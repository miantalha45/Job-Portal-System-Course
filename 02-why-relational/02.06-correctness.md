# Applications and hiring decisions demand correctness

There's no money moving through this portal — but don't mistake that for "the data doesn't have to be exactly right." Hiring data is the kind of data where *almost correct* is a real failure:

- **An application must never be silently lost.** An applicant who clicks "apply" and gets a confirmation must actually be in the recruiter's list. "Probably saved" is not acceptable.
- **An application must never be silently double-submitted.** If a flaky network makes the applicant click twice, or a retry fires, they must end up with **one** application, not two — recruiters reviewing the same person twice is a real, visible bug.
- **Uniqueness must hold: one application per applicant per job.** That rule has to be true even when two requests race each other at the same millisecond.
- **States and deadlines must stay consistent.** A job that's `closed` shouldn't accept new applications; an application's status (`submitted`, `under_review`, `rejected`) must move in sane steps, never land in two states at once.

Notice the pattern across this whole argument: a job portal's hardest requirements are all about **relationships and guarantees between many pieces of data** — all-or-nothing submission, honest ownership, reading across relationships, no lost or duplicated applications. That is precisely the home turf of the relational model. The document database's superpower — a self-contained, flexible blob — is least useful exactly where a job portal is hardest.

So the requirement is *correctness over convenience*. And there's a specific, named set of guarantees that delivers it — the **ACID** properties of a relational database — which is exactly what the next sub-chapter is about, and the reason we land on the choice we do.
