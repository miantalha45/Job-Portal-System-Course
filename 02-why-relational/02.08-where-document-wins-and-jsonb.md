# Being fair: where document databases win — and the hybrid you'll actually use

Good engineering isn't tribal, and in a design review you'll be expected to know the *other* side honestly. Document databases genuinely shine — and let's use *our* job portal for each, not abstract examples:

- **Your data is self-contained and read as a whole.** A single job's full detail page — title, description, attributes, screening questions — fetched and rendered in one go, rarely joined to anything else. A blob is a perfectly natural shape for that one read.
- **The shape varies wildly and you rarely query *across* records.** This is *exactly* a job's per-role attributes. An engineering role's `tech_stack` and `seniority` share nothing with a sales role's `commission_plan` and `territory`. They differ from one role to the next, and you almost never query across them.
- **You need to scale writes horizontally** beyond what a single relational primary comfortably handles, and you can relax strict cross-record consistency to get it. For us that's something like an append-only stream of **"job viewed" events** for analytics — sheer volume matters there, transactional correctness doesn't (a missed view count is harmless; a missed application is not).

Two of those three are things our job portal genuinely has — so the tension is real, not academic. The **wildly varying job attributes** especially are a true fit for the document model. So should you reach for MongoDB after all?

## The production answer: Postgres gives you both, via JSONB

The senior move isn't to switch databases — it's that **Postgres gives you both worlds in one table.** Postgres has a **JSONB** column type that stores a flexible, queryable JSON document *inside* a relational row. So your `jobs` table keeps the structured, related, must-be-correct fields as **real columns with real foreign keys**, and parks the free-form, per-role attributes in a **JSONB** field:

```
jobs
  id          uuid        (primary key)
  company_id  uuid        (foreign key → companies.id)   ← relational: ownership, enforced
  title       text                                       ← relational: every job has one, you sort/search it
  status      text        ('open' | 'closed')            ← relational: gates whether you can still apply
  deadline    date                                       ← relational: must be correct, compared in queries
  attributes  jsonb       { "salary_band": "…",          ← document: flexible, varies by role
                            "employment_type": "contract",
                            "tech_stack": ["go","sql"] }
```

The split is the whole point: anything that is **related, queried across jobs, or must be correct** earns a real column with real constraints (`id`, `company_id`, `status`, `deadline`). Anything that is **free-form and per-role** lives in `attributes`. And JSONB isn't just "a text blob" — the **B** is for *binary*, and Postgres can index and query *into* it when you need to:

```sql
-- the structured columns behave like any relational data…
SELECT id, title FROM jobs WHERE company_id = $1 AND status = 'open';

-- …and you can still reach inside the flexible attributes when it helps
SELECT id, title
FROM jobs
WHERE attributes->>'employment_type' = 'contract';
```

That `->>` operator pulls a value out of the JSONB document by key. So you get the best of both worlds: the relational model for the relationships and guarantees, JSONB for the parts that are honestly schemaless. You're not *rejecting* the document model — you're putting it exactly where it earns its place. You'll design this `jobs` table for real in [Chapter 9](../09-model-job-postings/).

> 💡 **Hint — drawing the column-vs-JSONB line.**
>
> The rule is: *if you filter, sort, gate, or enforce uniqueness on a field, it probably deserves a real column (and an index); if you only display it as part of a job's detail, JSONB is fine.*
>
> Two illustrations of how the line moves:
> - `status` and `deadline` you *filter* on — "show me open jobs whose deadline hasn't passed" — so they're real columns with indexes, not buried JSONB keys.
> - A `perks` list you only *show* on the job page and never filter the whole board by — so `perks` is happy living in JSONB.
>
> Hold this thought; you'll write it down in the next sub-chapter and act on it when you model the `jobs` table in Chapter 9.

## Why Postgres specifically?

Relational-vs-document is the decision that matters; Postgres-vs-MySQL is a smaller one. Postgres is a strong default for this course because it has **first-class JSONB** (so the hybrid above is a non-event, not a workaround), rich indexing — including indexes *into* JSONB — which you'll use in [Chapter 42](../42-indexing/), excellent transactional behaviour, and it's everywhere in production. If you're far more fluent in MySQL/MariaDB, that's a defensible choice too — the *reasoning* in this chapter is what's being graded, not the brand. You'll lock the full toolset in the [next chapter](../03-choosing-your-stack/).
