# The tempting choice — and why it disappoints here

If you've ever felt the friction of designing a schema and writing migrations, the document database is seductive — and a job portal makes it *especially* seductive. Here's the exact temptation:

> *"Job attributes vary wildly. An engineering role needs a tech stack and seniority; a sales role needs a commission plan; a design role needs a portfolio link. Why fight a rigid schema? I'll just save a JSON blob per job, every role can look however it wants, and I'll move fast."*

And that instinct is *correct about one thing*: job attributes genuinely do vary from one role to the next. That variability is real, and we'll come back to it — it's not a strawman. But hold the document temptation up against what a job portal *actually has to guarantee*, and the cracks show. None of these requires you to build the broken version to believe them — they're structural.

## Start with the hardest one: application submission must be all-or-nothing

When an applicant applies from their shortlist — a set of jobs that may span several companies — a pile of things must happen *together* in one instant:

- create **one application per job** on the shortlist;
- **snapshot** the applicant's résumé and profile onto each application (freeze a point-in-time copy, so a later profile edit never rewrites a sent application);
- record the applicant's **screening answers** for each job;
- bump each job's **applicant count** so recruiters see accurate numbers;
- and touch the applicant's record (e.g. "last applied at").

If that process dies halfway — the server restarts, the network drops — you must **not** end up with an application but no résumé snapshot, or screening answers recorded against no application, or a counter bumped for an application that was never really created. The whole thing must either *all* happen or *none* of it happen. That guarantee is a **transaction** — a group of changes that either all commit (land for good) or all roll back (vanish as if you never tried). Relational databases were built around this guarantee, across many rows and many tables at once.

To feel the tension, picture the *document* temptation — the applicant's whole submission nested in one blob:

```jsonc
// One application submission, everything nested inside a single document
{
  "applicationId": "app_123",
  "applicant": { "id": "appl_9", "name": "Ravi" },
  "resumeSnapshot": { "fileUrl": "…", "parsedAt": "2026-06-05T…" },
  "answers": [
    { "jobId": "job_55", "companyId": "co_2", "question": "Years with Postgres?", "answer": "4" },
    { "jobId": "job_91", "companyId": "co_7", "question": "Earliest start date?",  "answer": "2 weeks" }
  ]
}
```

It looks tidy — until you remember the *other* documents this one change must touch at the same instant. The shortlist spans two companies, so it becomes **two separate applications** (one per job — each role judged on its own screening questions). Each of those jobs has an **applicant count** that must increase. The applicant's own record may update. Those live in *separate* documents, and changing them all-or-nothing — so you never end up with `job_55`'s application created but `job_91`'s lost, or a counter bumped with no application behind it — is exactly the part document stores historically made hard. In the relational world the same change is **one transaction across a few tables**, which is the choice we'll land on.

This is the job-portal version of an e-commerce checkout: many linked writes that have to succeed or fail as a unit. It's the single strongest reason a job portal wants relational guarantees — so we led with it.

## And it gets worse the moment data outgrows one blob

The nested-blob model only stays tidy while everything you need lives *inside* the blob. But a recruiter doesn't want one applicant's submission — they want **all applications to their company's jobs, grouped, with each applicant's profile and each job's title**. That data lives across applicants, jobs, and companies. The moment you read *across* records like that, the self-contained blob stops helping and starts hurting — which is the thread the next three sub-chapters pull on: honest references, reading across relationships, and correctness under hiring data.
