# Apply it on your project

A concept chapter still moves your project forward — not by building the schema (that's the data-model module, Chapters 8–14), but by doing the *thinking* that the schema will be built from, and leaving real artefacts in your repo. Three small, concrete steps. Do them now, before the takeaways.

## 1. Create your learning log

If you haven't already, create a folder named **`learning-log/`** at the root of your project repo and commit it. This is where every "explain it" answer in the course goes, one file per chapter — and you'll write this chapter's answers into `learning-log/02-why-relational.md` in the final sub-chapter.

- ✅ **Do** commit the empty folder now (add a `.gitkeep` if your tooling needs a file to track it) so it's in history from the start.
- ❌ **Don't** put it inside `src/` or anywhere your app bundles — it's documentation, it lives at the repo root.

## 2. Sketch your core entities and their links

On paper, a whiteboard, or a scratch file (`scratch/data-model-sketch.md` — *not* a migration, *not* schema code), draw the four entities this chapter kept returning to and the links between them:

```
COMPANIES → JOBS            (one company, many jobs)
APPLICANTS → APPLICATIONS   (one applicant, many applications)
JOBS → APPLICATIONS         (one job, many applications)
APPLICATIONS → SCREENING_ANSWERS
```

For each arrow, write **which column will be the foreign key** (`jobs.company_id → companies.id`, `applications.job_id → jobs.id`, `applications.applicant_id → applicants.id`, …). You're not writing SQL — you're naming the links you now know the database will enforce for you.

- ✅ **Do** mark which link enforces "one application per applicant per job" (hint: it's a uniqueness rule across two foreign keys on `applications`).
- ❌ **Don't** try to get every column right — this is the *relationships*, not the full schema. The columns come in Chapters 8–11.

## 3. Decide your real-columns-vs-JSONB split

Using the rule from the last sub-chapter, make two short lists for the `jobs` table in your portal:

- **Real columns** — the job fields you will *filter, sort, gate, or enforce uniqueness on*. (`id`, `company_id`, `title`, `status`, `deadline` are almost certainly here — then add the other fields you'll genuinely query or gate on.)
- **JSONB `attributes`** — the per-role fields you'll only *display*, that vary wildly by role and that you rarely query across.

Run each applicant field through one question: *"Will any screen or rule ever need to find or block jobs by this field?"* Yes → real column (and probably an index later). No → JSONB.

- ✅ **Do** put any attribute that gates the apply action (a required field an applicant must satisfy) on the "real column" side — gating is a query.
- ❌ **Don't** dump everything into JSONB "to be safe." A field you filter the whole board by, buried in JSONB, is the slow board you'll be fixing in Week 3.

You'll turn exactly these two lists into the real `jobs` table — relational columns plus a JSONB `attributes` field — in [Chapter 9](../09-model-job-postings/), and you'll write the foreign keys and constraints from your sketch in [Chapter 11](../11-foreign-keys-and-constraints/). After this chapter, your repo has a `learning-log/` folder and a data-model sketch that didn't exist before — that's the project moving.
