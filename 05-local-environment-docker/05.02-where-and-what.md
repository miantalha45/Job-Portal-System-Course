# Where services run, and what Docker is

Your app boots, but right now it talks to nothing. It needs the two services you chose earlier — **PostgreSQL** and **Redis** — running somewhere it can reach. Before running anything, let's frame the options, then learn the tool we'll use.

## Where can services like this run?

There's more than one place a database can live:

- **Managed cloud services.** A provider runs it for you — hosted Postgres like Supabase, Neon, or AWS RDS; hosted Redis like Upstash or ElastiCache. You get backups and scaling and zero maintenance, but it costs money, needs accounts, and is far more than you want while developing on a laptop.
- **Installed natively on your machine.** You install Postgres and Redis directly through your OS package manager and run them as background services.
- **Run locally in containers with Docker.** You run each service in an isolated, throwaway box on your own machine.

For **local development** you want something free, fast to reset, and identical for everyone following this course — so we'll run them **locally with Docker**. In production (Chapter 65) you'll most likely point at a *managed* service instead, and because of the configuration you set up in Chapter 6, your application code won't care which one it's talking to. That's the payoff of doing config properly.

## Couldn't you just install them natively?

You could — `brew install postgresql redis` or the `apt` equivalent — and it would work today. It's just not the best option, for three quiet reasons:

- **Version drift.** You'd run whatever version your package manager happens to give you, which drifts away from your teammates' and your production server's versions — breeding bugs that reproduce on one machine but not another.
- **Global clutter.** The services install system-wide and stay running in the background long after you've moved on.
- **Hard to wipe.** A dev database that gets into a weird state is annoying to tear down and rebuild cleanly.

We want our environment *declared, versioned, and disposable* — which is exactly what Docker gives us.

## What is Docker?

Docker solves one of the oldest problems in software: *"it works on my machine."* Code that runs fine for you breaks for a teammate because their machine has a different version of something. Docker makes that impossible by shipping software **together with everything it needs to run**, in a sealed box that behaves the same everywhere.

A few core ideas — these are all you need:

- **Container.** A lightweight, isolated box holding one piece of software plus its dependencies, running on your machine but walled off from it.
- **Image vs container.** An **image** is the read-only *blueprint* ("PostgreSQL 16, configured like so"); a **container** is a *running instance* of it — like a recipe versus the cooked dish. One blueprint, as many running dishes as you like. You'll *pull* ready-made `postgres` and `redis` images, not build them.
- **Docker Engine.** The program on your computer that actually builds, starts, and stops containers. ("Docker Desktop" is Engine plus a GUI for Mac/Windows.)
- **Registry (Docker Hub).** The online library of prebuilt images; Docker downloads `postgres:16` from it the first time, then caches it.
- **Ports.** A container is isolated, so a service inside isn't reachable by default — you **map a port out**, connecting a port on your laptop to one inside the container, so your host app can reach Postgres.
- **Volumes.** A container is *disposable* — anything written inside vanishes when it's removed. A **volume** is storage that lives *outside* the container, so data you care about survives. Remember this one; it's the mistake everyone makes once.
- **Docker Compose.** Instead of starting each container by hand, you declare *all* your services in one `docker-compose.yml` file and bring them up with a single command. This is how you'll run your environment.

That's the whole mental model. Next, we use it.
