## Why cursor pagination instead of offset pagination?

Offset pagination (`LIMIT 20 OFFSET 40`) has a well-known problem: if a row is inserted or deleted between page requests, items shift in the result set. An item on page 2 can vanish from page 3, or appear on both pages.

Cursor pagination uses a stable position in the data. The "cursor" encodes the last item seen on the previous page. The next page query asks for rows "before this position" (for descending order). Items do not shift because the query is anchored to a row, not a row count.

For a list ordered by `(created_at DESC, id DESC)`, the cursor encodes both `created_at` and `id`. Both are needed to handle ties where two jobs share the same timestamp.

## What to build

### 1. Schema — `src/modules/jobs/jobs.schema.ts`

```ts
export const listCompanyJobsSchema = z.object({
  status: z.enum(['draft', 'open', 'closed']).optional(),
  cursor: z.string().optional(),
  limit: z.coerce.number().int().min(1).max(100).default(20),
});

export type ListCompanyJobsInput = z.infer<typeof listCompanyJobsSchema>;
```

Query parameters are strings by default — `z.coerce.number()` converts the string `"20"` to the number `20`.

### 2. Cursor helpers

Add a small utility. It does not need its own file — it can live in `jobs.repo.ts` or a `src/shared/cursor.ts`:

```ts
// Encode: created_at ISO string + '|' + id
export function encodeCursor(createdAt: Date | string, id: string): string {
  const ts = createdAt instanceof Date ? createdAt.toISOString() : createdAt;
  return Buffer.from(`${ts}|${id}`).toString('base64url');
}

// Decode: returns { createdAt: string, id: string } or null if invalid
export function decodeCursor(cursor: string): { createdAt: string; id: string } | null {
  try {
    const raw = Buffer.from(cursor, 'base64url').toString('utf8');
    const pipeIdx = raw.lastIndexOf('|');
    if (pipeIdx === -1) return null;
    return {
      createdAt: raw.slice(0, pipeIdx),
      id: raw.slice(pipeIdx + 1),
    };
  } catch {
    return null;
  }
}
```

### 3. Repository — `src/modules/jobs/jobs.repo.ts`

```ts
export async function listJobsForCompany(
  companyId: string,
  input: ListCompanyJobsInput,
): Promise<Array<{ id: string; title: string; status: string; createdAt: string }>> {
  const params: unknown[] = [companyId];
  const conditions: string[] = ['company_id = $1'];
  let idx = 2;

  if (input.status) {
    conditions.push(`status = $${idx}`);
    params.push(input.status);
    idx++;
  }

  if (input.cursor) {
    const decoded = decodeCursor(input.cursor);
    if (decoded) {
      conditions.push(`(created_at, id) < ($${idx}::timestamptz, $${idx + 1})`);
      params.push(decoded.createdAt, decoded.id);
      idx += 2;
    }
    // If cursor is malformed, ignore it and return from the start
  }

  params.push(input.limit + 1); // fetch one extra to detect if there is a next page

  const result = await db.query(
    `SELECT id, title, status, created_at AS "createdAt"
     FROM jobs
     WHERE ${conditions.join(' AND ')}
     ORDER BY created_at DESC, id DESC
     LIMIT $${idx}`,
    params,
  );

  return result.rows;
}
```

Fetching `limit + 1` rows is the standard technique: if the result has more than `limit` rows, there is a next page. The extra row is not returned to the caller — it is only used to determine whether `nextCursor` should be set.

### 4. Service — `src/modules/jobs/jobs.service.ts`

```ts
export async function getCompanyJobs(userId: string, input: ListCompanyJobsInput) {
  const company = await getRecruiterCompany(userId);
  if (!company) throw new ForbiddenError('No company workspace found.');

  const rows = await listJobsForCompany(company.companyId, input);

  const hasNextPage = rows.length > input.limit;
  const items = hasNextPage ? rows.slice(0, input.limit) : rows;

  const nextCursor =
    hasNextPage && items.length > 0
      ? encodeCursor(items[items.length - 1].createdAt, items[items.length - 1].id)
      : null;

  return { jobs: items, nextCursor };
}
```

### 5. Route — `src/modules/jobs/jobs.routes.ts`

```ts
router.get('/', async (req, res, next) => {
  try {
    const input = validate(listCompanyJobsSchema, req.query);
    const result = await getCompanyJobs(req.user!.userId, input);
    res.json(result);
  } catch (err) {
    next(err);
  }
});
```

Note: `req.query` not `req.body` — this is a GET request. The `validate` function handles this correctly because Zod does not care about the source of the data.

## The tuple comparison operator

The cursor condition `(created_at, id) < ($n::timestamptz, $m)` is a PostgreSQL tuple comparison. It is equivalent to:

```sql
created_at < $n OR (created_at = $n AND id < $m)
```

But more concise and often better optimized with a composite index. If you have an index on `(created_at DESC, id DESC)` on the `jobs` table, this query will use it efficiently.

Add the index:

```sql
CREATE INDEX IF NOT EXISTS jobs_company_created_idx
  ON jobs (company_id, created_at DESC, id DESC);
```

This index supports both the `company_id` filter and the `ORDER BY created_at DESC, id DESC` sort.
