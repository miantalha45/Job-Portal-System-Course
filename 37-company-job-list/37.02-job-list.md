# The Company Job List

## What the endpoint returns

```bash
GET /api/jobs
Authorization: Bearer <recruiter-token>
```

No query params — returns the first page (up to 20 jobs):

```json
{
  "jobs": [
    {
      "id": "f47ac10b-...",
      "title": "Senior Backend Engineer",
      "status": "open",
      "createdAt": "2026-06-07T10:00:00.000Z"
    },
    {
      "id": "a3c9e2d1-...",
      "title": "DevOps Engineer",
      "status": "draft",
      "createdAt": "2026-06-06T09:30:00.000Z"
    }
  ],
  "nextCursor": null
}
```

Results are ordered newest first (`created_at DESC, id DESC`).

---

## Filtering by status

```bash
GET /api/jobs?status=open
```

Returns only open jobs. Valid values: `draft`, `open`, `closed`. Any other value fails Zod validation (422).

---

## Pagination

When there are more jobs than the `limit`:

```bash
GET /api/jobs?limit=2
```

Response with more pages available:

```json
{
  "jobs": [
    { "id": "job-3-id", "title": "Job 3", "status": "open", "createdAt": "2026-06-07T..." },
    { "id": "job-2-id", "title": "Job 2", "status": "draft", "createdAt": "2026-06-06T..." }
  ],
  "nextCursor": "MjAyNi0wNi0wNlQwOTowMDowMC4wMDBafGpvYi0yLWlk"
}
```

Fetching the next page:

```bash
GET /api/jobs?limit=2&cursor=MjAyNi0wNi0wNlQwOTowMDowMC4wMDBafGpvYi0yLWlk
```

Response:

```json
{
  "jobs": [
    { "id": "job-1-id", "title": "Job 1", "status": "open", "createdAt": "2026-06-05T..." }
  ],
  "nextCursor": null
}
```

`nextCursor: null` means you have reached the last page.

---

## How the cursor encodes position

The cursor is a base64url-encoded string: `<ISO-timestamp>|<job-id>`.

For the last job on page 1 (`id = "job-2-id"`, `createdAt = "2026-06-06T09:00:00.000Z"`):

```
raw  = "2026-06-06T09:00:00.000Z|job-2-id"
cursor = base64url("2026-06-06T09:00:00.000Z|job-2-id")
```

The next-page query adds:

```sql
AND (created_at, id) < ('2026-06-06T09:00:00.000Z'::timestamptz, 'job-2-id')
```

This returns all jobs that come before that position in the sort order.

---

## Isolation

The SQL always includes `WHERE company_id = $1` where `$1` is the `companyId` from `getRecruiterCompany(userId)`. A recruiter never sees jobs from another company, regardless of query parameters. There is no `company_id` parameter in the request — the scope comes entirely from the authenticated user.

---

## What is NOT returned

The job list is a summary view. It does not return `description`, `salary_min`, `salary_max`, `attributes`, or `screening_questions`. These fields are available on the single-job detail endpoint (not built in this chapter). The list is intentionally lightweight for use in dashboard tables.

---

## Malformed cursor handling

If the cursor cannot be decoded (bad base64, missing pipe character, etc.), `decodeCursor` returns `null`. The query proceeds without the cursor condition — returning from the start of the list. This is a silent recovery: the caller receives the first page instead of an error.

An alternative is to return `422` on a malformed cursor. The silent approach is more tolerant for clients that construct cursors incorrectly; the strict approach is better for catching client bugs early. This build takes the tolerant approach.

---

## The +1 trick

The service fetches `limit + 1` rows from the database. If the result contains more than `limit` rows, there is a next page. The extra row is discarded before sending the response; only `limit` items appear in the `jobs` array. This avoids a separate `COUNT(*)` query, which would be slower on large tables.

Example with `limit = 2`:
- DB returns 3 rows → `hasNextPage = true`, return first 2, set `nextCursor`
- DB returns 2 rows → `hasNextPage = false`, return all 2, `nextCursor = null`
- DB returns 1 row → `hasNextPage = false`, return 1, `nextCursor = null`
