# Indexes and Reading Query Plans

## 1. The migration

Create `migrations/009_add_indexes.sql`:

```sql
-- migrations/009_add_indexes.sql

-- Public board: filters on status, orders by created_at DESC, id DESC
-- Leading column (status) handles the equality filter.
-- Remaining columns (created_at DESC, id DESC) match the ORDER BY exactly,
-- so PostgreSQL can serve the query with a single index scan in sort order.
CREATE INDEX idx_jobs_status_created
  ON jobs (status, created_at DESC, id DESC);

-- Company-scoped job queries (recruiter dashboard): filter by company_id
-- The public board join also benefits from this when looking up jobs by company
CREATE INDEX idx_jobs_company_id
  ON jobs (company_id);

-- Public board JOIN: filter companies by status
CREATE INDEX idx_companies_status
  ON companies (status);

-- Recruiter lookup: find which company a user belongs to
CREATE INDEX idx_recruiters_user_id
  ON recruiters (user_id);

-- Company member list: find all recruiters in a company
CREATE INDEX idx_recruiters_company_id
  ON recruiters (company_id);
```

Apply it:

```bash
psql $DATABASE_URL -f migrations/009_add_indexes.sql
```

## 2. Why composite index column order matters

The index `(status, created_at DESC, id DESC)` is useful for queries that:

1. Filter on `status` (equality), OR
2. Filter on `status` and sort/filter on `created_at`, OR
3. Filter on `status`, sort on `created_at`, and use `id` as a tiebreaker

It is **not** useful for:

- Queries that filter only on `created_at` without filtering on `status` first
- Queries that filter only on `id`

This is the **leftmost prefix rule**: a composite index `(a, b, c)` can serve queries that filter on `a`, or `(a, b)`, or `(a, b, c)` — but not queries that filter only on `b` or `c`.

Think of it like a phone book sorted by last name, then first name. You can look up "Smith, John" efficiently. You can look up all "Smiths" efficiently. You cannot look up all "Johns" efficiently — you would have to scan the entire book.

**The public board query:**

```sql
WHERE j.status = 'open'     -- uses the leading column of idx_jobs_status_created
ORDER BY j.created_at DESC, j.id DESC  -- matches the remaining columns in order
```

PostgreSQL can enter the index at `status = 'open'`, then traverse the sub-tree in `(created_at DESC, id DESC)` order — which is already sorted. It never needs to sort the result set.

**What happens without the index:**

PostgreSQL performs a Seq Scan (reads every row in the table), then sorts the matching rows. Cost is proportional to total table size, not to the result set size.

## 3. Reading EXPLAIN ANALYZE output

Run `EXPLAIN ANALYZE` on the public board query:

```sql
EXPLAIN ANALYZE
SELECT
  j.id, j.title, j.location, j.employment_type,
  j.salary_min, j.salary_max, j.created_at,
  c.name AS company_name
FROM jobs j
JOIN companies c ON c.id = j.company_id
WHERE j.status = 'open'
  AND c.status = 'verified'
ORDER BY j.created_at DESC, j.id DESC
LIMIT 20;
```

### What the output looks like

On a table with ~500 jobs from 10 companies, you might see:

```
Limit  (cost=0.28..85.32 rows=20 width=168) (actual time=0.042..0.195 rows=20 loops=1)
  ->  Nested Loop  (cost=0.28..2634.21 rows=617 width=168) (actual time=0.041..0.192 rows=20 loops=1)
        ->  Index Scan using idx_jobs_status_created on jobs j  (cost=0.14..2502.10 rows=617 width=148) (actual time=0.030..0.147 rows=20 loops=1)
              Index Cond: ((status)::text = 'open'::text)
        ->  Index Scan using companies_pkey on companies c  (cost=0.14..0.21 rows=1 width=28) (actual time=0.002..0.002 rows=1 loops=20)
              Index Cond: (id = j.company_id)
              Filter: ((status)::text = 'verified'::text)
              Rows Removed by Filter: 0
Planning Time: 0.183 ms
Execution Time: 0.231 ms
```

### What each part means

**`Index Scan using idx_jobs_status_created`**

The query is using the index you created. It did not do a Seq Scan. This is what you want to see.

**`Index Cond: ((status)::text = 'open'::text)`**

The index is being used to filter on `status = 'open'`. This is the leading column — the index can locate the `status = 'open'` section directly.

**`cost=0.14..2502.10`**

Two numbers: estimated startup cost (0.14) and estimated total cost (2502.10). Cost units are arbitrary — they are relative, not milliseconds. The important comparison is against what you would see with a Seq Scan, which might be `cost=0.00..48323.00` on the same table.

**`rows=617`**

PostgreSQL estimates 617 rows match `status = 'open'`. This is the planner's estimate, not the actual count. If the estimate is wildly off (say, 10x), running `ANALYZE jobs` updates the statistics.

**`actual time=0.030..0.147 rows=20`**

The query actually returned 20 rows (the LIMIT) in 0.147ms total. This is the measured result, not an estimate.

**`Limit (rows=20)`**

PostgreSQL stopped after 20 rows — it did not process all 617 matching rows. This is the key benefit of the index matching the ORDER BY: the database can stop early.

**`Nested Loop`**

For each row from `jobs`, PostgreSQL performs an index lookup on `companies`. Since the LIMIT stops after 20 jobs, there are at most 20 company lookups — not 617.

### What a Seq Scan looks like (bad)

Without the index, or on a very small table, you might see:

```
Seq Scan on jobs j  (cost=0.00..48323.00 rows=617 width=148)
              Filter: ((status)::text = 'open'::text)
              Rows Removed by Filter: 9383
```

`Rows Removed by Filter: 9383` means PostgreSQL read all 10,000 rows and discarded 9,383. Every Seq Scan scans the full table.

## 4. When PostgreSQL ignores an index

PostgreSQL may choose a Seq Scan even when an index exists, if:

- **The table is very small.** For a table with 50 rows, a sequential scan is faster than an index lookup. This is common in development — you may not see the index used until you have a realistic data volume.
- **The estimated selectivity is low.** If PostgreSQL estimates that 90% of rows match `status = 'open'`, the index provides little benefit over a full scan. This is a statistics issue — run `ANALYZE jobs` to refresh.
- **The index does not match the sort.** If the ORDER BY direction does not match the index direction, PostgreSQL cannot use the index for sorting and may fall back to a sort node followed by a seq scan.

To force an index scan for testing (never in production):

```sql
SET enable_seqscan = off;
EXPLAIN ANALYZE <your query>;
SET enable_seqscan = on;
```

This shows what the plan would cost if the sequential scan option were unavailable — useful for verifying the index would be used on a larger table.

## 5. Confirming idx_jobs_company_id is used

The authenticated job list (Chapter 37) queries:

```sql
WHERE company_id = $1 ORDER BY created_at DESC, id DESC
```

Run:

```sql
EXPLAIN ANALYZE
SELECT id, title, status, created_at
FROM jobs
WHERE company_id = 'your-company-uuid-here'
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

Expected: `Index Scan using idx_jobs_company_id` (or the composite index if PostgreSQL's planner prefers it). The `Filter` on `company_id` should appear as an `Index Cond`.
