# 71.02 — Structured Logging & Request IDs (Walkthrough)

## Why structured logging over console.log

`console.log('User logged in:', userId)` produces a plain string. To find all login events
for a specific user, you would need `grep`. `grep` on a log file works fine on one server.
It breaks when you have:

- Multiple servers (logs are on different machines)
- High volume (millions of log lines per day)
- Complex queries ("all 500 errors in the last hour on the /api/auth/login route")

Structured logging writes a JSON object per line. Log aggregators (Datadog, CloudWatch Logs,
Grafana Loki) index these fields. You query them with the aggregator's UI:

```
level=error AND url="/api/auth/login" AND timeframe=1h
```

This is the standard production logging pattern.

## The request ID problem

Without request IDs, log lines from concurrent requests are interleaved and impossible to
correlate:

```
INFO request received POST /api/auth/login
INFO request received GET /api/jobs
INFO user authenticated user-123
INFO job list fetched 42 jobs
INFO request completed 200 48ms
INFO request completed 200 12ms
```

Which "user authenticated" belongs to which "request received"? Impossible to tell.

With request IDs:

```json
{"requestId":"aaa","msg":"request received","url":"/api/auth/login"}
{"requestId":"bbb","msg":"request received","url":"/api/jobs"}
{"requestId":"aaa","msg":"user authenticated","userId":"user-123"}
{"requestId":"bbb","msg":"job list fetched","count":42}
{"requestId":"aaa","msg":"request completed","statusCode":200,"durationMs":48}
{"requestId":"bbb","msg":"request completed","statusCode":200,"durationMs":12}
```

Filter by `requestId=aaa` and you get the full lifecycle of that one request.

## Building it step by step

### Step 1 — Install pino and pino-pretty

```bash
npm install pino pino-pretty
npm install -D @types/pino   # if needed
```

### Step 2 — Rewrite logger.ts

The key decision is the `transport` option. In development, `pino-pretty` formats logs as
human-readable colored output. In production, it is removed — pino emits raw JSON which is
faster (no formatting overhead) and machine-parseable.

```ts
const logger = pino({
  level: config.LOG_LEVEL,
  transport: config.NODE_ENV !== 'production'
    ? { target: 'pino-pretty', options: { colorize: true } }
    : undefined,
});
```

### Step 3 — Request ID middleware

`crypto.randomUUID()` generates a V4 UUID. It is available in Node.js 14.17+ without importing
`crypto` — it is on the global `crypto` object. The UUID is attached to `req.id`, which the
TypeScript declaration merging in the middleware file makes type-safe.

### Step 4 — HTTP logger middleware

Two log events per request:

1. **`request received`**: logged at the start, before any route handler runs. Contains
   `method` and `url` but not `statusCode` (not known yet).
2. **`request completed`**: logged in a `res.on('finish')` handler. Contains `statusCode`
   and `durationMs` (time from request received to response finished).

The `finish` event fires after the response body is flushed and the connection is released.
`close` fires when the underlying connection is destroyed — use `finish` for logging.

### Step 5 — Order in app.ts

```ts
app.use(requestIdMiddleware);   // assign ID (must be first)
app.use(httpLogger);            // log with ID
app.use(globalLimiter);         // rate limit
app.use('/api/auth', authRouter);
// ...
```

If `httpLogger` comes before `requestIdMiddleware`, `req.id` would be undefined when the
log line is written. Order matters.

### Step 6 — Update the error handler

The error handler already catches all unhandled errors. Add a `logger.error` call:

```ts
logger.error({ requestId: req.id, err }, 'unhandled error');
```

Pino serializes `err` objects automatically — it extracts `message`, `stack`, and `type`.

### Step 7 — Grep and replace console.log

```bash
grep -rn 'console\.log\|console\.error\|console\.warn' src/
```

Replace each occurrence with the appropriate pino call. Pass an object as the first argument
and a message string as the second:

```ts
// Before:
console.log('Job fetched', job.id);

// After:
logger.info({ jobId: job.id }, 'job fetched');
```

## No `process.env` in this module

`LOG_LEVEL` and `NODE_ENV` are read only in `config.ts`. The logger reads `config.LOG_LEVEL`
and `config.NODE_ENV`. No other file reads these values from `process.env`.
