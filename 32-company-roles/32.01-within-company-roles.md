# Within-Company Roles and Permissions

## Two layers of authorization

The system has two separate role systems. Conflating them causes bugs.

**Platform role** (stored in `users.role`) — assigned at registration. Controls which top-level API sections a user can reach. A recruiter reaches `/api/companies` and `/api/jobs`. An admin reaches `/api/admin`. This is what `requireRole('recruiter')` checks.

**Company role** (stored in `recruiters.company_role`) — assigned when a user joins a company. Controls what the user can do *within* their company workspace. This is what the patterns in this chapter check.

A user has exactly one platform role and at most one company role. There is no concept of a user belonging to multiple companies.

---

## The four company roles

### owner

Created when a recruiter opens a workspace (`POST /api/companies`). There is exactly one owner per company. The owner can do everything:

- Invite new members and assign their company role
- Change any member's company role
- Remove any member (except themselves while the company exists)
- Post, edit, publish, and close jobs
- View all applications for any job in the company
- Access all member management endpoints

### hr_manager

Invited by the owner. A company may have multiple HR managers. An HR manager can:

- Invite new members (but cannot invite as owner)
- View all members of the company
- Post, edit, publish, and close jobs
- View and manage all applications

An HR manager cannot change another member's company role and cannot remove the owner.

### recruiter

Invited by the owner or an HR manager. A company may have many recruiters. A recruiter can:

- Post, edit, publish, and close jobs (their own and those of the company generally — scoped to the company, not the individual)
- View applications for the company's jobs

A recruiter cannot invite members, view member lists, or change roles.

### hiring_manager

Invited by the owner or an HR manager. Typically a department leader who reviews shortlisted applicants. A hiring manager can:

- View applications
- Leave feedback on applications
- Advance application stages

A hiring manager cannot post or edit jobs and cannot manage members.

## Permission matrix

| Action | owner | hr_manager | recruiter | hiring_manager |
|---|:---:|:---:|:---:|:---:|
| Invite members | Yes | Yes | No | No |
| Change member roles | Yes | No | No | No |
| Remove members | Yes | Yes | No | No |
| View member list | Yes | Yes | No | No |
| Post / edit jobs | Yes | Yes | Yes | No |
| Publish / close jobs | Yes | Yes | Yes | No |
| View applications | Yes | Yes | Yes | Yes |
| Manage applications (stage, feedback) | Yes | Yes | Yes | Yes |

## How the check works in code

Company role is not available in the JWT. The JWT contains only `userId` and the platform role. To check a company role, the service first resolves the recruiter row:

```ts
const company = await getRecruiterCompany(userId);
// company: { companyId, companyRole } | null
```

`getRecruiterCompany` joins `recruiters` to `companies` and returns both the `company_id` and `company_role` for the given user. If the user has no recruiter row, it returns `null`.

A helper that encapsulates the pattern:

```ts
function assertCompanyRole(
  companyRole: string,
  allowed: string[],
  message = 'You do not have permission to perform this action.',
) {
  if (!allowed.includes(companyRole)) {
    throw new ForbiddenError(message);
  }
}
```

Usage in a service function:

```ts
export async function inviteMember(userId: string, input: InviteInput) {
  const company = await getRecruiterCompany(userId);
  if (!company) throw new ForbiddenError('No company workspace found.');

  assertCompanyRole(company.companyRole, ['owner', 'hr_manager']);

  // ... rest of the invite logic
}
```

This is a **service-level check**, not a route middleware. The reason: the check requires a database call to resolve the company role. A middleware approach would fire the same query for every request, then discard the result, only for the service to run it again. Putting the check in the service keeps the query in one place.

---

## Why not put company role in the JWT?

The JWT is signed at login time and valid for the access token lifetime (typically 15 minutes). If the owner changes a member's company role, the member's existing JWT still carries the old role until it expires.

Since company role is checked by reading the database on every request (via `getRecruiterCompany`), a role change takes effect immediately — the next request by that user reads the updated row.

Encoding the company role in the JWT would make role changes eventually consistent, with a lag equal to the token lifetime. For a permission boundary that includes member removal, eventual consistency is not acceptable.

---

## The `requireCompanyRole` pattern

Each service function that enforces a company role follows this structure:

1. Call `getRecruiterCompany(userId)` — returns `{ companyId, companyRole }` or `null`
2. If `null`, throw `ForbiddenError` (the user has no workspace)
3. Call `assertCompanyRole(company.companyRole, allowedRoles)`
4. If the check passes, proceed with the operation using `company.companyId` as the scope

No operation uses a `company_id` taken from a URL parameter or request body. The company ID always comes from the authenticated user's recruiter row.

---

## Key Takeaways

- **Two separate role systems**: platform role (`users.role`) controls route access; company role (`recruiters.company_role`) controls actions within a workspace. They are independent.
- **Four company roles**: owner, hr_manager, recruiter, hiring_manager. Each has a distinct capability boundary. hiring_manager is the only role that cannot post jobs.
- **Company role is not in the JWT**. It is resolved from the database on each request, so role changes take effect immediately without waiting for token expiry.
- **Service-level checks, not middleware**. The `assertCompanyRole` helper lives in the service layer where the company ID is already available. Checking earlier would duplicate the database call.
- **The isolation rule holds**. The company ID used for all scoped queries always comes from `getRecruiterCompany(userId)` — from the authenticated user's recruiter row — never from a URL parameter.
