# Chapter 19.03 — The Password Module

## Install

bcryptjs is a pure JavaScript implementation — no native bindings, no build step beyond `npm install`:

```bash
npm install bcryptjs
npm install --save-dev @types/bcryptjs
```

The `@types/bcryptjs` package provides TypeScript declarations for the library. Both packages belong at their respective install targets: `bcryptjs` as a production dependency, `@types/bcryptjs` as a dev dependency (TypeScript types are stripped at compile time and are not present in the built output).

Do not install the `bcrypt` package (without the `js` suffix). That package requires native bindings compiled against your local Node.js version. It fails in Docker if the image's libc version does not match. bcryptjs is functionally identical from the outside — same API, same hash format, same output — and carries none of the build complexity.

## Building src/shared/password.ts

Create the file at `src/shared/password.ts`. This module has two exports and no default export.

```ts
import bcrypt from 'bcryptjs';

const BCRYPT_ROUNDS = 12;

export async function hashPassword(plaintext: string): Promise<string> {
  return bcrypt.hash(plaintext, BCRYPT_ROUNDS);
}

export async function verifyPassword(
  plaintext: string,
  hash: string,
): Promise<boolean> {
  return bcrypt.compare(plaintext, hash);
}
```

That is the entire file. Walk through each decision.

**`BCRYPT_ROUNDS = 12`.** The cost factor is a named constant at the top of the file, not a magic number inside the `hash` call. `bcrypt.hash(plaintext, 12)` is harder to audit — if you search the codebase for where the cost factor is set, you will not find it by searching for `BCRYPT_ROUNDS`. Named constants are also trivially searchable when the time comes to increase the cost factor as hardware improves. You change one line; every call to `hashPassword` picks up the change. If you want the cost factor to be configurable per environment (e.g., lower in CI for faster test runs), move it to `src/shared/config.ts` — but for this system a hardcoded value is appropriate since the cost factor does not vary by deployment.

**`bcrypt.hash(plaintext, BCRYPT_ROUNDS)`.** The second argument is the number of rounds — the cost factor. bcryptjs generates a new random salt internally on each call. You do not pass a salt. Do not call `bcrypt.genSalt` separately and then `bcrypt.hash` with it; `bcrypt.hash` with a rounds number does both in one step and is the correct usage.

**`bcrypt.compare(plaintext, hash)`.** This returns a `Promise<boolean>`. It extracts the salt embedded in the stored hash, recomputes bcrypt using that salt and the supplied plaintext, and compares the result to the stored hash using a byte-by-byte loop — a best-effort timing-safe comparison. Pure-JavaScript environments cannot guarantee constant-time in the formal cryptographic sense (a V8 optimizer might still short-circuit), but the loop structure prevents the most obvious timing oracle. For production systems requiring a cryptographic constant-time guarantee, a native `crypto.timingSafeEqual` wrapper would be more rigorous.

**No default export.** Named exports are used throughout this codebase. Default exports create ambiguity at the import site — the importer can name the import anything, which makes it harder to search for usages. `import { hashPassword, verifyPassword } from '../shared/password'` is unambiguous.

## The 72-Byte Truncation Limit

bcrypt has a hard limit: input longer than 72 bytes is silently truncated before hashing. "Silently" is the important word — bcryptjs does not throw, does not warn, and does not return an error. It just hashes the first 72 bytes.

The practical consequence: two passwords that share the same first 72 bytes hash identically, regardless of what comes after. A recruiter who sets a 100-character password and another recruiter who sets a different 100-character password but with the same first 72 characters will have the same hash. `verifyPassword` will return `true` for either plaintext against either hash.

This is not a bcrypt bug; it is a documented design limit inherited from Blowfish's key schedule. Every bcrypt implementation shares it.

There are two approaches to handle it.

**Option 1: Validate `max(72)` in the Zod schema.** The password field in the authentication schema rejects any password longer than 72 characters at the point of input. Chapter 20 adds `z.string().max(72)` to the password field in the auth schema. One caveat: `z.string().max(72)` counts Unicode code points (characters), not bytes. A password containing 72 emoji or Arabic characters exceeds 72 UTF-8 bytes and would still be silently truncated. For an ASCII-only password policy this is fine; for a system accepting any Unicode input, the correct check uses `Buffer.byteLength(password, 'utf8') <= 72`. This course uses the simpler character count — a 72-character limit is a practical constraint for most user passwords.

**Option 2: Pre-hash with SHA-256 before bcrypt.** Hash the plaintext with SHA-256 first, base64-encode the result (32 bytes → 44 characters, well under 72), and pass that to bcrypt. This lets users set arbitrarily long passwords without silent truncation. The trade-off: if an attacker ever gets the bcrypt hash and somehow knows you are pre-hashing, they need to think in SHA-256-output space rather than plaintext space — a minor complication that does not change the fundamental security analysis, since bcrypt is still the bottleneck. The implementation adds a dependency on Node's `crypto` module and a pre-processing step to both `hashPassword` and `verifyPassword`. For a teaching context and for most production applications, the added complexity is not worth it; the 72-character limit is straightforward to communicate to users and is not a meaningful restriction in practice.

This course uses Option 1.

## How Chapter 20 Will Call These Functions

The password module has no knowledge of HTTP, Express, or the database. It takes strings and returns promises. That is the right boundary — the utility does one job, and the route handler assembles the pieces.

In the register route (Chapter 20):

```ts
import { hashPassword } from '../shared/password';

// Inside the route handler, after validation:
const hash = await hashPassword(body.password);
// Insert user row with hash as password_hash
await db.query(
  'INSERT INTO users (email, password_hash, role, status) VALUES ($1, $2, $3, $4)',
  [body.email, hash, body.role, 'active'],
);
```

In the login route (Chapter 20):

```ts
import { verifyPassword } from '../shared/password';

// After fetching the user row by email:
const valid = await verifyPassword(body.password, user.password_hash);
if (!valid) {
  throw new UnauthorizedError('Invalid credentials');
}
// Issue access token and refresh token
```

Note the error message in the login case: "Invalid credentials" — not "Wrong password" and not "No account found for that email." Both wrong-email and wrong-password attempts receive the same error. This is intentional. Distinguishing them tells an attacker which emails are registered on the system, enabling account enumeration.

There is a timing side-channel to address: when the email is not found, the route returns immediately (no bcrypt call). When the email is found but the password is wrong, the route waits ~250ms for `verifyPassword`. An attacker measuring response times can distinguish "email not registered" from "email registered but wrong password" — even though the error message is the same. Chapter 20 handles this by calling `verifyPassword` with a dummy hash when no user row is found, ensuring both paths take the same time.
