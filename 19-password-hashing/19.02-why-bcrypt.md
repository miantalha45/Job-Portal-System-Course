# Chapter 19.02 — Why bcrypt

## The Problem with Fast Hashes

MD5, SHA-256, and SHA-512 were designed to be fast. That was the right design goal for their intended use cases: checksums, digital signatures, message authentication. In those contexts, you want to compute the hash of a large file in milliseconds, or sign thousands of records per second. Speed is a feature.

For password storage, speed is a liability.

When an attacker has your database, they do not need to break into your server again. They have the hashes. They can run their cracking operation entirely offline, on hardware they control, at whatever scale they can afford. The only thing limiting their throughput is how fast they can compute hashes. If you chose a fast algorithm, you gave them billions of attempts per second. If you chose a slow one, you gave them thousands.

The difference between billions per second and thousands per second is not a small optimization. Against a 100-million-entry dictionary:

- MD5: entire dictionary exhausted in under one second.
- SHA-256: entire dictionary exhausted in under one minute.
- bcrypt (cost 12): at ~20,000 hashes/sec per GPU, a 100-million-entry dictionary takes about 83 hours (roughly 3–4 days) per GPU card, per target account.

For users who chose strong passwords — ones that do not appear in any dictionary — the attacker gets nothing from MD5 or SHA-256 either. The dictionary attack fails because the password is not in the dictionary. But real users largely do not choose strong passwords. A large fraction of your user base has a password in rockyou.txt or something close to it. Fast hashes expose them. bcrypt does not eliminate the risk, but it turns a seconds-long operation into a weeks-long one, which changes the economics of the attack.

## How bcrypt Slows Down Attackers

bcrypt is built on the Blowfish cipher's key setup routine, which is intentionally expensive. The cost factor controls how many times that routine runs: cost 12 means 2^12 = 4,096 iterations. Each iteration takes a fixed amount of computation and memory access.

GPU hardware excels at operations that are parallel and independent. bcrypt's key setup involves sequential, data-dependent memory accesses — each step reads from a large P-array and four S-boxes, and the output of each step feeds the input of the next. This creates instruction-level dependencies that prevent parallelism: a GPU thread cannot start step N+1 until step N completes. Each GPU core must run bcrypt iterations sequentially, so adding more GPU cores does not multiply throughput the way it does for SHA-256. The practical result is that bcrypt throughput on a GPU is tens of thousands of hashes per second — not billions.

Thousands per second against a 100-million-entry dictionary takes around 28 hours per GPU card, focused on a single target. Spread across 10,000 targets, the attacker has to prioritize — they cannot crack everyone at once. Users who did not choose a password in the dictionary are effectively safe for the duration of any realistic attack.

## Why Not argon2?

argon2 is the 2015 winner of the Password Hashing Competition. It is a newer algorithm designed explicitly for password storage, and it is also a legitimate choice. argon2id in particular is resistant to both GPU attacks (via time cost) and side-channel attacks (via memory cost). If you are choosing a password hashing algorithm from scratch today, argon2id is well-regarded.

This course uses bcryptjs for a specific reason: zero native dependencies.

bcryptjs is a pure JavaScript implementation of bcrypt. It installs with `npm install` and requires no compiled native bindings. This matters in practice: native bcrypt bindings have historically caused build failures in Docker containers, in CI environments with mismatched libc versions, and on Node.js version upgrades that invalidate pre-built binaries. bcryptjs avoids all of that. The trade-off is that it is somewhat slower than a native implementation — which in this context is not a problem, since "slower password hashing" is not a liability.

The dominant `argon2` npm package requires native Node.js bindings compiled against your local Node.js version — the same build complexity that `bcrypt` (without the `js` suffix) has. For a teaching context where the goal is a working, deployable system with minimal build complexity, bcryptjs is the pragmatic choice. Either is correct from a security standpoint.

## When Not to Use bcrypt

bcrypt is the right tool for passwords. It is the wrong tool for everything else.

The job portal stores two kinds of secrets:

1. **Passwords.** Low-entropy values chosen by a user. An attacker who has the hash can guess their way to the original. The cost factor is what makes that guessing expensive. bcrypt is appropriate here.

2. **Refresh tokens.** High-entropy random values generated by the server — 256 bits of cryptographically random data. An attacker who has the hash cannot guess the original. There are no guessable values to try. Even if the hash function were instantaneous, the attacker gains nothing from it — they need the 256-bit random token itself, which they do not have. bcrypt's slowness is entirely wasted on high-entropy values. SHA-256 is correct here.

Using bcrypt for refresh token storage would impose 250ms of latency on every token refresh — not to protect against an attack that exists, but because the wrong tool was applied. The threat model determines the tool. Where the attacker cannot guess, you do not need a slow hash.

The same logic applies to API keys, session tokens, cryptographic nonces, or any other secret the system generates rather than the user choosing. If the system generated it with a cryptographically secure random number generator, it is high-entropy. Use a fast hash. If the user typed it, assume it is low-entropy. Use bcrypt.
