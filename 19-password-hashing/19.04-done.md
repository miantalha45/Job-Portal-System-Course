# Definition of Done — Chapter 19

## Checklist

- [ ] **`src/shared/password.ts` exists** with `hashPassword` and `verifyPassword` as named exports. No default export. `BCRYPT_ROUNDS` is defined as a named constant at the top of the file.

- [ ] **`bcryptjs` is listed in `dependencies`** in `package.json` and `@types/bcryptjs` is listed in `devDependencies`. Both are present in `node_modules`.

- [ ] **TypeScript compiles cleanly.** Run `npx tsc --noEmit` — zero errors. If `src/shared/password.ts` is not in the TypeScript compiler's `include` paths, add it or confirm that the existing `include` configuration covers `src/**/*`.

- [ ] **Hash format smoke test passes.** Run the following in a temporary script or a `ts-node` REPL:

  ```ts
  import { hashPassword, verifyPassword } from './src/shared/password';

  const hash = await hashPassword('test123');
  console.log(hash);
  // Must start with $2b$12$
  // Example: $2b$12$N9qo8uLOickgx2ZMRZoMyeIjZAgcfl7p92ldGxad68LJZdL17lhWy
  ```

  The prefix `$2b$12$` confirms two things: `$2b$` is the bcryptjs format identifier, and `12` is the cost factor. If you see `$2b$10$` you have the wrong cost factor. If you see `$2a$` you may be using a different bcrypt variant.

- [ ] **Verify returns the correct boolean in both cases.**

  ```ts
  const match = await verifyPassword('test123', hash);
  console.log(match); // true

  const noMatch = await verifyPassword('wrong', hash);
  console.log(noMatch); // false
  ```

  Both must be verified. A function that always returns `true` would pass only the first assertion.

- [ ] **The hash call takes more than 100ms.** Time a single `hashPassword` call:

  ```ts
  const start = Date.now();
  await hashPassword('test123');
  const elapsed = Date.now() - start;
  console.log(`hashPassword took ${elapsed}ms`);
  // Must be > 50ms. On typical hardware: 150–400ms. On fast Apple Silicon: may be 80–120ms.
  ```

  If the elapsed time is under 10ms, the cost factor is not being applied — check that `BCRYPT_ROUNDS` is 12 and passed to `bcrypt.hash`. Single-digit milliseconds means you accidentally used a fast hash or passed 0 rounds. bcryptjs (pure JS) runs somewhat slower than native bcrypt; your measured times will be higher than native benchmarks.

## Quick Quiz

**Q1.** You set `BCRYPT_ROUNDS` to 16 instead of 12. What changes for the legitimate user — and what changes for the attacker — and why does a 4-step increase in rounds have a much larger effect than 4x?

Think about: what the cost factor controls at the algorithm level; how cost 12 and cost 16 compare in terms of iterations; what the legitimate user experiences during login; what the attacker experiences per guess; and why the attacker's situation changes more dramatically than a linear scaling would suggest.

---

**Q2.** Your password utility is called from a route handler that registers a new user. The `hashPassword` call takes 250ms. A colleague suggests running bcrypt in a separate worker thread so it does not block other requests. Is this necessary — and why or why not?

Think about: what `await` does while bcrypt is running; whether bcrypt's 250ms blocks the Node.js event loop; what kind of operation bcrypt is (CPU-bound vs. I/O-bound); and under what circumstances a worker thread would actually be necessary for a CPU-bound task.

---

**Q3.** A recruiter tries to set a 100-character password. bcryptjs silently truncates it to 72 bytes before hashing. Two recruiters set the same 100-character password, but the last 28 characters differ. What does `verifyPassword` return when you compare the second recruiter's plaintext against the first recruiter's hash — and is this a security problem?

Think about: what bcrypt receives as input in each case; what bcrypt stores and what it reconstructs during comparison; whether the attacker learns anything useful from the fact that the two passwords produce the same hash; and what the `max(72)` validation in Chapter 20 prevents.
