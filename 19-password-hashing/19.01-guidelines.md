# Chapter 19 — Hashing Passwords: Guidelines

## Prerequisites

**From Chapter 8 — the users table schema.** The `users` table has a `password_hash` column, not a `password` column. That column name is a constraint: the application should never store the value a user typed. It stores a transformed, irreversible representation of that value. Chapter 19 implements the transformation.

**From Chapter 18 — the threat model.** Two distinct hashing strategies emerged from the threat model analysis. Passwords are low-entropy user-chosen secrets — they are guessable, and attackers with GPU clusters will guess them if given the hashes. Refresh tokens are high-entropy random values — they are not guessable regardless of hash speed. That distinction determines which algorithm goes where. Chapter 19 implements the password side. The refresh-token side lands in Chapter 22.

## Rethink Impact Prompt

Work through this scenario before reading the rest of the chapter.

Your database is dumped. The cause does not matter — SQL injection through an unpatched dependency, a misconfigured backup bucket set to public, a compromised database credential. An attacker now has a full copy of the `users` table. The `password_hash` column contains 10,000 rows. The attacker has access to a GPU cluster and a dictionary of 100 million common passwords — the kind compiled from every major public breach. They start attempting to reverse the hashes.

Walk through what happens under each of the three scenarios below.

---

### Scenario A: You stored MD5

MD5 is a fast cryptographic hash. On a modern GPU cluster, an attacker can compute roughly 50–100 billion MD5 hashes per second. Their dictionary has 100 million entries. At that rate, exhausting the entire dictionary takes well under one second — call it a few hundred milliseconds. Every user whose password appears anywhere in that dictionary has their password recovered. That is most users: rockyou.txt, the 14-million-entry breach list from 2009, is a subset of a 100-million dictionary and covers a large fraction of passwords chosen by real people. MD5 provides no meaningful resistance. The attacker does not even need to crack all 10,000 rows individually at first; they hash the dictionary once, build a lookup table, and match hashes against it in bulk.

---

### Scenario B: You stored SHA-256

SHA-256 is also a fast cryptographic hash, designed for speed and throughput. A GPU cluster can compute roughly 10–20 billion SHA-256 hashes per second — somewhat slower than MD5, but the same order of magnitude. Against a 100-million-entry dictionary, the attack completes in seconds to low tens of seconds. SHA-256 offers more computational resistance than MD5, but the difference is irrelevant at the scale of modern GPU hardware. If 60% of your users chose passwords in the top 100 million, all 6,000 of those accounts are cracked in under a minute. The "stronger" algorithm changes the timeline from milliseconds to seconds. That is not a meaningful security boundary.

---

### Scenario C: You stored bcrypt with cost 12

bcrypt is a deliberately slow hash. At cost 12, computing a single bcrypt hash takes approximately 250 milliseconds on a single modern CPU core. GPU acceleration helps less than it does with MD5 or SHA-256 — bcrypt's internal structure (the Blowfish cipher's key setup) is memory-access-heavy in a way that does not parallelize efficiently on GPU hardware. In practice, a GPU cluster might manage tens of thousands of bcrypt hashes per second across many cards, versus billions for MD5.

Against a 100-million-entry dictionary at, say, 20,000 bcrypt hashes per second, exhausting the full dictionary would take roughly 5,000 seconds — about 83 hours — per target. For 10,000 targets, the attacker cannot process them all simultaneously; GPU parallelism is finite. For users with strong passwords that do not appear in the top 100 million, the attacker gets nothing regardless of time. For users with genuinely weak passwords — "password123", "123456" — those are still recovered, because the dictionary covers them and the attacker prioritizes. But the marginal user whose password is uncommon, or who uses a randomly generated password, is protected. The attacker has to choose which accounts to invest time in, and many are effectively unreachable.

---

### What does "cost factor" actually control?

The cost factor is an exponent. bcrypt cost 12 means 2^12 = 4,096 internal iterations of the key setup routine. Cost 13 means 2^13 = 8,192 iterations — exactly twice the work of cost 12. Cost 14 means 2^14 = 16,384 iterations — exactly twice the work of cost 13.

This exponential relationship has two consequences. For the legitimate user, increasing the cost by 1 doubles the time spent during login. At cost 12, login takes roughly 250ms. At cost 14, it takes roughly 1 second. That is the upper edge of what users tolerate as a "normal" server response time before the interaction feels broken.

For the attacker, increasing the cost by 1 also doubles the time per guess — and across billions of guesses, doubling the time per guess has a compounding effect on total attack duration. The asymmetry is that the legitimate user pays the cost once per login. The attacker pays it once per guess, across millions or billions of guesses.

The cost factor does not change the output format or the length of the hash. It changes only how long bcrypt takes to produce that hash. The stored hash includes the cost factor, so the verifying function always knows how much work to reproduce.

Cost 10 takes roughly 60ms per hash — fast enough to feel instant but too cheap under heavy attack. Cost 12 sits in the 200–300ms range on modern hardware — slow enough to impose real cost on attackers, fast enough not to degrade login UX. Cost 14 sits above 1 second — appropriate for a system where login latency matters less than maximum resistance, but not the right default for a web application.
