# Definition of Done — Chapter 40

This chapter is primarily conceptual. The build task is a query-count verification that confirms Chapter 39 already uses the correct single-query approach.

---

## Key Takeaways

- The N+1 problem occurs when code makes 1 query for a list, then N additional queries to fetch related data — one per row.
- For the public job board, the JOIN-based query eliminates N+1 entirely: one SQL statement fetches jobs and company names together.
- When a JOIN is not possible, the batch query pattern (`WHERE id = ANY($1)`) reduces N+1 to exactly 2 queries regardless of list size.
- The loop pattern is tempting because it reuses existing single-record lookup functions — but each `await db.query()` inside a loop is a separate network round trip.
- Detection tools: `pg_stat_statements` shows call counts per query shape; a request-level counter logs total queries per HTTP request.
- A healthy list endpoint should run exactly 1 query per request.

## 3. Confirm with pg_stat_statements

Enable the extension if not already enabled:

```bash
psql $DATABASE_URL -c "CREATE EXTENSION IF NOT EXISTS pg_stat_statements;"
```

Reset stats and make one request:

```bash
psql $DATABASE_URL -c "SELECT pg_stat_statements_reset();"
curl -s http://localhost:3000/api/public/jobs > /dev/null
```

Check what ran:

```bash
psql $DATABASE_URL -c \
  "SELECT LEFT(query, 80) AS query_snippet, calls
   FROM pg_stat_statements
   WHERE calls > 0
   ORDER BY calls DESC
   LIMIT 10;"
```

Expected: the JOIN query (`FROM jobs j JOIN companies c`) appears once. No `SELECT ... FROM companies WHERE id = $1` with multiple calls appears.
