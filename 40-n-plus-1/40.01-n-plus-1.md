# The N+1 Problem

## What it is

The N+1 problem occurs when code fetches a list of N items and then makes one additional database query per item to retrieve related data. For a list of 20 jobs, that is 21 queries for a single page load. At 100 concurrent users, it is 2,100 queries per second — for what should be a simple read.

The name comes from the count: 1 query for the list + N queries for the related data = N+1.

---

## The bad version

Imagine the public job board had been written like this instead of using a JOIN:

```typescript
// BAD — N+1 pattern
export async function getPublicJobsBad(limit: number) {
  // Query 1: get the jobs
  const { rows: jobs } = await db.query(
    `SELECT id, title, company_id, location, employment_type, salary_min, salary_max, created_at
     FROM jobs
     WHERE status = 'open'
     ORDER BY created_at DESC, id DESC
     LIMIT $1`,
    [limit]
  );

  // Queries 2 through N+1: fetch each company separately
  const results = [];
  for (const job of jobs) {
    const { rows: companies } = await db.query(
      `SELECT name FROM companies WHERE id = $1 AND status = 'verified'`,
      [job.company_id]
    );

    // If the company is not verified, skip this job
    if (companies.length === 0) continue;

    results.push({ ...job, company_name: companies[0].name });
  }

  return results;
}
```

On a 20-job page this runs 21 queries. It also has a correctness bug: the first query fetches jobs without checking company status, so it might fetch 20 jobs but return fewer than 20 after filtering — breaking pagination assumptions.

---

## Fix 1: the JOIN (correct for the job board)

Chapter 39 already uses this. One query, one round trip:

```sql
SELECT
  j.id, j.title, j.location, j.employment_type,
  j.salary_min, j.salary_max, j.created_at,
  c.name AS company_name
FROM jobs j
JOIN companies c ON c.id = j.company_id
WHERE j.status = 'open'
  AND c.status = 'verified'
ORDER BY j.created_at DESC, j.id DESC
LIMIT $1
```

PostgreSQL evaluates the JOIN on the server. There is no round trip per row. The company filter is applied before rows are returned, so pagination counts are correct.

**Use a JOIN when:** you control the schema, the relationship is always needed, and you want the related data in the same result set.

## Fix 2: the batch query (for other use cases)

Sometimes you cannot use a JOIN — for example, if the related data comes from a different service or a dynamically constructed set of IDs. The batch query approach:

```typescript
// BETTER than N+1 — 2 queries total regardless of N
export async function getApplicationsWithJobTitles(userId: string) {
  const { rows: applications } = await db.query(
    `SELECT id, job_id, status, created_at
     FROM applications
     WHERE applicant_id = $1
     ORDER BY created_at DESC`,
    [userId]
  );

  if (applications.length === 0) return [];

  // One query for all job IDs at once, not one per application
  const jobIds = applications.map((a) => a.job_id);
  const { rows: jobs } = await db.query(
    `SELECT id, title FROM jobs WHERE id = ANY($1)`,
    [jobIds]
  );

  // Build a lookup map — O(1) per join in application code
  const jobMap = new Map(jobs.map((j) => [j.id, j]));

  return applications.map((a) => ({
    ...a,
    jobTitle: jobMap.get(a.job_id)?.title ?? null,
  }));
}
```

Total: 2 queries, regardless of how many applications exist. The `ANY($1)` operator accepts a JavaScript array and PostgreSQL expands it into an `IN` list internally.

**Use batch queries when:** you cannot use a JOIN (cross-service data, conditional lookups), or when you want to cache the lookup set separately.

## Why the loop feels natural but is wrong

The N+1 pattern often emerges from code that was written incrementally:

1. A developer writes a function to get one company by ID: `getCompany(id)`.
2. A developer writes a function to list jobs.
3. They combine them inside a loop because `getCompany` already exists and "works".

The result is correct but does not scale. Each `await db.query(...)` inside a loop is a network round trip to PostgreSQL — even on localhost this is typically 0.5–2ms. At N=20, that is 10–40ms of unnecessary latency before the query itself runs.

## Detecting N+1 in a running system

Two practical methods:

**Method 1: pg_stat_statements**

Enable the extension once:

```sql
CREATE EXTENSION IF NOT EXISTS pg_stat_statements;
```

Then after a page load:

```sql
SELECT query, calls, mean_exec_time
FROM pg_stat_statements
WHERE query ILIKE '%companies%'
ORDER BY calls DESC
LIMIT 10;
```

If you see a simple `SELECT name FROM companies WHERE id = $1` with `calls` spiking proportionally to page size, you have an N+1.

**Method 2: request-level query counter**

Add a simple counter in the `db` wrapper:

```typescript
// In src/shared/db.ts — add around the pool.query call:
let _queryCount = 0;
export function resetQueryCount() { _queryCount = 0; }
export function getQueryCount() { return _queryCount; }

// In the existing query function, increment before calling pool.query:
_queryCount++;
```

Then in a development middleware:

```typescript
// dev only — never ship this to production
app.use((req, _res, next) => {
  resetQueryCount();
  next();
});

app.use((req, res, next) => {
  res.on('finish', () => {
    if (process.env.NODE_ENV !== 'production') {
      console.log(`[${req.method} ${req.path}] queries: ${getQueryCount()}`);
    }
  });
  next();
});
```

A healthy `GET /api/public/jobs` should log `queries: 1`. If it logs `queries: 21`, you have found the N+1.

## The job board: confirmation

Chapter 39's `getPublicJobs` uses a single JOIN query. It produces exactly one database query per request, regardless of how many jobs are returned. Pagination does not change this — the `LIMIT` clause is applied server-side.

The only exception: if `cursor` is provided, the query still runs once. Decoding the cursor happens in JavaScript, not in a separate query.

**Query count for `GET /api/public/jobs` (any parameters): 1.**

---

## Key Takeaways

- The N+1 problem means 1 query for the list + N queries for related data = N+1 round trips. At N=20, that is 21 queries for one page.
- **Fix with JOIN** when the related table is part of the same database and the data is always needed: one round trip, filtering happens server-side.
- **Fix with batch query** (`WHERE id = ANY($1)`) when you cannot JOIN: 2 round trips instead of N+1, regardless of list size.
- The loop pattern feels natural because it combines existing functions — that is why it appears so often.
- Detect N+1 with `pg_stat_statements` or a request-level query counter. A healthy list endpoint runs exactly one query.
- The Chapter 39 public board runs exactly **1 query** per request.
