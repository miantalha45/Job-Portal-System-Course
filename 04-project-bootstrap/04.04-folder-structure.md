# The real decision — folder structure

You now have an empty TypeScript project. Give it a shape — and this is the one choice in the chapter that genuinely matters. There are two mainstream philosophies, both legitimate.

**Layer-based** — group by technical role. Everything of one *kind* lives together:

```
src/
  controllers/    # every HTTP handler, for every feature
  services/       # every piece of business logic, for every feature
  repositories/   # every database access, for every feature
```

**Feature- / module-based** — group by feature area. Everything about one *thing* lives together:

```
src/
  modules/
    jobs/
      jobs.routes.ts     # HTTP endpoints for jobs
      jobs.service.ts    # business logic
      jobs.repo.ts       # database access
      jobs.schema.ts     # request/response validation
    ...
```

The trade-off is **cohesion vs familiarity**. Watch what happens when you ship a feature — say "saved jobs" in a later module:

- **Layer-based:** you add a file to `controllers/`, another to `services/`, another to `repositories/` — three folders that already hold a dozen unrelated things — and you touch all three to ship one feature. They grow without bound, and related code scatters.
- **Feature-based:** you add one folder with everything about saved jobs inside it. Nothing else moves.

That's **high cohesion** (things that change together live together) and **low coupling** (modules don't reach into each other's guts). The honest comparison:

| | Layer-based | Feature / module-based |
|---|---|---|
| **Pros** | Familiar — most tutorials use it; dead simple for a tiny app | High cohesion; features are self-contained; the app scales by *adding* folders; a whole feature is easy to find, move, or delete |
| **Cons** | Folders grow without bound; one feature scatters across three places; merge conflicts cluster in shared folders | Slightly less familiar at first; a touch more upfront structure than a trivial app needs |
| **Best for** | Small apps with a handful of endpoints | Apps with many distinct feature areas — **exactly a job portal** |

## Mandate — feature/module-based (required)

**Use feature/module-based. It is required, not a preference.** This is one of the few decisions the course *makes for you*, on purpose: every later chapter is written assuming it. You'll read instructions like *"add this endpoint in `modules/jobs/jobs.routes.ts`"* or *"scope the query in `applications/applications.repo.ts`"* — if you built layer-based, none of those references line up and you'll be mentally translating every chapter. A foundational choice has to be *settled* so everything after it builds on solid ground.

## The job-portal tree

Create this shape. The six modules are this course's feature areas:

```
src/
  modules/
    auth/          # auth.routes.ts  auth.service.ts  auth.repo.ts  auth.schema.ts
    companies/     # companies.*  (a Company has Recruiters)
    jobs/          # jobs.*
    applications/  # applications.*
    applicants/    # applicants.*
    admin/         # admin.*
  shared/
    config.ts      # validated env config        → arrives in ../06-config-and-secrets/
    db.ts          # the Postgres client          → arrives in ../06-config-and-secrets/
    redis.ts       # the Redis client             → arrives in ../06-config-and-secrets/
    errors.ts      # shared error types           → arrives in ../17-errors-and-status-codes/
    logger.ts      # the logger                   → arrives in ../71-logging-and-request-ids/
  app.ts           # builds & wires the framework instance (does NOT listen)
  server.ts        # starts the app listening — the entry point
```

Create the `modules/` folders and the `shared/` folder now, each with empty (or one-line stub) `*.ts` files so the tree is real. The files in `shared/` are **placeholders** — you're reserving the slots; the actual config, db, redis, errors, and logger arrive in the chapters noted above. Don't try to fill them in yet.

✅ **Do** keep one module = one feature area, with its four files (`routes`, `service`, `repo`, `schema`).
✅ **Do** adapt the exact file names to your framework — if you chose NestJS its modules are already feature-based; with Fastify/Express you create the folders yourself.
❌ **Don't** invent a folder per technical layer "just in case." The test is simple: *a new reader should guess where job code lives without asking.*

> **📖 Mandatory read — before you lock in the structure.** Read one short piece comparing **layer-based vs feature-based (modular) project structure** (search: *"feature based vs layered folder structure node"*), and skim your framework's recommended layout. *Required: you're choosing the shape of the entire codebase — make it informed, not copied.*

**Verify:** `src/modules/` holds the six module folders, `src/shared/` holds the five placeholder files, and `src/app.ts` + `src/server.ts` exist (empty for now). The skeleton has a shape — next, make TypeScript work for you.
