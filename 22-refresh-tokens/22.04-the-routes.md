# Build: the new routes

## Schema additions in `auth.schema.ts`

The two new routes each accept a single field in the request body. Add two schemas to `src/modules/auth/auth.schema.ts`:

```ts
// src/modules/auth/auth.schema.ts — additions
import { z } from 'zod';

// (existing registerSchema and loginSchema remain unchanged)

export const refreshSchema = z.object({
  refreshToken: z.string().min(1),
});

export const logoutSchema = z.object({
  refreshToken: z.string().min(1),
});
```

`z.string().min(1)` — not `.min(64)` or a regex — is the correct choice here. The route's job is to pass the token to the service. The service hashes whatever it receives and looks up the hash. If the hash is not found, the service returns 401. There is no security benefit to validating the token format at the route layer: a correctly formatted but invalid token still fails; an incorrectly formatted token still fails (just one step earlier). Keeping the schema minimal avoids coupling the route to token format details that only the service layer understands.

`min(1)` does serve a purpose: it rejects an empty string immediately, before any hashing or database work.

## Updated `auth.routes.ts`

Open `src/modules/auth/auth.routes.ts`. The file from Chapters 20 and 21 has `POST /register` and `POST /login`. Add the two new routes and the new imports. Do not remove or modify anything from the existing file.

```ts
// src/modules/auth/auth.routes.ts
import { Router } from 'express';
import { validateBody } from '../../shared/validate';
import {
  registerSchema,
  loginSchema,
  refreshSchema,
  logoutSchema,
} from './auth.schema';
import { register, login, refresh, logout } from './auth.service';

const router = Router();

router.post('/register', async (req, res, next) => {
  try {
    const body = validateBody(registerSchema, req.body);
    const result = await register(body);
    res.status(201).json(result);
  } catch (err) {
    next(err);
  }
});

router.post('/login', async (req, res, next) => {
  try {
    const body = validateBody(loginSchema, req.body);
    const result = await login(body);
    res.status(200).json(result);
  } catch (err) {
    next(err);
  }
});

router.post('/refresh', async (req, res, next) => {
  try {
    const { refreshToken } = validateBody(refreshSchema, req.body);
    const tokens = await refresh(refreshToken);
    res.status(200).json(tokens);
  } catch (err) {
    next(err);
  }
});

router.post('/logout', async (req, res, next) => {
  try {
    const { refreshToken } = validateBody(logoutSchema, req.body);
    await logout(refreshToken);
    res.status(204).send();
  } catch (err) {
    next(err);
  }
});

export { router as authRouter };
```

## Route design decisions

### `POST /auth/refresh` — not `GET`

HTTP `GET` requests should not have a body; some proxies and clients strip it. The refresh operation sends a token in the body. `POST` is the correct verb.

`GET` is also cached by default in some HTTP intermediaries. A refresh endpoint must not be cached — each call must reach the server, which rotates the token. `POST` is not cached by default.

### `POST /auth/refresh` returns 200 with `{ accessToken, refreshToken }`

The response is the new token pair. The client must store the new `refreshToken` and discard the old one immediately upon receiving a 200. The old token is already deleted in the database; presenting it again returns 401.

The response shape is identical to the token portion of the login response:

```json
{
  "accessToken": "eyJ...",
  "refreshToken": "a3f9b2..."
}
```

The `id`, `email`, and `role` fields from the login response are not repeated here. The client already has those from login; the refresh endpoint's sole purpose is to renew tokens.

### `POST /auth/logout` returns 204

204 No Content is the correct status for a successful operation that has nothing to return. The client's refresh token has been deleted; there is no response body that adds information. Returning 200 with `{ "ok": true }` is a common pattern but it is semantically imprecise — 200 implies a response body worth reading.

204 also makes the logout response unambiguous to log parsers and monitoring tools: a 204 from `POST /auth/logout` always means the logout was processed. A 200 would require reading the body to distinguish "logged out" from a legacy endpoint that returns different shapes.

### `POST /auth/logout` does not require the access token

The access token cannot be revoked — it is stateless. There is nothing the logout endpoint could do with it. The refresh token is the revocable credential; it is what logout deletes.

A client implementing logout should:
1. Call `POST /auth/logout` with the refresh token.
2. Discard both the access token and the refresh token from local storage.

The access token will expire on its own within 15 minutes. The client must not use it after logout even though it is technically still valid at the server until `exp`. If the access token needs to be invalidated immediately (high-security logout), the architecture would need to introduce a token blocklist — a Redis set of revoked JTIs (JWT IDs). This is not implemented in this project; the threat model accepted the 15-minute window.

### No `authMiddleware` on `/auth/refresh` or `/auth/logout`

`authMiddleware` reads the `Authorization: Bearer <token>` header and validates the access token. These two routes receive the refresh token in the body — a completely different credential mechanism. Putting `authMiddleware` on them would require a valid access token to refresh or logout, which defeats the purpose of both operations:

- If the access token were still valid, there would be less urgency to refresh.
- If a user is logged out (access token expired, refresh token still valid), they could not call logout because they would fail the `authMiddleware` check.

The refresh and logout routes are intentionally unauthenticated from the access-token perspective. They authenticate the caller via the refresh token in the body.

## Manual smoke test

Start your server and run these commands in order. They form a single session flow.

**Step 1 — Login and capture both tokens:**

```bash
RESPONSE=$(curl -s -X POST http://localhost:3000/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"email":"alice@brightbuild.dev","password":"password123"}')

echo $RESPONSE | jq .

ACCESS_TOKEN=$(echo $RESPONSE | jq -r '.accessToken')
REFRESH_TOKEN=$(echo $RESPONSE | jq -r '.refreshToken')
```

Expected: HTTP 200, body contains `id`, `email`, `role`, `accessToken`, `refreshToken`. The `refreshToken` is a 64-character hex string (256 bits as hex).

**Step 2 — Verify the refresh token exists in the database:**

```bash
psql $DATABASE_URL -c "SELECT id, user_id, expires_at, created_at FROM refresh_tokens;"
```

Expected: one row. `expires_at` is approximately 7 days from now. `created_at` is approximately now. The `token_hash` column is not shown here intentionally — the raw token is never stored, only the hash. Confirm the raw value in `$REFRESH_TOKEN` does NOT appear in this output.

**Step 3 — Use the refresh token to obtain a new token pair:**

```bash
NEW_RESPONSE=$(curl -s -X POST http://localhost:3000/auth/refresh \
  -H 'Content-Type: application/json' \
  -d "{\"refreshToken\":\"$REFRESH_TOKEN\"}")

echo $NEW_RESPONSE | jq .

NEW_ACCESS_TOKEN=$(echo $NEW_RESPONSE | jq -r '.accessToken')
NEW_REFRESH_TOKEN=$(echo $NEW_RESPONSE | jq -r '.refreshToken')
```

Expected: HTTP 200, body contains `accessToken` and `refreshToken`. Both values are different from `$ACCESS_TOKEN` and `$REFRESH_TOKEN`. The old refresh token has been rotated out.

**Step 4 — Confirm the old refresh token no longer works:**

```bash
curl -s -X POST http://localhost:3000/auth/refresh \
  -H 'Content-Type: application/json' \
  -d "{\"refreshToken\":\"$REFRESH_TOKEN\"}" \
  | jq .
```

Expected: HTTP 401, body `{ "error": { "code": "UNAUTHORIZED", "message": "Invalid or expired refresh token" } }`.

**Step 5 — Logout with the new refresh token:**

```bash
curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:3000/auth/logout \
  -H 'Content-Type: application/json' \
  -d "{\"refreshToken\":\"$NEW_REFRESH_TOKEN\"}"
```

Expected: `204`.

**Step 6 — Confirm the database has no remaining refresh tokens for this user:**

```bash
psql $DATABASE_URL -c "SELECT COUNT(*) FROM refresh_tokens;"
```

Expected: `0`.

**Step 7 — Confirm logout is idempotent:**

```bash
curl -s -o /dev/null -w "%{http_code}" -X POST http://localhost:3000/auth/logout \
  -H 'Content-Type: application/json' \
  -d "{\"refreshToken\":\"$NEW_REFRESH_TOKEN\"}"
```

Expected: `204` again. Logging out with an already-deleted token returns success, not 404.
