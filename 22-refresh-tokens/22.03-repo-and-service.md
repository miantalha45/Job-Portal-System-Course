## `src/modules/auth/auth.repo.ts` — additions

The repo file from Chapter 20 has `findUserByEmail` and `createUser`, both using `db` (the default export from `../../shared/db`) and `db.query<T>(...)`. Add five new functions below them using the same `db` variable — do not add a second import for this module.

```ts
// src/modules/auth/auth.repo.ts
// (additions — append to the existing file)
// db is already imported at the top: import db from '../../shared/db';

// --- Refresh token functions ---

export async function createRefreshToken(
  userId: string,
  tokenHash: string,
  expiresAt: Date,
): Promise<void> {
  await db.query(
    `INSERT INTO refresh_tokens (user_id, token_hash, expires_at)
     VALUES ($1, $2, $3)`,
    [userId, tokenHash, expiresAt],
  );
}

export interface RefreshTokenRow {
  id:         string;
  user_id:    string;
  token_hash: string;
  expires_at: Date;
  created_at: Date;
}

export async function findRefreshTokenByHash(
  hash: string,
): Promise<RefreshTokenRow | null> {
  const result = await db.query<RefreshTokenRow>(
    `SELECT * FROM refresh_tokens
     WHERE token_hash = $1
       AND expires_at > NOW()`,
    [hash],
  );
  return result.rows[0] ?? null;
}

export async function deleteRefreshTokenByHash(hash: string): Promise<void> {
  await db.query(
    `DELETE FROM refresh_tokens WHERE token_hash = $1`,
    [hash],
  );
}

export async function deleteAllRefreshTokensForUser(userId: string): Promise<void> {
  await db.query(
    `DELETE FROM refresh_tokens WHERE user_id = $1`,
    [userId],
  );
}
```

### Why each function is written this way

**`createRefreshToken` returns `void`.**  
The caller (the service) does not need the newly created row. It already has the `userId`, `tokenHash`, and `expiresAt` it just passed in. Returning the full inserted row would require a `RETURNING *` clause and an extra parse — overhead for no benefit. If a future audit feature needs the `id` of the created row, the signature can be changed then.

**`findRefreshTokenByHash` checks `expires_at > NOW()` in SQL.**  
The expiry check is in the database, not in JavaScript. An expired token is indistinguishable from a missing token from the caller's perspective: both return `null`. The caller never sees a `RefreshTokenRow` with a past `expires_at`. This eliminates an entire class of bugs where a developer writes `if (row && row.expires_at > new Date())` — a condition that might be subtly wrong due to timezone handling or clock skew between the Node process and the database.

**`findRefreshTokenByHash` does not JOIN `users`.**  
The row contains `user_id`. If the service needs user details (email, role) after validating the token, it calls `findUserById` (which you should add to the repo, or reuse `findUserByEmail` with a modification — see below). Putting the JOIN in `findRefreshTokenByHash` would couple the token lookup to user data that is not always needed and would return a wider type than the function name suggests. Separate concerns; separate queries.

**`deleteRefreshTokenByHash` deletes by hash, not by id.**  
The caller (the `logout` and `refresh` functions) only has the raw token — and therefore the hash. It does not have the row `id`. Deleting by hash is the natural key for this operation.

**`deleteAllRefreshTokensForUser` is a building block for logout-all-devices.**  
A single `DELETE WHERE user_id = $1` removes every active session for that user — the right action when a user reports a compromised account or clicks "sign out everywhere." This chapter does not add a `POST /auth/logout-all` endpoint; the function is built here so that when that endpoint is added later (Chapter 37 — Account management), the repo layer is already in place. The routes layer will decide which operation to call.

## Add `findUserById` to `auth.repo.ts`

The `refresh` service function needs to look up the user after validating the token, to get the current `role` and `status` — both can change since the token was issued. Add this function after the refresh token functions above:

```ts
export async function findUserById(id: string): Promise<UserRow | null> {
  const result = await db.query<UserRow>(
    `SELECT id, email, role, status FROM users WHERE id = $1`,
    [id],
  );
  return result.rows[0] ?? null;
}
```

`UserRow` is the interface already exported by Chapter 20's repo file — do not redefine it here. The query names columns explicitly rather than using `SELECT *`, consistent with `findUserByEmail` in Chapter 20. The `password_hash` column is omitted: the refresh path does not need it and named projections prevent a future sensitive column from being silently included.

### `issueTokenPair` helper

```ts
// src/modules/auth/auth.service.ts

async function issueTokenPair(
  userId: string,
  role: 'admin' | 'recruiter' | 'applicant',
): Promise<{ accessToken: string; refreshToken: string }> {
  // Generate 256 bits of cryptographically random data.
  // toString('hex') produces a 64-character hex string.
  const rawRefreshToken = crypto.randomBytes(32).toString('hex');

  // Hash the raw token before storing. SHA-256 of a 256-bit random value
  // is collision-resistant and cannot be reversed to obtain the raw token.
  const tokenHash = crypto
    .createHash('sha256')
    .update(rawRefreshToken)
    .digest('hex');

  // Date.now() is in milliseconds; multiply days → hours → minutes → seconds → ms.
  const expiresAt = new Date(
    Date.now() + config.REFRESH_TOKEN_EXPIRES_IN_DAYS * 24 * 60 * 60 * 1000,
  );

  await createRefreshToken(userId, tokenHash, expiresAt);

  const accessToken = signAccessToken({ sub: userId, role });

  return { accessToken, refreshToken: rawRefreshToken };
}
```

`issueTokenPair` is `async` because `createRefreshToken` is async — it inserts a row. It is a private helper (not exported) because nothing outside the service module calls it. The routes layer calls `login`, `refresh`, and `logout`; it does not need to know that `issueTokenPair` exists.

The raw refresh token is returned to the caller, which will send it to the client. It is never stored. The database only ever sees the hash.

### Updated `login` function

Replace the existing `login` function body. The only change from Chapter 21 is replacing the direct `signAccessToken` call with `issueTokenPair`, and returning `refreshToken` in the result.

```ts
export async function login(
  input: LoginInput,
): Promise<{ id: string; email: string; role: string; accessToken: string; refreshToken: string }> {
  const user = await findUserByEmail(input.email);

  if (!user) {
    await verifyPassword(input.password, DUMMY_HASH);
    throw new UnauthorizedError('Invalid credentials');
  }

  if (user.status !== 'active') {
    throw new UnauthorizedError('Account suspended');
  }

  const valid = await verifyPassword(input.password, user.password_hash);
  if (!valid) {
    throw new UnauthorizedError('Invalid credentials');
  }

  const { accessToken, refreshToken } = await issueTokenPair(user.id, user.role);

  return { id: user.id, email: user.email, role: user.role, accessToken, refreshToken };
}
```

Everything above the `issueTokenPair` call is unchanged from Chapter 21. The error paths, the dummy hash call, the status check — none of that changes.

### `refresh` function

```ts
export async function refresh(
  rawToken: string,
): Promise<{ accessToken: string; refreshToken: string }> {
  // Hash the incoming raw token the same way it was hashed at creation.
  const hash = crypto.createHash('sha256').update(rawToken).digest('hex');

  // Look up the hash. Returns null if the token does not exist or has expired.
  const tokenRow = await findRefreshTokenByHash(hash);
  if (!tokenRow) {
    throw new UnauthorizedError('Invalid or expired refresh token');
  }

  // Find the user to get their current role. The role in the DB may have
  // changed since the token was issued — always re-read from the source.
  const user = await findUserById(tokenRow.user_id);
  if (!user || user.status !== 'active') {
    // The user was deleted or suspended since this token was issued.
    throw new UnauthorizedError('Invalid or expired refresh token');
  }

  // Rotate: delete the old token hash before issuing a new pair.
  // If deleteRefreshTokenByHash succeeds and createRefreshToken (inside
  // issueTokenPair) fails, the user must log in again — acceptable.
  // Note: a concurrent request presenting the same token can call
  // findRefreshTokenByHash between this delete and the insert, and both
  // requests may issue new tokens. For a production system, a single
  // DELETE...RETURNING statement (find-and-delete atomically) eliminates
  // this race. For this course, the delete-first approach is used for clarity.
  await deleteRefreshTokenByHash(hash);

  return issueTokenPair(user.id, user.role);
}
```

### `logout` function

```ts
export async function logout(rawToken: string): Promise<void> {
  const hash = crypto.createHash('sha256').update(rawToken).digest('hex');
  // Delete the row. If it does not exist (already deleted, expired, or
  // the token is unknown), the DELETE affects 0 rows. Return normally either
  // way — logout is idempotent. Throwing here would punish correct client
  // behaviour (retrying logout after a network failure).
  await deleteRefreshTokenByHash(hash);
}
```

## Why the service is structured this way

### `issueTokenPair` absorbs the complexity

Without this helper, both `login` and `refresh` would contain duplicated token generation logic: `randomBytes`, `createHash`, `expiresAt` arithmetic, `createRefreshToken`, `signAccessToken`. Duplication here is dangerous — if the hashing algorithm changes or the expiry calculation changes, both sites must be updated simultaneously. A mismatch would produce tokens the server cannot validate.

`issueTokenPair` is the single source of truth for how a token pair is generated. `login` and `refresh` call it; they do not implement it.

### `refresh` re-reads the user from the database

The refresh token row contains `user_id`, but not `role`. The service could store the role in the token row and skip the user lookup on refresh — saving one query. The reason not to do this: the role might have changed. An applicant who was promoted to admin would receive new tokens with the old role until their refresh token expired. By re-reading the user row, every new token pair reflects the current state of the account.

The same logic applies to `status`. A user who is suspended after logging in should not be able to obtain new access tokens via refresh. Checking `user.status !== 'active'` during refresh catches this case.

### Rotation on refresh: delete first, then insert

The token is deleted before `issueTokenPair` runs. This ordering matters. If the insert fails (database error, constraint violation), the old token is already gone. The user must log in again. The alternative — insert first, then delete — risks a race condition where both the old and new tokens are briefly valid simultaneously (if the response is lost in transit and the client retries the refresh with the old token). Delete-first eliminates this window.

The failure scenario (delete succeeds, insert fails) requires the user to re-authenticate. This is a recoverable inconvenience, not a data loss or security event. The decision is proportionate: a distributed transaction to prevent this edge case would add significant complexity for a failure mode that occurs rarely and has a simple recovery path.

### `logout` does not throw on missing tokens

A client calling `POST /auth/logout` with an already-expired or already-deleted token is doing the right thing. Returning an error would be punishing correct client behaviour. The `DELETE` affects zero rows; the function returns normally. The client receives a 200 and considers itself logged out — which is correct.

This is sometimes called an idempotent delete pattern: deleting something that does not exist is treated as success. It makes logout safe to retry (network failure, double-submit) without error handling on the client.
