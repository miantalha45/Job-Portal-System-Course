The access token mechanism from Chapter 21 is not replaced — it is extended. Every route guarded by `authMiddleware` continues to work exactly as it did. This chapter only adds the ability to obtain a new access token without re-entering credentials, and the ability to explicitly invalidate a refresh token.

## Rethink impact: why a second token at all

You have a 15-minute access token. It is stateless, verifiable in microseconds, and requires no database query. It is also irrevocable. The moment it is signed, it is valid until `exp`. If it leaks — from a log file, a browser extension, a compromised proxy — the attacker has 15 minutes. You cannot shorten that window by updating a database record because the server never checks the database for access tokens.

The obvious fix is to check a database on every request. But that reintroduces the per-request latency JWT was designed to avoid. The two-token pattern is the compromise:

- The **access token** is short-lived (15 minutes) and stateless. Servers verify it in memory — no database involved.
- The **refresh token** is long-lived (7 days) and stored as a hash in the database. It is only ever sent to `POST /auth/refresh`, not to general API routes. If it is stolen, it can be revoked by deleting the database row.

The access token travels with every API request — a high-traffic path. The refresh token travels once per 15 minutes to a single endpoint — a low-traffic path where a database lookup is acceptable.

There is a subtlety in the storage choice. The refresh token is stored as a SHA-256 hash, not in plaintext and not as a bcrypt hash. The reasoning:

- **Not plaintext**: if the `refresh_tokens` table is read by an attacker (SQL injection, backup exposure, a rogue database administrator), they must not be able to use the stolen values to impersonate users. Storing the hash means the raw token never appears in the database.
- **Not bcrypt**: bcrypt's slowness is its defence against brute-force attacks on *guessable* inputs, like human passwords. A refresh token is 256 bits of cryptographically random data — there are 2^256 possible values. An attacker who obtains the hash cannot brute-force the raw token regardless of how fast the hash function is. Bcrypt's slowness would be pure overhead here; SHA-256 is fast and sufficient.

The raw refresh token is generated once, sent to the client, and never stored anywhere on the server. The client stores it (in an `httpOnly` cookie or secure storage) and presents it when requesting a new access token. The server hashes the presented value and looks up the hash. If the row exists and has not expired, the token is valid.

Every successful refresh also rotates the token: the old hash is deleted and a new token pair is issued. This bounds the damage from a stolen refresh token — the first party to use it invalidates it for the other.

Keep this pattern in mind as you read the code. Every design choice in this chapter maps to a line in the threat model.
