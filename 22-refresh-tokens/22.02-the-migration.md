# Build: the refresh_tokens table

## The migration file

Create a new file in your migrations directory. The naming convention from Chapter 12 uses a timestamp prefix. Use the next sequential number or timestamp for your project:

```
migrations/007_create_refresh_tokens.sql
```

(Adjust the number to follow whatever you created last in Chapter 21.)

```sql
-- migrations/007_create_refresh_tokens.sql

CREATE TABLE refresh_tokens (
  id          UUID        PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID        NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token_hash  TEXT        NOT NULL UNIQUE,
  expires_at  TIMESTAMPTZ NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- The UNIQUE constraint on token_hash automatically creates an index on that
-- column; no separate CREATE INDEX is needed for token_hash lookups.
CREATE INDEX idx_refresh_tokens_user_id    ON refresh_tokens (user_id);
CREATE INDEX idx_refresh_tokens_expires_at ON refresh_tokens (expires_at);
```

Run it:

```bash
psql $DATABASE_URL -f migrations/007_create_refresh_tokens.sql
```

Verify it was applied:

```bash
psql $DATABASE_URL -c "\d refresh_tokens"
```

## Column decisions

### `id UUID PRIMARY KEY DEFAULT gen_random_uuid()`

Each row is a live refresh token. The primary key is a UUID, consistent with every other table in this project. The `gen_random_uuid()` default means the application does not need to generate the row ID — the database handles it. The `id` is not used in any lookup path (lookups go through `token_hash`), but a primary key is still the right structural choice: it uniquely identifies the row for deletions, foreign key targets, and any future tooling that needs to reference a token record directly.

### `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE`

Every refresh token belongs to exactly one user. The foreign key is `NOT NULL` because an orphaned token — one not linked to any user — is meaningless and should never exist.

`ON DELETE CASCADE` means that when a user row is deleted, all of their refresh tokens are deleted automatically. This is the correct behaviour: if an account is removed, all of its sessions are revoked without requiring the application layer to issue a separate `DELETE` before deleting the user. The alternative — `ON DELETE RESTRICT` — would prevent deleting a user who has any active tokens, which would require the application to first purge tokens before deleting accounts. The cascade is simpler and less error-prone.

### `token_hash TEXT NOT NULL UNIQUE`

This column stores the SHA-256 hex digest of the raw refresh token the client holds. It is `UNIQUE` because two different users receiving the same token hash would be a collision in SHA-256 — not impossible in theory, but so unlikely that enforcing uniqueness here is correct. More practically, the `UNIQUE` constraint means the database will reject a second insert with the same hash, which protects against a double-insert bug at the application layer.

`TEXT` is the right type for a hex string. The SHA-256 digest of any input is always 64 hexadecimal characters. You could use `CHAR(64)`, but PostgreSQL stores `CHAR(n)` padded to `n` characters, which wastes space. `TEXT` stores only the characters actually present — in practice 64 bytes — with no padding.

### `expires_at TIMESTAMPTZ NOT NULL`

The expiry is stored in the database and checked in SQL, not in application code. The `findRefreshTokenByHash` query includes `AND expires_at > NOW()` in its `WHERE` clause. A row that is past its expiry will simply not be found — the query returns no rows, and the application returns 401 as if the token did not exist.

This approach has two advantages over checking expiry in JavaScript:

1. **No race condition.** If the application fetched the row and then checked `row.expires_at > new Date()` in JS, there is a tiny window where the row expires between the SELECT and the check. The SQL `NOW()` comparison happens atomically inside the database.
2. **Expired rows are invisible to the application.** The application never handles the case "I found a token but it's expired." An expired token is exactly equivalent to a missing token from the application's point of view. The SQL expresses this directly.

`TIMESTAMPTZ` (timestamp with time zone) stores the absolute point in time in UTC, regardless of the server's local timezone. Always use `TIMESTAMPTZ` for timestamps that represent real-world points in time. `TIMESTAMP` (without time zone) stores a bare datetime with no timezone information, which creates ambiguity when servers are in different timezones or when daylight saving changes occur.

### `created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()`

Audit trail. You will want to know when a refresh token was issued — for debugging ("why does this user have 40 open sessions?"), for security investigations ("were refresh tokens issued from unexpected IP addresses in the last 24 hours?"), and for operational cleanup. The default is `NOW()` so the application does not need to supply it — the database fills it in at insert time.

## The indexes

### Index on `token_hash` (implicit via UNIQUE)

Every refresh request hashes the incoming raw token and issues a `SELECT WHERE token_hash = $1`. PostgreSQL automatically creates an index when you declare a `UNIQUE` constraint — no separate `CREATE INDEX` is needed. The lookup is O(log n) because the implicit unique index covers it. This index is the hot path for every authenticated API session that refreshes.

### `idx_refresh_tokens_user_id`

Used by `deleteAllRefreshTokensForUser`, which issues `DELETE WHERE user_id = $1`. Without an index on `user_id`, that deletion is a full table scan. The index also makes `ON DELETE CASCADE` efficient: when a user row is deleted, PostgreSQL needs to find all matching `refresh_tokens` rows; it uses this index to do so quickly.

### `idx_refresh_tokens_expires_at`

This index has two uses. First, the `findRefreshTokenByHash` query filters by both `token_hash` and `expires_at > NOW()`. PostgreSQL can use the `token_hash` index alone (the hash lookup is highly selective), but the `expires_at` index enables a future cleanup job.

Second — and more importantly — you will eventually want to purge expired rows. Expired refresh tokens accumulate in the table forever unless something removes them. A cleanup job that runs `DELETE FROM refresh_tokens WHERE expires_at < NOW()` needs this index to be efficient. The cleanup job is not built in this chapter, but the index is cheap to add now and expensive to backfill later when the table has millions of rows.

## What the table does NOT contain

There is no `revoked_at` column, no `is_active` boolean, and no soft-delete pattern. A refresh token row either exists (and has not expired) or it does not. Revocation is implemented by deletion: `deleteRefreshTokenByHash` issues a hard `DELETE`. This keeps the schema simple and the lookup query clean — the `findRefreshTokenByHash` query never needs to check a status flag.

The trade-off: once deleted, there is no audit trail that a token existed. If you need to audit revocations — "when did this session end and why?" — you would add a `revoked_at` column and a soft-delete pattern. This project does not require that level of audit; the `created_at` column on active tokens is sufficient.
