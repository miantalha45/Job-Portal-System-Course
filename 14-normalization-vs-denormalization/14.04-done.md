# Key takeaways — Chapter 14

- **The cost of normalization scales with join complexity; the cost of denormalization scales with the number of write paths that must stay in sync.** Every schema decision is a bet about which cost will dominate the actual workload — make the bet consciously.

- **Denormalization** is a deliberate trade: duplicate or flatten data to make reads faster or simpler. The cost is that writes must keep copies in sync, and inconsistency is invisible until a query surfaces it.

- **The column-vs-JSONB rule**: if the database needs to filter, sort, gate, or enforce a value — it needs a real column. If the value is display-only, varies structurally by role type, or is always consumed as a unit — JSONB is appropriate.

- **When historical state matters more than current state, denormalization is correct by design.** A snapshot that captures point-in-time data should diverge from the live record — that divergence is the feature, not a bug. Design for it explicitly rather than discovering it as an inconsistency.

- **JSONB decisions are revisable via a safe, phased migration**: dual-write → add column → backfill → add constraint → switch reads → drop JSONB key. The migration is non-breaking only if the phases are deployed in order.
