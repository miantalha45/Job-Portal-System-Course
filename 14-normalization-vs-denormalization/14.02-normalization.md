# Normalization — the practical version

## What it means

Normalization means putting each fact in exactly one place. If the company name is stored in the `companies` table, it should not also be stored in the `jobs` table, in the `recruiters` table, or anywhere else. When the company changes its name, one update — to one row — propagates everywhere via join.

The formal rules (first normal form, second normal form, third normal form) describe specific categories of redundancy and how to eliminate them. For this project the practical version is enough: if updating a piece of data requires changing it in more than one place, the schema is not fully normalized for that fact.

## What you gain and what you pay

**You gain:**
- **No update anomalies.** Change a company name once and every query that joins to `companies` sees the new name immediately.
- **Smaller tables.** Each table stores only what belongs to it — no repeated data.
- **Cleaner enforcement.** Constraints (NOT NULL, UNIQUE, CHECK) apply to each fact at its source.

**You pay:**
- **Joins.** Every related piece of data requires a JOIN. Showing an applicant's name on a job application means joining `applications → applicants`. Multiple facts = multiple joins.
- **Query complexity.** Joins are correct and efficient with proper indexes — but they require care at scale.

## Denormalization

Denormalization is the deliberate decision to put a fact in more than one place in exchange for a query benefit. It trades write-time simplicity for read-time speed, and it trades data consistency for convenience.

The cost is real: if the same fact exists in two places, an update must change both. If it changes in one and not the other, the data becomes inconsistent — and inconsistency is invisible until a query returns the wrong answer.

This is not a reason to never denormalize. It is a reason to denormalize deliberately, with a documented reason, knowing the risk you are accepting.

## The wrong extremes

**Over-normalized:** every job attribute in its own column.

```sql
CREATE TABLE jobs (
  ...
  seniority            text,
  tech_stack_primary   text,
  tech_stack_secondary text,
  tech_stack_tertiary  text,
  remote_policy        text,
  commission_plan      text,
  territory            text,
  -- 40 more nullable columns depending on which type of job this is
);
```

`tech_stack_primary/secondary/tertiary` is a repeating group — three columns encoding the same concept at positions 1, 2, and 3. First normal form (1NF) says each column holds one atomic value with no positional siblings; a list belongs in a related table or a structured column type, not spread across `_primary/_secondary/_tertiary`. The schema also has 40 nullable columns, most NULL for any given job. Adding a new job type requires a schema migration.

**Under-normalized:** everything in one JSON blob.

```sql
CREATE TABLE jobs (
  id   uuid PRIMARY KEY,
  data jsonb NOT NULL DEFAULT '{}'
);
```

Every fact — title, status, deadline, company, description — lives in an unstructured bag. No constraints can enforce that `title` exists. You can add an expression index on a JSONB path, but it requires knowing the path at index-creation time and is invisible to the query planner unless queries are written to match the exact expression. More critically: `company_id` is a string buried in JSON — PostgreSQL foreign keys require a typed column reference, so no FK constraint can enforce it, and `ON DELETE RESTRICT` or `CASCADE` rules have no way to find it.

The right design is not the midpoint between these; it is a specific, per-column decision.
