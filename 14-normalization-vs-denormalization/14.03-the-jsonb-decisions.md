# The JSONB decisions in this schema

## The column-vs-JSONB rule

Every column in chapters 8–10 was decided by one test:

> **Filter, sort, gate, or enforce it → real column. Display only, varies by role type, or consumed as a unit → JSONB.**

"Filter" means `WHERE column = value`. "Gate" means CHECK constraints, FK references, or NOT NULL. "Sort" means `ORDER BY column`. "Enforce" means the database must guarantee the value is always there or always valid.

If the database never needs to look inside the value — only store it and return it — JSONB is correct. If any future query needs to filter, sort, group, or constrain on it, it needs to be a real column with a real index.

## Walking through the schema

**`jobs.attributes`** — JSONB. An engineering job stores `{ "tech_stack": ["Go", "PostgreSQL"], "seniority": "mid" }`. A design job stores `{ "software": ["Figma"], "portfolio_required": true }`. The schema makes no assumptions about which keys exist. No current query filters across all jobs by `seniority` — it is displayed on the job detail page, not used as a filter. If that changes — if the product needs a "filter by seniority" feature on the public board — `seniority` becomes a real column at that point, via a migration that backfills from JSONB.

**`jobs.screening_questions`** — JSONB. The questions for a job are always created together, stored together, and read together. There is no query that asks "give me all jobs where question #3 is a yes/no question." The questions are always consumed as the full array for a specific job. A separate `screening_questions` table (one row per question) would add a join to every job fetch for no practical benefit.

**`applicants.attributes`** — JSONB. Skills, portfolio links, years of experience. Same reasoning as `jobs.attributes`: the content varies per person and is displayed, not filtered on. Skills-based filtering is possible with JSONB operators and a GIN index (a PostgreSQL index type built for array and JSONB values; covered in [Chapter 42](../42-indexing/)), but that is an optimization decision made later, not a schema-design one made now.

**`applications.screening_answers`** — JSONB. Answers are keyed by the question's UUID (established in Chapter 9). They are read together with the question definitions, not queried individually across applications. There is no use case for "find all applications where the answer to question X is Y" in the MVP.

**`applications.profile_snapshot`** — JSONB. This one is different: it is intentional, explicit denormalization. When an applicant submits an application, their profile at that moment is captured in `profile_snapshot`. Later, if the applicant updates their profile, the recruiter's view of that application still shows the profile *at submission time* — not the current profile. This is the correct behavior. The cost: `applicants.full_name` and `profile_snapshot.full_name` can diverge after an update. This is accepted by design. The exact fields captured and the submission logic are covered in [Chapter 51](../51-application-snapshots/).

## When to revisit a JSONB decision

The rule has a natural migration path. Start with JSONB. Add a real column when:
1. A filter, sort, or aggregate query is needed on that value
2. The value must be enforced as NOT NULL or validated by CHECK
3. The value must be the target of a FK reference

The migration sequence — in safe deployment order:

1. **Deploy code that writes both** the JSONB key and the new real column (dual-write). Do not skip this step — existing rows still have only the JSONB key, and any code deployed before the backfill would read a NULL real column.
2. **Add the real column** (nullable, no constraint yet) via a migration.
3. **Backfill existing rows** from the JSONB key: `UPDATE jobs SET seniority = attributes->>'seniority'`.
4. **Add the constraint** (NOT NULL, CHECK, or index) once every row has a value.
5. **Deploy code that reads from the real column** and stops writing the JSONB key.
6. **Drop the JSONB key** in a later migration after confirming nothing reads it.

This is a non-breaking additive migration when the deployment steps follow the migration steps. Skipping step 1 — deploying code that reads the real column before the backfill exists — is the common failure.

The `seniority` scenario from the rethink prompt is exactly this path: if "filter by seniority" becomes a real feature, `jobs.seniority text` becomes a real column, backfilled from `attributes->>'seniority'`, indexed, and the JSONB key is eventually removed.
