# In scope / Out of scope

This is the boundary of the build. Read both lists — the *out of scope* one matters just as much, because it's what stops you gold-plating the wrong thing.

## In scope

- **Production project setup:** configuration read from the environment and **validated at startup** (so the app refuses to boot with a missing or malformed secret), secrets kept out of Git, and PostgreSQL and Redis run locally with Docker.
- **Real authentication:** hashed passwords, access + refresh tokens with rotation, and email verification.
- **Authorization and multi-tenant isolation** — *multi-tenant* meaning many companies share one system but each is sealed off from the others, so a company can never read or change another company's jobs or applicants.
- **Three role-based panels (Admin, Company, Applicant), and a public job board** that stays fast as it grows: no N+1 queries, cursor pagination, deliberate indexing, and cached hot reads.
- **Résumé uploads** to object storage (a file store like S3, separate from the database), resized and parsed in the background.
- **A multi-company application shortlist and submission** that splits into one application per job (each role judged on its own screening questions), with the résumé and profile **snapshotted** at apply time — so a later edit to the job posting or the applicant's profile never rewrites an application already sent — inside a database transaction (all-or-nothing), and safe to retry.
- **An admin panel** for platform oversight — verify and suspend companies, moderate and take down job postings, suspend/reinstate users, and see platform-wide stats — including the deliberate, tightly-scoped exception that lets an admin (and only an admin) read across all companies.
- **Multi-recruiter company workspace** — within-company roles (owner, HR manager, recruiter, hiring manager), email invitations with secure tokens, invitation acceptance flow, and member management (view, change role, remove).
- **Interview scheduling & tracking** — application stage pipeline (Applied → Screening → Interview → Final Interview → Offer → Hired/Rejected), recruiter-initiated interview scheduling with async email notification, interview feedback, and stage-aware tracking views for both recruiter and applicant.
- **Background / async processing** with a job queue — a list of "do this later" tasks that worker processes pick up off the request path — and workers: application confirmation emails, new-applicant alerts to recruiters, résumé processing, and scheduled recruiter digests / recruitment-analytics reports — with retries, idempotency (running a job twice does no harm), and failure handling.
- **Production hardening:** rate limiting, structured logging with request IDs, health and readiness checks, graceful shutdown, and a real deployment running the web app and the worker as **separate processes**.

## Out of scope

Deliberately **not** building these — so you don't gold-plate the wrong thing:

- **Event-driven architecture** — no pub/sub, no event bus, no CQRS. We do async with a **job queue + workers**; that's the production pattern this course teaches.
- **A real payment processor** — if any paid-job-posting concept ever appears, it's *simulated*; you build everything around it correctly, but no real money moves.
- **Real-time features** (websockets, live chat) and a **native mobile app**.
- **Advanced admin tooling** — user impersonation, manual data edits, feature flags, and a full audit-log subsystem are out of scope; the admin panel does moderation and oversight, not everything.

## The flow in one line

*A recruiter opens a company workspace and posts jobs → an applicant browses the board and shortlists roles across several companies → applies once → the shortlist splits into one application per job with the résumé and profile snapshotted → confirmation emails, recruiter alerts, and résumé processing run in the background → recruiters move applicants through interview stages and schedule interviews → applicants receive notifications and track their stage → recruiters review applicants and receive scheduled digests, while an admin moderates companies and jobs across the platform.*
